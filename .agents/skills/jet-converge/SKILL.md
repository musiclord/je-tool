# JET 收斂

把分散的說法磨成可由使用者裁定的決策包。終點是「共同理解與明確裁定」，不是自動開始開發。

## 先載入什麼

1. 完整閱讀 `.agents/harness/convergence-and-memory.md`；它定義專案記憶、證據層級與回寫位置。
2. 需求跨多個 session、對話或待完成事項時，再閱讀 `references/session-synthesis.md`。
3. 只有維護本 skill 或重新查核上游時，才閱讀 `references/upstream-provenance.md`。

## 不可跨越的界線

- 本 skill 只做查證、訪談、比較、裁決與必要的文件回寫。除非使用者在收斂後另行要求，不寫產品程式、
  不建 issue、不 stage、不 commit、不 push。
- 對話、本機記憶、task 摘要與歷史文件是線索，不是現行規格。每項結論都要回到目前程式、測試、現行文件
  或使用者本輪明示裁定。
- 不把所有想法升格為需求。沒有來源、已被取代、重複或偏離核心業務的項目，要照實分類。
- 不建立 `CONTEXT.md`、ADR、`.reversa/`、`_reversa_*` 或另一套 backlog／規格根目錄。JET 已有自己的
  現行文件與 `docs/specs/`。
- 不讀取未獲授權的私人案件路徑，也不把敏感內容寫進收斂材料。

## 收斂流程

### 1. 盤點證據

先查實際 branch、HEAD、dirty tree、現行大型計畫與「已知但延後的事項」。只讀與主題相關的現行規格、
程式、測試、歷史與可取得的 session 內容，記下來源日期與目前狀態。Repository 已能回答的事，不再問使用者。

把材料分成：

- 已確認裁定或現行需求
- 尚未裁定的候選想法
- 互相衝突的說法
- 已知但延後，且有明確重啟條件
- 已被取代或明確否決
- 重複、查無依據或只有推測

### 2. 框定核心問題

用白話說清楚四件事：最近一次具體情境、受影響的人與工作環節、不處理的代價、這次成功的可觀察條件。
再用一句話收成：「當〔情境〕，我想要〔動機〕，以達成〔結果〕。」

同時回讀 `docs/project-context.md` 與 `docs/idea-replacement-scope.md`，先說出本輪依循的核心業務主線，再判斷
每個項目是直接服務核心、提供必要支撐、屬周邊改善，或會把方向拉離核心。核心不是用來壓掉新需求，而是
讓偏移成本可見。

### 3. 建立決策樹

把尚未決定的事情排成有前後依賴的決策樹。每輪只問目前已具備前提的「前緣」問題，最多五題；每題提供
具體選項、實際影響與建議答案。答案依賴另一個未決問題時，留到下一輪。

查得到的事由 Agent 查，不轉問使用者。若 host 能並行查證，可讓查證進行，同時詢問不受它影響的其他前緣；
不得用尚未完成的查證結果推動下游裁決。

每輪回答後重畫決策樹。新答案使舊假設失效時，先指出衝突，再繼續。

### 4. 發散可行方向

提出三到五個實質不同的方向；在合理時包含「不改」與「沿用／組合既有機制」。此階段只解釋，不排序、
不偷渡推薦。若方向依賴會變動的外部技術、政策或產品能力，先用最新第一方來源研究再提出選項。

### 5. 挑戰每個方向

對每個方向一視同仁地寫出：

- 十二個月後失敗的一句話標題
- 足以讓整個方向失效的中心假設
- 幾天內可完成的最便宜驗證
- 隱藏成本，特別檢查 provider 差異、大母體效能、機敏資料、人工驗收與跨 session 維護
- 過了哪個點就難以回頭

「可能延誤」「可能有風險」不算分析；要說明失敗機制。

### 6. 比較並推薦

用固定判準比較：核心業務貼合度、使用者價值、證據強度、依賴是否已具備、工作量、殘餘風險、架構侵入度、
可逆性，以及是否降低未來發散。給出單一推薦，明說接受的取捨與會讓推薦反轉的條件。

推薦不是裁決。使用者選擇其他方向時，保留原比較結果，將分歧記為裁定理由，不回頭改分數粉飾一致。

### 7. 形成最小決策包

收尾固定包含：

- 目標與核心業務錨點
- 已確認裁定
- 範圍內與範圍外
- 最小可行範圍與完成條件
- 已接受風險
- 待完成／延後事項及各自重啟條件
- 尚未解決的疑問，以 `[待裁定]` 標示
- 建議的唯一下一步，以及何時應停止或回頭重裁

請使用者確認「是否已達共同理解」。在確認前不開始實作。

### 8. 回寫專案記憶

只有使用者要求保存，或本輪已明確授權文件修改時，才依
`.agents/harness/convergence-and-memory.md` 回寫現有權威文件。每個主題只留一個現行來源；不把逐句對話、
所有備選方案或完整終端輸出搬進 repository。

大型工作把已核准決策寫進唯一現行 `docs/specs/` 計畫；真正延後的項目寫入
`docs/development-status.md`，且必須保留背景、目前邊界與重啟條件。已被取代但仍有解釋價值的內容才進
`docs/history/`。

到此停止。實作、驗證與 Git 交付需要使用者後續明示。
