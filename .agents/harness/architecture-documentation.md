# JET 架構文件的分析與繪圖

這份流程讓不同 agent 使用同一份來源證據繪圖。閱讀入口在[架構文件](../../docs/architecture/README.md)，
目前工作範圍與計畫入口見[開發現況](../../docs/development-status.md)。現有圖表依提交 `40440b9` 的程式快照繪製；
上一次重繪的範圍不是持續開發的授權，要更新時照本文件另建快照重繪。

## 工具分工

| 工具或角色 | 責任 | 不能代替的工作 |
|:---|:---|:---|
| RepoWise | 建立檔案、符號與關係索引，協助探索程式。 | 不能將索引推定的關係當成完整 C# 呼叫證明。 |
| Roslyn | 在明確的編譯設定下辨識型別、介面實作、方法多載與呼叫位置。 | 不直接證明執行時物件、分支條件或業務結果。 |
| Agent | 閱讀 action 註冊、組裝、SQL、交易、規格與測試，選定圖表範圍。 | 不用合理猜測補上查不到的關係。 |
| LikeC4 | 以可編輯模型維護系統情境、容器、元件協作與部署視圖。 | 模型檢查通過不代表模型符合程式。 |
| Archify | 由候選 JSON 產生詳細圖表與離線 HTML。 | 圖面或格式檢查通過不代表業務正確。 |
| diagram-design | 協助選擇圖種、配置版面與檢查可讀性，採用方式見「繪圖前的設計」。 | 不產生 JET 來源證據，也不取代 LikeC4、Archify 與文件檢查。 |

既有研究使用 RepoWise 0.56.0、Roslyn 5.9.0.0、LikeC4 1.59.4 與 Archify 3.1.0。
這是已執行版本，不是要求所有環境永遠安裝相同版本。Archify 目前已更新到 3.2.0；安裝核對、更新與封裝參數見
[封裝與檢查工具](../../tools/harness/architecture/README.md#archify-安裝與版本)。舊圖的版本紀錄保留原值，重繪後才由實際工具與收據更新。
RepoWise 與 Roslyn 的結果分開保存，以來源位置及符號身分對照；目前沒有修改 RepoWise，讓它直接吸收全部 Roslyn 資料。

## 開始之前

1. 讀取現行計畫，確認是重繪既有圖，還是更新到新版程式。兩者不能默默混在一起。
2. 重繪時沿用固定快照、候選 JSON、LikeC4 模型及證據；只改版面不用重新索引。
3. 更新來源時另建快照並記錄檔案雜湊。只選程式、測試與必要設定，不讀取私人案件或整份本機工作目錄。
4. 工具、索引、套件快取與完整執行紀錄放在本機 ignored 目錄。程式不傳外部分析服務，不修改共用工具或其他 session 的設定。
5. 編譯設定、參考組件、來源產生器或來源檔有變動時，重新確認相依分析；不能只比較 C# 文字就宣稱分析仍有效。

## 更新到新版程式

在研究目錄的 `runs/` 下另建一個快照目錄，名稱寫日期與提交，例如 `2026-11-03-head-40440b9`；上一份快照不動。
2026-11-03 這一次的做法，下一次可以照用，腳本都在那個快照目錄的 `scripts/`。兩份快照之間改過名稱時，先用改名對照把舊名稱換成新名稱，
再比對證據與程式；改名之後還留下的差異，才是邏輯真的改過的地方。那一次改圖用的腳本留在重繪工作目錄的 `scripts/`：

1. 用 `git archive` 從已提交的 HEAD 取檔，工作樹未提交的修改不進證據；儲存庫只讀。檔案選取規則和 2026-10-16 相同，
   結果寫成 `evidence/source-manifest.json`，清單裡記提交編號。先比對新舊清單，列出改動、新增與移除的檔案。
2. 參考組件沒變時沿用既有的 Roslyn 設定，只換快照與輸出目錄，結果放在快照目錄的 `evidence/roslyn/`；
   套件或編譯設定變了就重新準備設定。RepoWise 與代表呼叫對照照 2026-10-16 的腳本重跑，呼叫位置由 Roslyn 在新快照裡定位。
3. 重抽資料表結構與方法簽章，規則和 2026-10-16 相同。
4. 逐項重對已核對事實的來源範圍：程式沒變的範圍直接沿用，變了的範圍重讀程式後改寫說明，寫成快照目錄的 `evidence/verified-facts.json`。
   同時把重繪規格裡類別圖成員的宣告位置對到新行號。
5. 看每條線的 Roslyn 證據還綁不綁得上；綁不上的線就是程式改過的地方，依新程式改圖，再補證據。
   讀過的差異也要反映到圖上的文字與卡片，不只修綁不上的線。
6. 先把圖表目錄 `docs/architecture/diagrams/evidence/dynamic-view-pairs.json` 的內容複製到重繪規格的 `dynamicViewPairs`，
   再依新圖核對訊息編號、略過的步驟、範圍外的訊息與參與者對應；新增的動態視圖各加一組。
7. 封裝時以 `--run` 指定快照目錄。

## 分析與事實核對

RepoWise 先以結構索引協助探索。既有試作使用 fast 模式、mock provider 與 mock embedder，
沒有生成 Wiki，也沒有用 mock 向量評估語意搜尋。新環境先讀該版本的命令說明，關閉遙測、編輯器設定與 Agent 掛鉤。

Roslyn 分析要保存來源、條件編譯符號、參考組件、來源產生器及編譯診斷。既有分析器只擷取明確方法呼叫與物件建立；
屬性、事件、委派、反射及動態 SQL 仍需另外處理。編譯器找到目標，不表示此次操作會執行到該行。

Agent 從前端 action 追到 handler、介面、組裝、資料庫與回應，另外核對成功、取消、失敗和提交後的處理。
資料表欄位讀建表與遷移定義。相同欄名不是外鍵證據，實作介面也不是某次呼叫選到該類別的證據。

每項用於繪圖的關係至少保存：

- 穩定識別碼、起點、終點與關係種類，例如依賴、實作、繼承或資料讀寫。
- 來源檔案、位置、雜湊及分析設定。
- 編譯時目標、可能實作、成立條件，以及仍無法確認的部分。
- 是否真的執行過；有觀察時附測試情境、輸入範圍與結果。單次觀察不升格成所有輸入的保證。

可以繪製尚未確認的關係，但必須就近標示不確定性。類別圖的依賴線不表示呼叫順序；
循序圖則在標題或說明寫出設定、前置條件與所選分支。不要為了統一「確定與可能」的外觀，改掉 UML 本身的線條語意。

## 繪圖前的設計

本節將 diagram-design 的選型、留白、連線與文字檢查整併到 JET。先依「分析與事實核對」確認內容，再做版面；
外部範例只提供構圖方法，不能當成 JET 的元件、呼叫或資料庫關係。來源與採用範圍見本節末尾。

### 先決定讀者要看懂什麼

在重繪工作目錄簡短記下下列內容，沿用到最後看圖時，不另外建立一份大型計畫：

- 讀者是誰，以及這張圖要回答的一個問題。
- 使用哪份程式快照、起點和終點在哪裡，以及要說明的成功、取消或失敗情境。
- 圖種、主要閱讀方向，以及要交付的閱讀尺寸。
- 哪些內容放在總覽、哪些移到細節圖或卡片，以及兩者如何互相找到。

若一段文字或表格已能完整回答，就沿用文字或表格。需要圖時，先說明上述選擇並開始繪製；
已有明確範圍、配色與工具時直接沿用，只有來源仍有會改變行為的歧義才請使用者裁定。

| 讀者的問題 | 圖種與現有工具 | 圖上要保留的內容 |
|:---|:---|:---|
| 系統由誰組成，各自負責什麼 | LikeC4 的系統情境、容器或元件視圖；詳細圖可用 Archify `architecture`。 | 元件職責、邊界與協作方向；不把位置當成執行順序。 |
| 一次操作經過哪些判斷與步驟 | Archify `workflow`。 | 起點、終點、條件與分支；跨角色交接可用泳道表達。 |
| 資料從哪裡來，在哪裡轉換或保存 | Archify `dataflow`。 | 每項輸入、轉換、保存位置與輸出；不把記憶體中的結果畫成資料庫。 |
| 誰先呼叫誰，何時回傳 | Archify `sequence`，並核對同流程的 LikeC4 動態視圖。 | 參與者、訊息順序、成立條件與回傳；自我處理用該版本支援的註解表達。 |
| 類別和介面如何分工 | Archify `class`。 | 必要成員及依賴、實作、繼承等關係；保留原有 UML 語意。 |
| 資料表有哪些欄位，如何關聯 | Archify `erd`。 | 真實表名、型別、鍵與 SQL 關聯；程式使用的連接欄位不能標成資料庫外鍵。 |
| 一個工作如何等待、重試、取消或結束 | Archify `lifecycle`。 | 狀態、轉換條件與真正的終止狀態；不能用裝飾性循環假造重試。 |

一張圖以一種關係為主。總覽和細節圖可分開，但各圖名稱、證據編號與對同一事實的說明必須一致。

### 安排內容與版面

1. 先排主要路徑，再把資料庫、分支與回傳放在所屬節點附近。用群組與間距表達層次；
   邊界必須有實際的程序、部署、責任或資料保存依據，不能只為了填滿畫面而加框。
2. 依 diagram-design 的建議，總覽超過 9 個節點或 12 條線、循序圖超過 5 個參與者、類別圖超過 7 個類別時，
   先檢查是否該分成總覽與細節。這些數字是檢討密度的起點，不是 JET 的硬性上限；
   不為達到數字而刪掉必要關係、失敗分支或證據，也不以此降低 Archify 的檢查要求。
3. 刪去重複文字與裝飾。合併節點前確認不會隱藏介面、交易、資料保存或控制責任；
   拆圖、合併或省略時記明原因及細節去向。宣稱完整資料表結構的圖要保留全部欄位，
   只畫部分欄位時說明範圍並連到完整欄位頁。
4. 預留實際文字需要的空間，再調整方框與路線。優先用清楚的直線或直角折線，先讓工具自動排線；
   有碰撞證據才使用該版本 schema 支援的定位欄位。手動配置可用 4px 間距單位，不強套到工具自動產生的座標。
5. 每條線都要能從起點一路追到終點。線不得穿過無關節點、共用到無法分辨的線段，或被另一條線與標籤蓋住。
   多條線進入同一節點時分開接點；標籤與線保留可見間距，背景遮罩不能遮住其他路線或相鄰方框。
6. 保留 JET 配色與線型。額外用來吸引視線的強調集中在一到兩個重點；證據種類原本需要的顏色不受此數量限制。
   不加發光、陰影、裝飾圖示或無內容的卡片來填空。圖例放在不遮圖的位置，只解釋這張圖實際使用的符號。

### 繁體中文與離線閱讀

繁體中文使用既有主題的中文字型，不照搬上游的細小等寬標籤、大寫與字距設定。12px 可作為中文排版起點，
最後仍以瀏覽器縮放後的實際字級判讀。長類別名稱、全形標點與中英混排要實際量寬，不能只用英文字數估算。

字太擠時先加空間、換行或拆圖，再精簡不影響意思的文字。程式名稱與有意義的關係標籤不能為了排版改名或刪除。
循序圖依已安裝版本的欄寬設定調整；保留固定座標的舊圖時明示固定配置，新圖則先用該版本的自動配置。

圖面沿用 JET 的離線字型與配色檔，不新增 Google Fonts、CDN 圖示或外部圖片依賴。
檢查淺色、深色及無法載入網路資源時的畫面。文字、箭頭與背景必須可辨識，不能只靠顏色表達差異；
一般文字對比 4.5:1、必要線條 3:1 可作為檢查依據，尚未量測時不能宣稱已達標。

### 與上游做法不同的地方

| diagram-design 的做法 | JET 的採用方式 |
|:---|:---|
| 直接撰寫 HTML 與 SVG。 | 維護 LikeC4 模型與 Archify 候選 JSON，再由既有工具產生及封裝。 |
| 初次使用先詢問品牌與配色。 | 使用者已裁定的 JET 配色就是本專案設定，直接沿用。 |
| 虛線也可表示非同步、可選或回傳。 | 使用下方證據種類表及該圖的 UML 語意，不重新指派虛線、箭頭或強調色的意思。 |
| 圖種有固定數量上限，資料表範例可以省略欄位。 | 用數量提醒檢討密度，完整性由本張圖的問題與來源範圍決定。 |
| 單檔模板可載入網路字型，並以固定最小寬度配合橫向捲動。 | 維持 JET 的離線閱讀與既有檢視器縮放方式，不把上游 CSS 整段套進產生的 HTML。 |
| `self_check.py` 等腳本驗證上游模板。 | 這次只整併設計程序，沒有安裝那些腳本；JET 仍執行 LikeC4、Archify 與 Documentation 各自的檢查。 |

### 看圖後才能完成的檢查

先依下節產圖，再逐張看實際畫面。以 1440×900 為主要閱讀尺寸，也查看 1920×1080，
確認工具縮放後仍能讀懂，不以裁切、隱藏溢出或縮小必要文字通過檢查。使用無頭瀏覽器擷取畫面，不操作實體滑鼠鍵盤。

- 第一眼能否找到主體、起點、閱讀方向和結論？總覽是否清楚指出細節在哪裡？
- 每個節點名稱、條件、訊息與圖例是否完整可讀？是否有遮擋、截字、誤接線或無法分辨的交叉？
- 淺色與深色是否都能辨識？圖例、文字及線型能否在不依賴顏色的情況下說明關係？
- 圖的標題與文字說明是否足以讓看不到圖的人知道內容？若產物提供 SVG 可及性資訊，確認標題、說明與引用識別碼正確。
- 互動與動態效果能否停止？停止播放或使用減少動態模式時，必要資訊是否仍完整？
- 候選來源、工具原始輸出與套用 JET 主題後的最終頁面是否一致？最後的主題與字型也要看過，不能只看套色前的圖。

把圖名、檢查尺寸、主題、發現與修正結果留在重繪工作目錄。自動檢查通過與實際看圖分開記錄；
尚未檢視的圖明寫未檢視，不能用幾張樣本代表全部圖表。幾何問題回到模型或候選 JSON 修正；
主題問題回到配色來源修正，再重新產生、封裝與檢查。

## 產圖與檢查

1. LikeC4 與 Archify 引用同一批已核對事實。總覽可以彙整多條關係，但保留回查細節的方式。
2. LikeC4 修改模型後執行模型檢查，再輸出離線 HTML。現行可編輯來源是[jet.c4](../../docs/architecture/diagrams/likec4/jet.c4)，
   每條關係以 `metadata { evidence '識別碼' }` 對應連線證據。
3. Archify 先讀選定安裝目錄的 SKILL.md、相關 schema 與例子。修改候選 JSON，使用同一目錄的 finalize 產生與檢查，
   封裝時以 `--archify-root` 傳入該目錄，再依「看圖後才能完成的檢查」查看最終圖面；不要直接修產生的 HTML。現行圖在[圖表目錄](../../docs/architecture/diagrams/archify/)。
4. 圖表固定放在 `docs/architecture/diagrams/`。依使用者 2026-10-21 的裁定，每次重繪都直接覆寫這個目錄，不另開版本或日期目錄；
   重繪日期只記在頁面與清單裡，前一版留在 Git 歷史。發布前清除匯出檔內的本機絕對路徑，來源連結改用包內相對位置；模型與圖表內容不因此改寫。
   核對本機連結、離線載入、來源引用，以及不同圖表是否對同一個事實作出矛盾說明。
   依使用者 2026-10-21 的要求，圖面與閱讀頁面用同一組配色。Archify 候選 JSON 一律設 `meta.visual_preset: "editorial"`，
   封裝時插入 JET 配色；LikeC4 的顏色寫在 `likec4.config.json`。配色檔與插入方式見[封裝與檢查工具](../../tools/harness/architecture/README.md)，
   不要為了換色直接改產生的 HTML。
5. 實際看圖時，以 1440×900 的瀏覽器視窗為準。Archify 會把類別圖與流程圖整張縮進視窗高度，
   版面寬高比接近 16:9、寬度約 1200 到 1470 時最容易讀；循序圖依寬度縮放、可往下捲，訊息註解只寫短句，細節寫進圖下方的卡片。
   循序圖的寬度有可讀性上限，參與者越多方框越窄；類別名稱放不下時，小字改寫這個參與者負責的 action，類別名稱寫進卡片，不硬加寬度。
   依使用者 2026-10-21 的要求，頁面與圖面的文字只寫讀者在那個位置需要的事：不寫 `meta.subtitle`，卡片只寫這張圖特有的情境、範圍與沒畫的分支；
   線型交給圖例，程式行號留在連線證據頁，快照範圍只寫在閱讀說明，入口不放注意事項，不常用的細節預設收合。
   用詞沿用系統規格已有的說法，例如操作紀錄、報告清單與支援日誌，不自己翻譯程式概念；類別名稱照寫，並說出它在這張圖裡做什麼。
   節點的補充說明畫在節點上，連線標題只寫兩端的節點名稱，不用括號把說明接在名稱後面。
6. 執行正式 Documentation，再完整閱讀改動段落。驗證記錄留在本機收據，文件只寫有效結論與邊界。

線型要對應證據種類，兩種工具用同一套分類：

| 證據種類 | 依據 | Archify 循序圖 | LikeC4 關係 |
|:---|:---|:---|:---|
| 直接呼叫 | Roslyn 的呼叫，編譯時目標是具體方法。 | 不設 variant | `calls` |
| 介面呼叫 | Roslyn 的呼叫只確定介面方法；畫出實作類別時，另附實作紀錄與 AppCompositionRoot 的建立位置。 | `dashed` | `viaInterface` |
| 間接觸發 | action 字串、WebMessage、委派或延遲串流；附已核對事實。 | `emphasis` | `indirect` |
| 回傳 | 對應同一張圖裡方向相反的呼叫。 | `return` | 不使用 |
| 實作、建立、資料讀寫與使用 | 實作或繼承紀錄、AppCompositionRoot 的建立位置，或已核對事實。 | 不使用 | `implements`、`injects`、`data`、`uses` |

業務流程、資料流、部署與資料表關聯圖的每條線，綁定到已核對事實。類別圖的依賴線上寫的方法，要出現在 Roslyn 證據裡；
只在組裝時才決定的對象，不畫成編譯時依賴，改用 AppCompositionRoot 的「建立」線與卡片說明。

連線證據的規格放在本機工作目錄，由 [`package-redraw.py`](../../tools/harness/architecture/package-redraw.py) 解析 Roslyn 紀錄並封裝成
`evidence/connection-evidence.json`，全部通過後才覆寫圖表目錄；找不到證據、線型和證據種類不符或有線沒有綁定時，封裝直接停止，圖表目錄維持原樣。
類別圖上每個成員的宣告位置也寫在同一份規格，封裝成 `evidence/member-sources.json`；畫出的成員和規格不一致時同樣停止。
畫同一個流程的 LikeC4 動態視圖與 Archify 循序圖怎麼配對，寫在規格的 `dynamicViewPairs`，封裝成 `evidence/dynamic-view-pairs.json`，
沒有這一節就停止；每一組寫參與者對應、循序圖裡要比的訊息、範圍外的訊息與略過的步驟，略過與範圍外都要附原因。
規格放在 Git 忽略的目錄，換機或清理後就不在了；已封裝進圖表目錄的那一份才是持久版本，下一次重繪從那裡複製。
沿用的研究事實不改研究目錄的原檔；要改寫標題或說明時寫在規格的 `researchFactWording`，代號、來源、狀態與結論不變，
封裝時原文留在 `evidence/verified-facts.json` 的 `researchWording`。

[圖表檢查](../../tools/harness/architecture/Check-Architecture.ps1)已納入 Documentation，並以[合成反例](../../tools/tests/architecture-evidence.tests.ps1)檢查分類。
它保護圖表目錄的檔案與來源雜湊，並檢查每條線都有證據、類別關係符合 Roslyn 紀錄、
線型和證據種類一致、回傳對應到呼叫、事實引用存在、類別圖成員都有宣告位置，以及匯出檔沒有本機路徑；
2026-10-25 起也依配對設定逐步比對畫同一個流程的 LikeC4 動態視圖與 Archify 循序圖，比呼叫順序、參與者、方法與程式位置。
它不能證明業務結果正確；沒有通過這些檢查的內容不能標成已受完整檢查保護。

## 後續補強

缺少來源、來源變動、關係種類不符，以及沒有觀察卻聲稱已執行，都應明確失敗。
檢查器新增能力時也新增獨立合成反例，不把由圖表反推的資料當成正確答案。

關鍵業務流程另外規劃有固定輸入與預期結果的驗證。靜態證據與執行觀察分開報告；
一般圖表工作不自行執行 PrivateCase 或啟動 SQL Server，也不以圖表驗證取代產品驗證。
DocFX 維持暫緩。
