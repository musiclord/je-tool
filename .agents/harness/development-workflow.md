# JET 大型開發與跨 session 續接

更新日期：2026-09-23

這份文件只處理需要跨多個步驟或多個 session 的開發。小型、可在一次工作內完成並驗證的修改，不必建立
額外流程文件。

## 何時建立現行計畫

工作符合下列任一情況時，應在 `docs/specs/` 建立一份現行計畫：

- 會同時改動多個產品層、資料庫實作、GUI、Excel 或正式報告。
- 有多個驗收階段、外部能力或使用者裁定。
- 預期會跨 session、換用 Agent，或可能因環境中斷而續接。
- 一旦誤解範圍，會造成大量無效實作或改變對外行為。

使用者提出的執行計畫、範圍與裁定優先。若使用者只給了清楚的成果目標，Agent 可以先整理成最小計畫；
遇到會改變範圍、對外行為或需要新權限的選擇時，仍要請使用者決定。

## 一次只有一份現行大型計畫

`docs/development-status.md` 的「目前大型計畫」只放「無」或一個連結。計畫本身至少保存：

- 目標、範圍與不做事項。
- 審計員在哪一步做什麼、看到什麼；每個可能擋住使用者的錯誤，使用者接下來能做什麼。分段開發最容易
  在模組交接處失去這條線，所以它要寫在計畫最前面，不是實作完再補。
- 使用者已確定的裁定，以及仍需確認的問題。需求與裁定逐字保留使用者原話並附日期，不改成 Agent 自己的
  轉述；要改寫需求段落或計畫標題，先取得使用者授權。提交前的複審對照原話，不對照改寫後的版本。
  2026-09-05 到 06 的篩選工作就是對照改寫後的需求複審，才會做出使用者沒有要的功能。
- 目前步驟、已完成工作與尚未完成工作。
- 第一次失敗、失敗原因及後來如何驗證；診斷重跑不能覆蓋第一次失敗。
- 最後有效驗證的命令、結果和適用範圍。
- 本輪要交付的成果、完成條件，以及中斷後的下一個具體動作；工作順序和本輪邊界分開寫。

計畫不複製完整程式差異、逐行終端輸出或每一次 receipt 路徑。詳細證據留在本次 ignored 執行目錄；計畫只
保存換機或重新 clone 後仍看得懂的摘要。

## 工作順序、本輪邊界與職責

計畫中的「下一步」「第一段」「第二段」說明先後順序和依賴，不表示做完其中一項就結束 session。
本輪交付範圍則回答「使用者這次要拿到什麼、怎樣算完成」。使用者明示只做某一段時依其邊界執行；
未明示時，Agent 依成果目標說明範圍與完成條件，不自行用項目數或一次測試通過縮小任務。
例如「先查來源，再修正，再驗證」是同一任務的連續步驟；「這次只整理來源，不改產品」才是本輪邊界。

使用者決定成果目標、業務歧義與需要另外授權的動作。Agent 負責來源查核、設計、實作、選擇驗證與判讀結果；
harness 提供環境觀察、測試和證據，不決定需求、不替使用者授權，也不替 Agent 判定整輪完成。
某項歧義只暫停相依工作，其他已授權且可獨立完成的工作繼續。當成果達成、使用者要求停止，或剩餘工作
確實受限於未取得的裁定、權限或環境時，再說明完成範圍或具體阻礙。被迫中斷仍是未完成，不改寫成已結案。

## 專案記憶與跨 session 收斂

JET 的專案記憶是受版控的現行文件、程式、測試與目前計畫，不是某一個 Agent 的對話或本機 memory。
Task／thread、memory、compaction 摘要與 ignored receipt 可以協助找回來源，但不能單獨建立規則或證明
目前狀態。完整層級、分類與回寫位置見
[`convergence-and-memory.md`](convergence-and-memory.md)。

使用者明確呼叫 `$jet-converge` 時，由 `.agents/skills/jet-converge/SKILL.md` 收集多個 session 的觀點、
需求、功能與待完成事項，先區分已確認、候選、衝突、延後、已取代與無依據，再用目前核心業務與重啟條件
收斂。新的業務裁定須由使用者確認；已明示的裁定和已授權的文件修正直接寫回，不重複索取同一份授權。
沿用現行計畫，不建立第二份 backlog、`CONTEXT.md`、ADR 或 session dump。

待完成事項若要長期保留，至少要寫清楚背景、目前邊界、現在不做的原因、重啟條件與重啟後第一個可驗證
動作。只有標題或曾在對話提過的想法，不直接進入 `development-status.md`。

## 新 session 如何開始

先取得足以開始工作的上下文。`tools/verify.ps1 -Command Context` 可一次列出目前計畫摘要、Git 狀態、
近期驗證及來源入口；Agent 再依本次問題讀取相關規格與程式。計畫缺少摘要或某項工具不可用，會得到提示，
其餘資料仍可使用。這不是每次開工都要通過的檢查，也不要求先完整重讀所有歷史文件。

接著查本次問題的來源，做足以驗證判斷的修改，執行相應檢查，再依結果修正或繼續下一步，直到本輪成果完成。
一般設計與可回復的實驗由 Agent 自行判斷；失敗時保留原因與證據，不把每個例外都升級成新規定。
工作順序可隨證據調整；哪些情況需要使用者決定，依前節的職責與本輪邊界判斷。

2026-09-18 使用者指出，以長篇限制避免判斷會削弱開發能力。因此交接只需說明目標、重要裁定、目前證據
和未完成事項；狀態蒐集由 Context 協助，驗證沿用正式框架，無需在每份 prompt 重複整套專案規定。

## 工作中如何更新

### 前端文字與操作的複審

2026-09-23 的科目配對提示曾把實際欄名縮成「C 欄」，檢查仍通過，卻讓審計員不知道要在哪個欄位選什麼。
後續修改先核對來源中的操作對象、輸入內容與執行結果；精簡只能刪掉重複內容，不能省略必要欄名、條件或影響。
同一概念須查第四步、條件選單、總覽及報告的共同來源，不只改使用者圈選的位置。

互動修改則比較操作前後的位置、草稿、結果與保存狀態。測試應涵蓋這些關係，實際畫面另檢查滑鼠、鍵盤、
窄版及多個條件組；原有檢查若只鎖住舊字串，先記明新需求與第一次失敗，再調整對應預期，不刪其他斷言。
工具通過只證明已檢查的範圍，文字是否容易理解仍需設計判斷與使用者試用，不以禁詞清單或字數取代。

### 業務裁定如何落實到操作與驗證

2026-09-17 的完整性限制缺陷顯示，只讀到「審計員可信」仍不足以防止誤加限制。
當時程式與測試共同要求差異歸零，卻沒有驗證 legacy 保留差異說明後繼續工作的路徑。
因此既有實作和已通過測試只能證明當時行為，不能自行成為新增業務限制的來源。

2026-09-23 的黃色提示複審又發現：底稿實際會自行重算，卻被另一份報告檔是否存在所限制；
科目配對工作檔沒有使用驗證摘要，卻要求先有驗證 run。兩者的舊測試都曾將這個限制固定下來。
判斷能否移除前置條件，應追到實際讀取的資料，而不是依頁面順序、提示文字或舊測試名稱推定。
本次將檢查改為直接產生正確底稿、保留舊檔及正確科目，不刪除來源版本、必要欄位、取消與發布原子性的檢查。

修改流程限制或接到相反裁定時，沿下列方向蒐集證據並實作，可依問題穿插進行：

1. 逐字保存使用者原話與日期，說明取代哪一項舊結論。接手時先讀最新裁定，再使用舊驗證紀錄。
2. 列出規格、畫面入口、action、業務判定、保存與重開、下游查詢及報表的對應位置。
   每一個阻擋都要分清是結果不存在或已失效，還是留給審計員解釋的差異。
3. 用固定的非零差異建立行為測試，驗證差異保存不變而後續操作成功；同時保留過期結果的拒絕案例。
   不可只把按鈕改成可按，或讓測試資料差異歸零。規則改變前先保存第一次失敗的證據。
4. 同一規則在預篩選、條件預覽、保存重算與報表的必要來源及計算方式要一致；不能一處顯示無法執行，另一處當成零筆。
   新增運算子時保留完整目錄對照，逐項補獨立固定答案，不以另有局部測試為由刪掉目錄檢查。
5. 第二遍從返回、取消、失敗重試、重開與匯出反查上游。將已執行與未執行的路徑寫回同一份計畫。

完整性案例由 `CompletenessBackendGateProviderTests` 在 SQLite 與 DuckDB 沿正式 action 驗證，
`CompletenessEligibilitySupportTests` 核對舊案件摘要轉換，`frontend-workflow.test.cjs` 核對可繼續時
畫面仍顯示差異。它們分別納入正式 Public 與 FrontendMapping 檢查；只通過文件檢查不能結案。

### 保存實際進度

- 完成一個可獨立驗證的步驟後，更新目前步驟、結果、第一次失敗及下一動作。
- 使用者作出會影響後續工作的裁定時，同輪寫回計畫；長期有效的產品或環境決策也要寫入相應現行文件。
- 若 session 即將中斷，先保存實際修改、未完成狀態、已執行與未執行的驗證，以及可直接開始的下一動作。
- 摘要同時保留仍有效的重要否決及理由，避免續接時再次採用已被排除的方案。上下文壓縮後先核對摘要與最新
  使用者要求，有疑點才回查對應原話；不重讀整份歷史，也不把壓縮視為任務結束。
- 更新目前摘要時取代過期敘述。已結束的執行紀錄移入有日期與來源連結的歷史文件，保留原話、首次失敗和驗證
  邊界；現況入口只保留短摘要及連結，不再複製一份逐輪紀錄。
- 不用「全部完成」取代具體範圍。沒有執行 GUI、Excel、provider 或私人案件時，要逐項說明。
- 大型階段結束或使用者詢問未完成事項時，逐項核對 `development-status.md` 的「已知但延後的事項」。只在
  有新證據或使用者裁定時更新狀態；問題解決後才移除，不能因目前不阻擋工作就省略。

## 驗收與關閉

1. 依計畫的驗收條件執行正式 `tools/verify.ps1` 命令，保留第一次失敗與最後有效結果。
2. 提交前由沒有參與實作的另一個 session 或子 Agent 複審。只給它 diff 與計畫，請它核對每項需求都有實作
   與測試、範圍外沒有改動、移除的行為有重建、既有測試沒有被放寬；只回報影響正確性或需求的缺口，不報
   風格。另外問每個新增的關卡或核對防的是誰：防 JET 自己的失敗可以留，防審計員自己的操作要改成提醒
   或拿掉（`AGENTS.md`「預設審計員可信」）。缺口修完後重跑對應命令。2026-09-01 的提交前複審就是這樣
   抓到 `dev.log.exportFile` 的 fallback 缺陷。
3. 將長期有效的背景、操作方法、契約和限制寫回各自現行文件，不讓完成計畫成為唯一事實來源。
4. 計畫標為「待使用者驗收」；只有使用者確認成果或計畫明定的客觀驗收已完成後，才標為「已完成」。
5. 將 `development-status.md` 的目前計畫改回「無」，並保留一段短的完成摘要。詳細過程不搬進現況入口，
   「已知但延後的事項」仍繼續保留。
6. 是否 stage、commit 或 push 仍由使用者另外授權，計畫完成本身不是 Git 授權。

## 不同 Agent 的共同做法

GitHub Copilot、Claude Code、Codex 與 VS Code 的 AI Agent 都使用相同文件、命令與驗收條件。工具有沒有
原生計畫模式、子 Agent 或本機記憶，不會改變這份流程；缺少某項原生能力時，就用現行計畫和較小的可驗證
步驟續接。各工具如何讀取共用規則，見 [`agent-compatibility.md`](agent-compatibility.md)。
