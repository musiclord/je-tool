# SAT 文件的製作與交接

這份文件給製作或修改 `docs/SAT/` 的 agent 讀。SAT 是公司核准查核工具上線前的評估程序，`docs/SAT/` 是 JET 送審用的文件。
產生命令與執行環境寫在 [`tools/harness/sat-documents/README.md`](../../tools/harness/sat-documents/README.md)，歷次修改與目前的差距記在
[首次 SAT 文件製作計畫](../../docs/specs/2026-11-06-sat-initial-documents-plan.md)。這裡只寫標準是什麼、哪些能寫、哪些不能寫。

## 標準是公司的 SAT 文件目錄

使用者 2026-11-10 提供公司的 SAT 文件目錄，並要求以它作為滿足標準。這個目錄放在使用者電腦上、儲存庫以外的位置，
裡面的採用表與測試情境含有人員姓名與測試資料，所以不複製進儲存庫，位置也不寫進文件；需要核對時請使用者當次提供。

使用者 2026-11-12 提供新版的目錄，分成兩個資料夾：一個是要填好交出去的文件，另一個是參考資料。和 2026-11-10 相比，
要交的文件多了 `Workflow.xlsx`，圖表改成 `Structure Diagrams` 與 `Behavior diagrams` 兩個子資料夾，原本的 `UML Diagram.txt` 不在新目錄裡。
參考資料有公司的 SAT 作業辦法、流程圖、各種表單，以及另一個工具首次評估與版本更新時交的整套文件；它們只用來了解公司的要求與寫法，
不複製進儲存庫，也不照抄內容。其中一份作業程序的 PDF 受資訊保護，讀不到內文，不要嘗試解除保護。

使用者 2026-11-23 又提供一份更新版的目錄，並指示送審文件先符合更新後的文件架構，再把先前寫好的內容補回去（裁定 2026-11-23-16）。

- 技術文件範本從 19 節變成 17 節。「Development Environment & Configuration」與「APIs & External Integrations」兩節拿掉了，後面的節次往前遞補。

  第 5 節與第 17 節仍是待填寫的項目清單，項目和先前相同，改成中文。第 6 到第 16 節各只有一句話，指向放在同一層的資料夾或檔案。

## 誰填什麼

| 內容 | 誰負責 |
|:---|:---|
| 技術文件、設計原則、圖表、測試報告 | Agent 依現行程式與直接執行測試的結果撰寫或產生。 |
| 複核結論、複核人員、複核日期、例外核准 | 複核人員。Agent 不代填，重新執行產生腳本時這些欄位維持空白。 |
| 文件負責人、核准狀態、部門 repository 的設定、部署核准、聯絡窗口、開發人員 | Word 文件與文字檔照範本寫「待填寫」；活頁簿裡等人填的儲存格留空。 |
| SAT 採用表、SAT 測試情境與結果 | 專案負責人與公司測試人員。Agent 不撰寫，也不替它們準備內容，除非使用者當次要求。 |

這張表是給 agent 看的分工，不要把「誰填什麼」寫進文件。文件裡要人填的地方只寫「待填寫」或留一個空白欄位，不另外說明由誰填。

## 從開發者的角度寫

使用者 2026-11-10 指出，文件讀起來詭異的主因是視角錯了：文件應該是開發者交出去的文件，寫的是這個軟體與開發者做了什麼；
先前的版本卻站在旁觀者的位置解說整個 SAT 流程。動筆前先確認下面幾條。

1. 文件的作者是開發團隊，讀者是審查的人。寫軟體是什麼、怎麼做的、測試結果如何。
2. 不解說 SAT 流程，也不安排別人的工作。不寫「交由某單位確認」「公司接手」「交接」「送審時附上」「本文件不代表核准」這類句子，
   也不寫哪個欄位由誰填、哪張工作表放什麼。
3. 不寫開發過程的內部紀錄。裁定編號、`docs/rulings.md`、agent、AI 工具、收據編號、驗證工具的內部名稱，都不出現在文件裡。
4. 一般公司怎麼記錄，就怎麼記錄。審查紀錄就是變更說明、檢查項目、發現事項與結論；測試報告就是範圍、數字與結果。
   不把和使用者討論過的每一件事列成一條審查項目。

## 送審的只有 `src/JET`

使用者 2026-11-10 說明：SAT 只會提交 `src/JET/`，那才是專案的原始碼。`data/`、`docs/`、`tools/`、`.agents/` 這些目錄是給 agent 用的開發紀錄，
屬於外部操作，不是部門看得到的內部流程（裁定 2026-11-10-09）。所以文件只描述 `src/JET` 裡的東西：

- 不引用 `src/JET` 以外的檔案、文件與工具。`docs/jet-guide.md`、`docs/glossary.md`、`docs/action-contract-manifest.md`、`tools/verify.ps1`、
  根目錄的 `global.json` 都不寫進文件，「系統規格」「名詞表」「驗證工具」這些說法也不用。
- 路徑以方案檔 `JET.slnx` 所在的資料夾為起點，寫成 `JET/AuditCore/…`、`tests/JET.Tests`，不寫 `src/JET/` 開頭。
- 建置與測試寫 `src/JET` 自己做得到的方式：`dotnet build JET.slnx`、執行測試專案產生的 `JET.Tests.exe`，以及用 Node.js 執行 `tests/frontend` 的前端測試。測試專案只靠 `src/JET` 就能建置；執行時只排除 `Scale` 標記。測試報告的數字在儲存庫外、只有 `src/JET` 的副本照這三行命令產生，不用 `Public` 的收據。
- 測試寫 `tests/JET.Tests` 與 `tests/frontend` 的結果。留在 `tools/tests` 的前端測試、另開桌面的端對端測試與 Excel 驗證都由 `tools/` 的工具執行，
  不寫進文件，也不列進測試報告。
- 需求依據寫舊版 JET 的功能與查核團隊的作業需求。技術文件第 3 節「驗收與參考資料」的需求參考資料例外，照範本寫「使用者提供的架構圖」（裁定 2026-11-23-22）。元件清冊直接列在技術文件第 5 節，不指向來源檔。
- 唯一的例外是技術文件第 6、7、9 節照範本指向的架構文件資料夾。使用者 2026-11-23 說明：「指向的目錄應該是 "je-tool\docs\architecture" 而目前文件的目錄應該是 "je-tool\docs\SAT"」，
  所以那一句寫 `..\architecture`。文件裡不寫 `docs/` 開頭的路徑。

Agent 自己查證時照常使用 `docs/` 與 `tools/`；限制的是寫進文件的內容，不是查證的來源。

## 這是首次 commit

開發期間使用個人的 GitHub 儲存庫。對部門來說，JET 1.0.0.0 是第一次同步到部門的 repository，所以文件一律把它記成首次 commit（使用者 2026-11-10）。
產品的正式名稱是 JE Tool，文件可簡稱 JET（裁定 2026-11-13-07）；寫法見「用語與語氣」的對照表。

- `git_code_changes_log.txt` 只記一筆首次 commit，照 `git log` 的樣子寫 commit、Author、Date 三行。commit 與 Date 照更新版範本寫 `XXX` 與 `yyyy-MM-dd`；
  範本的 Author 是人員姓名，不抄進儲存庫，寫待填寫。commit message 照設計原則第 7 節的規則用中文，寫「首次提交：JET 1.0.0.0」。
  開發期間的 commit 不列進去。
- 技術文件第 15 節寫首次 commit、全部原始碼、沒有先前的修訂；第 16 節與版本更新紀錄只有 1.0.0.0 一列。
- 版本更新紀錄的說明寫中文，第一行是「JE Tool 主要功能」，底下列三項主要功能；表頭照公司範本寫 Date、Description、Version（使用者 2026-11-13 的回覆）。
- 版本號的規則寫在設計原則第 7 節：初版 1.0.0.0；修正錯誤增加第三碼，例如 1.0.1.0；相容的新功能增加第二碼，例如 1.1.0.0；
  不相容的大改版增加第一碼，例如 2.0.0.0；最後一碼固定為 0（裁定 2026-11-13-08）。專案檔還沒設定版本屬性是現況，寫在技術文件第 17 節，不寫進設計原則。
- 複核紀錄的變更說明寫首次 commit。驗收依據與人工複核範圍的寫法見下面「人工複核的範圍」。
- 技術文件第 8 節不寫分支策略與貢獻流程；第 3 節的驗收條件只寫自動化測試與 Code Review 兩項，第 12 節不另列驗收測試（使用者 2026-11-13 的回覆）。
  更新版範本的第 12 節指向公司測試人員的兩份測試情境活頁簿，那一句照範本保留，JET 的文件仍不替它寫驗收條件。
- 技術文件第 10.2 節寫部門 repository 的設定，還沒建立前寫待填寫；不寫個人儲存庫的設定。
- 待填寫與空白各用在哪裡：技術文件、設計原則、文字檔與版本更新紀錄的日期，一律照範本寫「待填寫」，不寫成「待填」（裁定 2026-11-23-22）；`Code review.xlsx` 與 `Unit test Report.xlsx` 裡等人填的儲存格留空，
  例如開發人員與複核人員。
- 還沒發生的事不寫成已完成。部門 repository 的 commit、掃描與複核都還沒做，文件裡照上一點寫待填寫或留空。

## 寫作界線

使用者多次指出 SAT 文件的同一個問題：過度解釋、寫進不必要的內容、AI 感太重（2026-11-06 與 2026-11-10，原話在計畫檔）。
使用者 2026-11-13 的回覆又提了一次，下面兩段是原話的節錄：

> 我擔心你過度解釋一些不需要顧慮的細節而影響你對專案的判斷與理解，也就是過度解釋非必要的細節。

> 不要接露測試由AI撰寫，請避免這類過度解釋的額外說明，如果有相關規範我會手動修正。而其他事項例如文件的檔名都請先以遵循提供的範例為主要參考，我應該有提供足夠的參考文件讓你對照，因此你不應該提出過多需要我決定的問題才對。

所以公司的參考文件、裁定與名詞表查得到答案的事，直接照做，回報時用一句話說明選了什麼，不列成要使用者決定的問題。
文件與回報都不解釋讀者沒有問的細節。

1. 只寫公司範本要求的項目。技術文件的 17 個章節標題照更新版範本，不增、不刪、不改名；每一節寫什麼見「技術文件的架構照更新版範本」。
2. 不新增文件、章節、工作表、圖表或簽核欄位。認為需要新增時，先問使用者，說明是範本的哪一項要求它。
3. 不適用的項目寫「不適用」加一句原因。還沒有的內容照範本寫「待填寫」。兩者都不用長段說明。
4. 每一句都要有本次實際讀到的出處：現行程式、測試收據、系統規格或官方文件。找不到出處就刪掉，不以合理推測填空。
5. 一件事只寫一次。其他地方需要時引用檔名或節次，不重述。
6. 活頁簿不放說明文字。表頭與欄名說得清楚就不再加一段話解釋這張表怎麼用。
7. 日期只在範本要求時寫，例如修訂紀錄、查詢日期。不提已決定不做的功能。
8. 用完整的句子。通用且常見的技術術語照「用語與語氣」的對照表寫：表裡寫成英文的直接寫英文，不附中文；寫成「中文（英文）」的，每份文件只在第一次出現時附英文。
   不另外解釋讀者已經知道的事；程式名稱只在讀者要靠它找到程式時才寫。
9. 現況照實寫。還沒做到的事寫成現況或「待填寫」，不寫成已完成，也不靠措辭帶過。會影響公司判斷的差距另外回報使用者。
10. 文件不寫公司名稱、人員姓名、真實案件與私人路徑。測試數字只用合成資料，照「送審的只有 `src/JET`」一節寫的命令執行測試，取那次的結果。

## 用語與語氣

使用者 2026-11-12 指出，文件的用詞仍然不夠專業，而且帶有 AI 的角度（原話在計畫檔，裁定 2026-11-12-36）。

語氣：

1. 每一句陳述一件查得到的事實：系統做什麼、設定是什麼、測試結果是多少。不對讀者說話，不解釋文件自己怎麼寫成的。

5. 一件事只在一份文件的一個地方寫，其他地方引用節次，寫成「見第 5.1 節」。設計原則寫規則，技術文件寫現況，兩份不互相重複。

## 人工複核的範圍

使用者 2026-11-12 說明：先由自動化的單元測試把關，只有剩下較為核心的程式才交給人複核。這和公司規則第 1 節一致：
單元測試結果是大部分程式的主要驗收依據，人工複核補足固定值、業務規則與測試不足以確認的行為。文件照下面的寫法：

- 驗收依據寫「以自動化測試結果為主要驗收依據」，結果記在 Unit test Report。技術文件第 11 節與複核紀錄的「驗收依據與測試佐證」用同一句。
- 人工複核的範圍是程式內的固定值與規則（hard-coded content），也就是寫在程式內的六項核心查核邏輯，以及它們用到的固定值。
  六項邏輯的程式位置列在 Code review.xlsx 的「複核範圍」工作表，固定值列在「固定值與規則」工作表。不寫「複核範圍為全部原始碼」，
  也不把固定值寫成和核心查核邏輯並列的另一個範圍。技術文件第 11 節與複核紀錄的「人工複核的範圍」用同一句。
- 複核紀錄裡取自規則第 4 節的檢查項目，文字不動。其中需求、可讀性與錯誤處理三項只檢查人工複核的範圍，這個限制寫在複核紀錄「人工複核的範圍」的第二句。
- 範圍怎麼定只寫一句依據：依風險決定，直接影響查核結果的邏輯由人工複核。不引用外部標準替這個做法背書。
- 「複核範圍」工作表列到檔案與測試類別，不列程序與函式的名稱。使用者 2026-11-19 說明模組太多，逐一列出人工複核做不完（裁定 2026-11-19-06）。
  人工複核逐項核對的是「固定值與規則」的清單。要改變人工複核的做法或範圍時先問使用者，不自行提出偏離上面原則的方法。
- 複核紀錄上方的說明一格只寫一件事，照公司參考文件的寫法（裁定 2026-11-19-08）：變更說明只寫這次變更是什麼，
  驗收依據與人工複核的範圍各自一列。固定值清單各項的由來不另外補說明（裁定 2026-11-19-07）。
- 文件不寫測試由誰或由什麼工具撰寫，照「從開發者的角度寫」第 3 點。使用者 2026-11-13 的回覆決定不揭露測試由 AI 撰寫，原話在「寫作界線」；
  也不寫成由開發人員手寫。

使用者 2026-11-19 說明固定值與規則指的是什麼：通常是核心審計邏輯。後端沒有分模組的時候，指定的指令與邏輯會直接寫成硬編碼的 SQL 查詢；
這些程式直接決定查核結果，所以交給人複核。JET 的後端已經分模組，當初要求獨立出 `AuditCore`，就是為了把要人工複核的核心程式分出來。
原話在裁定 2026-11-19-03。寫這份範圍時照下面七點：

- 「複核範圍」與「固定值與規則」兩張工作表列的程式位置都在 `AuditCore` 與 `Domain`。使用者 2026-11-19 同意把留在其他模組的查核邏輯收進 `AuditCore`（裁定 2026-11-19-04），
  其他模組的查詢要用到這些邏輯時呼叫 `AuditCore` 的定義；架構測試 `AuditLogicOwnershipTests` 檢查已經收進去的幾種寫法沒有再出現在別的模組。
  資料庫引擎怎麼寫週末、大小寫與空白字元屬於 Infrastructure 的方言，不列進複核範圍。之後若發現還有查核邏輯留在其他模組，照實列出檔案，不因為想讓範圍看起來集中就省略。
- 公司規則第 6 節要開發人員送交複核時附上重大固定值與規則的清單與理由，第 3 節要複核人員確認每一項的依據、用途與行為。
  這份清單與理由用中文寫；提到規則的要求時也用中文說，不直接貼規則的英文句子。規則的節名照公司原文，不翻譯。
- Code review 看程式裡寫的條件與固定值。公司測試人員的測試情境從畫面操作，拿報告與工作底稿的輸出核對手動驗算的結果。
  `Code review.xlsx` 不寫操作步驟、測試案例與預期的輸出數字；項目名稱用 JET 現行的名稱。兩份文件講到同一條規則時，內容不能互相矛盾。
- 使用者 2026-11-24 指出：過度詳細的測試交給 Unit test Report，人工複核只看核心的審計邏輯與審計業務（裁定 2026-11-24-01）。
  業界的人工複核依風險挑出要看的程式，看程式是否符合需求，也看測試是否存在、是否正確、程式壞掉時會不會失敗，不逐一重跑測試案例；
  所以 `Code review.xlsx` 只放複核紀錄、六項核心查核邏輯與固定值清單，測試案例的清單與結果放在 Unit test Report，見「核心查核邏輯的測試案例」。
- 安全相關的程式，例如讀取客戶檔案、畫面與後端之間的訊息、組資料庫查詢與決定匯出路徑的程式，不列進人工複核範圍，交給 GitHub 的安全功能處理。
  複核紀錄不記錄複核花的時間、看了多少行與參與的人（裁定 2026-11-24-02）。
- 一個複核項目只講一件事。規則或邏輯一次要求好幾件事時，拆成最多三個最核心的事項，各有自己的結果欄，並附一個「例：」說明這條規則的效果，
  例如「總帳日期是查核起始日或截止日當天的分錄，納入測試」。例子只說明規則，不是測試案例，不寫操作步驟與報告的輸出數字。
  不要求逐一複核每個模組、函式或變數（裁定 2026-11-24-03）。
- 複核項目寫給人看，用審計的說法寫規則與它對查核結果的影響，看的是程式模組有沒有對齊審計業務與查核邏輯，

  不寫排序鍵怎麼算（裁定 2026-11-24-04）。

### 核心查核邏輯的測試案例

使用者 2026-11-23 要求替人工複核設計一份更直觀呈現查核邏輯的測試文件，並希望遵循業界標準，因為文件還要交給 IT 部門與資安單位審閱；
2026-11-24 回覆「接著補齊」，案例擴到三個範圍：公司測試人員的測試情境目錄裡每一項篩選條件、「固定值與規則」的每一項，以及產品登錄的每一條預篩選規則。
同一天使用者看過成品後指出，要人工審核的項目太多太細，詳細的測試要交給 Unit test Report（裁定 2026-11-24-01）。原話在計畫檔。

- 案例只在 `Unit test Report.xlsx` 的「案例清單」工作表列出。這份是測試結果報告，不照公司參考的測試情境活頁簿的欄位與排法。
  上方四列是自動化測試、測試資料與預期結果、執行日期與結果，前兩列寫自動化測試的檔案與案例定義檔；底下的表格有案例編號、案例名稱與結果三欄。
  測試資料、預期結果與執行操作留在案例定義檔，不印進活頁簿。
  「案例清單」是使用者指定放進 Unit test Report 的工作表，「寫作界線」第 2 點的限制不適用於它。
- 「核心查核邏輯」工作表各項邏輯的測試案例數包含這些案例：`Export-SatEvidence.py` 依案例編號找出案例所屬的邏輯，只算進那一項。
  `Code review.xlsx`「複核範圍」的測試類別也列出 `AuditLogicCaseTests`。
- 案例只定義一次：`src/JET/tests/JET.Tests/Fixtures/audit-logic-cases.json`。測試類別 `AuditLogicCaseTests` 照這份定義把每個案例
  交給產品實際執行，核對結果和定義的預期結果完全相同；`Build-ReviewData.py` 從同一份定義取出案例清單。要增減或修改案例時改這一份，
  不改腳本，也不直接改活頁簿。
- 案例檔的查核目的與規則說明用白話寫，不寫程式名稱，讓打開案例檔的人直接看懂這個查核程序在查什麼、規則怎麼判斷。
- 案例檔分成「測試資料」與「案例」兩段。一份測試資料寫一次：前置條件、GL 分錄與 TB；案例只寫用哪一份資料、執行什麼，以及每一筆分錄的預期歸屬與原因。
  同一個欄位的篩選條件共用一份資料，例如總帳日期與傳票核准日的 48 個案例都用同一份八張傳票。測試類別替每一份資料只建立一次案件，
  用到它的案例各自執行自己的操作，每個案例仍是測試結果裡獨立的一列。
- 測試資料全部是自己編的合成分錄，不取自任何真實案件。一份資料最多 16 筆，少到人可以用眼睛驗算。欄名用 `docs/glossary.md` 的欄位名稱。
  資料要像真的帳：科目、摘要與借貸方向對得上，例如迴轉估列費用是借應付費用、貸費用，押金記在存出保證金；完整性測試的 TB 年度變動金額合計是 0。
  共用的資料要讓每一個條件都有命中與不命中的分錄，並放進邊界：區間的兩端、門檻當日、空白，以及只差頭尾空白或大小寫的值。
- 畫面會先換算的條件，案例執行換算後的條件，並在規則說明寫出怎麼換算。「查核期末最後幾天」由畫面換成日期區間：查核截止日往前數 X 減 1 天，到截止日為止。
  月初與月底幾天不換算，天數直接交給程式判斷。畫面的「指定日期」送的是日期清單，只指定一天時清單只有一個值，案例照這個寫法執行。
- 完整性測試與借貸不平測試的案例，每一筆分錄寫的是有沒有納入測試，測試一併核對。定義另外列出各科目的 TB 與 GL 金額、各傳票的借貸合計，
  測試會確認這些數字等於定義裡納入測試的分錄的合計，所以案例檔裡沒有未經核對的金額。
- 預期結果照規則人工推得，逐筆寫明歸屬與原因，不由受測程式算出來再貼回去。案例跑出來和推得的不同時，先查清楚是理解錯還是產品的問題；
  是產品的問題就回報使用者，不改預期結果去遷就。
- 結果來自測試結果檔：`Export-SatEvidence.py` 依測試顯示名稱裡的案例編號，把每個案例的結果寫進 `source/test-record.json` 的 `reviewCases`。
  測試結果檔記的開始時間是 UTC，腳本換算成這台電腦的日期再寫成執行日期；報告的執行日期用同一個算法。
  結果檔裡沒有的案例寫未執行，不補成通過。`reviewCases` 另外記下案例檔的雜湊；產生活頁簿時雜湊和現在的案例檔不同，全部案例寫未執行，
  所以改了案例之後要重新執行測試並轉換。欄名寫「結果」，和「測試結果」工作表的寫法相同。
- 案例檔寫了測試不認得的鍵，或某一筆分錄的預期歸屬不屬於那種操作，測試會失敗。
- 抽到哪幾筆樣本由案件的隨機種子決定，資料可靠性測試的案例寫明實際核對的項目：筆數、樣本不重複、樣本都是納入測試的分錄，以及重新執行後相同。
- 案例名稱有兩個來源。預篩選的案例用產品登錄的規則名稱，例如「週末過帳」「假日過帳」「未預期出現之特定借貸組合」，登錄在 `PrescreenRuleDefinitions`。
  進階條件篩選的案例照公司測試人員的測試情境目錄原字，寫成「欄位_符合或排除_條件」，例如「總帳日_符合_補班日」「總帳日_符合_周末」，方便兩邊對照；
  目錄的每一項篩選條件都要有案例。案例檔記下那一項在目錄裡的序號，用來排列案例的順序；活頁簿不列序號，也不帶進目錄記的測試狀態與活頁簿的其他內容。
  同一個目錄名稱有兩個案例時，在後面用括號寫差別，例如「（空白也列入）」。產品有、目錄沒有的條件，例如常用篩選條件的卡片、條件組合與整張傳票條件，
  用畫面上的名稱，序號留空。
- 案例編號發出去之後不重編。新增的案例接在同一個字首的最後一號之後，所以進階條件篩選的編號順序和目錄的順序不同；案例清單照下面兩點的順序排，不照編號。
  「核准日不在期間」原本編成 FLT-155、放在進階條件篩選；它是資料驗證的輔助檢視，在送出複核前移到「納入測試的分錄範圍」並改編 POP-08，FLT-155 不再使用。
- 每個案例有一個分類，進階條件篩選的分類是欄位，例如「總帳日期」「傳票摘要」。案例清單在同一項邏輯裡依分類分段：分類照它在目錄裡最小的序號排，
  目錄沒有的分類接在後面；分類裡照目錄的序號排。
- 案例清單照操作順序排：納入測試的分錄範圍、完整性測試、借貸不平測試、資料可靠性測試、預篩選、進階條件篩選。「複核範圍」工作表原本的順序不動。
- 「固定值與規則」的每一項至少要有一個案例直接用到，`Build-ReviewData.py` 會檢查。只影響匯出報告檔的兩項不做成案例：資料驗證報告的借貸淨額與報告明細列數上限，
  腳本記下核對它們的測試類別。要再增加不做成案例的項目時，先確認有測試核對它。
- 案例檔的欄位參考 ISO/IEC/IEEE 29119-3:2021（Software and systems engineering — Software testing — Part 3: Test documentation）的測試案例規格：
  編號、目的、前置條件、輸入、預期結果，以及案例和查核邏輯、自動化測試之間的追溯。活頁簿不引用這份標準。
- 「案例清單」的每項查核邏輯有一列帶底色的標題，寫該項的案例數與通過數，有失敗或未執行的案例時另寫個數；底下每個分類一列粗體標題，再列各案例。
  表頭在每一頁重複，失敗的結果用紅字標出，工作表不凍結窗格。列印時一個分類放得下一頁就不跨頁，放不下時在案例之間分頁。

固定值清單每一格都要短，不寫成長句、不引用章節，也不加「未載明」這類但書；使用者 2026-11-10 指出，這種寫法一眼就看得出是 AI 寫的。
清單不設「來源」欄。這一欄原本只填舊版 JET、查核需求、會計慣例、程式設計四種之一，使用者 2026-11-19 認為它沒有呈現關鍵的必要資訊，決定移除（裁定 2026-11-19-02）。
每一項為什麼寫在程式內，改由範圍的那一句與複核紀錄的「需求依據」說明。要增減審查範圍或固定值清單的項目時，先問使用者。

## 製作與交接

1. 先改 `tools/harness/sat-documents/source/` 的來源或腳本裡的設定，再照 `tools/harness/sat-documents/README.md` 的順序重新產生，不直接改 Word 或 Excel 成品。
2. 圖表與固定值清單由腳本對照現行程式產生。腳本找不到對應的程式時會停止；這時去改來源設定，不繞過檢查。
3. 重新產生後，把 Word 與 Excel 轉成 PDF 逐頁看過，確認沒有截斷或重疊。Word 與 Excel 都在背景開啟，不在使用者的桌面操作。
4. 執行 `pwsh -NoProfile -File tools/verify.ps1 -Command Documentation`。
5. 在計畫檔記下：使用者這次的原話、改了哪些來源、測試數字取自哪一天執行的哪個命令，以及沒有做的檢查；不寫收據編號。差距清單也更新在計畫檔。

交付前逐項確認：

- `docs/SAT/` 的資料夾與檔名和上面的對照表一致，沒有多出來的文件、腳本或來源。
- 「用語與語氣」最後列的舊寫法，在成品抽出的文字裡搜尋不到，允許的例外照那一節；同一個概念沒有兩種說法。
- `Code review rule.docx` 的段落文字和公司原文逐字相同。
- 技術文件是更新版範本的 17 節，沒有空白的章節；不適用與待填寫都有寫明。兩份 Word 文件互相引用的節次都指得到現在的節。
- `Workflow.xlsx` 解開後搜尋不到機構、部門與團隊的名稱。
- 活頁簿與圖表的標題不帶 JE Tool；活頁簿的工作表解開後沒有凍結窗格的設定。
- 文件裡搜尋不到「裁定」「rulings」「agent」「交接」「送審」「公司接手」，也沒有公司名稱、單位名稱與簡稱、人員姓名、私人路徑、收據編號與開發時的 commit ID。
  技術文件第 1 節範本原句的「交接」不算。
- 文件裡沒有黃色標示，也沒有「[待填寫]」這種範本留下的待填寫記號。
- 文件裡搜尋不到 `docs/`、`tools/`、`src/JET`、`verify.ps1`、`global.json`、「系統規格」與「名詞表」。公司的 `Code review rule.docx` 原文有 verify 這個英文字，不算。
  第 6、7、9 節的 `..\architecture` 是唯一指向 `docs/SAT/` 以外的路徑。
- Word 與 Excel 成品的文件屬性裡，作者與上次儲存者是 JET 或空白；內嵌的佈景主題名稱，Word 文件是 Office Theme，活頁簿是 Office。成品的內部檔案搜尋不到這台電腦的使用者名稱、
  Office 使用者名稱、本機路徑與 AI 產品的名稱。產生腳本會自己檢查這幾項，交付前仍要解開成品再確認一次（2026-11-12 的複核查到這兩種外洩）。
- `docs/SAT/` 底下沒有 Word 或 Excel 開啟檔案時留下的 `~$` 暫存檔。
- 複核人員要填的欄位是空的。
- 每個數字都對得上來源檔。
- 回覆使用者時，列出仍待公司或使用者處理的差距，不只說文件已更新。
