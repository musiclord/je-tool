# SAT 文件的製作與交接

這份文件給製作或修改 `docs/SAT/` 的 agent 讀。SAT 是公司核准查核工具上線前的評估程序，`docs/SAT/` 是 JET 送審用的文件。
產生命令與執行環境寫在 [`tools/harness/sat-documents/README.md`](../../tools/harness/sat-documents/README.md)，歷次修改與目前的差距記在
[首次 SAT 文件製作計畫](../../docs/specs/2026-11-06-sat-initial-documents-plan.md)。這裡只寫標準是什麼、哪些能寫、哪些不能寫。

## 標準是公司的 SAT 文件目錄

使用者 2026-11-10 提供公司的 SAT 文件目錄，並要求以它作為滿足標準。這個目錄放在使用者電腦上、儲存庫以外的位置，
裡面的採用表與測試情境含有人員姓名與測試資料，所以不複製進儲存庫，位置也不寫進文件；需要核對時請使用者當次提供。

`docs/SAT/` 的資料夾與檔名照這個目錄。下表是對照，公司目錄的拼字照原樣記錄；來源都在 `tools/harness/sat-documents/` 底下：

|:---|:---|:---|:---|

`docs/SAT/` 是存放文件的目錄，只放上表有對應的文件。使用者 2026-11-10 的兩項指示：

- 不放附件。原本有五份公司目錄沒有的文件，分別是使用說明 `Readme.md`、`第三方元件.xlsx`、`Code and Explanation.xlsx`、
  `Workflow.xlsx` 與 `程式修訂紀錄.md`；使用者指示移除（裁定 2026-11-10-07），不要再做回來。
- 不放產生腳本與來源。腳本與來源在 `tools/harness/sat-documents/`（裁定 2026-11-10-08）。元件清冊的來源是那裡的 `source/dependencies.csv`，技術文件第 5 節只列直接引用的元件。

`Github Security Reports/` 只放 GitHub 匯出的檔案，不放自己寫的摘要。GitHub 會產出哪些檔案寫在 `tools/harness/sat-documents/README.md`；
這個資料夾目前只有讓 Git 保留空資料夾的 `.gitkeep`。

## 誰填什麼

| 內容 | 誰負責 |
|:---|:---|
| 技術文件、設計原則、圖表、測試報告 | Agent 依現行程式與直接執行測試的結果撰寫或產生。 |
| 審查結論、審查者、審查日期、核准的程式版本、例外核准 | 審查者。Agent 不代填，產生腳本重跑時這些欄位維持空白。 |
| 文件負責人、核准狀態、代碼庫的設定、部署核准、聯絡窗口、提交編號 | 文件裡寫「待填」。 |
| SAT 採用表、SAT 測試情境與結果 | 專案負責人與公司測試人員。Agent 不撰寫，也不替它們準備內容，除非使用者當次要求。 |

這張表是給 agent 看的分工，不要把「誰填什麼」寫進文件。文件裡要人填的地方就是一個空白欄位，不另外說明由誰填。

## 從開發者的角度寫

使用者 2026-11-10 指出，文件讀起來詭異的主因是視角錯了：文件應該是開發者交出去的文件，寫的是這個軟體與開發者做了什麼；
先前的版本卻站在旁觀者的位置解說整個 SAT 流程。動筆前先確認下面幾條。

1. 文件的作者是開發團隊，讀者是審查的人。寫軟體是什麼、怎麼做的、測試結果如何。
2. 不解說 SAT 流程，也不安排別人的工作。不寫「交由某單位確認」「公司接手」「交接」「送審時附上」「本文件不代表核准」這類句子，
   也不寫哪個欄位由誰填、哪張工作表放什麼。
3. 不寫開發過程的內部紀錄。裁定編號、`docs/rulings.md`、agent、AI 工具、收據編號、驗證工具的內部名稱，都不出現在文件裡。
4. 一般公司怎麼記錄，就怎麼記錄。審查紀錄就是變更說明、檢查項目、發現事項與結論；測試報告就是範圍、數字與結果。
   不把和使用者討論過的每一件事列成一條審查項目。

## 送審的只有 `src/JET`

使用者 2026-11-10 說明：SAT 只會提交 `src/JET/`，那才是專案的原始碼。`data/`、`docs/`、`tools/`、`.agents/` 這些目錄是給 agent 用的開發紀錄，
屬於外部操作，不是部門看得到的內部流程（裁定 2026-11-10-09）。所以文件只描述 `src/JET` 裡的東西：

- 不引用 `src/JET` 以外的檔案、文件與工具。`docs/jet-guide.md`、`docs/glossary.md`、`docs/action-contract-manifest.md`、`tools/verify.ps1`、
  根目錄的 `global.json` 都不寫進文件，「系統規格」「名詞表」「驗證工具」這些說法也不用。
- 路徑以方案檔 `JET.slnx` 所在的資料夾為起點，寫成 `JET/AuditCore/…`、`tests/JET.Tests`，不寫 `src/JET/` 開頭。
- 建置與測試寫 `src/JET` 自己做得到的方式：`dotnet build JET.slnx`、執行測試專案產生的 `JET.Tests.exe`，以及用 Node.js 執行 `tests/frontend` 的前端測試。測試專案只靠 `src/JET` 就能建置；執行時排除 `PrivateCase`、`Scale` 與 `DevelopmentRepository` 三組標記，最後一組是要讀 `src/JET` 以外檔案的測試。測試報告的數字用這個命令的結果，不用 `Public` 的收據。
- 測試寫 `tests/JET.Tests` 與 `tests/frontend` 的結果。留在 `tools/tests` 的前端測試、另開桌面的端對端測試與 Excel 驗證都由 `tools/` 的工具執行，
  不寫進文件，也不列進測試報告。
- 需求依據寫舊版 JET 的功能與查核團隊的作業需求。元件清冊直接列在技術文件第 5 節，不指向來源檔。

Agent 自己查證時照常使用 `docs/` 與 `tools/`；限制的是寫進文件的內容，不是查證的來源。

## 這是首次提交

開發期間使用個人的 GitHub 儲存庫。對部門來說，JET 1.0.0.0 是第一次同步到部門代碼庫，所以文件一律把它記成首次提交（使用者 2026-11-10）。

- `git_code_changes_log.txt` 只記一筆首次提交，提交編號與日期寫待填。開發期間的提交不列進去。
- 技術文件第 17 節寫首次提交、全部原始碼、沒有先前的修訂；第 18 節與版本更新紀錄只有 1.0.0.0 一列。
- 審查紀錄的變更說明寫首次提交，審查範圍是全部原始碼。
- 技術文件第 12.2 節寫部門代碼庫的設定，還沒建立前寫待填；不寫個人儲存庫的設定。
- 測試報告的提交編號留空。開發時的提交編號只留在 `source/test-record.json`，不寫進報告。
- 還沒發生的事不寫成已完成。部門代碼庫的提交、掃描與審查都還沒做，文件裡是待填或空白欄位。

## 寫作界線

使用者多次指出 SAT 文件的同一個問題：過度解釋、寫進不必要的內容、AI 感太重（2026-11-06 與 2026-11-10，原話在計畫檔）。

1. 只寫公司範本要求的項目。技術文件的 19 個章節標題照範本，不增、不刪、不改名；每一節只回答範本在該節列出的項目。
2. 不新增文件、章節、工作表、圖表或簽核欄位。認為需要新增時，先問使用者，說明是範本的哪一項要求它。
3. 不適用的項目寫「不適用」加一句原因。還沒有的內容寫「待填」。兩者都不用長段說明。
4. 每一句都要有本次實際讀到的出處：現行程式、測試收據、系統規格或官方文件。找不到出處就刪掉，不以合理推測填空。
5. 一件事只寫一次。其他地方需要時引用檔名或節次，不重述。
6. 工作簿不放說明文字。表頭與欄名說得清楚就不再加一段話解釋這張表怎麼用。
7. 日期只在範本要求時寫，例如修訂紀錄、查詢日期。不提已決定不做的功能。
8. 讀者不一定有資訊背景。用完整的句子，不堆術語；程式名稱只在讀者要靠它找到程式時才寫。
9. 現況照實寫。還沒做到的事寫成現況或「待填」，不寫成已完成，也不靠措辭帶過。會影響公司判斷的差距另外回報使用者。
10. 文件不寫公司名稱、人員姓名、真實案件與私人路徑。測試數字只用合成資料，照「送審的只有 `src/JET`」一節寫的命令執行測試，取那次的結果。

AGENTS.md「寫給人的文字」與 `jet-readable-docs` 的規則同樣適用。

## 審查門檻以公司規則為準

`Code review rule` 是公司提供的規則，照原文收錄，不翻譯、不改寫、不補充。使用者 2026-11-10 指示：審查規則與限制不需要高於這份規則。

- 不自行訂定涵蓋率百分比門檻。規則只要求確認改動的行為與重要分支有被測試執行到。
- 結論只用規則的三種：通過、需修正、例外核准。
- 不新增規則沒有要求的佐證、表單或流程。

`Code review.xlsx` 照規則第 6 節的內容編排，共三張工作表：

| 工作表 | 內容 | 對應規則 |
|:---|:---|:---|
| 審查紀錄 | 變更說明、需求依據、程式版本、檢查項目、發現事項、結論、審查者、日期、核准的程式版本、後續事項與例外 | 第 6 節；檢查項目取自第 2 到第 4 節 |
| 審查範圍 | 六項主要功能的程式位置與對應的單元測試 | 第 6 節的 affected procedures or functions |
| 固定值與規則 | 程式內會影響審計結果的固定值與規則，各附項目、內容、程式位置與來源 | 第 3 節 |

固定值清單每一格都要短。「來源」欄只填四種：舊版 JET、查核需求、會計慣例、程式設計。使用者 2026-11-10 指出，
在這一欄寫成句子、引用章節或加上「未載明」這類但書，一眼就看得出是 AI 寫的。Agent 用裁定與系統規格判斷每一項屬於哪一種，但不把出處寫進去。
要增減審查範圍或固定值清單的項目時，先問使用者。

## 製作與交接

1. 先改 `tools/harness/sat-documents/source/` 的來源或腳本裡的設定，再照 `tools/harness/sat-documents/README.md` 的順序重新產生，不直接改 Word 或 Excel 成品。
2. 圖表與固定值清單由腳本對照現行程式產生。腳本找不到對應的程式時會停止；這時去改來源設定，不繞過檢查。
3. 重新產生後，把 Word 與 Excel 轉成 PDF 逐頁看過，確認沒有截斷或重疊。Word 與 Excel 都在背景開啟，不在使用者的桌面操作。
4. 執行 `pwsh -NoProfile -File tools/verify.ps1 -Command Documentation`。
5. 在計畫檔記下：使用者這次的原話、改了哪些來源、測試數字取自哪一天執行的哪個命令，以及沒有做的檢查；不寫收據編號。差距清單也更新在計畫檔。

交付前逐項確認：

- `docs/SAT/` 的資料夾與檔名和上面的對照表一致，沒有多出來的文件、腳本或來源。
- 技術文件仍是範本的 19 節，沒有空白的章節；不適用與待填都有寫明。
- 文件裡搜尋不到「裁定」「rulings」「agent」「交接」「送審」「公司接手」，也沒有公司名稱、人員姓名、私人路徑、收據編號與開發時的提交編號。
- 文件裡搜尋不到 `docs/`、`tools/`、`src/JET`、`verify`、`global.json`、「系統規格」與「名詞表」。
- 審查者要填的欄位是空的。
- 每個數字都對得上來源檔。
- 回覆使用者時，列出仍待公司或使用者處理的差距，不只說文件已更新。
