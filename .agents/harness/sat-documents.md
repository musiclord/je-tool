# SAT 文件的製作與交接

這份文件給製作或修改 `docs/SAT/` 的 agent 讀。SAT 是公司核准查核工具上線前的評估程序，`docs/SAT/` 是 JET 送審用的文件。
產生命令與執行環境寫在 [`tools/harness/sat-documents/README.md`](../../tools/harness/sat-documents/README.md)，歷次修改與目前的差距記在
[首次 SAT 文件製作計畫](../../docs/specs/2026-11-06-sat-initial-documents-plan.md)。這裡只寫標準是什麼、哪些能寫、哪些不能寫。

## 標準是公司的 SAT 文件目錄

使用者 2026-11-10 提供公司的 SAT 文件目錄，並要求以它作為滿足標準。這個目錄放在使用者電腦上、儲存庫以外的位置，
裡面的採用表與測試情境含有人員姓名與測試資料，所以不複製進儲存庫，位置也不寫進文件；需要核對時請使用者當次提供。

使用者 2026-11-12 提供新版的目錄，分成兩個資料夾：一個是要填好交出去的文件，另一個是參考資料。和 2026-11-10 相比，
要交的文件多了 `Workflow.xlsx`，圖表改成 `Structure Diagrams` 與 `Behavior diagrams` 兩個子資料夾，原本的 `UML Diagram.txt` 不在新目錄裡。
參考資料有公司的 SAT 作業辦法、流程圖、各種表單，以及另一個工具首次評估與版本更新時交的整套文件；它們只用來了解公司的要求與寫法，
不複製進儲存庫，也不照抄內容。其中一份作業程序的 PDF 受資訊保護，讀不到內文，不要嘗試解除保護。

## 誰填什麼

| 內容 | 誰負責 |
|:---|:---|
| 技術文件、設計原則、圖表、測試報告 | Agent 依現行程式與直接執行測試的結果撰寫或產生。 |
| 複核結論、複核人員、複核日期、核准的提交識別碼、例外核准 | 複核人員。Agent 不代填，重新執行產生腳本時這些欄位維持空白。 |
| 文件負責人、核准狀態、儲存庫的設定、部署核准、聯絡窗口、提交識別碼 | 文件裡寫「待填」。 |
| SAT 採用表、SAT 測試情境與結果 | 專案負責人與公司測試人員。Agent 不撰寫，也不替它們準備內容，除非使用者當次要求。 |

這張表是給 agent 看的分工，不要把「誰填什麼」寫進文件。文件裡要人填的地方就是一個空白欄位，不另外說明由誰填。

## 從開發者的角度寫

使用者 2026-11-10 指出，文件讀起來詭異的主因是視角錯了：文件應該是開發者交出去的文件，寫的是這個軟體與開發者做了什麼；
先前的版本卻站在旁觀者的位置解說整個 SAT 流程。動筆前先確認下面幾條。

1. 文件的作者是開發團隊，讀者是審查的人。寫軟體是什麼、怎麼做的、測試結果如何。
2. 不解說 SAT 流程，也不安排別人的工作。不寫「交由某單位確認」「公司接手」「交接」「送審時附上」「本文件不代表核准」這類句子，
   也不寫哪個欄位由誰填、哪張工作表放什麼。
3. 不寫開發過程的內部紀錄。裁定編號、`docs/rulings.md`、agent、AI 工具、收據編號、驗證工具的內部名稱，都不出現在文件裡。
4. 一般公司怎麼記錄，就怎麼記錄。審查紀錄就是變更說明、檢查項目、發現事項與結論；測試報告就是範圍、數字與結果。
   不把和使用者討論過的每一件事列成一條審查項目。

## 送審的只有 `src/JET`

使用者 2026-11-10 說明：SAT 只會提交 `src/JET/`，那才是專案的原始碼。`data/`、`docs/`、`tools/`、`.agents/` 這些目錄是給 agent 用的開發紀錄，
屬於外部操作，不是部門看得到的內部流程（裁定 2026-11-10-09）。所以文件只描述 `src/JET` 裡的東西：

- 不引用 `src/JET` 以外的檔案、文件與工具。`docs/jet-guide.md`、`docs/glossary.md`、`docs/action-contract-manifest.md`、`tools/verify.ps1`、
  根目錄的 `global.json` 都不寫進文件，「系統規格」「名詞表」「驗證工具」這些說法也不用。
- 路徑以方案檔 `JET.slnx` 所在的資料夾為起點，寫成 `JET/AuditCore/…`、`tests/JET.Tests`，不寫 `src/JET/` 開頭。
- 建置與測試寫 `src/JET` 自己做得到的方式：`dotnet build JET.slnx`、執行測試專案產生的 `JET.Tests.exe`，以及用 Node.js 執行 `tests/frontend` 的前端測試。測試專案只靠 `src/JET` 就能建置；執行時排除 `PrivateCase`、`Scale` 與 `DevelopmentRepository` 三組標記，最後一組是要讀 `src/JET` 以外檔案的測試。測試報告的數字用這個命令的結果，不用 `Public` 的收據。
- 測試寫 `tests/JET.Tests` 與 `tests/frontend` 的結果。留在 `tools/tests` 的前端測試、另開桌面的端對端測試與 Excel 驗證都由 `tools/` 的工具執行，
  不寫進文件，也不列進測試報告。
- 需求依據寫舊版 JET 的功能與查核團隊的作業需求。元件清冊直接列在技術文件第 5 節，不指向來源檔。

Agent 自己查證時照常使用 `docs/` 與 `tools/`；限制的是寫進文件的內容，不是查證的來源。

## 這是首次提交

開發期間使用個人的 GitHub 儲存庫。對部門來說，JET 1.0.0.0 是第一次同步到部門的儲存庫，所以文件一律把它記成首次提交（使用者 2026-11-10）。

- `git_code_changes_log.txt` 只記一筆首次提交，照 `git log` 的樣子寫 commit、Author、Date 三行，值寫待填。開發期間的提交不列進去。
- 技術文件第 17 節寫首次提交、全部原始碼、沒有先前的修訂；第 18 節與版本更新紀錄只有 1.0.0.0 一列。
- 複核紀錄的變更說明寫首次提交。全部原始碼以自動化測試驗收，人工複核的範圍見下面「人工複核的範圍」。
- 技術文件第 12.2 節寫部門儲存庫的設定，還沒建立前寫待填；不寫個人儲存庫的設定。
- 測試報告的提交識別碼留空。開發時的提交識別碼只留在 `source/test-record.json`，不寫進報告。
- 還沒發生的事不寫成已完成。部門儲存庫的提交、掃描與複核都還沒做，文件裡是待填或空白欄位。

## 寫作界線

使用者多次指出 SAT 文件的同一個問題：過度解釋、寫進不必要的內容、AI 感太重（2026-11-06 與 2026-11-10，原話在計畫檔）。

1. 只寫公司範本要求的項目。技術文件的 19 個章節標題照範本，不增、不刪、不改名；每一節只回答範本在該節列出的項目。
2. 不新增文件、章節、工作表、圖表或簽核欄位。認為需要新增時，先問使用者，說明是範本的哪一項要求它。
3. 不適用的項目寫「不適用」加一句原因。還沒有的內容寫「待填」。兩者都不用長段說明。
4. 每一句都要有本次實際讀到的出處：現行程式、測試收據、系統規格或官方文件。找不到出處就刪掉，不以合理推測填空。
5. 一件事只寫一次。其他地方需要時引用檔名或節次，不重述。
6. 活頁簿不放說明文字。表頭與欄名說得清楚就不再加一段話解釋這張表怎麼用。
7. 日期只在範本要求時寫，例如修訂紀錄、查詢日期。不提已決定不做的功能。
8. 用完整的句子。有業界通行的術語就用術語，第一次出現時附英文，不另外解釋讀者已經知道的事；程式名稱只在讀者要靠它找到程式時才寫。
   用語與語氣照下面「用語與語氣」一節。
9. 現況照實寫。還沒做到的事寫成現況或「待填」，不寫成已完成，也不靠措辭帶過。會影響公司判斷的差距另外回報使用者。
10. 文件不寫公司名稱、人員姓名、真實案件與私人路徑。測試數字只用合成資料，照「送審的只有 `src/JET`」一節寫的命令執行測試，取那次的結果。

AGENTS.md「寫給人的文字」與 `jet-readable-docs` 的規則同樣適用。

## 用語與語氣

使用者 2026-11-12 指出，文件的用詞仍然不夠專業，而且帶有 AI 的角度（原話在計畫檔，裁定 2026-11-12-36）。
這一節是對照公司的參考文件、業界標準與現行文件逐句盤點後訂的，寫文件前先讀。

語氣：

1. 每一句陳述一件查得到的事實：系統做什麼、設定是什麼、測試結果是多少。不對讀者說話，不解釋文件自己怎麼寫成的。
2. 用書面語，可以用「未」「僅」「須」「於」；不用「茲」「予以」「進行」這類公文腔，也不用「即可」「才不會」「走完」「各算一套」「交給」這類口語和比喻。
3. 限制與還沒做的事，直接寫現況或「待填」。不加緩頰，也不補一句替代措施替自己辯護；真有補償控制，另外用「現行控制」寫一句。
4. 表格的欄名用名詞，儲存格用短句或名詞片語，同一張表的句式一致。不用「部分」「工作」「做法」「前提」「不涵蓋」這類口語欄名。
5. 一件事只在一份文件的一個地方寫，其他地方引用節次，寫成「見第 5.1 節」。設計原則寫規則，技術文件寫現況，兩份不互相重複。
6. 給數字、欄位、檔名與具體規則，不寫「確保良好的體驗」這種通則。公司的參考文件裡，值得學的是有數字與規則的段落；它也有只寫一句通則的段落，那些不學。
7. `humanizer` 的規則照用：不寫「不是…而是…」的對比句、不加節尾的收束句、不湊三項排比、不用破折號、不在每個項目前加粗體標籤。

用語，同一個概念全文只用一個說法：

| 概念 | 文件裡的說法 | 不用的說法 |
|:---|:---|:---|
| review | 複核；程式碼複核（code review）；複核人員 | 審查、審核、檢視。公司的 SAT 表單全篇用「複核」 |
| repository | 程式碼儲存庫（repository），之後寫儲存庫 | 代碼庫 |
| commit 的識別 | 提交識別碼（commit ID） | 提交編號；「程式版本」只指 1.0.0.0 這種版本號 |
| release | 發行、首次發行、發行檔、發行資料夾 | 發布、交付、發布包。Git 的第一筆提交另稱「首次提交」 |
| vulnerability | 弱點 | 漏洞 |
| hard-coded content | 固定值與規則，第一次出現附（hard-coded content） | 寫死 |
| 相依的東西 | 總稱第三方元件；NuGet 的稱套件；清單稱元件清冊 | 相依元件、相依套件混用 |
| 畫面那一側 | 前端；講使用者看到的東西時用使用者介面；隨程式發行的頁面稱本機頁面 | 畫面程式、操作畫面、內建網址、隨程式提供的網頁 |
| C# 那一側 | 後端 | 主程式、C# |
| 測試 | 總稱自動化測試，分後端測試與前端測試；迴歸測試；合成測試資料；預期結果 | 自動測試、回歸測試、預期答案、重跑、複測 |
| coverage | 程式碼涵蓋率；行涵蓋率（line coverage）；已涵蓋行數、可執行行數 | 已執行行數、可量測行數 |
| 版本 | 舊版 JET（IDEA 版），之後寫舊版 JET | 舊版 IDEA JET |
| 人員 | 使用端寫審計員；開發端寫開發人員 | 作者、操作人員、使用者混用 |
| 規則 | 審計規則 | 審計邏輯、審計判斷、業務規則混用 |
| 驗證 | 只指資料驗證；登入身分寫身分驗證；還沒試過的情境寫尚未測試 | 用「驗證」指三件不同的事 |
| 分層 | 展示層、應用層、領域層、基礎設施層，後面附模組名稱 | 操作畫面、操作處理這類自取的層名 |
| 安全做法 | 參數化查詢；允許清單（allowlist）；容許誤差 | 「限制在程式允許的清單」「容許差」 |
| 發行方式 | 獨立式單一檔案（self-contained single-file） | 自含式單一執行檔 |

畫面、報告、底稿與功能的名稱照 `docs/glossary.md`，例如審計員、進階條件篩選、工作底稿、資料可靠性測試、GL 與 TB；
總帳與試算表第一次出現寫「總帳（GL）」「試算表（TB）」。這張表只管一般的技術與文件用語，不新增產品名詞。

## 人工複核的範圍

使用者 2026-11-12 說明：先由自動化的單元測試把關，只有剩下較為核心的程式才交給人複核。這和公司規則第 1 節一致：
單元測試結果是大部分程式的主要驗收依據，人工複核補足固定值、業務規則與測試不足以確認的行為。文件照下面的寫法：

- 全部原始碼以自動化測試驗收，結果記在 Unit test Report。
- 人工複核的範圍是核心審計規則，以及程式內的固定值與規則，各列在 Code review.xlsx 的一張工作表。不寫「複核範圍為全部原始碼」。
- 範圍怎麼定只寫一句依據：依風險決定，會直接影響查核結果的規則由人複核。不引用外部標準替這個做法背書。
- 文件不寫測試由誰或由什麼工具撰寫，照「從開發者的角度寫」第 3 點。業界指引對 AI 產生的測試有揭露的建議，
  要不要在文件揭露由使用者決定；使用者沒有指示前不寫，也不寫成由開發人員手寫。

## 審查門檻以公司規則為準

`Code review rule` 是公司提供的規則，照原文收錄，不翻譯、不改寫、不補充。使用者 2026-11-10 指示：審查規則與限制不需要高於這份規則。

- 不自行訂定涵蓋率百分比門檻。規則只要求確認改動的行為與重要分支有被測試執行到。
- 結論只用規則的三種：通過、需修正、例外核准。
- 不新增規則沒有要求的佐證、表單或流程。

`Code review.xlsx` 照規則第 6 節的內容編排，共三張工作表：

| 工作表 | 內容 | 對應規則 |
|:---|:---|:---|
| 複核紀錄 | 變更說明、需求依據、提交識別碼、檢查項目、發現事項、結論、複核人員、日期、核准的提交識別碼、後續事項與例外 | 第 6 節；檢查項目取自第 2 到第 4 節 |
| 複核範圍 | 六項核心審計規則的程式位置與對應的單元測試 | 第 6 節的 affected procedures or functions |
| 固定值與規則 | 程式內會影響審計結果的固定值與規則，各附項目、內容、程式位置與來源 | 第 3 節 |

固定值清單每一格都要短。「來源」欄只填四種：舊版 JET、查核需求、會計慣例、程式設計。使用者 2026-11-10 指出，
在這一欄寫成句子、引用章節或加上「未載明」這類但書，一眼就看得出是 AI 寫的。Agent 用裁定與系統規格判斷每一項屬於哪一種，但不把出處寫進去。
要增減審查範圍或固定值清單的項目時，先問使用者。

## 製作與交接

1. 先改 `tools/harness/sat-documents/source/` 的來源或腳本裡的設定，再照 `tools/harness/sat-documents/README.md` 的順序重新產生，不直接改 Word 或 Excel 成品。
2. 圖表與固定值清單由腳本對照現行程式產生。腳本找不到對應的程式時會停止；這時去改來源設定，不繞過檢查。
3. 重新產生後，把 Word 與 Excel 轉成 PDF 逐頁看過，確認沒有截斷或重疊。Word 與 Excel 都在背景開啟，不在使用者的桌面操作。
4. 執行 `pwsh -NoProfile -File tools/verify.ps1 -Command Documentation`。
5. 在計畫檔記下：使用者這次的原話、改了哪些來源、測試數字取自哪一天執行的哪個命令，以及沒有做的檢查；不寫收據編號。差距清單也更新在計畫檔。

交付前逐項確認：

- `docs/SAT/` 的資料夾與檔名和上面的對照表一致，沒有多出來的文件、腳本或來源。
- 「用語與語氣」表裡「不用的說法」在文件裡搜尋不到；同一個概念沒有兩種說法。
- 技術文件仍是範本的 19 節，沒有空白的章節；不適用與待填都有寫明。
- 文件裡搜尋不到「裁定」「rulings」「agent」「交接」「送審」「公司接手」，也沒有公司名稱、人員姓名、私人路徑、收據編號與開發時的提交識別碼。
- 文件裡搜尋不到 `docs/`、`tools/`、`src/JET`、`verify`、`global.json`、「系統規格」與「名詞表」。
- Word 與 Excel 成品的文件屬性裡，作者與上次儲存者是 JET 或空白；內嵌的佈景主題名稱是 Office。成品的內部檔案搜尋不到這台電腦的使用者名稱、
  Office 使用者名稱、本機路徑與 AI 產品的名稱。產生腳本會自己檢查這幾項，交付前仍要解開成品再確認一次（2026-11-12 的複核查到這兩種外洩）。
- `docs/SAT/` 底下沒有 Word 或 Excel 開啟檔案時留下的 `~$` 暫存檔。
- 複核人員要填的欄位是空的。
- 每個數字都對得上來源檔。
- 回覆使用者時，列出仍待公司或使用者處理的差距，不只說文件已更新。
