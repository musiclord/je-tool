# JET 驗證框架

更新日期：2026-11-24

這份文件寫給維護驗證框架，以及在框架下開發與驗證的 Agent 和開發者。它只說明框架要負責什麼、判定
依據是什麼，以及哪些工作必須分開進行。命令、參數、各路線的操作細節與結束碼見
[`tools/README.md`](../../tools/README.md)。

## 要解決的三個循環

1. **開發循環**：快速確認程式可以編譯，並執行這次改動真正影響到的測試。
2. **測試循環**：用合成資料檢查產品規則、不同資料庫是否得到相同答案，以及輸出檔案是否正確。
3. **驗證循環**：在所需軟體、資料和授權都齊備時，再檢查 GUI、原生 Excel、私人 JE 與 TB 案件及正確底稿。
   GUI 一律用拿掉系統管理員權限的身分啟動 JET，也包含單一執行檔關閉後重新開啟同一個案件（裁定 2026-11-09-01）。

驗證框架只是用來檢查產品，不是產品本身的一部分。沒有這套框架時，`src/JET/` 仍應能正常建置、發布及執行。
框架提供合成資料、GUI 與 Excel 驅動程式、失敗紀錄和唯讀的 `Context` 導覽等可重現的回饋，設計判斷由
Agent 負責，不用持續累加限制來代替判斷。審計員的判斷不能被測試框架擅自改成操作限制；新增限制必須有
使用者裁定或可追溯的業務來源，不能只引用既有程式或測試。工作順序與本輪交付範圍的區分見
[`development-workflow.md`](development-workflow.md)；通過一項檢查不代表整輪工作完成。

## 基本原則

- 對外只提供 `tools/verify.ps1` 這一個入口。它負責檢查參數、啟動子程序、管理共享資源及寫下執行結果。
- 執行器本身保持精簡。有哪些驗證路線、每條路線需要什麼能力，放在可直接檢查的設定檔中。
- 每次執行都有獨立編號和專屬資料夾。不同執行不得共用暫存結果，也不得拿舊專案的輸出冒充新證據。
- 第一次失敗必須保留。診斷重跑或修正後重跑可以新增紀錄，但不能覆蓋原始失敗。
- 只有會共用測試、GUI 或 Excel 資源的工作才需要互斥鎖，Restore 和 Build 不應被無故鎖住。
- 缺少必要能力、必要測試被略過、輸出缺件或清理失敗，都不能算通過。
- 只管理本次執行明確啟動的程序與建立的資料夾；不得按程序名稱大量終止，也不得清除來源不明的路徑。
- 普通 `dotnet build` 或局部測試只能證明它實際涵蓋的範圍，不能代替完整驗收。
- 子程序輸出寫入紀錄前，先將儲存庫根目錄、使用者目錄及本次明示的敏感值換成固定標記。需要連線資訊的
  測試也要先清理 TRX 等文字證據；遇到無法安全處理的附件就停止。
- 遇到逾時要保留原紀錄並先單獨重現，不直接放寬時間、動作或診斷容量限制。
- `Gui` 在另一個 Windows 桌面執行，不搶使用者前景、滑鼠或鍵盤；依 `AGENTS.md` 在提交、交付或確認整合時才跑；
  computer use 會操作實體桌面，只在使用者當次要求時使用。兩者的能力與證據分開回報。
- 壓力測試、變異測試或涵蓋率只有在能回答獨立問題時才加入。各類證據各自保留，不用其中一項代替其他項。
- `Documentation` 只檢查文件缺檔、必要指向與已確認過時的事實，驗證框架不宣稱能保證模型行為。寫作規範見
  [`docs/README.md`](../../docs/README.md)，各 Agent 工具的轉接方式見 [`agent-compatibility.md`](agent-compatibility.md)。

## 選擇足夠的驗證

先用受影響的 `Focused` 或特定 `Contract` 情境回答本次問題。前端互動用 `FrontendMapping`，
固定預覽工具用 `FrontendPreview`，受管文件用 `Documentation`。`Public` 是完整公開回歸，包含前端檢查，
適合跨層修改與整合；不因 Stop 提醒就對每個小改重跑全部測試。

改到 JET 的啟動、案件或 WebView2 資料的存放位置、發布設定或原生元件時，先單跑
`Gui -GuiScenario single-file-relaunch`，確認沒有系統管理員權限的單一執行檔仍能建案、匯入與重開；
單跑只算診斷，正式結果仍以完整 `Gui` 為準。

失敗先讀該次收據與第一個失敗，再修正並重跑受影響的部分。已通過且未被後續修改影響的路徑不重跑。
局部通過只能證明局部範圍，不能冒充完整 `Public`、`Gui` 或交付驗收。

目前 `Focused`、`Public` 與 `Package` 的測試類別可平行執行，時間敏感測試另行隔離；合成案件可由共用樣板複製到
各測試自己的暫存目錄。這些做法減少重複建案，但不改變獨立預期答案或每個測試的資料隔離。
實作與操作細節見 `tools/README.md`、`tools/harness/lanes.json` 與 `src/JET/tests/JET.Tests/Application/CaseTemplates.cs`。

## 執行狀態

收據的 JSON 使用下列固定值，中文說明才是使用時應理解的意思。

| 固定值 | 意義 |
|:---|:---|
| `passed` | 所有必要步驟均實際完成，證據及清理也完整 |
| `failed` | 工作已執行，但產品結果、測試或比對結果不正確 |
| `blocked` | 被鎖、逾時、取消或缺少外部能力，因此尚不能判斷產品正誤 |
| `not_run` | 本次沒有選取，或尚未開始 |
| `skipped` | 只適用於事先標明可略過的檢查；不能用來滿足必要條件 |

## 驗證路線

下表的英文是程式內部固定名稱。列為可用只代表命令已經實作；是否通過，仍要看該次執行是否完成所有必要步驟。

| 固定名稱 | 用途 |
|:---|:---|
| `Foundation` | 不是命令名稱，而是 `Context`、`Restore`、`Build`、`Contract`、`Documentation` 五個命令共用的路線：檢查執行器、文件用語、鎖、子程序、輸出限制、執行紀錄及安全清理 |
| `Focused` | 執行指定測試，並帶上必要的架構與介面檢查 |
| `Public` | 執行安全、合成且不需要外部環境的產品測試 |
| `Package` | 檢查產品內建範本、正式報告及封裝內容 |
| `Gui` | 在本次另建的 Windows 桌面，以拿掉系統管理員權限的身分操作真實 WinForms 與 WebView2，不切換使用者桌面；執行時機見 `AGENTS.md`「測試」 |
| `Excel` | 用原生 Excel 開啟與重算合成產物，並確認程序能完整關閉 |
| `ReleaseCandidate` | 檢查可公開交付的候選快照 |
| `Mutation` | 在固定小範圍刻意改壞程式，確認公開測試是否抓得到；需要時才執行，不含壓力測試 |

每條路線都只用合成資料，不讀取私人案件資料夾。原本把真實案件走完正式流程、再和舊版底稿比較的 `PrivateCase` 路線，
2026-11-24 依使用者的決定刪除（裁定 2026-11-24-05）。

`Focused` 與 `Public` 不得用共同前綴整批隱藏一系列測試，也不能因名稱相近就整組略過。

短期上線版本只支援 SQLite（裁定 2026-11-06-08）。原本比較三種資料庫共同業務結果的 `Provider` 路線，
隨 DuckDB 與 SQL Server 暫時刪除，還原點是提交 `7e88b7b`。

## 資料與判定依據

### 合成資料測試

每項規則放在足以證明行為的最低層級測試，跨層測試只確認各層連接正確。預期答案要來自現行規格、手算
小案例、獨立算法或已核准的標準檔案，不能由被測程式重新計算。同一規則支援多種資料庫時，比較相同輸入
得到的資料集合、排序、金額及失效狀態。

### `data/` 與產品內建範本

`data/` 的十份工作簿是使用者裁定保留的業務範例，不得為了測試方便而重存或去識別化；
`src/JET/JET/Templates/` 是隨程式發布的範本，細節見 [`data-and-legacy.md`](../../docs/data-and-legacy.md)。
兩處的 `WorkingPaper.xlsx` 都不是任何案件的正確答案，只能用來檢查範本與封裝。

### Legacy 業務來源

[`legacy/idea-tool.bas`](../../legacy/idea-tool.bas) 用來查 IDEA 正式工具的特定規則，
[`legacy/idea-script.bas`](../../legacy/idea-script.bas) 用來追查較完整的舊流程與邊界。兩份程式不直接執行，
也不整段翻譯成 .NET；每項要驗證的舊規則，都要先指出來源區段、現行程式位置，以及能獨立算出預期答案的
測試案例。Legacy 與現行規格或使用者新裁定衝突時，依
[`business-logic-provenance.md`](../../docs/business-logic-provenance.md) 的權威順序處理，驗證框架不替產品做決策。

### 私人資料

- 私人案件放在受 `.gitignore` 排除的 `data/test-case/` 等本機資料夾，可以在這台電腦讀取，用來核對業務邏輯。
  驗證框架與測試不列舉、猜測或解析這些資料夾，已追蹤的檔案也不保存客戶檔名、欄位配對或內容。
- 對真實案件的觀察只寫在本機的 `local/`，例如某個案件驗得到哪些規則、哪些差異還沒有裁定（裁定 2026-11-16-06）。
- 長期保存的紀錄不得寫下私人路徑、公司、工作表、欄位、儲存格、科目、傳票、人員或金額。
- 和舊版比對時已裁定的業務規則，例如「未預期借貸組合」改計整張傳票、非營業日的週末納入補班日，記在
  [`rulings.md`](../../docs/rulings.md)，由合成資料的測試守住。

## 每次執行要留下什麼

每次正式執行的收據至少記錄：格式版本、執行編號、入口版本、目前的 Git 分支與提交、選取的驗證路線、
組態、開始與結束時間、各步驟結果、必要能力、測試與輸出數量、第一次失敗、產物相對位置及清理結果。
第一次失敗的證據寫在 `firstRed`，讓讀的人不必再翻 TRX。測試步驟失敗時，它會寫出失敗數、依名稱
排序的第一個失敗測試，以及壓成一行、最多 240 字的訊息。`Focused`
與 `Public` 另在 `testBoundary.assertionDrift` 記錄工作樹相對 HEAD 在測試中移除的斷言與測試數、新增的
`Skip =` 數。這只是提醒，數字大於 0 時要說明原因，不會讓命令失敗。

`privateData.pathInspected` 記錄這次是否真的查看過私人案件資料夾，每條路線都必須是 `false`。執行紀錄只描述這一次真正做過的事。舊專案的結果、別次執行的產物或人工推測，都不能補成通過。

舊執行不代表永久保存完整產物。框架目前按檢查種類完整保留最新 10 次，較早執行保留收據摘要；
變異測試另有保留期限，見 `tools/README.md`。因此引用證據時確認檔案仍存在，不以已清理的附件作為可回查的來源。
