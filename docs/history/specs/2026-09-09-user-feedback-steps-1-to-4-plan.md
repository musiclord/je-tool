先前 Agent 容易漏掉的原因：身分、配對草稿與訊息規則分散在前後端，沒有跨層不變條件；前端測試只檢查文字存在，
沒有走「先設定、取消配對、再提交」的狀態轉換；錯誤沒有送回使用者正在操作的配對區；介面用「來源品質」「Part B」這類泛稱；
建案測試跟著表單傳入假操作人員，GUI 驗證也照舊表單逐欄填滿。

驗收標準：建立案件時只有案件名稱、查核期間與資料儲存方式必填；`project.create` 不能指定另一個操作人員；
匯入說明能回答「右側為何仍能預覽」；人工或自動欄位取消配對後不再顯示舊代碼；空白、未歸類及只顯示部分值造成的失敗在 GL 配對區
直接指出來源列與修正方式；攸關資料元素可全選與全部取消；畫面不再出現 `Part A` 或 `Part B`。未經裁定，不刪除 `voucherDate`、
不把科目名稱改成選填、不把兩份 TB 當成普通追加，也不把 `.xls`、`.xlsb` 或 Access 冒充為已支援格式。

## 新格式與兩份 TB 的研究結果

- Microsoft 的 [Office 檔案格式參考](https://learn.microsoft.com/office/compatibility/office-file-format-reference)
  說明 `.xlsm` 與 `.xlsx` 都是 XML 格式，差別是 `.xlsm` 可以保存巨集；`.xlsb` 與 `.xls` 是不同的二進位格式。
- [Open XML SDK 唯讀開啟範例](https://learn.microsoft.com/office/open-xml/spreadsheet/how-to-open-a-spreadsheet-document-for-read-only-access)
  與 JET 現有讀取器的唯讀方式相同，因此 `.xlsm` 可以沿用同一讀取器，巨集不會執行；本輪已實作。
- `.xlsb` 與 `.xls` 需要新的串流解析器，不能以改副檔名或呼叫 Excel 另存檔代替。
- [Access 與 WinForms 連線說明](https://learn.microsoft.com/visualstudio/data-tools/connect-to-data-in-an-access-database-windows-forms)
  指出 `.mdb` 與 `.accdb` 依賴 OLE DB 及相符位元的 Access Database Engine。JET 固定發行為 `win-x64`，公司雖有
  Office 365 和 Access，仍不能假設每台代表設備都已有可由 JET 使用的 64 位元 ACE。

期初與期末 TB 分檔可做，但現有追加模式不是答案。開始實作前仍要裁定：同一份快照的重複科目要拒絕或加總；只在
一側出現的科目是否以零補齊並列為提醒；兩側科目名稱不同時採哪一個；借貸分欄的正負方向如何驗證。這些答案會
改變完整性測試，不由 Agent 自行選邊。

## 第一輪修正（2026-09-09）

- 案件編號及客戶名稱改成選填，空白時案件清單和工作區改用案件名稱。建立案件的操作人員欄已移除，
  `ProjectCreateHandler` 直接保存目前 Windows 短帳號。
- 匯入說明使用較寬的段落，直接說明右側只有少量預覽，完整資料寫入案件資料庫。本輪另加入 `.xlsm`。
- `postDate` 的使用者名稱統一為「過帳日期」，並明說選填的傳票日期只供回溯過帳判斷；action 欄位、資料庫欄位與
  Working Paper 正準欄名沒有改動。
- 人工或自動欄位取消或換欄時重設上一欄的代碼政策；值摘要明說空白不在清單中，截斷時也明說仍有其他值；
  投影失敗改用中文指出來源、列號、欄位、值和處理方式，並在 GL 配對區就地顯示。
- 攸關資料元素增加全選及全部取消；核心配對使用某個來源欄時，立即移除同欄的 RDE 草稿。
- 第四步採用具體說明，`INF 抽樣測試` 的畫面名稱改成「資料可靠性測試」。完整性訊息不再顯示 Part A 或 Part B，
  「來源品質」改成實際內容「過帳日空白」。使用者提供的「GL 發生數」改為「GL 發生額」，因程式實際比較的是
  金額加總，不是分錄筆數。

人工或自動的補集模式尚未實作。legacy 只接受 `0` 或 `1`；現行版允許多個代碼，但要求每個非空白值明確歸類。
若改成「列出人工，其餘算自動」或相反，拼錯及新出現的非空白代碼也會自動落入另一類。
這是資料品質取捨，需由使用者決定是否接受；空白值仍建議維持失敗，不靜默歸類。

架構複審結論：案件名稱仍是 `projectId` 及案件資料夾的必要識別，舊 `project.json` 欄位形狀沒有改動；舊呼叫即使傳入
`operatorId` 也不能改變保存結果；`.xlsm` 沿用既有讀取器邊界；靜態前端守衛不能代替行為驗收，因此最小建案、操作人員保存、
人工或自動來源欄重設及畫面截圖納入正式 GUI 路線。

驗證結果：11 項新增測試先如預期失敗，修正後通過。完整 Public 第一次有 5 項失敗，都是舊測試仍期待英文列號或把建立請求的
操作人員當成署名，調整測試身分後通過。GUI 第一次在建立案件時逾時，原因是驅動器仍等待已移除的操作人員欄；修正驅動器後，
案例改成只填案件名稱和兩個查核日期。匯入說明從 68ch 再放寬至 84ch，合成截圖由三行收斂為兩行。
最終 Public 3,466 項通過、0 失敗、0 跳過；Gui 八個情境通過；Debug Build、Contract、Documentation（35 份文件）
與驗證框架自身測試（444 項斷言）都通過。沒有讀取私人資料、啟動 SQL Server、執行 Excel，也沒有暫存、提交或推送。

第一輪續接點：人工或自動的補集模式、兩份 TB 的四個資料問題，以及其他格式仍待裁定。

### 已確認的失敗範圍

- 失敗的是 `import.gl.fromFile`，記錄耗時 5,090 ms，錯誤碼 `file_read_error`，堆疊包含 `LocalImportRepository.ReplaceBatchAsync`。
  SQLite 與 DuckDB 都用這個類別，日誌不足以分辨是哪一種；不能推定是 SQL Server 問題。
- 標頭預讀與檔案檢視已成功，因此應優先盤查串流開始時重新開檔，以及後續讀列、解析與轉換。檢視成功不保證後段資料可解析。
- `file_read_error` 不是對所有資料庫例外的統一改名，不能僅因堆疊停在該類別就判定資料庫損壞。沒有 `import.milestone` 完成事件，
  也不能據此認定完全沒有讀到資料列。

來源：[`ImportFromFileHandler.cs`](../../../src/JET/JET/Application/Handlers/Import/ImportFromFileHandler.cs)、
[`LocalImportRepository.cs`](../../../src/JET/JET/Infrastructure/Persistence/Local/LocalImportRepository.cs)、
[`AppCompositionRoot.cs`](../../../src/JET/JET/AppCompositionRoot.cs)、
[`OpenXmlSaxTableReader.cs`](../../../src/JET/JET/Infrastructure/FileIO/OpenXmlSaxTableReader.cs) 與
[`CsvTableReader.cs`](../../../src/JET/JET/Infrastructure/FileIO/CsvTableReader.cs)。

### 已確認的診斷缺口

| 缺口 | 下次修正方向 |
|:---|:---|
| 原始例外遺失：[`JetActionException`](../../../src/JET/JET/Domain/JetActionException.cs) 只有訊息建構式，沒有保留 `InnerException` | 加入相容的原始例外保存方式，既有 `Code`、`Field`、`Details` 不因包裝遺失。 |
| 重新拋出時重設堆疊：`throw AddBatchSourceContext(...)` | 不需要補來源資訊時直接用 `throw;`；需要包裝時保存原始例外。 |
| 讀檔錯誤的分類過寬：`WithSourceContext` 把非取消的例外統一轉成 `file_read_error` | 分開識別來源讀取與進度通知的失敗。 |
| 支援日誌無法區分失敗原因：[`SupportRingBufferLoggerProvider`](../../../src/JET/JET/Infrastructure/Diagnostics/SupportRingBufferLoggerProvider.cs) 刻意不保存原始訊息 | 維持去識別，增加固定分類的失敗階段、讀取器、資料庫類型、來源序號及安全的例外原因，不記檔名、工作表名稱、欄名或資料值。 |

Microsoft 的 [CA2200 說明](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca2200)與
[`InnerException` 文件](https://learn.microsoft.com/dotnet/api/system.exception.innerexception?view=net-10.0)支持上述判讀。
這些是已確認的診斷缺陷，不等於已找到本次 PBC 失敗的唯一原因。

### 尚待確認的原因

日誌沒有副檔名、來源數量、原始錯誤訊息或失敗位置，不能把候選原因寫成案件結論，也不能先要求重建案件。候選有三類：
來源重新開啟或讀取失敗；Open XML 後段結構或儲存格轉換失敗，其中時間樣式分支直接呼叫 `TimeSpan.FromDays`，超界值是可設計合成重現的候選
（見 [`TimeSpan.FromDays(Double)` 文件](https://learn.microsoft.com/dotnet/api/system.timespan.fromdays?view=net-10.0)）；
CSV 或 TXT 後段解碼或解析失敗。證實後的處理都不能默默跳過失敗列，也不能用清空或刪列掩蓋。本次未製作合成檔重現。

目前可先取得的證據是第二步顯示的完整錯誤文字，以及同一個 Debug 程序的「DEV — 診斷日誌匯出」。DEV 日誌可能含案件資料，
只在本機檢查，不貼到聊天或放進文件。操作與界線見[`畫面說明`](../../jet-frontend-description.md#診斷日誌)及
[`action 契約`](../../action-contract-manifest.md)。
