## 為什麼舊版底稿帶不進來

- 按鈕只讀新版 JET 另外寫在檔案裡的隱藏配對紀錄，有兩種：
  - 六份正式報表共用的隱藏工作表 `JET_Metadata`。
  - 「自動化工具-檔案欄位資訊」隱藏的 F1 到 H1 三格。
- 舊版 IDEA JET 兩種都沒有寫，所以一定走到那句錯誤（`src/JET/JET/Infrastructure/FileIO/OpenXmlMappingMetadataReader.cs`）。
- 舊版確實寫了看得見的「配對前欄位名稱」到「配對後欄位名稱」對照表，工作表名稱與五欄標題都和新版相同；JET 只是從來不讀這張表。
- 「不從看得見的欄位推測配對」最早寫在 2026-08-30 的 action 契約，是當時 Agent 定的做法，裁定總表查不到使用者裁定。2026-11-05 恢復這個按鈕時，範圍寫的是「JET 匯出的六種檔案都能用」（裁定 2026-11-05-03），沒有提到舊版底稿。

舊版和新版的對照表有幾處寫法不同，讀的時候都要認得：

| 項目 | 舊版 IDEA JET | 新版 JET |
|:---|:---|:---|
| 配對前欄位名稱 | 直接寫來源欄名 | 寫成「【來源欄名】」 |
| 系統產生的金額欄 | `傳票金額_JE 由系統產生 : …`，來源欄名不加括號，借貸別那一句寫「借方為【代碼】」 | `【傳票金額_JE】由系統產生 : …`，來源欄名加【】，借方代碼寫「借方為「代碼」」；2026-11-10 起只填貸方代碼時寫「貸方為「代碼」」 |
| 核准日同總帳日期 | `系統產生 : 同總帳日期_JE來源` | `【傳票核准日_JE】由系統產生 : 同【總帳日期_JE】來源`；2026-11-03 以前寫 `傳票核准日_JE 由系統產生 : 同總帳日期_JE來源` |
| 過帳狀態 | `來源欄 ：過帳判斷值【值】` | `【來源欄】過帳判斷值「值」` |
| TB 段與 GL 段之間 | 空一列 | 空兩列 |

出處：`legacy/idea-tool.bas` 第 10824 到 10963 行、第 12611 到 12846 行；新版見 `src/JET/JET/Domain/Rules/FieldInfoProjector.cs`。
2026-11-03 以前的新版說明句不加【】，寫法和舊版相同，見提交 `40440b9` 的上一版 `src/JET/JET/Domain/Rules/LegacyFieldDefinitionProjector.cs`。

## 做法

### 讀檔與推得配對（後端）

- 讀檔順序不變：先讀 `JET_Metadata`，沒有時讀 F1 到 H1；這兩種紀錄存在但格式不對時，照舊整份不帶入（裁定 2026-11-05-14）。
  F1 到 H1 三格都空白才算沒有這份紀錄；有任何一格有內容而 F1 不是標記，算紀錄存在但格式不對。
- 兩種紀錄都沒有，但有「自動化工具-檔案欄位資訊」時，讀看得見的 A 到 E 欄：用「TB檔案配對前後欄位對照表」「GL檔案配對前後欄位對照表」兩個標題找出兩段，
  不靠固定列號。舊版與新版的寫法都要認得。
- 推得配對的規則放在 Domain，讀檔只負責把表格讀出來。規則：
  - 「配對後欄位名稱」是標準欄名（例如 `傳票號碼_JE`、`會計科目編號_TB`）的列，「配對前欄位名稱」就是來源欄。配對前是空白表示系統產生，不算配對。
  - 兩欄相同時，新版和舊版的意思不同：
    - 新版來源欄本來就叫標準欄名時，配對前寫成「【欄名】」，算配對；沒有括號的是系統產生，例如自動編號的 `傳票文件項次_JE_S`
      （`src/JET/JET/AuditCore/FieldInfoProjection.cs` 的 `ProjectRow`）。
    - 舊版 A 欄寫欄位說明，沒有說明時寫欄名，改名時說明是原欄名（`legacy/idea-tool.bas` 第 10948 到 10952 行、第 5375 到 5417 行）。
      寫進 E 欄而說明空白的系統產生欄位，在 `legacy/idea-tool.bas` 查不到：第 7661 行的 `Step1_Append_IsManual` 沒有被呼叫。所以舊版兩欄相同都算同名配對。
    - 整張表只要有一格配對前欄位名稱整格加【】，就當成新版。
    - 來源欄名本身有括號時，新版寫成「【【舊】地區】」。整格由一對【】包起來、裡面的括號也成對時，去掉最外層。
      新版改名列的配對前欄位名稱一律是「【來源欄名】」，所以來源欄名的括號不成對時（例如「【舊地區」寫成「【【舊地區】」），也只去掉最外層。
      借貸方判斷欄的欄名本身整格加了【】時（例如「【DC】」），依原樣留著的那一列判斷欄位型態；
      判斷欄同時配給其他欄位、沒有原樣留著的列時，依它改名的那一列。
    - 同名配對的來源欄在目前資料找不到時，照其他配對一樣列出來請審計員重選。
  - 金額、核准日與過帳狀態從說明句讀出來源欄、計算方式與代碼。
  - 舊版金額句不加括號：單一帶號金額的說明句與算式都只寫欄名，借貸兩欄寫「借方欄-貸方欄」（第 12611 到 12634 行）。
    欄名若有「-」，單一金額的算式就成了減法，所以說明句裡的「-」一律當成借方欄與貸方欄的分隔，不當成單一欄。
    先找兩邊都對得上目前欄名的切法；找不到而只有一個「-」時，照那一刀切開，對不上的欄列出來請審計員重選；其他情況列出金額請審計員選。
    冒號後面空白時也列出金額，這時沒有原本的來源欄可寫。
  - 新版說明句的欄名都加【】。欄名本身有「】」時，金額加借貸別與過帳狀態的說明句分隔的寫法固定，照樣讀得出欄名；
    其他新版的寫法對不上時，整句只有一個加括號的欄名就去掉最外層括號再找，其他情形列出金額請審計員選，不套用上面舊版「-」的規則。
    TB 也一樣，新版說明句不套用舊版期末期初的讀法。來源欄名有儲存格裡的換行時，說明句照樣讀得出欄名。
  - 2026-11-03 以前的新版說明句不加【】，照舊版的規則讀。這種檔案若有 F1 到 H1 的紀錄就先讀紀錄，不會走到看得見的表。
    紀錄被刪掉時，欄名有「-」的單一金額欄會被當成借貸兩欄，這是已知限制。
  - 借貸別欄的「欄位型態」是數字型態時算借貸標誌（`flag`），其他算借貸別（`side`）；兩者的計算相同。
  - TB 只有兩欄相減（`A - B`）時，看不出是借減貸還是期末減期初，不帶入金額，列出來請審計員選。
  - TB 段沒有任何配對、也沒有要重選的項目時，不回 TB 草稿，審計員已選的 TB 欄位與金額格式不動。
  - 舊版的說明句沒寫借方代碼時，列出借方代碼請審計員填。貸方代碼不列：舊版只記借方代碼，其他值都算貸方，和現行只填一側代碼的規則結果相同。
  - 新版說明句完整寫出已填代碼。兩側都填時寫「借方為「代碼」，貸方為「代碼」」，推回兩側代碼；只有一側時只寫該側並推回該側代碼（裁定 2026-11-10-03）。
    這次修改前已產生、只寫借方代碼的檔案仍只推回借方代碼，不猜另一側。只填貸方代碼卻寫成配對鍵名稱 `drCrDebitCode` 的舊檔案，照沒寫借方代碼處理。
  - 舊版過帳判斷值填「XXXX」，表示過帳狀態空白的分錄才算有效（`legacy/idea-tool.bas` 第 511 行的畫面說明與第 1637 行），讀成「空白也算已過帳」、沒有其他值。
  - 人工傳票否照舊版，「1」是人工、「0」是自動。
  - 其他以 `_JE` 結尾、不是標準欄名的列，當作攸關資料元素：顯示名稱去掉 `_JE`，值型別依「欄位型態」，識別碼由後端新產生。
    名稱空白或太長、來源欄重複或來源欄已配給標準欄位時不帶入，列出來請審計員選；來源欄重複時保留第一個。
    名稱相同但來源欄不同時照樣帶入；輸出欄名與第五步欄位條件的欄位清單會在名稱後面加上來源欄名區分，其他畫面只寫名稱。
    新版只在名稱和另一個攸關資料元素相同，或名稱加 `_JE` 剛好是標準欄名時，才在名稱後面補「（來源欄名）」。
    讀的時候照同一條規則反推：去掉後綴的名稱有兩列以上相同，或加 `_JE` 是標準欄名，就當成補上的後綴去掉，其他情形照寫的名稱。
    名稱本身就叫「X（來源欄名）」而 X 符合上面兩種情形時，寫出的欄名和補了後綴的一模一樣，推回的名稱是 X。
  - 下面這些是看得見的表推不出來的已知限制，審計員在配對畫面上補選：
    - 補值欄位不寫在表上，推得的草稿沒有補值欄位。

    - 人工傳票否照上面的舊版代碼，不是當初選的代碼。
    - 名稱本身以「（來源欄名）」結尾的攸關資料元素，可能推回去掉後綴的名稱，見上面。
  - 來源欄名先找完全相同的；找不到時，比對只留文字與數字、全形半形視為相同、不分大小寫的寫法，只有唯一一個對得上才算。

  對照表上根本沒有的必要欄位不另外列出，配對畫面照常標成「必填」。

## 同類問題的處理結果

上一個 session 列出的同類問題，本輪已依使用者的決定修改。最終驗證結果會記在本計畫前面的交付狀態。

| 原本的問題 | 本輪處理 |
|:---|:---|
| 案件資料夾複製或改名後可能開到或刪到原件 | 設定檔名稱與資料夾不符時列成錯誤列，刪除只刪該資料夾；原件照常使用。 |
| 情境存檔或報告產生後讀回失敗，被報成整個動作失敗 | 已成功寫入的動作回成功並附既有提醒，請重新開啟案件更新畫面。 |
| 已存 JSON 過深，到送往畫面時才失敗 | 共用解析最多讀取 60 層，超過時沿用無法讀取內容的處理。 |
| 預篩選摘要沒有形狀檢查，驗證摘要形狀不對卻不標過期 | 驗證摘要檢查完整結構；預篩選檢查已提供區塊的必要欄位與型別，保留舊摘要未提供區塊的回放。內容損壞時回 null 並標過期，相關報告索引也過期，原檔不改寫。匯出資訊不足時請重新執行。 |
| 結構損壞的情境讓第五步整頁畫不出來 | 保留名稱、動機、錯誤原因與移除入口，條件組回空陣列，原始定義不改寫。 |
| 結果列的日期讀不出來 | 開案不帶該結果並標過期，請重新執行；新結果保存成功時，在同一交易只清掉日期無效的舊結果列，有效舊結果與正式檔案保留。 |
| 情境列的日期、位置與編號讀不出來 | 回既有資料庫損壞訊息，請從備份還原或重新建案，不補造值、不跳過損壞列。 |
| moneyScale 缺少或不是正數 | 案件清單列設定檔無法讀取的錯誤列，不補預設值。 |
| 匯入批次的時間、筆數或欄位清單讀不出來，結果狀態列缺失 | 回既有資料庫損壞訊息。 |
| 原始 GL JSON 讀不出來，底稿第 4-1 步的值轉型失敗卻被報成範本問題 | 正式報告、INF 與底稿共用原始資料檢查，回既有資料庫損壞訊息，不再要求重新下載範本。 |
| 查詢與匯出解析已存情境的例外漏接，命中的組號條號沒有核對範圍 | 沿用既有條件無法讀取或結果過期訊息，要求重新檢查情境。 |
| 貼上含不成對代理字元的文字，原本只有推測 | 已用篩選情境名稱、動機與條件值的合成請求重現並修正，回既有條件內容無法讀取訊息。 |

前一輪判定不算問題的三項維持原行為：目前確認的配對讀不出來、科目分類的序號與版本超出整數範圍，以及 GL 控制總數被存成文字。
目前確認的配對沒有「讀不出來就當作沒有」的設計，仍需從備份還原或重新建案。這三項沒有新增恢復規則。
