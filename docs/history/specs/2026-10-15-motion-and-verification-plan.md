這份計畫處理使用者 2026-10-15 提出的三件事：依 Apple 現行的 Liquid Glass 設計重新校準 JE Tool 的動態，
整理過重的測試與驗證循環，以及讓 Gui 檢查不再干擾使用者使用電腦。三件事都以同一條審計員使用情境為準，
所以放在同一份計畫。開發現況「下一階段」裡的 Gui 視窗不搶前景、驗證框架瘦身、Gui 縮減與前後端契合度測試，
同日併入本計畫。

## 審計員的使用情境

審計員用六步完成一個案件的分錄測試：設定查核範圍、匯入來源、確認欄位、檢查 GL 及分類、選取待查核分錄，
最後產生底稿。本計畫從這條線看兩件事。

- 操作的回應：審計員在第四步勾選科目、套用分類，在第五步反覆加入與移除條件、切換「篩選與檢視」和
  「已儲存情境與矩陣」、展開常用查核條件。每次操作在下一個畫格就要看到回應。動態交代東西從哪裡來、
  到哪裡去，結束時不拖尾，也不讓審計員等動畫跑完才能做下一步。
- 檢查的涵蓋：審計員實際會回頭修改前面的資料、取消、失敗後重試、重開案件、存多個情境。檢查要用正式前端、
  正式後端與資料庫走過這些情境，審計結果要和獨立算出的固定答案一致，SQLite 與 DuckDB 的結果一致。
  檢查執行時不出現在使用者的螢幕上，也不搶滑鼠。

本計畫不新增會擋住審計員的錯誤。檢查過程發現的產品問題先列出，由使用者決定要不要修。

## 範圍

要做：

1. 動態：依研究結論定出全站一致的動態性格，套用到 `app.js` 的 `SPRINGS` 與 `app.css` 的動態變數，
   同步文件、設計 skill 與測試。
2. 前後端契合：前端測試讀的後端回應改由正式後端產生；前端組出的 action 資料送進正式後端核對。
3. Gui 改到另一個 Windows 桌面：全部情境照舊用 WebView2 視窗執行，但開在使用者看不到的桌面。
   另外補上匯出後回頭修改上游資料的完整旅程。
4. 審計邏輯與資料庫邏輯：每條審計規則都有獨立的固定答案，兩種資料庫結果一致。原本也要替只在 SQLite 跑的
   action 處理程式測試補上 DuckDB，盤點後使用者 2026-10-15 勾選 V1，改為不全面補。
5. 驗證框架與 Gui 的縮減：列出非必要的過程，替代的檢查到位後逐項確認再刪。

不做：

- 不改分層、材質、色系與版面；2026-10-11、12 裁定的外觀維持。
- 不改審計判斷、資料庫行為與畫面流程。檢查發現的產品問題列進開發現況，由使用者決定。
- 不執行 SQL Server、`Provider` 與 `PrivateCase`。
- 下一階段的其餘事項繼續延後，例如上游修改後清除下游狀態的重大事件盤點、預篩選收斂與架構圖。

## 研究結論：動態

2026-10-15 Claude 直接讀了 Apple 的原文。包括人機介面指引（Human Interface Guidelines，下稱 HIG）的 Design principles、
Materials、Motion、Color、Buttons、Toolbars、Segmented controls、Scroll views、Accessibility、Windows 與 Designing for macOS，
Liquid Glass 的技術文件與 `Spring` 文件，
WWDC 2025 的 Meet Liquid Glass、Get to know the new design system 與三個框架的採用說明，WWDC 2026 的
Principles of great design 與 Modernize your AppKit app，以及 WWDC 2023 的 Animate with springs。

- 分層、材質與色系和 Apple 的做法一致：頂端一條玻璃、選單與對話框是玻璃、選取只在移動時浮起成玻璃、
  內容層不透明、只有主要動作上色、同心圓角。
- 最大的落差在動態的性格。Apple 描述 Liquid Glass 在互動時立刻彎曲、帶著像凝膠的彈性；Mac 上用觸控板操作時反應較收斂；
  macOS 27 給控制項加了被點擊時的輕微回彈，原文提醒「A little goes a long way」。
- 開啟「減少動態效果」時，系統會關掉玻璃的彈性；HIG 對這個設定的做法第一條是收緊彈簧、減少回彈。
  JE Tool 從 2026-10-12 起，除了按鍵放開，其餘動態都不回彈，等於停在減少動態效果的狀態。這是 Claude 當時自己的選擇，
  不是使用者的裁定。
- Apple 的彈簧用時間與回彈兩個參數描述。回彈 0 是預設，平順但尾巴長。回彈約 0.15 時 Apple 說還不太像在彈，
  但收尾比較俐落；約 0.3 開始明顯，0.4 以上對介面太誇張。
- Claude 計算：時間相同時，不回彈要到 0.755 倍時間才走完 95%；回彈 0.15 約 0.59 倍就到，最多只超過目標約 0.6%。
  移動 100 像素時約 0.6 像素，看不出回彈。
- 實測：在第五步換頁籤、展開常用查核條件、加入與移除條件，從按下到第一個畫格都在 56 到 64 毫秒，
  動態在 475 到 590 毫秒後全部結束。慢的主因不是畫面重繪，而是動態的長度與不回彈的長尾巴。
- 2026-10-13 使用者不喜歡的是拋物線軌跡，不是回彈。帶到右側的標籤維持直線移動。

使用者裁定直接套用的動態系統：

- 玻璃層的互動，包括分段選取滑動、按鍵放開、選單與對話框浮現、加入條件時帶過去的標籤：
  用接近 Apple `snappy` 的少量回彈，回彈約 0.15。
- 內容層的版面改變，包括長出來、收起、窗格換掉與高度改變：維持不回彈，時間維持 2026-10-15 縮短後的長度。
- 一併處理三個次要落差。加入條件是第五步最頻繁的操作，HIG 建議頻繁的互動不另加動態，要確認這個操作同時有幾種效果。
  選單只有淡入和放大，Apple 的玻璃則是逐步出現折射與模糊。視窗失去焦點時，玻璃沒有退淡。
  提出建議時 Claude 說選單與對話框都用淡入；實作時查到對話框已經是從稍小、稍霧變清楚，只有選單不一致。

## 做法

### 動態

玻璃層與內容層各用一組彈簧參數，同類元件全站用同一組，`SPRINGS`、`--ease-*` 與 `--motion-*` 一起改；處理三個次要落差；
同步前端說明、設計 skill 與 `DesignIntegrationFrontendTests`；使用者試用後依回饋微調。

### 前後端契合

這是 2026-10-14 記下的重啟後第一個動作。用正式的 runtime 處理合成案件，SQLite 與 DuckDB 各一次，記下每個 action 收到的資料與回應的形狀，
存成受版控的契約檔；前端測試的假後端在回應前核對每個欄位都在契約檔裡、型別相同，前端送出的資料也要是後端收過的欄位與型別。
刻意模擬失敗或極端狀態的假回應明確標出不核對並註明原因。這些紀錄只代表資料形狀，審計結果仍由獨立算答案的測試判定。

2026-10-15 細化做法時，Claude 把「前端測試改讀這些回應」改成「前端測試的回應都要符合真的回應」。原因是 301 處假回應各自配合測試要的狀態，
全部換成同一個案件的回應會改掉每個測試原本要檢查的情況；核對形狀一樣能抓到前後端各說各話，既有斷言也不用動。

### Gui 改到另一個桌面

先由 Gui 驅動程式另建一個 Windows 桌面，只跑 `startup-smoke` 試驗，確認頁面載入、操作與截圖正常後再改全部 19 個情境，
有情境失敗就記下原因，不放寬斷言。另補上匯出後回頭修改上游資料的完整旅程，核對每一步被清除與保留的狀態。
使用者 2026-10-15 勾選 V2：只更新事實並拿掉事前告知，執行時機不變；`AGENTS.md`、`tools/README.md` 與
`.agents/harness/frontend-design-mode.md` 已照改。

### 審計邏輯與資料庫邏輯

列出每條驗證、預篩選與篩選規則對應的獨立答案測試及是否在兩種資料庫執行。使用者勾選 V1 後，不全面替只在 SQLite 跑的處理程式測試補 DuckDB。
缺獨立答案的規則仍先補會失敗的測試；盤點沒有找到缺獨立答案的規則。

### 驗證框架與 Gui 的縮減

先整理各命令的用途與可以合併的部分，不改變驗證的判定。候選刪減每一項先找到涵蓋同一行為的檢查，逐項請使用者確認後才刪。
