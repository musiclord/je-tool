## 一、查核結論與前次失誤

**前次計畫沒有完整達成你的要求。** 底層條件能力已有實作，但操作設計偏離既有分工，情境編輯也仍有缺口。先前測試通過的紀錄有效，卻不足以證明整體使用體驗符合需求。

從原有畫面分工與 [`filter-step.js`](../../../src/JET/JET/wwwroot/js/steps/filter-step.js)、程式差異及 GUI 測試腳本確認的問題：

| 項目 | 判定 |
|---|---|
| 條件入口位置 | 三個快捷按鈕放在「建立篩選情境」，違反「上方挑選條件，下方組合與設定」的原有分工，必須移除。 |
| 條件加入位置 | Cash 快捷按鈕會另建群組，沒有遵循畫面承諾的「加入作用中的組」，必須修正。 |
| 自訂條件分類 | 「指定值與排除」與文字、日期、金額等卡片重疊。新增能力沒有融入既有類別，必須整合。 |
| 預覽流程 | 畫面寫「預覽後命名保存」，前後端卻都在預覽前要求名稱與動機。依本輪決定，改為保存時才要求。 |
| 未分類判定 | 只有「完全沒有指定分類」支援待判定，存在條件尚未一致處理。 |
| 待判定後續操作 | 只有張數與補分類入口。本輪已確認要補上傳票清單、原因與缺少分類的科目。 |
| 已保存 KCT 情境的編輯 | 保存時移除卡片來源標記，編輯時未還原；情境仍標為 KCT，但卡片顯示未選，必填判斷也與原來不同。必須修正。 |
| 條件說明與排版 | 摘要仍直接顯示 AND、OR；新增提示沿用舊的絕對定位樣式，有脫離控制項的風險。 |
| 驗證方法 | 新 GUI 測試直接使用錯置的快捷按鈕，沒有驗證從兩類正式入口完成任務，也未涵蓋保存後的 KCT 編輯。必須補足。 |

前次失誤主要在三個環節：把使用者的業務案例直接做成快捷入口；新增控制項時沒有核對既有畫面責任；測試跟著新增實作走，沒有回頭驗證原始操作要求。

保留不退回的成果：多日期、文字與金額比較、獨立排除、主要條件、傳票分頁、底稿版本，以及前四步已完成的操作修正。

## 二、修正後的操作方式

- **條件從兩類入口加入**：保留「KCT 條件」與「自訂篩選條件」兩大入口，「建立篩選情境」只負責調整條件、組合、預覽及保存。移除三個快捷按鈕；兩種 Cash 組合保留為操作範例，由審計員透過通用的借貸科目分類條件完成。自訂區把日期區間與指定日期整合為「日期條件」，文字比較與清單整合為「文字條件」，金額比較整合為「金額條件」；已配對的額外欄位依型別出現在對應條件中。畫面分類與後端儲存格式分開處理。
- **加入位置明確**：一般條件加入作用中的組，不自動新增群組或切換比對範圍。排除區獨立呈現，其中的新增按鈕帶回自訂條件選擇處；排除只支援已核准的文字、日期與金額比較。條件組合與摘要用「全部符合」「符合任一」等完整中文，忠實呈現既有括號與結合順序。
- **先預覽，再決定是否保存**：有有效條件即可預覽，不要求先填名稱與動機；保存自訂情境時才檢查必填資料，KCT 保留既有例外。前後端分開「可否預覽」與「可否保存」的檢查，不以假名稱或偽裝 KCT 來源繞過。保存失敗不改動原情境，更新不占新名額。
- **KCT 卡片來源**：新保存的情境保留必要的 KCT 卡片來源資訊，重開後恢復正確勾選與群組關係；取消某張 KCT 卡不得刪除相同型別的自訂條件。舊情境缺少來源資訊時，不憑名稱或條件外形猜測 KCT 字母，清楚提示無法還原個別卡片來源，仍可直接編輯。
- 新增控制項的說明、錯誤與舊規則提示留在對應欄位旁並正常換行；最小視窗與放大文字後不能遮擋或漂移。

## 三、分類判定與結果說明（已被 2026-09-07 取代）

你同意的「先列為待判定，補分類後再決定」納入本次實作，並依本輪選擇一致套用到新的借貸分類條件。（來源任務已獲使用者確認。）

- 明確符合的已分類科目才算命中；未分類不視為 Cash，也不視為非 Cash。
- 沒有確定命中、但補分類後仍可能符合整個情境的傳票，列為待判定；其他必要條件已確定不符合或條件互相矛盾時不列。同一科目在不同分錄中必須用一致分類。
- 待判定按完整情境及排除後的結果計算，不與確定命中重複計數。舊配對條件、KCT 判斷及舊空白規則保留原有語意。
- 結果分開提供「命中傳票」與「待判定傳票」，都能分頁展開完整分錄；待判定顯示受影響條件與缺少分類的科目，並提供前往第四步的入口。完整傳票要說明哪些列符合主要條件、哪些提供佐證、哪些只是參考，以及排除原因。
- 第六步明示待判定數及「未計入命中」，允許匯出已確定的結果，不新增阻擋關卡；舊底稿不改寫。
- 介面上沿用 `filter.preview` 與 `filter.commit`；兩個既有傳票分頁查詢以可省略的結果類別選擇命中或待判定，省略時維持命中；分頁游標綁定結果類別、條件及資料版本；情境增加可選的編輯來源資訊，只用來還原 KCT 操作，不參與審計判斷。

## 四、驗收方式

每項需求都要留下「從哪裡操作、預期看到什麼、程式與測試證據、人工驗收狀態」。驗收至少涵蓋：從空白情境只透過兩類正式入口建立日期與四種借貸條件；
跨月、跨年與閏日的包含及排除，文字前置零、特殊字元與清單正規化，金額正負號、零元與區間邊界；未分類與互斥條件；不填名稱可預覽而保存時要求必要資料；
KCT 單獨使用、混合自訂條件、保存後編輯及重開案件；待判定清單與補分類後的轉換；預覽、保存後查詢、完整傳票與底稿一致；保護已驗收的專案載入、刪除與必填檢查。
SQLite 與 DuckDB 用預先寫定答案的合成資料；GUI 測試必須從正式入口操作，含最小視窗、鍵盤、焦點與提示位置。

## 實作結果

- 實作期間的第一次失敗都已保留並修正：空白名稱預覽被拒、兩個本機資料庫沒把新的存在條件列入待判定、未分類與 Cash 被誤列待判定，以及架構檢查仍只憑草稿 marker 決定 KCT 來源。測試依本次裁定改為同時保護新編輯來源與無法還原來源的舊 KCT 情境。
- 第一次 `Public` 共 3,403 項，3,376 項通過、27 項失敗：23 項摘要或預覽必填測試仍固定舊行為，兩項分類測試未計入已核准的新存在條件，一項核心必填檢查須移到保存責任。測試依新裁定改為中文摘要、預覽可用、保存仍拒絕缺漏資料，原布林順序和命中分錄不改。
- 新的 Excel 合成案例抓到正式 `AccountMappingProjection` 沒有保存 `HasExplicitCategory`，分類留白被當成已分類，已修正。已匯入的 v10 案件也可能留有錯誤旗標，新增一次性修復：每批最多 500 筆，只依原始分類回填旗標，缺證據設為未知；實際變更才使篩選結果失效，第二次開案不再重複。
- GUI 情境增加 KCT 重開編輯、切換作用中組與四種借貸條件、待判定清單及補分類，使用 1024 × 640 最小視窗與 125% WebView 放大。補分類只以隔離合成檔代替原生選檔回應，不宣稱驗證原生檔案對話框。

## 人工驗收與另案邊界

各需求的自動證據都已備齊，人工驗收全部「待驗收」。合成操作資料與逐項答案在 `artifacts/acceptance/filter-completeness/`，只是本機驗收輔助。審計員尚需確認：

1. 由兩類正式入口完成日期、文字、金額與四種借貸條件；切換作用中組與排除位置後，操作符合預期。
2. 不填名稱預覽，保存、更新、另存、取消，並在重開案件後編輯新舊 KCT 情境。
3. 逐列理解主要、佐證、參考、排除與待判定說明；自行透過原生選檔視窗補分類，確認兩種判定轉換。
4. 在實際螢幕與縮放下用鍵盤操作日曆、欄位與焦點；確認提示沒有遮擋。
5. 在原生 Excel 填寫科目配對範本後匯回，核對第六步與底稿的待判定說明、命中數及歷史版本；Excel 佔用中的再次匯出，仍需在實際工作環境確認。
