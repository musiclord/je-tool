### 各步的做法

第 2 到第 21 步的做法已在 2026-11-06 原文移到[執行紀錄](../2026-11-06-deferred-items-plan-execution-records.md)，這裡從第 22 步寫起。

**第 22 步。** 使用者預告 SQLite 要上線到正式環境（裁定 2026-11-05-69），所以先唯讀盤點 SQLite 的穩健性與測試涵蓋。盤點由子代理讀 `src/`、`tools/` 與 `docs/` 完成，沒有執行測試；Claude 讀程式抽查了下面第 2、3、5 項與資料庫版本的註解，和盤點寫的一致。

下面幾項已經做好，大多有在 SQLite 上實際執行的測試，`Public` 會跑到：

- 案件資料庫用 WAL 模式，也就是先寫進記錄檔再併回資料庫；連線用私有快取。
- 每項寫入作業包在單一交易裡。匯入、確認欄位配對、驗證、篩選保存與命中、休息日與補班日等設定、報告與底稿，都有在 SQLite 上取消或寫入失敗後復原的測試。
- 審計員取消作業時，執行中的資料庫命令會被中斷。
- 同一個 JET 一次只執行一項會改資料的作業，跨程序有案件鎖檔；JET 被強制結束後，重開同一個 SQLite 案件可以重新取得鎖。
- 案件資料庫不是第 20 版就拒絕開啟，檔案保持原狀。

還沒有涵蓋的，依盤點的嚴重程度排列：

1. 高：SQLite 沒有大資料量的完整流程證據。目標是處理約一百萬筆分錄，但 SQLite 最大的自動測試只到十萬列的匯入暫存，也不檢查耗時；歷史量測只用 DuckDB 驗證過。一百萬筆時確認欄位配對、驗證、預篩選、篩選保存與命中、底稿匯出的耗時、記憶體尖峰與檔案大小都沒有量過。盤點建議新增選擇性執行的量測測試，用程式生成的合成資料走完整流程，最後檢查資料庫完整性；另外在公司規格的電腦上人工跑一次。
2. 高：發布出去的單一執行檔從來沒有在自動測試裡開過 SQLite。發布設定把 SQLite 的原生程式庫包在單一執行檔裡，執行時才解壓到暫存資料夾；`Gui` 用的是一般建置，`Package` 只檢查執行檔結構與檔案清單。公司電腦如果擋下暫存資料夾裡的程式庫，SQLite 會完全無法使用。這一項要在公司電腦用一般使用者帳號執行 `Package` 的產出，建立 SQLite 案件、匯入、重開。
3. 中高：沒有測過寫到一半被強制結束或斷電的情形。另外，`project.json` 換檔前沒有把暫存檔寫到磁碟（`JsonFileProjectStore.cs`），報告與工作檔換檔前則有寫到磁碟。盤點推論斷電時 `project.json` 可能變成空檔或內容錯亂，案件就開不起來。建議換檔前補上寫入磁碟，並用啟動子程式再強制結束的方式，測匯入、確認配對、篩選保存寫到一半的情形。
4. 中：唯讀、防毒軟體鎖檔、無法開檔、權限不足、記憶體不足這幾種錯誤沒有對應，畫面只顯示通用的「發生非預期的錯誤，此操作未完成。請再試一次。」，這幾種重試也不會成功。磁碟已滿只用單元測試灌錯誤碼，沒有經過真正的寫入。建議補上對應的原因與審計員接下來能做什麼，並用合成資料重現唯讀與磁碟已滿。
5. 中：`jet.db` 不見或變成 0 位元組時，開案會默默建出一個空的案件，因為 SQLite 案件資料庫找不到資料表時會直接建表；SQL Server 案件則明確擋下。這一項會改變對外行為，使用者選了比照無法開啟的案件，並要求建立案件的初始化程序也要穩健（裁定 2026-11-05-72）。
6. 中：離開案件時不清空連線池，產品也不把 WAL 併回資料庫。盤點推論一百萬筆的匯入失敗後，記錄檔可能一直很大；JET 還開著時複製案件資料夾，也可能拿到不同步的副本。
7. 較低：逐列讀取時，取消只在每一列開始前生效，審計員按取消後可能要等到下一筆才停；沒有測試比現行版本新的資料庫；從不執行 `ANALYZE`，篩選在一百萬筆時是否變慢要靠第 1 項的量測確認；長時間匯入時訊息紀錄寫不進去，審計員看不到錯誤，只是支援日誌多出失敗紀錄；100 字的中文案件名稱沒有走完整流程的測試。
8. 只能人工確認：公司電腦是否用漫遊設定檔，防毒即時掃描對 SQLite 記錄檔的影響，以及磁碟接近滿載時匯入。

另外有兩處文件與程式不一致。`SqliteProjectDatabase.cs` 與 `DuckDbProjectDatabase.cs` 的註解寫「第 19 版」，實際是第 20 版，已改正。`docs/test-environment-notes.md` 第 140 行寫 SQLite 的大型案件取消時要等目前那一段跑完，寫在 2026-10-20 補上中斷之前，看起來已經過時；要先補第 7 項逐列讀取取消的測試確認，再改文件。

**第 23 步。** 照裁定 2026-11-05-72，`jet.db` 不見或變成 0 位元組時比照無法開啟的案件，建案的初始化程序也改穩健。

- 根本原因在本機資料庫讀寫前的共用檢查：找不到資料表就直接建表。所以不只開案，案件開著時資料庫檔被刪掉，下一次讀寫也會默默建出空的資料庫。現在只有建案會建表；開案與每次讀寫前的檢查遇到資料庫檔不見、是 0 位元組或沒有任何資料表，都回 `file_read_error`，訊息寫資料庫檔案遺失或沒有內容，下一步和設定檔無法讀取時相同，檔案保持原狀。SQLite 與 DuckDB 共用同一套檢查。
- 案件清單只看資料庫檔在不在與大小，不開資料庫，把資料庫檔不見或是 0 位元組的本機案件列成錯誤列；有檔案但沒有資料表的情形，開案時才查得到。錯誤列照舊可以刪除。
- 穩健的初始化：原本建案先發布設定檔，再取鎖、建資料庫，中間當掉會留下有設定檔、沒有資料庫的資料夾，改完後這種案件會被當成資料遺失。所以建案時把建案中的標記 `.project-creating` 和設定檔一起發布，資料庫建好、建案完成後才刪。開案時標記還在，表示上一次建案在完成前中斷，審計員沒有拿到這個案件，資料庫裡不會有資料，就照建案的做法把初始化做完再刪標記；遇到 0 位元組的檔案，連同記錄檔刪掉重建。案件清單看到標記時照常列出。
- DuckDB 開案前保持資料庫開啟的那一段，原本只略過不存在的檔案，現在也略過 0 位元組的檔案，免得替空檔開出資料庫實體。
- SQL Server 案件的開案原本就由登記檢查擋下不存在的 schema，沒有改；線上案件物化本機快取後一併刪掉標記，這段只經編譯，記在 SQL Server 封存事項。
- 錯誤碼沿用 `file_read_error`，沒有新增。新取的名稱與兩句畫面訊息寫在名詞表「資料庫遺失的案件」一列，等停點五確認。

**第 24 步。** 第 22 步盤點的第 3 項，寫到一半被強制結束或斷電的情形。

- `project.json` 換檔前先把暫存檔寫到磁碟，建案發布前的設定檔也一樣，和報告與工作檔的寫法相同。寫出的內容和原本一模一樣，UTF-8 不加 BOM。斷電無法在自動測試裡重現，這一項靠寫法保證，另有新測試核對寫出的內容沒有變。
- 新加強制結束的測試：子程式在寫入交易進行中送出的進度事件裡停住，父程式這時強制結束它，所以時間點是確定的，不靠等待時間。匯入大檔與改用另一欄重新確認 GL 配對兩種作業，SQLite 與 DuckDB 各測一次。重開後核對四件事：強制結束前的資料逐表相同、資料庫完整性檢查通過、能重新取得案件鎖、重試會成功。DuckDB 沒有對應的完整性檢查，改成讀完每一張比對的表。
- 條件保存沒有進度事件，也沒有能從外部接上的訊號，要在它寫到一半結束只能靠等待時間猜，結果不確定，所以沒有做成強制結束的測試。它和匯入、確認配對用同一種單一交易，資料庫在強制結束後的復原由這兩種作業的測試證明；條件保存在寫入失敗與取消時的回復，另有既有測試。

**第 25 步。** 第 22 步盤點的第 1 項，SQLite 沒有大資料量的完整流程證據。

- 新加的量測測試 `ScaleJourneyTests` 用程式生成的合成 GL 與 TB，照審計員的順序走完建案、匯入 GL 與 TB、確認兩份配對、驗證、預篩選、條件保存、條件篩選報告與底稿。每一步記下耗時、記憶體、資料庫檔與記錄檔大小，最後檢查資料庫完整性；只記數字，不判斷快慢。設定 `JET_SCALE_JOURNEY=1` 才會執行，`Public` 與 `Focused` 都不會跑到，要量時直接執行建置好的測試程式。
- 2026-11-06 在這台開發電腦上量一百萬筆，兩種資料庫各用一個程式量，記憶體尖峰才不會互相墊高。下表是第 26 步改完後的耗時，單位是秒；建案、匯入 TB 與確認 TB 配對都不到 1 秒，沒有列出。

| 步驟 | SQLite | DuckDB |
|:---|---:|---:|
| 匯入 GL | 8.1 | 6.8 |
| 確認 GL 配對 | 17.4 | 18.0 |
| 驗證 | 9.1 | 1.8 |
| 預篩選 | 14.0 | 1.3 |
| 條件保存 | 1.0 | 0.5 |
| 條件篩選報告 | 2.3 | 3.3 |
| 底稿 | 9.3 | 3.1 |

- 全程 SQLite 約 62 秒、DuckDB 約 35 秒。記憶體尖峰 SQLite 約 462 MB、DuckDB 約 829 MB；資料庫檔 SQLite 約 530 MB、DuckDB 約 198 MB。SQLite 的完整性檢查通過；DuckDB 沒有對應的檢查，當時只數了兩張表的筆數，提交前複審後改成逐表讀完每一欄，重跑一百萬筆也通過，見第 34 步。
- 第 26 步之前量的那一次，SQLite 匯入 GL 之後記錄檔一直停在約 282 MB，印證了盤點的第 6 項；第 26 步之後每一步結束時記錄檔都是 0，耗時沒有明顯差別。
- 這些是合成資料在開發電腦上的數字，不是效能承諾。公司規格的電腦要人工再跑一次，列進停點五的人工清單。

**第 26 步。** 第 22 步盤點的第 6 項，記錄檔不併回、連線不關閉。

- 根本原因：SQLite 先把資料寫進記錄檔再併回資料庫檔，記錄檔用過不會自己縮小；連線池一直留著連線，這個程式最後一條連線關閉時才會刪掉記錄檔，所以 JET 開著時記錄檔一直在。記錄檔還有資料沒併回時，只複製資料庫檔會拿到不完整的副本。
- 現在每項改資料的作業結束後，不論成功、失敗或取消，都把記錄檔併回資料庫檔並清空，在放開作業閘之前做完。查詢裡補算過期的篩選結果也會寫入，這段不經過一般作業的收尾，由補算服務自己在放開閘之前併回。
- 離開案件、開案失敗與結束 JET 時，先清掉這個案件的連線池再併回，最後一條連線關閉時記錄檔與共用記憶體檔跟著刪除，JET 不再開著 `jet.db`。正常關窗會先離開案件；畫面已經無法使用、由主機直接關窗時，程式結束前的收尾會關閉目前案件，順序在放開案件鎖之前。
- 併回或關閉失敗不改變作業結果，已提交的資料在記錄檔裡照樣完整，只在支援日誌記一筆。有其他連線正在讀寫時只併回能併的部分，不等待。
- DuckDB 每項作業結束時最後一條連線關閉，資料庫跟著關閉，關閉時就會併回，第 25 步的量測裡記錄檔一直是 0，所以不另外處理。SQL Server 是遠端服務，不受影響。
- 新測試 `ProjectDatabaseCheckpointTests` 在 SQLite 與 DuckDB 核對六種情形：改資料之後記錄檔是空的，只複製資料庫檔也有完整資料；取消寫到一半的大量匯入之後記錄檔是空的，之前的資料還在；離開案件、開案被拒與沒有離開案件就結束 JET 之後，都沒有留下記錄檔與共用記憶體檔，資料庫檔也沒有被任何程式開著；查詢補算篩選結果之後記錄檔是空的。另核對收尾不會替不存在的案件建立資料夾。暫時拿掉併回時，六種情形的 SQLite 測試全部失敗，DuckDB 照樣通過。
- 架構檢查規定只有選組的程式能拿整組資料存取物件，所以比照 DuckDB 保持資料庫開啟的做法，把 SQLite 的資料庫物件直接交給作業收尾、離開案件、開案與程式結束這幾處；DuckDB 與 SQL Server 案件的資料夾沒有 `jet.db`，交給它們時自然不做事。
- 第 25 步量測測試的四個環境變數，比照既有的量測測試，加進驗證時要清掉的環境變數清單。

**第 27 步。** 第 22 步盤點的第 4 項，唯讀、鎖檔、無法開檔、權限不足與記憶體不足沒有對應。

- 對應集中在本機資料庫引擎錯誤的單一對應處 `LocalEngineErrors`，新增三個錯誤碼。`database_read_only` 是資料庫檔唯讀，包括放在唯讀的位置與共用記憶體檔無法寫入，訊息「案件資料庫是唯讀的，資料無法寫入。請確認案件資料夾和裡面的檔案不是唯讀，再重新開啟案件。」；唯讀時已經開著的連線不會變成可寫，所以下一步寫重新開啟案件。`database_unavailable` 是沒有權限、開不了檔或讀寫失敗，常見原因是權限、拔掉的磁碟或網路位置，以及防毒軟體這類程式獨占檔案，訊息「JET 無法讀寫案件資料庫。請確認案件資料夾所在的磁碟仍然連接，資料夾和裡面的檔案不是唯讀，而且目前的 Windows 帳號可以寫入。防毒軟體或雲端同步正在處理這個資料夾時，請等處理完成後再試一次。」。`database_out_of_memory` 是資料庫引擎配置不到記憶體，訊息「電腦的記憶體不足，此操作未完成。請關閉其他程式後再試一次。」
- 案件設定檔寫不進去，原本就有自己的訊息，請審計員確認案件資料夾不是唯讀、設定檔沒有被其他程式開啟，這次沒有改；案件鎖檔放在案件資料夾外面，錯誤也已有對應。
- DuckDB 把作業系統依語言翻譯的原因放進訊息，中文 Windows 上不會出現英文的系統句子，所以原本比對英文句子的磁碟已滿在這台電腦抓不到，這次一併改正：磁碟已滿改向 Windows 取得同一句系統訊息比對，記憶體不足看 DuckDB 的錯誤分類，其餘讀寫資料庫檔的錯誤看 DuckDB 自己的英文開頭 `IO Error:`，歸到無法讀寫。
- 新測試 `CaseDatabaseAccessErrorTests` 用合成資料在真正的檔案上重現四種情形。SQLite 資料庫檔唯讀時寫入被擋下、資料不變，取消唯讀、重新開啟案件後可以寫入；整個案件資料夾唯讀時開案寫出原因、檔案都不變，SQLite 在寫入案件設定時擋下，DuckDB 在開資料庫檔時擋下；資料庫檔被其他程式獨占時開案寫出原因，釋放後可以開案；匯入大檔途中磁碟已滿時寫出原因，之前的資料完整、完整性檢查通過，空間釋出後重試成功。磁碟已滿用 SQLite 的頁數上限重現，上限只作用在設定它的連線上，所以測試先把 JET 的連線池換成設好上限的連線。
- 權限不足、記憶體不足與其他讀寫錯誤無法在測試裡安全重現，改用錯誤碼建構引擎例外的單元測試核對；DuckDB 的單元測試用這台 Windows 的系統句子組出訊息。

**第 28 步。** 第 22 步盤點的第 7 項，較低的缺口。

- 逐列讀取的取消：原本只有語句的第一步可以中斷，之後每讀一列只在開始前檢查一次取消；第一列很快出來、下一列要掃過很多資料時，按取消後要等下一列出來才停。現在 SQLite 的讀取器在讀下一列的期間也接上中斷，和執行語句時相同，讀完就解除。新測試第一列馬上讀到、第二列要很久，取消後很快停下；暫時拿掉這個改法時，要等測試自己在 30 秒後強制中斷才停。DuckDB 一次算完整個結果才交出第一列，沒有這段等待。`docs/test-environment-notes.md` 那條「SQLite 按取消要等目前那一段跑完」的限制已不成立，刪掉。
- 比現行版本新的資料庫：照現行規則拒絕開啟，訊息是「版本資訊無法辨識」那一句，資料庫檔保持原狀，案件照樣可以刪除；補了 SQLite 與 DuckDB 的測試，程式不用改。
- 100 字的中文案件名稱：用第 25 步量測的同一段流程、200 筆合成資料，從建案走到底稿，再從清單重新開啟、讀到兩份報告並刪除案件，SQLite 與 DuckDB 都通過，程式不用改。
- 長時間作業時的訊息紀錄：長作業的寫入交易占著資料庫，這時寫訊息要等它結束，超過 30 秒就失敗，支援日誌多一筆失敗紀錄，訊息由前端留著稍後重寫。現在前端在作業進行中先不寫入，作業結束後依序寫入；複製紀錄這類明確要求照舊先寫完再讀。另加一個前端行為檢查。
- `ANALYZE`：第 25 步的一百萬筆量測裡，篩選條件保存 1 秒、條件篩選報告約 2 秒，最慢的預篩選約 14 秒，看不出查詢計畫選錯的跡象，所以沒有加。

**第 30 步。** 使用者要求推送前補齊 Gui、真實案件與涵蓋率的測試（裁定 2026-11-06-01），所以先盤點審計員的使用情境被哪一層測試涵蓋。盤點由子代理讀 `src/`、`tools/` 與 `docs/` 完成，沒有執行測試；Claude 讀程式抽查了下面 Gui 的兩項，和盤點寫的一致。

- 已經涵蓋的：建案、匯入、欄位配對、驗證、預篩選、篩選條件、條件篩選報告與底稿，Gui、真實案件與 C# 測試都有；C# 測試大多同時跑 SQLite 與 DuckDB。重新開啟、重新匯入或重新確認配對後清掉條件，有 Gui 與 C# 測試。取消作業、強制結束後重開與資料庫存取錯誤，只有 C# 測試與前端行為檢查。
- Gui 的 18 個情境都用 SQLite 建案，驅動程式裡沒有 DuckDB。
- 缺口一：真實案件只走一次從建案到六份報告的直線流程，沒有核對重新開啟、重新確認配對或重新匯入之後，結果是否仍和第一次一樣。
- 缺口二：Gui 沒有取消作業、刪除案件與無法開啟的案件。產品裡已有延遲匯出、案件清單讀取失敗等 11 個只在 Gui 測試建置裡的夾具，沒有任何情境使用。
- 缺口三：Gui 沒有用 DuckDB 建案走完整流程。
- 缺口四：現有的驗證路線都沒有量程式涵蓋率；變異測試只涵蓋 `GlProjectionGuard` 與 `MoneyScaling` 兩個範圍。
- 只能人工確認：停點五的五項，以及原生的檔案對話框與各家輸入法，Gui 用固定的合成選檔回應與組字事件代替（`tools/README.md` 的 Gui 一節）。

**第 31 步。** 依第 30 步的缺口補測試。

- 真實案件的核對加上重做後的比對，由子代理實作，只改測試程式。第一次走完並和舊版比對之後，在同一個案件接著重新開啟、照原本的配對重新確認 GL 配對，以及重新匯入同一份 GL；每一段都重新匯出六份報告，用同一組舊版預期底稿、同一份比對規則與內容裁決再比一次，三段都通過才算通過。重新確認配對與重新匯入之後，要核對回應寫的五項結果都已清除，產品實際清掉的範圍和測試重做的步驟不一致時直接失敗。
- 重新匯入只重新匯入 GL，TB 與它的配對照舊。子代理讀產品程式確認：GL 的匯入或投影會清掉資料驗證、預篩選、篩選命中、已儲存的條件與科目配對，TB 的匯入與配對、授權清單、假日與補班日都不會被清掉。這是讀程式的結果，沒有裁定逐字寫明。
- 合成資料走同一段流程的測試在 SQLite 與 DuckDB 上，三段重新匯出的六份報告都和第一次相同。
- 真實案件的核對加上這三段之後，SQLite 與 DuckDB 的 `PrivateCase` 都通過。核對清單裡 R4 的放行還在，所以這次通過代表其他報告在三段重做之後仍和舊版一致，不能證明 R4 已經對上。使用者刪掉這條放行後重跑，兩種資料庫也都通過，R4 已經和舊版一致。
- 程式涵蓋率直接執行建置出來的測試程式量測，排除私人案件、SQL Server 與大資料量三類測試，5,802 個測試都通過。JET 產品程式的行涵蓋率是 82.9%、分支是 79.5%；其中 SQL Server 是 10.0%，因為它的測試暫緩沒有跑，不含 SQL Server 時是 91.2%。
- 沒有執行到的程式大多是三類：防範 JET 自己的範本或路徑壞掉的檢查，審計員碰不到；開案與案件清單裡 SQL Server 線上案件的分支；以及底稿寫入程式裡三個沒有任何程式呼叫的方法 `EmitTableSheetAsync`、`StreamRowsAsync`、`StreamItemsFromAsync`，只出現在註解裡，這是遺留的程式，不是缺測試，要不要刪掉留到停點六問使用者。
- 依涵蓋率補了三組實際可能發生的錯誤路徑。`ProjectDatabaseCheckpointFailureTests` 核對記錄檔併回或關閉失敗時，作業結果與原本的錯誤都照舊，離開案件與結束 JET 照常完成，只在支援日誌記一筆。`SqliteCancellationBoundaryTests` 核對取消剛好在 SQLite 交出第一列或後面某一列時才送達、讀到後面某一列時出錯，以及一次讀多段結果；連線之後都能繼續用。`LocalFileLockServiceTests` 新加兩個測試，核對鎖檔的位置被資料夾占住時寫出原因，資料夾移走後照常鎖定；以及案件資料夾已被移走時寫出資料夾已不在，也不替案件建出空的資料夾。
- 這三組第一次執行就通過，所以只對它們再量一次涵蓋率，確認真的執行到目標的程式。第一次寫的「後面某一列剛交出時才取消」其實沒有測到：取消的函式放在 `CASE` 的 `THEN` 分支，SQLite 在分支結束的跳躍檢查中斷，那一列沒有交出來就中止了。改放在 `ELSE` 分支後，重量確認執行到。
- Gui 新增兩個情境，由子代理實作，各單跑一次就通過；原本的 `case-to-working-paper` 與 `validation-auto-outputs` 重跑也通過。`case-list-cleanup-cancel-export` 在案件清單把資料庫檔不見的案件列成無法開啟、寫出原因並刪掉它，再到另一個案件的第四步準備科目配對範本時取消，核對畫面恢復、沒有留下範本檔，再準備一次就成功。`case-to-working-paper-duckdb` 和 `case-to-working-paper` 走同一段程式，只在建案時選 DuckDB，兩個情境都核對資料庫種類與案件資料夾裡的資料庫檔。資料庫檔不見的案件由新的 Gui 夾具 `seed-missing-database-project` 放出來。DuckDB 情境第一次超過操作上限，原因是選一次下拉選單要算兩次操作，改了上限後通過。
