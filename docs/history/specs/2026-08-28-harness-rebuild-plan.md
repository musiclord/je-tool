# JET 驗證框架重建計畫

狀態：已完成  
開始日期：2026-08-28  
完成更新：2026-08-29  
目前階段：Phase 7 — 發布候選與乾淨快照驗證已完成

## 目標

這個計畫會逐步為 `je-tool` 建立新的驗證框架。`new-je-tool/tools/` 只用來了解過去需要解決哪些問題，
不會把舊腳本、設定、輸出或基準檔整包搬回來。

完成時應具備：

1. 一個公開入口，以及清楚分開的開發、測試和驗證循環。
2. 使用合成資料的公開測試、資料庫一致性檢查和輸出檔案檢查。
3. 可隔離、有限時且能完整清理的 GUI 與原生 Excel 驗證。
4. 經使用者當次授權後，能將私人 JE／TB 走完正式產品流程，匯出工作底稿，並和獨立正確底稿比較。
5. 重要業務規則能追溯到 `idea-tool.bas`／`idea-script.bas` 的相關區段，而不是只比較檔案外觀。
6. 能在乾淨的工作目錄重新產生必要證據，且完全不依賴舊專案或舊執行輸出。

驗證框架完成後，仍要由使用者另行確認第一次提交的完整內容、分支和遠端位置；本計畫不自行提交或推送。

## 已確定的做法

- 先清除舊驗證框架對產品測試的反向依賴，再從乾淨狀態重建。
- 保留成熟的安全觀念，但重新設計結構；不複製三千行的 `verify.ps1` 或八千行 GUI 控制腳本。
- `data/` 十份 JET 業務範例維持原檔，不因驗證框架而重存或去識別化。
- 私人案件及其輸出不進 Git。沒有當次授權時，不讀取、不掃描，也不自行搜尋。
- 正確底稿必須是獨立的比對依據；JET 產物不能核准自己。
- Legacy 只用來查已明確對應的規則，不復活 IDEA 或 VBA 執行環境。
- 本機私人驗收案件放在 `data/test-case/`，整個目錄由 Git 排除。舊 CaseWare IDEA JE Tool 產出的報告與
  底稿是這個案件的獨立標準，JET 不得覆寫或更新它們。
- 各階段依序進行。每一階段都要完成自己的驗證並留下紀錄，不能把「程式寫完」當成「已驗證」。
- 能安全自動完成的建置、封裝、GUI 或 Excel 準備，不應轉成使用者的例行工作。
- `tools/` 第一層只按責任分成 `harness` 與 `tests`。驗證框架內的子目錄名稱使用小寫並以連字號分隔；
  C# 型別、namespace、組件與原始碼檔名維持 PascalCase。

## 已固定的 Phase 6 驗收規則

使用者已作出以下決定，驗證框架不得自行放寬：

1. 六份正確底稿同時比較內容與版面，不採逐位元比較，也不只比較業務內容。
2. INF 的 59 筆樣本依抽樣規則與實際母體判定，不要求重現舊 IDEA 當時隨機選到的相同資料列。
3. `PrivateCase` 成功或失敗都要清除本次建立的私人副本與輸出，不保留失敗產物；也不得搜尋或刪除其他
   執行留下的資料夾。

## 已釐清的後續邊界

下列事項不是 Phase 1 至 Phase 7 或第一次根提交的缺口；需要擴大範圍或執行破壞性操作時，再另外授權：

1. 目前的原生 Excel 證據涵蓋這台電腦的 Excel 16.0。其他版本屬於新增支援範圍；沒有 Excel 或無法證明
   原生行為時一律回報 `blocked`。
2. Phase 3 曾記錄 `JET_Test` 中有較早的測試資料。清理工作延後到新儲存庫完成遠端讀回驗證之後，屆時要
   重新盤點即時數量、確認刪除範圍並另行授權；驗證框架不會自行刪除來源不明的資料。
3. 變異測試、壓力測試與涵蓋率目前不列為發布必要條件。只有能回答獨立品質問題時才建立新工作，不恢復
   舊專案的設定或輸出。
4. `PrivateCase` 維持需要當次明示授權的本機命令，不自動加入 `ReleaseCandidate` 或公開 CI。既有收據只能
   描述當次執行；需要新的私人案件結論時必須重新授權。
5. 第一次根提交不複製舊專案 CI。新的 CI 在根提交與遠端讀回完成後，從適合遠端環境的公開命令重新設計。
6. 空的 `.agents/`、`.claude/`、`.config/`、`.github/` 與 `.vscode/` 不加佔位檔；有實際內容時才納入 Git。

真實案件的三個篩選差異已由使用者裁定：情境 1 採舊 IDEA 的整張傳票口徑，且只套用於單獨的「未預期
借貸組合」；情境 5 採同列成立；情境 6 納入週末補班日。這三項不再列為待決事項。

本機案件的 JE、TB、欄位配對、匯入模式、日期、支援資料與六個情境，已從使用者授權的案件檔案整理成
Git 排除的本機清單，並由程式檢查過。這些設定不再要求使用者重新抄寫；如果正式執行時發現證據互相矛盾，
才停止並請使用者判斷。

## 各階段內容

### Phase 0 — 定義邊界與順序

- 盤點舊驗證框架和現行儲存庫，不建立執行器、GUI 控制程式或私人資料入口。
- 分開公開測試、資料庫、輸出檔案、GUI、Excel、私人案件及發布候選的責任。
- 明文禁止自動搜尋私人資料、用 JET 輸出產生自己的正確答案，以及沿用舊執行結果。
- 檢查文件連結，並更新第一次 commit 的候選清單。

### Phase 1 — 最小執行器與執行紀錄基礎

- 建立 `tools/verify.ps1`；Phase 1 當時先支援 Help、Contract、Restore 和 Build。
- 由設定檔明確列出已啟用和未啟用的驗證路線；本階段不接入產品測試、Provider、GUI、Excel 或私人案件。
- 建立跨程序共享鎖、每次執行專屬資料夾、原子寫入的 JSON 紀錄、輸出大小限制、逾時及精確清理。
- 驗證框架自身測試放在 `tools/tests/`；核心 `JET.Tests` 不得反向要求 `tools/` 或執行紀錄存在。
- 依目前 .NET 10 與 Microsoft Testing Platform 官方文件核對命令列介面，再固定參數與結束碼。
- 驗證正常執行、錯誤參數、路徑越界、鎖被占用、子程序失敗、逾時、輸出截斷、紀錄寫入失敗及拒絕清理不明資料夾。

### Phase 2 — 公開開發與測試循環

- `Focused` 接受有限且明確的 xUnit v3/MTP 測試選取條件，並附帶必要的架構與介面檢查。
- `Public` 執行所有安全、合成、不需外部環境的產品測試。
- 明確區分 Restore、Build 與 Test；測試不能使用來源不明的舊 build。
- 保存測試清單、TRX、摘要及第一次失敗，並檢查必要測試沒有被略過。

### Phase 3 — 資料庫與正式輸出檔案

- `Provider` 先比較 SQLite 與 DuckDB 的共同結果，再依 `Capability=SqlServer` 執行完整 SQL 測試；最後另外檢查
  LocalDB Express 仍被排除。SQL Server 無法使用時回報 `blocked`，不能用 SQLite 或 DuckDB 代替。
- SQL 連線只接受 `JET_SQLSERVER_CONNECTION`。連線值不進命令、收據或測試證據；缺少連線時不啟動 build。
- `Package` 固定使用 Release，先拒絕可追蹤設定中的憑證，再執行目前的範本與報告測試及 FolderProfile
  publish。輸出位於本次專屬暫存目錄，驗證後自動清除。
- 封裝清單直接核對同一次執行的 `JET.exe`、八份範本、`wwwroot` 與安全設定；不恢復舊 P5 基準、來源專案
  的執行產物或舊檔案數量要求。

### Phase 4 — GUI

- 先依現行產品流程找出只有透過 GUI 才能驗證的部分，再挑選仍有價值的舊情境。
- 使用隔離的 `AgentGuiTest` 組態、真實 WinForms／WebView2、封閉操作及有限時間與動作數。
- 不接管使用者正在使用的程式，不接受任意 JavaScript，也不以截圖取代業務結果檢查。
- 所有程序和資料夾都要能追到本次執行，成功或失敗都要驗證清理結果。

### Phase 5 — 原生 Excel

- Excel 控制程式與主執行器分開，只接受固定格式的命令、專屬路徑和有限逾時。
- 先用合成工作簿驗證開啟、重算、儲存／關閉、輸出檔案及本次啟動的 Excel 程序清理。
- Excel 不可用、檔案被鎖或無法證明原生行為時，回報 `blocked`；不能退化成只讀 Open XML 後仍宣稱 Excel 通過。

### Phase 6 — 私人案件與業務比對

- 由 Git 排除的本機案件清單明確列出 JE、TB、舊工具匯入紀錄、驗證報告、支援檔及標準底稿；已追蹤的
  程式只保存清單格式與合成範例，不保存真實檔名或欄位內容。
- 每次都要同時提供案件清單與明確授權。`PrivateCase` 不會因為 `data/test-case/` 存在就自行列舉或執行。
- 先用合成案件檢查路徑是否在授權範圍內，並防止重新解析點與 `..` 造成的路徑穿越。
- 獲得當次授權後，才按照本機案件清單中已確認的設定走 JET 正式匯入、配對、驗證、篩選、報告與底稿匯出
  流程。本機清單已從這次授權的舊工具紀錄與驗證資料整理完成；若後續證據無法相互吻合，執行器必須停止，
  不能補上猜測值。
- JET 產物一律寫進本次執行專屬資料夾；來源檔、舊工具報告與標準底稿都以唯讀方式開啟，不重存也不改
  中繼資料。
- 六份底稿固定比較工作表、儲存格、公式、樣式、尺寸、合併範圍、頁面與列印設定。封裝時間等不影響
  工作簿行為的資料不列入差異；不能因真實案件失敗而改成只比較部分業務內容。
- 建立 Legacy 規則對應表，讓重要比較能追到舊程式區段、現行程式位置和獨立預期答案。
- 比較結果只保存去識別化的差異種類、數量、規則代碼與雜湊，不記錄私人路徑、工作表、欄位、儲存格或值。

### Phase 7 — 發布候選與交付準備

- 只組合已經各自穩定的驗證路線，順序固定；任何必要步驟失敗就停止。
- `PrivateCase` 維持明示授權的本機命令，不會暗中變成一般 CI 或公開發布的資料依賴；需要新的私人案件
  結論時，必須由使用者在當次工作重新授權。
- 在乾淨的工作目錄重新執行必要的 Restore、Build、公開測試、資料庫、封裝、GUI 與 Excel 驗證。
- 更新現況文件、結束本計畫並重建第一次 commit 候選清單；不自行 stage、commit 或 push。

### Phase 6 現行產品流程查核

- `HandlerTestHost` 會組裝正式的 `ActionDispatcher` 與產品處理器。專案、使用者快取、診斷紀錄及本機資料庫都
  放在本次測試的暫存根，結束時由同一個 host 清除。PrivateCase 可以從這裡執行產品 action；不需要用 GUI
  模擬每一次匯入與按鈕操作。GUI 是否能啟動及建案，仍由獨立的 `Gui` 路線檢查。
- 現行完整流程依序是：建案；匯入 GL、TB 與明示提供的支援檔；提交 GL／TB 欄位配對；執行資料驗證並匯出
  ValidationReport、AccountMapping、INFReport；執行預篩選並匯出 PrescreeningReport；提交條件篩選；最後
  匯出 CriteriaSelectionReport 與 WorkingPaper。六份產物都由同一條產品流程建立，不由驗證框架自行重製。

### 本機案件清單涵蓋的內容

以下內容來自現行 `project.create`、匯入、欄位配對、驗證、篩選及匯出 action，已納入版本 1 的清單格式。
