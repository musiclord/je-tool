這份是 2026-11-01 壓縮後的摘要。使用者原話、題目與回答、日期、數字與裁定照原文保留；實作經過、驗證收據與重跑過程壓成結果。

狀態：已完成。開始日期 2026-08-28，完成更新 2026-08-29。最後階段是 Phase 7，發布候選與乾淨快照驗證已完成。

## 目標

這個計畫逐步為 `je-tool` 建立新的驗證框架。`new-je-tool/tools/` 只用來了解過去需要解決哪些問題，不把舊腳本、設定、輸出或基準檔整包搬回來。
完成時應具備：

1. 一個公開入口，以及清楚分開的開發、測試和驗證循環。
2. 使用合成資料的公開測試、資料庫一致性檢查和輸出檔案檢查。
3. 可隔離、有限時且能完整清理的 GUI 與原生 Excel 驗證。
4. 經使用者當次授權後，能將私人 JE、TB 走完正式產品流程，匯出工作底稿，並和獨立正確底稿比較。
5. 重要業務規則能追溯到 `idea-tool.bas`、`idea-script.bas` 的相關區段，而不是只比較檔案外觀。
6. 能在乾淨的工作目錄重新產生必要證據，且完全不依賴舊專案或舊執行輸出。

驗證框架完成後，仍要由使用者另行確認第一次提交的完整內容、分支和遠端位置；本計畫不自行提交或推送。

依據：儲存庫共通規則 [`AGENTS.md`](../../../AGENTS.md)、驗證框架的長期規範 `harness.md`、業務規則的裁決順序
[`business-logic-provenance.md`](../../business-logic-provenance.md)、現行產品與測試 `src/JET/`，以及 Legacy 對照來源 `legacy/idea-tool.bas`、`legacy/idea-script.bas`。
`new-je-tool` 的舊驗證框架只供盤點能力與失敗經驗，不是後續執行的依賴。

## 已確定的做法

- 先清除舊驗證框架對產品測試的反向依賴，再從乾淨狀態重建。
- 保留成熟的安全觀念，但重新設計結構；不複製三千行的 `verify.ps1` 或八千行 GUI 控制腳本。
- `data/` 十份 JET 業務範例維持原檔，不因驗證框架而重存或去識別化。
- 私人案件及其輸出不進 Git。沒有當次授權時，不讀取、不掃描，也不自行搜尋。
- 正確底稿必須是獨立的比對依據；JET 產物不能核准自己。
- Legacy 只用來查已明確對應的規則，不復活 IDEA 或 VBA 執行環境。
- 本機私人驗收案件放在 `data/test-case/`，整個目錄由 Git 排除。舊 CaseWare IDEA JE Tool 產出的報告與底稿是這個案件的獨立標準，JET 不得覆寫或更新它們。
- 各階段依序進行。每一階段都要完成自己的驗證並留下紀錄，不能把「程式寫完」當成「已驗證」。
- 能安全自動完成的建置、封裝、GUI 或 Excel 準備，不應轉成使用者的例行工作。
- `tools/` 第一層只按責任分成 `harness` 與 `tests`。驗證框架內的子目錄名稱使用小寫並以連字號分隔；C# 型別、namespace、組件與原始碼檔名維持 PascalCase。

## 已固定的 Phase 6 驗收規則

使用者已作出以下決定，驗證框架不得自行放寬：

1. 六份正確底稿同時比較內容與版面，不採逐位元比較，也不只比較業務內容。
2. INF 的 59 筆樣本依抽樣規則與實際母體判定，不要求重現舊 IDEA 當時隨機選到的相同資料列。
3. `PrivateCase` 成功或失敗都要清除本次建立的私人副本與輸出，不保留失敗產物；也不得搜尋或刪除其他
   執行留下的資料夾。

## 已釐清的後續邊界

下列事項不是 Phase 1 至 Phase 7 或第一次根提交的缺口；需要擴大範圍或執行破壞性操作時，再另外授權：

1. 目前的原生 Excel 證據涵蓋這台電腦的 Excel 16.0。其他版本屬於新增支援範圍；沒有 Excel 或無法證明原生行為時一律回報 `blocked`。
2. Phase 3 曾記錄 `JET_Test` 中有較早的測試資料。清理工作延後到新儲存庫完成遠端讀回驗證之後，屆時要重新盤點即時數量、確認刪除範圍並另行授權；驗證框架不會自行刪除來源不明的資料。
3. 變異測試、壓力測試與涵蓋率目前不列為發布必要條件。只有能回答獨立品質問題時才建立新工作，不恢復舊專案的設定或輸出。
4. `PrivateCase` 維持需要當次明示授權的本機命令，不自動加入 `ReleaseCandidate` 或公開 CI。既有收據只能描述當次執行；需要新的私人案件結論時必須重新授權。
5. 第一次根提交不複製舊專案 CI。新的 CI 在根提交與遠端讀回完成後，從適合遠端環境的公開命令重新設計。
6. 空的 `.agents/`、`.claude/`、`.config/`、`.github/` 與 `.vscode/` 不加佔位檔；有實際內容時才納入 Git。

真實案件的三個篩選差異已由使用者裁定：情境 1 採舊 IDEA 的整張傳票口徑，且只套用於單獨的「未預期
借貸組合」；情境 5 採同列成立；情境 6 納入週末補班日。這三項不再列為待決事項。

本機案件的 JE、TB、欄位配對、匯入模式、日期、支援資料與六個情境，已從使用者授權的案件檔案整理成 Git 排除的本機清單，並由程式檢查過。
這些設定不再要求使用者重新抄寫；如果正式執行時發現證據互相矛盾，才停止並請使用者判斷。

**輸入預檢（2026-08-28）。** 經使用者明示授權，完整只讀檢查 `data/test-case/`：沒有重新解析點，共有八份工作簿、兩份文字紀錄及一份 Word 文件；

匯入模式、欄位配對、日期、Account Mapping、假日與補班日、六個篩選情境及六份正確底稿的角色都能交叉對上。案件沒有另附授權編製人員檔，本機清單記為未提供。
GL 沒有來源行號欄，依操作說明與現行 JET 的規則由匯入流程按傳票產生行號，再由底稿比較確認結果。

**接入前的結構查核。** 舊兩案 driver、固定批次、Stage 6 至 Stage 9 的收尾程式及案件專屬差異清單已移除，不能成為新 `PrivateCase` 的通過條件。
工作簿內容比較與舊兩案裁定拆開，固定標題列與續頁規則獨立為 `LegacyWorkbookHeaderCatalog`。`Focused` 與 `Public` 不再以 `LegacyAuditParity` 名稱整批排除測試，
原本使用舊工作根的測試改用系統暫存目錄。查核也發現兩份舊報表的檔名解析用錯名稱：legacy BAS 與資料說明都確認舊 JET 實際輸出是 `INFReport` 與 `PrescreeningReport`，已依證據修正。

**現行產品流程。** `HandlerTestHost` 組裝正式的 `ActionDispatcher` 與產品處理器，`PrivateCase` 從這裡執行產品 action，不用 GUI 模擬每次匯入；GUI 能否啟動與建案仍由 `Gui` 檢查。
完整流程依序是：建案；匯入 GL、TB 與明示提供的支援檔；提交 GL 與 TB 欄位配對；執行資料驗證並匯出 ValidationReport、AccountMapping、INFReport；
執行預篩選並匯出 PrescreeningReport；提交條件篩選；最後匯出 CriteriaSelectionReport 與 WorkingPaper。六份產物都由同一條產品流程建立。
舊 `LegacyAuditParityJourney` 可重用 action 順序、結果引用與清理，但不沿用它的 case-A、case-B 身分、固定 sample seed、舊 provider 組合或「未提供授權編製人員」的決定。

**本機案件清單涵蓋的內容。** 清單格式版本 1，大小上限 1 MiB，多餘欄位、缺少必要配對、重複檔案、越界路徑與不支援的設定都會直接失敗。儲存庫文件只描述角色與規則，實際值只留在 Git 排除的本機清單：

- 案件基本設定：案件代號、資料庫實作、專案代碼、公司名稱、執行人員、查核期間及上一期起日；執行紀錄只保存去識別化案件代號。
- GL 與 TB 來源：明列相對路徑及 `replace` 或 `append`；Excel 指定工作表，CSV 或文字檔可指定編碼與分隔字元。不掃描目錄找來源。
- GL 欄位配對：除了來源欄對應與金額模式，還有核准日來源、過帳狀態範圍、人工與自動代碼及 RDE 欄位，不能從欄名相似自行推定。
- TB 欄位配對：明列來源欄對應及變動模式；`direct`、`debitCredit`、`openClose` 與 `openCloseBySide` 是不同語意，不把舊 case-B 的預設套到新案件。
- 支援檔：Account Mapping、授權編製人員、假日與補班日逐項標示有無，有提供時列出路徑。
- 篩選情境：實際使用的一至十個情境及完整條件；沒有可靠來源時不自動補值。
- 獨立正確輸出：逐一標示六份報告中哪些是比對基準。使用者已決定六份都要比較內容與版面，不能因其中一份差異較多就臨時縮小範圍。

兩者無法靠共同種子重播同一批樣本。使用者已決定依抽樣規則、實際母體與樣本有效性判定，不要求逐筆重現舊 IDEA 的隨機結果。

## 2026-08-30 後續邊界調整

Phase 7 上述七個子命令與收據保留為當時的歷史事實。依使用者後續裁定，SQL Server 中心化方向目前暫緩，只有本機可能具備 live 測試環境；
因此 runner contract 8.0 將 `Provider` 從一般 `ReleaseCandidate` 拆出。目前候選快照固定執行 Contract、Documentation、Public、Package、Gui 與 Excel；
需要證明 SQL Server 實跑相容性時，仍必須另行明示執行完整 `Provider`，缺少連線或發生 skip 都不能算通過。這項調整沒有刪除 SQL Server 產品程式，也不回寫或改稱舊收據的內容。
