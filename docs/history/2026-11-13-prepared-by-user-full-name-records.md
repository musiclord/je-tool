# 2026-11-13 建案者改記 Windows 帳號的使用者全名

這份紀錄保存使用者 2026-11-13 的原話、查到的原因、這次的修改與限制。現行規則寫在 [`../jet-guide.md`](../jet-guide.md)
第 3 節與第 7 節、[`../action-contract-manifest.md`](../action-contract-manifest.md) 的 `project.create`，以及
[`../glossary.md`](../glossary.md) 的「建案者」一列；裁定編號見 [`../rulings.md`](../rulings.md) 的 2026-11-13-04 與 2026-11-13-06。

## 使用者原話

使用者 2026-11-13 的問題，逐字：

> 另外請說明 IDEA JET 是如何抓取使用者資訊的? 也就是底稿文件要記錄的 Prepared by，因為以我目前觀察到的狀態為例，他貌似只會抓取郵箱所屬用戶名，但在 IDEA JET 中不會只抓這麼簡單，而是顯示更完整的使用者名稱，比如 `<FirstName>, <LastName> ...(TW/部門編號)` 這樣

Agent 說明兩邊的取法時，附上下面三點建議：

- 保留「寫建案者」這條裁定，只把值改成 Windows 顯示名稱。
- 取不到顯示名稱時，照舊版退回帳號短名。
- 已建立的案件存的是短名，不會自動變，只有新建的案件會用新的名稱。

Agent 接著問「要讓 Prepared by 改成照舊版取 Windows 顯示名稱嗎？」，使用者回覆：

> 改用顯示名稱

Agent 接著用選項問三題，使用者的選擇與那個選項的說明如下，題目只摘結尾：

- 「新概念與程式名稱要用哪一組？」＝「使用者全名（舊版用語）」，選項說明：
  「照舊版 IDEA JET 的 UserFullName。程式：CurrentPrincipal.UserFullName、ResolveCreatorNameAsync、類別 UserFullNameLookup、選用參數 userFullName、等待上限 UserFullNameWait」
- 「這行要怎麼處理？」（建立案件表單上方的「目前帳號：<帳號短名>。建立案件時由系統取得，不能自行更改。」）＝「維持現狀 (Recommended)」，選項說明：
  「這行與頂部徽章都繼續顯示帳號短名；建案後第一步摘要與總覽的「建案者」顯示 Windows 名稱。不改 system.whoAmI」
- 「建案時最多等多久，等不到就改用帳號短名？」＝「3 秒 (Recommended)」，選項說明：
  「啟動後先在背景開始查；建案時最多再等 3 秒，超過就用帳號短名，不提示也不擋建案」

## 查到的原因

舊版 IDEA JET 的 `legacy/idea-tool.bas` 第 1165 到 1174 行先用 `WScript.Network` 取得登入帳號與網域，
再用 `GetObject("WinNT://網域/帳號,user")` 取帳號的 `FullName`；查不到時因為 `On Error Resume Next`，全名空白，改用帳號。
驗證報告 E4、預篩選報告 E4 與條件篩選報告 D1 都寫 `"Prepared by: " & UserFullName`（第 5517、9153、10193 行），
寫的是每次匯出時執行的人。工作底稿沒有這一欄。
舊版另外把同一個全名用在歡迎視窗的問候語（第 1221、1233 行等），也寫進案件資料夾 `ProjectOverview.db` 的 `JE_STEP_USER` 表
（第 1803、6205 行等）；`idea-tool.bas` 裡這張表只寫入、沒有讀出。JET 沒有歡迎視窗的問候語，也不記每一步由誰執行。

修改前的 JET 在建案時把 Windows 帳號的短名存進 `project.json` 的 `operatorId`，三份報告的 Prepared by 寫這個短名，
不向 Windows 查全名。寫建案者而不是匯出者，是裁定 2026-10-06-02。

## 這次改了什麼

- 建案時改記 Windows 帳號的使用者全名，存進 `operatorId`，欄位名稱不變。
  起初 JET 用 Windows 名稱格式 `NameDisplay` 查帳號的顯示名稱；同一天改成和舊版相同的取法，經過見下面的「2026-11-13 追加：取法改成和舊版相同」。
- JET 啟動時就在背景開始查，不拖慢視窗出現；建案時最多再等 3 秒。
- 查不到或等超過 3 秒時，改存帳號短名，不提示也不擋建案。
- 報告的 Prepared by 仍寫建案者；建立案件表單上方的「目前帳號」、頂部徽章與 `system.whoAmI` 都照舊用帳號，案件鎖也照舊。
- 測試與 Gui、瀏覽器預覽注入合成身分時，不查這台電腦的帳號，開發者的真實姓名不會寫進測試案件與報告。

## Agent 定的做法，使用者已確認

下面兩項原本不在使用者回答過的題目裡，是 Agent 定的：

- 全名去掉前後空白後才存。
- 全名只有空白、含控制字元或超過 256 字時，改存帳號短名。

舊版只在全名完全是空字串時改用帳號（`legacy/idea-tool.bas` 第 1174 行），其他情況照原樣寫出全名。
所以全名前後有空白、只有空白、含控制字元或超過 256 字時，JET 寫出的名稱都和舊版不同。

Agent 第一次收尾時寫「現在的做法和舊版只差在一種情況：全名只有空白字元時，舊版照樣寫出空白，JET 會改存帳號短名。」，
接著問「全名的修剪與退回規則（只有空白、含控制字元、超過 256 字）要照現在的做法嗎？」，使用者 2026-11-13 回覆：

> 照現在的做法

之後的複核發現，那句說明漏了另外三種和舊版不同的情況。Agent 更正後重問，題目原文是「更正：我先前說「現在的做法和舊版只差在全名只有空白這一種情況」，
這句漏了三種。全名前後有空白、含控制字元、超過 256 字時，舊版都照原樣寫出全名；JET 會去掉前後空白，後兩種則改存帳號短名。這三種要怎麼處理？」。
使用者選「照現在的做法 (Recommended)」，選項說明：
「程式不改。三種都登錄成刻意和舊版不同的地方，和全名只有空白那一項一起記在裁定 2026-11-13-04。前後空白只影響版面；含控制字元或超過 256 字的值不像正常姓名，改用帳號短名，報告比較好讀。」

建案時最多等 3 秒，是使用者在「使用者原話」一節選的。舊版沒有自己設等待上限；查詢超過 3 秒時 JET 改存帳號短名，
Agent 依使用者選的 3 秒，一併登錄成和舊版不同的地方。

## 2026-11-13 追加：取法改成和舊版相同

使用者 2026-11-13 補充的原話如下。原話中間舉了一個名稱當範例，這裡略去，用「…」表示：

> 補充一個要點，如果可以的話會希望顯示為舊版 IDEA JET 的原因是，他會更直觀的顯示操作使用者的名稱及所屬部門…請從這個角度出發去改良目前 `je-tool` 抓出使用者名稱的方式，但同時避免過度複雜化，因為如你所見，IDEA JET 並沒有使用過度複雜的邏輯

為什麼要換取法：

- 使用者要的是舊版顯示的那種名稱，有姓名也有所屬部門。舊版的取法在公司環境用過，取得到這種名稱。
- 原本的 `NameDisplay` 取法，在公司電腦會不會回同一個名稱，查不到官方出處，公司電腦也沒有實測。
- Microsoft 的 [`GetUserNameExW` 說明頁](https://learn.microsoft.com/en-us/windows/win32/api/secext/nf-secext-getusernameexw)（2026-11-13 讀英文版）還寫
  「If the user account is not in a domain, only NameSamCompatible is supported.」，意思是帳號不在網域時不支援 `NameDisplay`。
  這和開發用電腦的實測不一致：那台電腦沒有加入網域，`NameDisplay` 卻取得到全名。

這次改了什麼：

- `UserFullNameLookup` 改成照舊版的做法：把「網域\帳號」組成 `WinNT://網域/帳號,user`，向 Windows 取帳號物件，讀它的 `FullName`。
  舊版用 `WScript.Network` 取網域與帳號；JET 從登入身分的「網域\帳號」拆出這兩個值。
- 帳號物件是 Windows 提供的 COM 物件，JET 直接用屬性名稱讀 `FullName`，沒有新增套件。原本處理緩衝區長度與重試的程式都拿掉了。
- 不另外保留 `NameDisplay` 當備用，和舊版一樣只有一種取法；取不到就存帳號短名。
- 修剪與改存帳號短名的規則、背景查詢與 3 秒上限都不變。
- 用哪一種方式向 Windows 取帳號物件，以及不保留備用取法，原本是 Agent 依使用者的方向定的。
  Agent 收尾時問「取名只用舊版那一種方式、不留原本的當備用，這樣可以嗎？」，使用者 2026-11-13 回覆「可以，照這樣」。

Agent 在開發用電腦的實測，只看成功與否、長度與耗時，不輸出名稱：

- 在 .NET 10 的一般執行與單一執行檔兩種方式下，背景執行緒都取得到全名，約 3 毫秒。
- 取到的全名和 `NameDisplay` 取到的逐字相同。
- 帳號不存在時 3 到 4 毫秒就失敗；網域找不到時要 1 到 3 秒才失敗。查詢在背景執行，所以不會卡住畫面。

交接前的複審另外補了三件事，都不改變行為：

- `RuntimeCompositionTests` 組裝 runtime 時改成注入合成身分，測試不再讀這台電腦的 Windows 帳號。
- 新增 `UserFullNameLookupWiringTests`：核對產品程式只有組裝 runtime 的地方啟動查詢，而且只在沒有注入身分時啟動；
  也核對測試與驗證工具組裝 runtime 時都有注入身分。
- `CurrentPrincipalTests` 補上兩則：建案等待全名時被取消要往外丟；查詢自己被取消時用帳號短名。

## 限制

- 已建立的案件保留建案時存的名稱；要看到使用者全名，要重新建立案件。
- 只在沒有加入網域、也沒有加入 Entra ID 的本機帳號電腦實測過。公司網域電腦與加入 Entra ID 的電腦，取到的值和需要的時間都沒有實測，
  列在 [`../development-status.md`](../development-status.md) 的「未完成項目」。
- 加入 Entra ID、沒有加入傳統網域的電腦，舊版的取法可能取不到全名；這時 JET 和舊版一樣改用帳號。這一點是推測，沒有實測。
- 向 Windows 取帳號物件的那一步沒有自動測試，因為它會讀真實帳號。自動測試只核對 JET 問的路徑與失敗處理。
