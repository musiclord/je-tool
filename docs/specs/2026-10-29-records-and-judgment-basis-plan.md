## 這份計畫在做什麼

使用者 2026-10-29 指出兩個根本原因，並認為兩者互相加重：

- 紀錄太長，又由不同 Agent 在不同時期各自寫下，事項互相混淆。原本容易解決的問題，Agent 也要來回翻找，
  甚至派子代理查歷史紀錄，只為了釐清早已定案的事。
- Agent 在沒有明確指定時自行判斷。例如理解審計業務時傾向國際標準，疏忽本地業務的客製需求；
  或只改使用者點名的地方，忽略專案其他部分。開發方針因此來回變動，目標不一致，又讓紀錄更混亂。

範圍包括前端設計、後端程式、文件紀錄與 harness 循環，有些地方要重構或重寫。原話見附錄一「2026-10-29：紀錄混淆與 Agent 自行判斷」。

這份計畫原本是預篩選收斂計畫最後的草稿。使用者同日在視窗選項回答十一題後，草稿搬成這份獨立計畫；題目與回答見附錄一

## 判斷依據

使用者 2026-10-29 的裁定，原文見附錄一：

- 審計業務的權威順序：使用者的裁定最優先；沒有裁定時照 IDEA 版 JET 的作法；舊版沒有涵蓋的，參考 KCT 小組提出的作業方式與期望。
  國際準則只用來理解名詞，或找出要問使用者的問題，不能單獨決定規則；三者都沒有答案時先問使用者。第三階段寫進 `AGENTS.md` 與
  `docs/business-logic-provenance.md`。
- 名稱：對外名稱與程式識別字都由使用者確認。對外名稱是審計員看得到的畫面、報告、底稿與檔名用語；程式識別字是程式、action 欄位、
  資料庫與測試的名稱。要確認的名稱多時，整理成本機確認頁。使用者在確認頁補充：除了前端顯示的 PBC-GL、PBC-TB、GL 這類名稱，
  資料實體、資料庫表名與程式名稱都統一命名，避免依賴對照表出錯；追問後確認，報告與底稿上照舊版範本的欄名不改。
- 審計邏輯：Agent 不自行更動審計邏輯，基本的審計邏輯要和舊版 JET 吻合。照舊版核對時要注意，舊版 JET 的 GL 母體前處理很混亂，
  例如標準作法是匯入時就移除區間外的資料，舊版因為程式品質沒有處理。這是使用者在確認頁 2-1 與 2-9 的備註。
- JET 的定位：讓審計員不必操作資料庫，就能直觀地篩選 GL 與 TB。程式只為了確保資料完整性設防呆，不因審計業務擋下；
  案件資料的缺失或風險由審計員在底稿備註，不由系統決定。這是使用者在確認頁 2-2 的備註。
- 歷史文件：壓縮成摘要。使用者原話、題目與回答、日期、數字與裁定逐字保留；Agent 寫的實作經過、驗證收據與重跑過程壓成幾句結果。
  壓縮前的全文留在 Git，摘要開頭寫明從哪一個提交找回。等裁定總表建好、每則裁定都有出處後才壓縮。
- 舊案件：刪除後重建，不寫讀取相容。

## 階段一：只讀盤點與全部回饋重核

### 要做什麼

不改程式，交出四類清單給使用者裁定：

- 名稱的來源：畫面、報告與底稿、action 欄位、資料庫與案件檔、程式識別字與測試名稱的用語，逐一標出來源是使用者指定、
  舊版 JET 與 IDEA，還是 Agent 自取；Agent 自取的附上建議名稱。註解與測試名稱裡的計畫代號另列。
- 裁定：從現行文件、計畫與歷史文件收集仍然有效的使用者裁定，標出已被取代與互相矛盾的。
- 過去的修正：把過去全部使用者回饋逐項對照現行程式與文件，找出像 PartA、PartB 這樣只改了一部分的。
- 業務判斷：找出沒有使用者裁定或舊版來源、由 Agent 依一般或國際準則決定的業務規則。

### 做法

依使用者裁定，一次派四個唯讀子代理：一個搜尋子代理盤點名稱與計畫代號；三個研究子代理依時期分讀，逐則判斷回饋與裁定是否仍有效、是否落實。
三段時期是 2026-06 到 2026-09-16、2026-09-17 到 2026-10-05，以及 2026-10-06 到 2026-10-29。子代理只讀，不改任何檔案，清單放在最後的回報裡。

研究子代理的落實判斷是初判。「只落實一部分」「未落實」「互相矛盾」的每一則，以及其他各段抽樣的幾則，由主對話對照原文與程式核對後才寫進附錄。
現行文件裡引用的裁定、三段時期的重複項、Agent 自取名稱的建議名稱，以及系統規格第 4 到第 7 節的業務規則有沒有來源，由主對話整理。
子代理的原始清單只留在本機，整理後的結果寫進附錄二到四。盤點時查到的現行文件過時說法只列進清單，不在這個階段改。

- 沒有 TB 時，驗證報告與底稿第一步要怎麼呈現逐科目比對無法執行。底稿要以舊版為基礎改良，這是使用者在確認頁 2-21 的備註。

### 確保資料完整性的防呆，保留

下列地方擋下時，都是資料不存在、彼此不一致或格式不對；照樣做下去，會產生錯的或過期的結果。

| 擋下的地方 | 現在在哪裡 | 為什麼算防呆 |
|:---|:---|:---|
| 沒有目前可用的驗證結果時，預篩選、條件篩選與匯出都擋下 | `AuditCore/CompletenessEligibility.cs`；`Application/Support/CompletenessEligibilitySupport.cs` 的 `RequireCurrentAsync` | 只在結果不存在、不完整或已過期時擋，完整性有差異不擋。使用者在確認頁 2-2 追認 |
| 結果已過期或和目前資料不一致，例如報告依據的驗證結果不是目前資料的結果，或已儲存的情境和目前版本不一致 | 錯誤碼 `stale_result`，例如 `Application/Support/ReportExportSupport.cs` 第 92 到 95 行 | 避免把舊結果當成目前的結果；重新執行就能繼續 |
| 確認 GL 配對時，依查核期間與過帳狀態篩選後沒有可測試的分錄，或借方與貸方總額都是 0，這次配對不儲存 | `Infrastructure/Persistence/Local/LocalGlRepository.cs` 的 `GlProjectionGuard`，第 284 到 306 行 | 幾乎都是選錯金額欄、查核期間或過帳狀態；存下來之後，後面每一步都沒有可測的分錄或金額。兩句訊息是使用者 2026-10-13 確認的；算成防呆是 Claude 的判斷，沒有另外問使用者 |
| 欄位配對缺少必填欄位，或設定互相衝突，例如借方與貸方代碼相同、過帳狀態欄位和要納入的值不一致 | 必填欄位由 `Domain/Rules/MappingValidator.cs` 檢查；衝突在確認配對時檢查 | 沒有這些欄位就無法建立 GL；設定衝突會把借貸方向或納入範圍算錯 |
| 規則需要的資料不足時，第四步與第五步的卡片停用並寫原因，例如需要的 GL 欄位沒有配對、沒有授權名單、沒有假日檔、沒有期末財報準備日 | `docs/jet-frontend-description.md` 第 795 行與第 868 行 | 沒有資料就算不出這條規則；其他規則照常執行 |
| 舊情境用到已不存在的欄位或已停用的寫法 | `Domain/Rules/FilterScenario.cs` 的 `FilterScenarioValidator` | 條件讀不出來，不能猜原意 |
| 篩選情境最多 10 個 | `Domain/Rules/FilterScenario.cs` 第 93 行；`Application/Handlers/FilterHandlers.cs` 第 166 到 170 行 | 舊版的進階篩選有十個條件，見 `legacy/idea-tool.bas` 第 4516 行起；底稿第四步的範本也只有 C1 到 C10 十個標記欄 |
| 沒有任何條件的情境不能預覽或儲存 | `Domain/Rules/FilterScenario.cs` 第 428 到 432 行 | 空條件不等於選取全部分錄；2026-09-17 那一輪檢查擋下的地方時也這樣判斷 |
| 輸入格式與長度，例如查核起始日不可晚於截止日、文字欄的長度上限、一次最多儲存 500 個科目的分類 | 各操作的輸入檢查；`Domain/Contracts/TextStorageLimits.cs` | 格式不對就存不進資料庫，或不同資料庫算出不同結果。文字欄的長度上限，使用者在確認頁 2-18 追認 |
| 分類還在使用時不能刪除、科目清單已被另一個操作改過、另一項作業還在進行 | 錯誤碼 `taxonomy_category_in_use` 與 `operation_in_progress` | 避免兩個操作互相覆蓋 |
| 技術上做不到，例如案件名稱已被使用、案件位置已有同名資料夾 | 建立案件、匯入與匯出 | 訊息寫出改用其他名稱或先刪除資料夾這類下一步 |
