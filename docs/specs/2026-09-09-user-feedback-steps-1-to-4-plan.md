# 建立案件到資料驗證的使用者回饋修正計畫

## 這次要解決的問題

本計畫接續 [`2026-09-07-filter-convergence-plan.md`](2026-09-07-filter-convergence-plan.md)。前一份計畫記錄的
公司設備三項驗收、空值明細待辦與其他延後事項都保留，但目前開發先處理使用者對第一步到第四步的實際操作回饋。

這次不只調整文字。每一項先核對前端、action、後端規則、資料保存與測試，再判斷是缺陷、可直接改善的操作問題，
或需要另行裁定的新能力。修正時不讀私人案件，不啟動 SQL Server，也不暫存、提交或推送 Git。

開始時的實際狀態為 `main`、HEAD `aef76db438fe83d78224c858c39ba811b18f18e7`，工作樹乾淨，
`git status --short --branch` 顯示 `main...origin/main`，沒有顯示本機與遠端分歧。

> 完整性測試"Part B" 是甚麼

> 一些文字敘述調整一下:

## 為什麼先前的 Agent 容易漏掉

1. 身分、配對草稿與使用者訊息都在前後端各留了一部分規則，卻沒有跨層不變條件。個別 action 或畫面測試通過，
   仍可能同時存在兩套互相矛盾的來源。
2. 部分前端測試只檢查函式或文字是否存在，沒有走「先設定、取消配對、再提交」等狀態轉換，因而保護不了殘留資料。
3. 後端把安全的失敗資訊集中到訊息區，但沒有把錯誤送回使用者正在操作的配對區。技術上有報錯，不等於使用者能知道哪裡要改。
4. 介面先使用可擴充的泛稱，例如「來源品質」與「Part B」，卻沒有同步說明目前實際只做哪一件事。
5. 新能力若只看 UI，容易把「多檔追加」誤當成「兩種角色資料的科目配對」，或把新增副檔名誤當成完整格式支援。
6. 建立案件的測試跟著表單欄位準備資料，沒有先寫下「操作人員只能來自目前 Windows 身分」這個不變條件。
   因此舊測試可以一直傳入假操作人員，卻沒有證明一般呼叫者無法冒名。
7. GUI 驗證也照舊表單逐欄填滿，既沒有走「只填案件名稱」的最小路徑，也把畫面上的案件名稱誤記成案件編號。
   表單改動後，它只會等待不存在的欄位直到逾時，無法指出契約真正改了什麼。

## 執行順序

1. 先為已確認缺陷加入會失敗的測試：案件選填欄位、後端身分來源、人工或自動欄位取消後清理、就地錯誤、
   攸關資料元素全選，以及不再顯示 Part A 或 Part B。
2. 修正建立案件。保留舊案件檔相容性，新增案件以目前 Windows 帳號作為操作人員；案件編號與客戶名稱改成選填。
3. 修正匯入說明的寬度與內容，不變更匯入資料量、預覽上限或資料庫寫入方式。
4. 修正欄位配對的狀態清理、錯誤位置、空白與截斷提示、攸關資料元素全選，以及日期名稱。
5. 修正資料驗證文字。完整性與借貸不平沿用使用者提供的意思；資料可靠性說明要放在 INF 抽樣與攸關資料元素的
   實際關係上，不把尚未存在的硬性前置條件寫進程式。
6. 分別研究人工或自動的補集模式、新檔案格式、兩份 TB 的資料模型。沒有相容策略與固定答案前，不用前端捷徑假裝支援。
7. 每一小步先跑對應的 `Focused`。產品與文件修改完成後，依影響範圍依序執行 Build、Contract、Public、Gui 與
   Documentation；不執行 SQL Server `Provider` 或私人案件。

## 驗收標準

- 建立案件時只有案件名稱、查核期間與資料儲存方式必填；案件編號和客戶名稱可以留空。
- 使用者不能由 `project.create` 建立請求指定另一個操作人員；新案件保存目前程序的 Windows 短帳號。
- 匯入說明能直接回答「右側為何仍能預覽」，且不暗示完整母體進入 WebView2。
- 人工或自動欄位取消配對後，不再顯示或提交前一個欄位的代碼；重新配對時從明確預設開始。
- 空白值、未歸類值及只顯示部分值造成的失敗，在 GL 配對區直接指出來源列與修正方式。
- 攸關資料元素可以全選與全部取消，核心欄位仍不會被重複選入。
- 使用者畫面與可見錯誤不再出現 `Part A` 或 `Part B`；來源品質說明明確指出目前只檢查過帳日空白。
- 未經裁定，不刪除 `voucherDate`、不把科目名稱改成選填、不把兩份 TB 當成普通追加，也不把 `.xls`、`.xlsb`
  或 Access 冒充為已支援格式。

## 新格式與兩份 TB 的研究結果

現有 `ITabularFileReader` 與 `CompositeTabularFileReader` 已把格式讀取封裝在 Infrastructure，handler 不需要知道
每一種格式的解析細節。這個邊界可以繼續使用，但 `TabularSourcePayload`、檔案檢視、前端工作表分支與錯誤文字
也要一起更新，不能只在選檔視窗加副檔名。

- Microsoft 的 [Office 檔案格式參考](https://learn.microsoft.com/office/compatibility/office-file-format-reference)
  說明 `.xlsm` 與 `.xlsx` 都是 XML 格式，差別是 `.xlsm` 可以保存巨集；`.xlsb` 與 `.xls` 是不同的二進位格式。
- Microsoft 的 [Open XML SDK 唯讀開啟範例](https://learn.microsoft.com/office/open-xml/spreadsheet/how-to-open-a-spreadsheet-document-for-read-only-access)
  使用 `SpreadsheetDocument.Open(..., false)`。JET 現有讀取器已採相同的唯讀方式和逐列 SAX 路線，不啟動 Excel。
  因此 `.xlsm` 可以沿用同一讀取器，巨集不會執行；本輪已實作並用正確的 macro-enabled workbook content type 測試。
- `.xlsb` 不是 XML，不能交給 Open XML 讀取器；`.xls` 也是舊二進位格式。兩者需要新的串流解析器，並先檢查
  函式、日期、錯誤值、共用字串、工作表列舉、大檔記憶體與套件授權，不能以改副檔名或呼叫 Excel 另存檔代替。
- Microsoft 的 [Access 與 WinForms 連線說明](https://learn.microsoft.com/visualstudio/data-tools/connect-to-data-in-an-access-database-windows-forms)
  指出 `.mdb` 與 `.accdb` 依賴 OLE DB 及相符位元的 Access Database Engine。JET 固定發行為 `win-x64`，公司雖有
  Office 365 和 Access，仍不能假設每台代表設備都已有可由 JET 使用的 64 位元 ACE。Access 還需要讓使用者選資料表
  或查詢，處理密碼及欄位 schema；它不是工作表讀取器的副檔名分支。

期初與期末 TB 分檔可做，但現有追加模式不是答案。穩健的設計至少要讓使用者明確指定期初及期末角色，分別配對
科目編號、科目名稱和餘額，再由後端按科目連接。開始實作前仍要裁定：同一份快照的重複科目要拒絕或加總；只在
一側出現的科目是否以零補齊並列為提醒；兩側科目名稱不同時採哪一個；借貸分欄的正負方向如何驗證。這些答案會
改變完整性測試，不由 Agent 自行選邊。

## 第一批修正

- 案件編號及客戶名稱改成選填，空白時案件清單和工作區改用案件名稱。建立案件的操作人員欄已移除，
  `ProjectCreateHandler` 不採用呼叫者傳入的 `operatorId`，直接保存目前 Windows 短帳號。
- 匯入說明使用較寬的段落，直接說明右側只有少量預覽，完整資料寫入案件資料庫。本輪另加入 `.xlsm`；
  `.xlsx`、`.csv` 與 `.txt` 的既有路線不變。
- `postDate` 的使用者名稱統一為「過帳日期」，並明說選填的傳票日期只供回溯過帳判斷。action 欄位名稱、資料庫欄位與
  Working Paper 的既有正準欄名沒有改動。
- 人工或自動欄位取消或換欄時，`state.js` 會重設上一欄的代碼政策；已提交摘要只在真的配對該欄時顯示代碼。
  值摘要明說空白不在清單中，截斷時也明說仍有其他值。投影失敗改用中文指出來源、列號、欄位、值和處理方式，
  並在 GL 配對區就地顯示，不只放在共用訊息區。
- 攸關資料元素增加全選及全部取消。核心配對一旦使用某個來源欄，`state.js` 立即移除同欄的 RDE 草稿，避免畫面把
  衝突藏起來後仍送出後端必定拒絕的資料。
- 第四步採用具體說明，`INF 抽樣測試` 的畫面名稱改成「資料可靠性測試」。完整性訊息不再顯示 Part A 或 Part B，
  「來源品質」改成實際內容「過帳日空白」。使用者提供的「GL 發生數」改為「GL 發生額」，因程式實際比較的是
  金額加總，不是分錄筆數。

人工或自動的補集模式尚未實作。legacy 只接受 `0` 或 `1`，其他值直接警告；現行版允許多個代碼，但仍要求每個
非空白值明確歸類。若改成「列出人工，其餘算自動」或相反，拼錯及新出現的非空白代碼也會自動落入另一類。
這是資料品質取捨，需由使用者決定是否接受；空白值仍建議維持失敗，不靜默歸類。

## 架構複審結論

- 案件名稱仍是 `projectId` 及案件資料夾的必要識別；案件編號與客戶名稱只保留為選填顯示資訊。案件清單、工作區
  抬頭及載入訊息都以案件名稱為準，空白顯示資訊不再被拿來當識別。舊 `project.json` 的欄位形狀沒有改動。
- 操作人員由程式組裝入口建立的 `CurrentPrincipal` 提供，`ProjectCreateHandler` 只讀它的短帳號。
  前端沒有操作人員輸入框，舊呼叫即使傳入 `operatorId` 也不能改變保存結果。報表測試改為固定注入測試身分，
  沒有把產品改回信任建立請求。
- `.xlsm` 沿用既有 `ITabularFileReader` 邊界，由 Open XML 讀取器唯讀處理。選檔、檔案檢視、請求欄位適用性、
  預覽、正式匯入及私人案件格式白名單一起更新；沒有啟動 Excel 或執行巨集。二進位 `.xls`、`.xlsb` 與 Access
  仍留在不同讀取器及資料選擇設計之後，不用副檔名捷徑冒充支援。
- 人工或自動政策現在跟著來源欄生命週期走。共用 `state.js` 在簡易配對、對照表格及整份草稿替換三個入口都檢查
  來源是否改變；GUI 另實際把代碼設定改壞、取消來源欄、核對預設值回復，再還原已提交版本。
- RDE 核心欄衝突由 `state.js` 立即清除，後端仍作最後驗證。全選沿用既有欄位身分，來源欄名以無原型字典處理，
  避免 `__proto__` 之類的合法欄名誤入 JavaScript 物件原型邏輯。
- 日期改的是使用者名稱，不是 action 欄位名稱、資料庫欄位或報表正準欄名。完整性內部資料仍保留 Part A 與 Part B，
