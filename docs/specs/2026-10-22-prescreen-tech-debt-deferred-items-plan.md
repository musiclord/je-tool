## 這份計畫在做什麼

2026-10-22 使用者把架構文件計畫結案後，要求依延後清單起草下一階段的計畫，範圍先列出來讓使用者勾選。使用者勾選了 11 項延後事項；
同日又追加兩項，一項是第五步能不能使用未配對的欄位，另一項是資料預覽要列出已配對的選填欄位、呈現資料庫保存的值。共 13 項。

這 13 項大多不是新需求，而是前幾份計畫開發途中查到、當時決定先延後的事；最早的一項，是 2026-08-20 預篩選條件併入進階篩選的計畫結案時，
留到以後再做的預篩選收斂。每一項當初怎麼出現、之後的裁定有沒有改過，寫在各階段的「來由」；裁定改過的地方，另外整理在「和當初延後時說法不同的地方」。

同日使用者要求以架構師的角度整理，找出每一項真正的問題核心，避免拆東牆補西牆。整理後發現，大多是同一件事在程式裡定義了不只一次，
例如 GL 的範圍、哪些欄位可以用、同一條審計規則的寫法。所以每個階段都先找到定義那件事的地方，改在那一層，其他地方改用那一份定義，
不在出問題的那一行另補例外。13 項依問題核心排成十一個階段。

修改分兩種做法：盤點與評估類的事項，先交出清單和建議，由使用者裁定後才修改；修正類的事項，先寫測試保存第一次失敗，再改程式。

整理的依據：依[業務邏輯來源與裁決程序](../business-logic-provenance.md)的權威順序，先讀現行程式與測試，再讀現行文件，最後才看歷史文件與 legacy。
2026-10-22 整理時做了三份只讀盤點：讀取 GL 分錄表的全部查詢有沒有限定在 GL；「欄位是否已配對」在前端與後端各在哪裡判斷；
預篩選規則的定義、第五步三個入口的對應、報告各頁的來源與 legacy 段落。另外逐檔讀了失效政策、情境檢查、日期解析、資料預覽、
對話框與焦點的程式，以及系統規格第 4 到第 6 節、第 9 節與 KCT 流程文件。

## 階段二：GL 母體只有一個述詞

### 要做什麼

第二步匯入授權編製人員清單後，畫面寫「有效名單 N 位中，有 M 位出現在 GL 傳票建立人員」。這個 M 原本也算進只出現在 GL(未納入測試) 的人員；
改成只算 GL，畫面文字不變。另外加一個架構測試掃描產品原始碼，以後再有查詢讀分錄表卻漏了 GL 的範圍，建置時就會被擋下。

### 來由

- 2026-10-21 [架構文件與圖表維護計畫](../history/specs/2026-10-16-architecture-documentation-plan.md)盤點總帳日期在期末之後的分錄時查到，
  和期後無關，列進開發現況的延後事項。當時寫的重啟做法是先用 SQLite 與 DuckDB 的合成資料重現，再決定人數只算 GL，或改寫畫面文字。
  預篩選的非授權編製人員比較只用 GL，不受影響。
- 2026-10-22 使用者勾選「授權人員比對人數」。整理時選了只算 GL、不改文字，因為畫面文字本來就寫 GL，action 契約對 `matchedPreparerCount`
  的說明也已寫 GL。這是整理時的決定，沒有另外請使用者選「改文字」。附錄一的題目稱這個階段為主題一。

### 問題核心

GL 的範圍由 `GlEffectivePopulation.SqlPredicate()` 唯一決定，也就是 `is_effective = 1`。系統規格第 4 節寫明驗證、預篩選、條件篩選與完整性彙總
共用已保存的 GL，不各自重算。

2026-10-22 盤點 `src/JET/JET` 裡讀取 `target_gl_entry` 的查詢約 90 條，沒有限定 GL 而且看不出理由的只有一條：
[AuthorizedPreparerMetadataSql.CountMatchedAsync](../../src/JET/JET/Infrastructure/Sql/AuthorizedPreparerMetadataSql.cs) 的子查詢只寫 `g.created_by IS NOT NULL`，
本機與 SQL Server 的倉儲共用這段 SQL。其他沒有限定的查詢都有明確用途：GL(未納入測試) 的預覽刻意讀 `is_effective = 0`；
驗證母體摘要一次算出原始、GL 與未納入三組合計；缺總帳日期的來源品質是 `ValidationProcedures` 註解寫明的唯一例外；
結構升級、依 entry_id 回取原始列、匯入當下對整批剛寫入的列偵測空白欄，都要讀全部的列。

### 結果

2026-10-22 完成。

- `CountMatchedAsync` 的子查詢加上 `GlEffectivePopulation.SqlPredicate("g")`，畫面文字與 action 契約不改。
- `Batch3AuthorizedPreparerTests` 新增一組固定答案，SQLite 與 DuckDB 各跑一次：一位名單人員只出現在總帳日期早於查核期間的分錄，
  修正前兩種資料庫都算成 3 位，修正後是 2 位。
- 新增架構測試 `GlEffectivePopulationReadGuardTests`，比照 [ExcelTextOwnershipTests](../../src/JET/tests/JET.Tests/Architecture/ExcelTextOwnershipTests.cs)
  的做法掃產品原始碼：把原始碼依分號與大括號切成陳述句，每句讀 `target_gl_entry` 的 SQL 都要帶 `is_effective`、`GlEffectivePopulation.SqlPredicate`、
  包裝它的 `GlPopulationScopeSql.Predicate`，或名稱含 population 的參數。刻意讀全部列的 18 處列在測試的允許清單並附理由，清單過期也會失敗。
  修正前只有授權名單比對這一條沒有理由。階段四把兩個 GL 倉儲的整欄空白偵測合成 `GlMappedColumnAudit` 一筆，現在允許清單是 17 處。
- 2026-10-28 複審時補了兩件事。第一，資料預覽 GL 頁把表名當參數傳進共用的查詢，掃描檢查看不到它；查詢改成表名直接寫在 SQL 裡、
  母體條件由頁別決定，檢查也多一項：產品程式不得把分錄表名當成字串值傳遞，列出的幾個非讀取用途除外。第二，附錄三派給這個階段的
  「母體摘要在兩邊重列三種日期未納入原因」當時沒有處理，現在由 `GlEffectivePopulation` 依未納入原因的分類產生「日期不符」那組原因，
  兩個驗證倉儲都引用它。SQL Server 這兩處只改不執行，記在封存文件。
- 第一次失敗的收據記在兩個測試旁的註解。`Focused` 與 `Public` 通過。SQL Server 共用同一段 SQL，只改不執行。

### 問題核心

後端已經有唯一的組裝點 [FilterValidationContextFactory](../../src/JET/JET/Application/Handlers/FilterHandlers.cs)：
用 `JetFieldCatalog.HasMappedGlSemanticField` 算出 `AvailableGlFields`，以及傳票建立人員、傳票核准人員、人工或自動分錄、傳票摘要四個旗標。
問題在於這份答案沒有被所有人用：

- 驗證器只在少數組合檢查。`FieldValueConditions` 只對「空白」與「非空白」查 `AvailableGlFields`；`FilterScenario.cs` 的 `ValidateRule`
  只對 KCT 的傳票建立人員清單、KCT 的空白摘要、人工收入分錄、編製等於核准，以及兩個需要傳票建立人員的預篩選鍵要求已配對。
  其他比較方式用到未配對欄位時不檢查，結果可能是 0 筆，也不提醒。
- 前端沒有拿到這份清單。`filter-step.js` 的 `glFieldMapped` 自己看 `committed.mapping`，而且只給傳票核准人員與傳票建立人員用；
  欄位按鈕、KCT 卡 E、G、J、D、預篩選分頁的空白摘要、常用查核條件的空白摘要、人工分錄、核准日非營業日，都不看配對狀態。
  前端描述前置條件也用了三套寫法：`FILTER_RULE_TYPES` 的 `accountMappingRequirement`、常用查核條件的 `requires`、預篩選選項的 `requiresCreateBy` 這類旗標。
  同一段程式的註解寫「未配對的欄位或沒有假日清單不在此列」，但同一個函式會檢查傳票核准人員與傳票建立人員兩個欄位，註解和行為不符。
- 第四步另算一次。`PrescreenRunHandler` 自己算有沒有核准日與傳票建立人員，`PrescreenProcedures` 依此寫不適用原因；
  同一條「財報準備日起核准」在第四步要求核准日已配對，在第五步的 `ValidatePrescreen` 只看期末財報準備日。同一條規則在兩步給出不同答案。
- 第四步無法執行時的說明也拆成兩層。後端 `PrescreenProcedures` 寫原因，`validate-step.js` 每條規則再接一句補救文字，`detailHtml` 把兩句都畫出來。
  十條規則裡，四條的兩句互相矛盾，三條的補救文字永遠不會出現，三條同一件事說兩次，逐條對照在附錄三。
  完整性測試卡也一樣：後端的原因已經寫了請重新執行資料驗證，前端又接一句同樣意思的話。
- 週末與假日兩張卡各合併過帳與核准兩側，`PrescreenRunHandler` 取原因的方法卻不同：週末卡取核准側的原因，假日卡只取過帳側的原因。
  前端看到原因就把整張卡當成無法執行，也不提供明細。所以缺傳票核准日的配對時，週末卡整張顯示無法執行，總帳日期那一側的命中筆數與明細都看不到；
  假日卡照常顯示，核准側的提示由 `pairCountStatus` 另寫一句。這是 2026-10-22 讀程式的結論，還沒有用執行結果確認。
- 傳票文件項次沒有來源時由系統自動編號，但 `AvailableGlFields` 不含它；使用者 2026-10-22 裁定自動編號算已配對。
  傳票核准日選「與總帳日期相同」時，工廠用一句特例處理，不是欄位目錄說的。
- GL 必填文字欄整欄空白的偵測是另一份手寫的欄位清單。[LocalGlRepository](../../src/JET/JET/Infrastructure/Persistence/Local/LocalGlRepository.cs)
  在確認配對的同一個交易裡，對傳票號碼、會計科目編號、會計科目名稱與傳票摘要四欄各寫一段判斷，SQL Server 的 GL 倉儲另寫一份；
  結果是不擋操作的提醒，用來發現可能配錯的欄。

### 做法

1. Domain 新增一張「規則需要什麼」的表，和 `JetFieldCatalog` 放在同一層：每個條件型別、預篩選鍵、KCT 預設與常用查核條件，
   寫明需要哪些 GL 語意欄位、需不需要期末財報準備日、授權名單與科目分類。第四步的不適用原因、第五步的驗證器、前端的停用原因都讀這一張表。
   階段九收斂規則時，這張表就是每條規則定義的一部分。
2. `AvailableGlFields` 的算法改由欄位目錄決定：欄位有來源欄，或欄位目錄標示它有衍生來源，就算可用。
   傳票核准日的「與總帳日期相同」與傳票文件項次的自動編號都在目錄裡標示，工廠不再寫特例。
3. `project.load` 與 `mapping.commit.gl` 的回應加 `availableGlFields`，內容就是後端算好的清單；前端存進 state，
   `Ui.FilterValues.fields(state)` 帶 `mapped` 旗標，`glFieldMapped` 改讀這份清單。欄位按鈕、常用查核條件、範例、KCT 卡、
   預篩選分頁與條件卡片的欄位下拉，都依同一份清單與同一張表停用並寫原因。三套前置條件寫法收成一套 `requires`，
   上面那段和行為不符的註解一併改成現況。前端只鏡射後端的答案，不再自己推。
4. 驗證器改成一條規則：凡條件引用核心 GL 欄位，不論比較方式，都要求在 `AvailableGlFields`；原因沿用既有的
   「「欄位名稱」尚未選擇來源欄」。待修正清單不必另寫：開案時的逐筆檢查用同一個驗證器，用到未配對欄位的舊情境自然列進清單，
   改好之前矩陣、條件篩選報告與第六步照待修正的規則鎖住，下一步的寫法比照「攸關資料元素欄位已不在欄位配對中」。
5. 停用時的文字由後端的原因句決定，前端不另造句；下方多一句可以回欄位配對補上。
6. 第四步的補救說明併進後端的原因句，一個原因一句，寫出缺什麼、到哪裡補；原因句和第五步、前端停用原因一樣讀「規則需要什麼」表。
   前端只顯示後端的句子：拿掉 `detailHtml` 接補救文字的段落與它的樣式，刪掉三個執行不到的分支，完整性測試卡也不再另接一句。
   週末與假日兩張卡改用同一個合併原因的方法，分開「整張卡無法執行」與「只檢查了其中一側」兩種情形。只有一側能檢查時，
   照常顯示那一側的筆數與明細，並附後端那句說明；`pairCountStatus` 裡前端自己寫的核准日提示改用後端的句子。
   回應要多帶欄位時，照 action 契約一起改。`validate-step.js` 檔頭註解改成第四步。
7. 第五步沒有匯入假日檔的情形不在 2026-10-22 的改裁定裡，照 2026-10-04 的裁定不擋。
8. GL 整欄空白偵測照 TB 的做法建共用的 GL 版本，欄位清單由欄位目錄產生，本機與 SQL Server 的 GL 倉儲都改用它。

### 舊情境的排除區

2026-10-22 讀程式查到的根因：後端的 [FilterScenarioPayloadParser](../../src/JET/JET/Application/Support/FilterScenarioPayloadParser.cs)
對帶排除區的定義是明確拒絕，寫「使用了已移除的「排除區域」，請改用條件中的「不屬於」或「不在區間」」，開案時這句也會列進待修正清單；
前端 `projectWireScenario` 也會把草稿上的排除區原樣送出。真正丟掉它的是
[FilterScenarioSummaryRenderer](../../src/JET/JET/Application/Support/FilterScenarioSummaryRenderer.cs)：送到前端的情境摘要只帶名稱、動機、
條件組、來源與保存時間，沒有排除區，所以編輯器讀不到，存回去時就沒有了。

做法：摘要照原樣帶出排除區；編輯器把它畫成唯讀的「舊排除區」區塊，寫上後端那句原因，旁邊一顆「移除」按鈕；
審計員沒移除就儲存，後端照既有行為擋下；移除後才能儲存。不自動轉成否定條件，因為條件組之間可以選「符合任一」，
整個情境層的排除沒有一定等價的寫法。

## 階段五：資料預覽依欄位目錄與配對呈現資料庫原樣

### 要做什麼

右側資料預覽的 GL 與 GL(未納入測試) 頁，除了現在固定的幾欄，也列出全部已配對的選填欄位與攸關資料元素欄位，兩頁列同一組欄位，
欄名和欄位配對畫面相同。資料預覽裡的金額固定顯示四位小數，例如 1,234.5000；其他畫面、報表與底稿不變。
另外改寫三句叫審計員調整「金額小數位數」的錯誤訊息，因為案件沒有這個設定。

### 來由

- 2026-10-02 使用者裁定畫面統一兩位小數加千分位，報表與底稿不變。
- 2026-10-22 使用者追加這一項，認為資料預覽應該讓操作者直接看到資料庫原樣，避免因技術問題或系統差異誤判；原話在附錄一。
  同日用視窗選項裁定的六題裡，四題是資料預覽：加列已配對的選填欄位與攸關資料元素，不列未配對的欄位，也不分借方與貸方金額兩欄；
  金額固定顯示四位，只改資料預覽，沒有選建議的「至少兩位最多四位」；來源超過四位小數時不提醒，沒有選建議的「提醒列數與列號」，
  只在系統規格寫明四捨五入；叫審計員調整小數位數的錯誤訊息一併修改。
- 整理時排在階段四之後，因為可用欄位要用階段四算出的同一份清單。附錄一的題目稱這個階段為主題四。

### 問題核心

2026-10-22 讀 [LocalDataPreviewRepository](../../src/JET/JET/Infrastructure/Persistence/Local/LocalDataPreviewRepository.cs) 核對的現況，
SQLite 與 DuckDB 共用這段程式，SQL Server 另有一份：

- GL 頁固定列九欄：傳票號碼、傳票文件項次、總帳日期、會計科目編號、會計科目名稱、傳票摘要、金額、借貸別，以及人工或自動分錄的判定。
  GL(未納入測試) 頁固定列十欄，有過帳狀態與未納入原因，沒有人工或自動分錄。標準化分錄另外存了傳票核准日、分錄來源模組、
  傳票建立人員、傳票核准人員、過帳狀態與分開的借方貸方金額，攸關資料元素欄位存在另一張表；這些都沒有列出。
- 欄位清單在三處寫死：本機倉儲、SQL Server 倉儲，以及只共用 GL 九欄的 `DataPreviewColumns`。前端 `data-preview.js` 另有一張欄名表，
  名稱和欄位目錄不同，例如「項次」「科目編號」「摘要」對上欄位配對畫面的「傳票文件項次」「會計科目編號」「傳票摘要」；
  數字欄靠掃值猜，金額格式綁在資料集與欄 id 上。
- 欄位目錄 `JetFieldCatalog` 已經有每個欄位的語意、型別、儲存欄與標籤，預覽沒有用它。
- 金額在資料庫裡存成乘以 10,000 的整數，保留到小數第四位；來源超過四位小數時匯入四捨五入到第四位，見
  [MoneyScaling](../../src/JET/JET/Domain/Primitives/MoneyScaling.cs)。畫面一律兩位小數加千分位，是使用者 2026-10-02 對 P3-4 回答「同意建議」，
  也就是畫面統一兩位小數加千分位，報表與底稿不變，見[使用者回饋計畫](../history/specs/2026-09-17-user-feedback-and-workflow-review-plan.md)。預覽的金額由程式從整數換算，不經過資料庫的小數運算。
- 日期在匯入時統一寫成 `yyyy-MM-dd`；文字檔解碼失敗時可以改選編碼重試；Excel 檔裡 `_xHHHH_` 寫法的字元在讀入時還原。
  不同資料庫之間的小數點差異目前不會發生。
- 核對時另外查到：攸關資料元素的金額錯誤訊息寫「不是有效的金額，或小數位數超過案件設定」，金額超出範圍的兩句寫「或調整案件的金額小數位數」。
  超過四位小數的值會被四捨五入，不會因此失敗，案件也沒有可以調整位數的設定。訊息在
  [ProjectionErrorReasons](../../src/JET/JET/Domain/Rules/ProjectionErrorReasons.cs)。

### 做法

1. 建立一份「預覽欄位計畫」：給它已確認的配對與攸關資料元素欄位，就產生有序的欄位清單，每欄有識別、顯示名稱、型別與 SQL 來源。
   可用欄位用階段四的同一份 `AvailableGlFields`；顯示名稱取自欄位目錄，和欄位配對畫面同名。本機與 SQL Server 的 GL 與 GL(未納入測試) 查詢
   都由它產生 SELECT 清單，三處寫死的欄位清單收成一處。
2. 攸關資料元素的值存在 `target_gl_rde_value`，主鍵是分錄與欄位；每個已配對的欄位用一個相關子查詢或 LEFT JOIN 取值，一頁 200 筆不會慢。
3. 回應加欄位的顯示名稱與型別，前端 GL 與 GL(未納入測試) 的欄名與對齊改讀回應，不再掃值猜數字欄；前端那張欄名表只留其他資料集。
4. 列哪些欄：已配對的選填欄位、已配對的攸關資料元素欄位，接在核心欄位後面；未配對的不列，借方與貸方金額分欄也不列；
   兩頁列同一組欄位，GL(未納入測試) 另有未納入原因。人工或自動分錄改成有配對才列，兩頁一致。傳票文件項次自動編號時照舊列出。
5. 資料預覽裡的金額固定顯示四位小數，例如 1,234.5000，含 GL 統計列與 TB 的變動金額；其他畫面維持兩位，報表與底稿不變；
   PBC-GL 與 PBC-TB 照舊顯示來源文字。
6. 來源金額超過四位小數時照舊四捨五入，匯入時不提醒；四捨五入的規則寫進系統規格。
7. 上面那幾句錯誤訊息改寫，拿掉不存在的設定，改成審計員實際能做的事，例如確認來源金額或改選欄位。

### 做法

- 欄名在第幾列：匯入選項多收「欄名在第幾列」，每個來源的畫面多一格，檢視與預覽也帶這個值；文字檔讀取器補上略過列數，Access 不適用。
  讀 Excel 的程式已經用 `TabularSourceRequest.LeadingRowsToSkip` 支援，以實際列號計算含空白列。`TabularSourcePayload.Parse` 現在只收工作表、
  編碼與分隔符，契約註解寫「不對一般匯入開放新的前置處理選項」，這兩處跟著改。它只解決表頭，表尾的合計列仍會被當成分錄匯入，
  審計員還是要在 Excel 刪。
- 往下填補空白：在投影讀暫存列的串流上包一層狀態，記住每個勾選欄最後一個非空白值，本機與 SQL Server 兩條投影路徑都要；
  投影器是純函式，狀態放在串流包裝層。勾選的是已配對的欄位；填了幾格寫進配對確認的回應與驗證摘要；PBC-GL 保持原樣，GL 是整理後的值。
  多來源追加時不跨來源延續，每個來源第一列的空白就是空白；填補以列序為準，依賴來源檔的列序正確；只填勾選的欄位，其他欄不動。
  改選擇只重新投影，走既有的失效規則。
- 接合：開發現況的延後事項改寫接合的結論與重啟條件。日後要做時，第一個要裁定的是「一列來源資料」的定義，不是 SQL 怎麼寫。

## 階段七：日期解析一套規則，前後端同一份固定答案

### 要做什麼

GL 的日期欄或第五步的日期清單出現 `2025`、`2025.12` 這類純數字時，現在會被當成 Excel 日期序列值，換成 1905 年的日期。
改成純數字不再當成日期：沒套日期格式的數字儲存格與文字檔裡的數字，確認配對時列為無法辨識並寫出列號，審計員在 Excel 把欄位設成日期格式後重新匯入。
第五步的日期清單照同一規則。前後端讀同一份日期固定答案，以後一邊改了規則，另一邊的測試就會失敗。

### 來由

- 2026-10-19 使用者在[延後事項清理計畫](../history/specs/2026-10-19-deferred-items-cleanup-plan.md)，對 GL 日期欄出現「050315」這類六位數字的情形選「維持現狀」。
- 2026-10-20 同一份計畫提交前，複審的子 Agent 從程式推論出 `2025`、`2025.12` 這類純數字會先被當成 Excel 序列值；它不在當時選項的範圍，
  列進開發現況的延後事項，沒有測試重現。當時寫的重啟做法是先用 SQLite 與 DuckDB 的合成資料重現，再請使用者裁定純數字要不要另外視為無法辨識的日期。
- 2026-10-22 使用者勾選「純數字年份當成序列值」，同日用視窗選項裁定「原則式」與「共用固定答案」，沒有選「例外式」「維持現狀」與「前端不再解析」。
  附錄一的題目稱這個階段為主題五。

### 問題核心

[DateNormalizer](../../src/JET/JET/Domain/Primitives/DateNormalizer.cs) 的判定順序是 ISO、顯式西元、民國年、Excel 序列值、寬鬆解析。
第四關把 1 到 2,958,465 之間的任何純數字都當序列值，所以 `2025` 變成 1905-07-17，`2025.12` 也是 1905 年，走不到要求寫出四位數年份的寬鬆解析。

2026-10-22 再讀讀取器查到：日期型儲存格已經由讀取器依儲存格的數字格式換成 ISO，`OpenXmlSaxTableReader` 與 `BinaryExcelTableReader` 都是；
只有超出 1900 到 2100 年的才用帶小數點的序列文字交給投影報錯。所以走到第四關的純數字，是沒套日期格式的數字儲存格，或文字檔裡的數字，
在這一層分不出它是年份還是序列值。前端 `filter-values.js` 的日期清單另有一份鏡像規則，改一邊要改兩邊。

### 做法

- `DateNormalizer` 拿掉序列值這一關，不再把純數字當日期。日期型儲存格由讀取器依儲存格格式換算，這已是現況，不受影響；
  文字檔或沒套格式的數字儲存格，在確認配對時列為無法辨識並寫出列號，這也是既有機制，訊息已寫「請確認來源的日期格式，或改選正確的日期欄」。
  審計員在 Excel 把欄位設成日期格式後重新匯入，和「匯入前整理留在 Excel」的裁定一致。
- 讀取器對超出 1900 到 2100 年的日期型儲存格，現在用帶小數點的序列文字交給投影報錯；拿掉序列值關卡後這條路要重看：
  投影遇到它仍要報「無法辨識為日期」並寫出列號，不能因為少了那一關而變成別的訊息或不報。
- `filter-values.js` 的日期清單同步拿掉序列值換算，其餘規則不動。
- 建一份前後端共用的日期固定答案：JSON 夾具列出原文與預期結果，含 ISO、顯式西元、民國年開關兩種、純數字、帶千分位、
  短年份與寬鬆寫法；C# 的 `DateNormalizer` 測試與前端 `filter-values.js` 的測試都讀同一份，一邊改了規則另一邊就失敗。
  既有分散在兩邊的日期案例併進夾具，不刪案例。

### 驗證

- 先用合成資料重現 `2025` 變成 1905 年，保存第一次失敗；SQLite 與 DuckDB 用純數字日期欄確認配對，核對列出的列號與訊息。
- 既有序列值測試改成無法辨識時，寫明原因與第一次失敗。
- 共用夾具的 C# 與前端測試；階段結束跑 `Focused` 與 `FrontendMapping`。完整的 `Public` 等階段九做完再跑。
- 文件：系統規格第 6 節「貼上日期清單」那段、action 契約對 Excel 序列值的說明，以及[測試環境交付說明](../test-environment-notes.md)，
  都改成純數字不當日期；改完跑 `Documentation`。

  讀取器對超出 1900 到 2100 年的日期型儲存格交給投影的序列文字（例如 73416.0）同樣在這裡拒絕，投影照舊報「無法辨識為日期」並寫出列號；

## 階段八：對話框與焦點交接只有一套

### 要做什麼

1. 流程總覽與刪除案件對話框同時開著時，一次 Escape 只關最上層，Tab 也只在最上層循環。現在一次 Escape 兩個都關，只是目前操作上碰不到。
2. 第三步欄位配對的人工分錄代碼與過帳狀態，按「讀取來源值」後，焦點先交給讀取中的提示，再交給讀出的代碼清單，清單留在畫面裡。
   現在焦點落到頁面本身，代碼清單有時被捲出畫面。

### 來由

- 一次 Escape 關兩層：2026-10-13 流程總覽改用共用的焦點圈限後，複審從程式推論出這件事，經過記在
  [KCT 需求計畫](../history/specs/2026-10-06-kct-gl-requirements-plan.md)第八節「流程總覽打開時焦點沒有進入對話框」。目前碰不到，
  因為刪除鈕只在案件清單上，總覽開著時蓋住它。開發現況當時寫的重啟條件，是新增可以疊在總覽上的對話框，或做共用的對話框堆疊時一併處理。
- 讀取來源值後的焦點：2026-10-14 KCT 需求計畫正式整合時在 Gui 查到；當時 Gui 改成先找到清單再操作，產品沒有修改，列進延後事項。
  重啟時先寫一個按下後檢查焦點位置的前端測試，保存第一次失敗。
- 焦點交接的規則：2026-10-13 KCT 需求計畫交接到新的工作階段時，列下的待辦寫「焦點要回到同一個控制項；控制項不見了，就落在接替它的控制項上，

  步驟模組用 `JetFocus.deferFirst` 把焦點交給接替它的控制項。這份計畫先前把這條規則寫成使用者 2026-10-13 的原話，重寫時查不到那句原話，
  改成上面查得到的出處。
- 2026-10-19 延後事項清理計畫依使用者的要求，把同功能卻各做一套的前端元件收成一套，例如尚未儲存的對話框與選單；對話框堆疊照同一個方向做。
- 2026-10-22 使用者勾選「Escape 一次關兩層」與「讀取來源值後焦點掉落」。附錄一的題目稱這個階段為主題六。

### 一次 Escape 關兩層的現況與做法

現況有三套對話框各自接鍵盤：刪除案件對話框在元素上接 Escape 與 Tab；「尚未儲存」對話框在 document 的捕獲階段接；流程總覽也在捕獲階段接，
並用 `overviewCoveredByDialog` 猜上面有沒有別的對話框。那個函式把根元素裡的 `.modal` 排除，而刪除案件對話框就在根元素裡，
所以總覽和它同時開著時兩個都處理 Escape。總覽的註解還寫第五步的日期多選用 showModal 開原生對話框，但那個對話框在更早的改版已經拿掉。

做法：`app.js` 的 `JetFocus` 擴成對話框堆疊。開啟時登記元素、關閉函式與 Tab 圈限範圍，關閉時移除；整個頁面只有一個捕獲階段的鍵盤監聽，
Escape 與 Tab 只交給最上層；原生對話框開著時不處理，這是留給日後的防衛判斷。三個對話框改用登記，各自的監聽與 `overviewCoveredByDialog` 移除。

### 讀取來源值後焦點的現況與做法

現況是 `renderContent` 用 `captureContentFocus` 與 `findContentFocus`，依 `data-focus-key` 或控制項特徵，把焦點放回重繪後的同一個控制項。
控制項重繪後不見或停用時沒有通用的接手，各處自己呼叫 `JetFocus.deferFirst` 指定接替者，全站有二十多處。
「讀取來源值」按下後按鈕換成「讀取來源值中…」的文字，沒有接替者，焦點掉到頁面本身，外層有時把代碼清單捲出畫面。

做法：控制項可以用 `data-focus-successor` 宣告接替者的選擇器清單；`captureContentFocus` 記下它，`findContentFocus` 找不到原控制項時依序找接替者，
沿用 `deferFocusFirst` 可見且可按的規則。人工分錄代碼與過帳狀態的兩顆「讀取來源值」按鈕宣告接替者：先是讀取中的提示，提示要能拿焦點，
再是讀出的值清單第一個控制項。既有的 `deferFirst` 呼叫不必一次改完，以後新按鈕用宣告就好。

### 驗證

- 前端測試：兩層對話框一次 Escape 只關上層，Tab 只在上層循環，關閉後焦點回原處；按「讀取來源值」後焦點的位置與清單在可見範圍內。

- 產品修好後，Gui 腳本 2026-10-14 的繞法改回直接操作。

## 階段九：審計規則的單一定義與預篩選收斂

### 要做什麼

同一條預篩選規則，現在最多有四種寫法：第四步的逐筆標記、第五步「預篩選」分頁的條件、第五步常用查核條件或 KCT 預設用欄位條件另寫的版本，
以及預篩選報告的 R 頁。這個階段讓每條規則只有一個定義，第四步、第五步三個入口與報告都呼叫它；規則的身分只登錄一份；
系統規格、action 契約與畫面的規則數量一致。預篩選報告與 14 條規則都保留。另外用 JET 實際的查詢路線，在 SQLite 與 DuckDB 各量一次
「財報準備日起核准」的速度。

### 來由

  預篩選報告暫時完整保留、改成純可選的輸出；報告的長期去留與預篩選條件的最終棄用清單，留待未來另場收斂。紀錄在
  [2026-08 的開發現況](../history/superseded/development-status-2026-08.md)。

  附錄一的題目稱這個階段為主題三。

### 問題核心

同一條審計規則目前最多有四種存在形式，就是上面「要做什麼」列的四種。規則的身分也有三份登錄：
`PrescreenRules` 的 wire key、`RuleCatalog` 的命名登錄表、`FilterConditionLabels` 與前端的鏡像。規則數量在各處不一致：
系統規格第 5 節寫 13 項，`JetAuditProgram` 的程序清單 14 條，逐筆鍵 12 個，第四步畫面 12 張卡。

2026-10-22 盤點到的對應，逐條規則的完整對照在附錄二：

- 「預篩選」分頁的 12 個鍵全部經 `FilterCompilation.BuildPrescreenRule` 呼叫 `GlRulePredicates`，和第四步計數用的是同一組方法。
- 常用查核條件只有「財報準備日起核准的分錄」與「未預期的借貸組合」走同一組方法。週末、假日、空白摘要、摘要字詞、金額尾數零
  是用欄位條件另寫的版本，其中假日的 EXISTS 子查詢和 `GlRulePredicates.Holiday` 是兩份相同形狀的 SQL；較少使用的科目與人員走統計條件。
- KCT 的 E、F、G、H、I 是欄位條件的預設值，不呼叫預篩選的方法。KCT C「收入貸方但缺少一般對方科目借方」是「未預期借貸組合」的變體：
  對方科目不含現金、對方借方的判定用大於或等於零。這是使用者裁定的差異，系統規格第 6 節寫明現金不算一般對方科目，不是技術債。
- 不同寫法算出同一結果，目前靠等價測試鎖住：`FilterSinglePurposeEquivalenceTests`、`GlRuleSqlEquivalenceTests`、`PrescreenPreviewParityTests`。
- 預篩選報告的範本只有一張摘要表，R1 到 R7 由 `LegacyReportWriter.Prescreen` 動態產生：R1 到 R4 與 R7 用同一組述詞取出命中的分錄再回取原始列，
  R5 與 R6 是彙總；摘要表第 14 到 16 列是已退役的 A2 到 A4，寫「N/A（現行 JET 已移至 Step 4）」。報告預設勾選、可取消，不產生也能繼續篩選與匯出底稿。

既有限制：預篩選報告的欄位來源忠實性裁決只涵蓋 R2 明細家族與 R6，R5 的彙總頁標題維持既有輸出名稱。

### 做法

- 摘要關鍵字、空白摘要、尾零、週末、假日五條的常用查核條件與 KCT 預設，改呼叫 `GlRulePredicates` 同一個方法，等價測試改成固定答案。
- `TrailingZeros` 併入 `TrailingDigits`。
- 低頻人員與低頻科目的預篩選述詞改由 `EntityFrequency` 同一個方法產生，固定 11 是它的參數；舊型別 `customPreparerEntryCount` 與
  `customAccountEntryCount` 列為停用寫法並寫出重建方式；兩條規則各加固定答案。
- `RuleCatalog`、`PrescreenRuleKeys`、`FilterConditionLabels.PrescreenKeys` 與前端鏡像合成一份登錄。
- 第四步的空白摘要只留預篩選訊號那一處，「資料缺漏輔助檢視」只列空白傳票號碼與空白科目編號，驗證報告 V_Report 3 不變；
  留哪一處是整理時的決定。
- 系統規格第 5 節的 13 項改成現況，規格、契約與畫面的數量一致；前端型別表移除已停用的舊型別。
- 預篩選報告維持預設勾選、可取消，摘要表第 14 到 16 列照範本留；核准側的「週末核准」「假日核准」照舊留在第四步的卡與第五步「預篩選」分頁。
- 每條規則的定義包含鍵、名稱、述詞、需要的欄位與前置資料；階段四建立的「規則需要什麼」的表，就是這個定義的一部分。

### 做的時候要決定的事

「未預期借貸組合」在情境只有這一條時改算整張傳票，這個例外散在 `WorkpaperProgram` 與規格第 6、7 節；附錄二建議收斂時決定它是不是規則定義的一部分。
十二題裡沒有問過這一點，改動會影響對外行為時，先請使用者裁定。

階段四留下一項發現：預篩選的 `Finalize` 只依手列的清單丟棄不適用規則的計數，只需要必填欄的六條即使判定不適用，計數也照傳，
經過見階段四的「結果」。目前碰不到；收斂時決定丟棄計數要不要改讀「規則需要什麼」的表。

### 驗證

- 保留的每條規則在 SQLite 與 DuckDB 都有固定答案；報告匯出在整合時走 `Excel` 路線核對。

### 偵錯時停在升版的欄位探查

### 實作時的取捨

- 共用來源欄成組時，後端只把配到同一來源欄、可以填補的欄位列入，字面值的借貸代碼不算；前端用同一條規則決定勾選、畫面與送出的內容，
  草稿與已確認版本才比得出「沒有改」。
- 填了幾格存在配對選項裡，由投影算出，請求不帶；改版前確認的配對沒有這一項時是 0。重新匯入後帶回的上次配對與從報告還原的配對是草稿，不帶格數。
- 借貸代號的規則：借貸別模式的金額正負號由代碼決定，所以整理後的方向就是填進去的那一側；金額為 0 的列一律算借方，看不出填的是哪一側，
  所以和那一側沒有指定代碼時一樣留白，不寫可能不對的代碼。第一次的題目沒有問到這一點，同日另外詢問，使用者選「留白 (Recommended)」。
- 「讀取來源值」依勾選先填補再計數：後端 `mapping.valueProfile` 多收布林的 `fillDown`，三種資料庫共用一段視窗函數。
  它在每份來源內依列序累計非空白值的個數，個數相同的一段只有第一列有值，整段都取那個值；
  確認配對時依 row_number 讀列、換來源就重來，兩者的填補結果相同。
  前端只在來源欄會被填補時才帶這一項，沒勾時送出的內容和以前相同。已讀到清單後改勾選，清單留著並寫「正在依往下填補的勾選重新計數…」，
  舊的空白提醒先收起來；值不會因填補而增減，只有列數會變，所以不必把清單收掉再長出來。存在性核對照原樣做，因為填補只複製已有的值。
- 欄名列超出內容只在審計員指定欄名在第 2 列以後時換成新的句子；沒有指定欄名列的空檔案仍是原本的「檔案沒有內容」，

### 數量對不上的原因

- 系統規格第 5 節寫「畫面提供 13 項預篩選檢查」，這句是 2026-10-05 寫的，當時還有回溯過帳；2026-10-08 移除後沒有改，現在是 12 張卡。
- `JetAuditProgram` 的程序 14 條：12 條逐筆加 2 條彙總。逐筆鍵 12 個。
- 第四步的卡 12 張（計畫先前寫 11 張，本次核對為 12 張）：週末、假日各一張卡含兩條規則，所以 14 條規則收成 12 張卡；空白摘要另外在「資料缺漏輔助檢視」再列一次。
- 預篩選報告 7 頁：R1 到 R4、R7 是 GL 全欄明細，R5、R6 是彙總；摘要表第 14 到 16 列是 A2 到 A4 的退役文字。
- `RuleCatalog` 的歷史代號 R7 指空白摘要，legacy 工具自己的 R7、R8 段是週末與假日旗標；兩套代號不能互推。

### 「財報準備日起核准」執行太久的一次量測

KCT 第 11 項說它執行太久，指的是舊工具在 IDEA 抽檔、接檔與改名的流程。JET 的這條規則是一句「核准日大於或等於準備日」的計數查詢，
2026-10-22 用合成資料量了一次：Python 內建的 SQLite 3.45.1，100 萬列、約 25 萬張傳票、核准日隨機落在 2025 全年，查詢形狀照
`LocalPrescreenRunRepository.CountWhereAsync`，同時算列數與相異傳票數。這不是 JET 實際的資料庫驅動，數字只供看形狀。

| 情況 | 命中約 8% | 命中約 50% |
|:---|:---|:---|
| 沒有核准日索引 | 0.085 秒 | 0.120 秒 |
| 有核准日索引（JET 的三種資料庫都建了 `ix_target_gl_entry_approval_date`） | 0.238 秒 | 1.642 秒 |

對照同一母體上空白摘要的形狀 0.106 秒、低頻科目的分組子查詢 0.411 秒。規則本身不慢；慢在 SQLite 選用核准日索引後，
為了算相異傳票數要回主表逐列取傳票號碼，核准日隨機分布時變成隨機讀。真實總帳的核准日多半和列序相關，影響會比合成資料小；
DuckDB 沒有量，這台電腦沒有可用的 DuckDB 工具。結論：列成效能項，不改規則。做法候選是用 JET 實際路線在 SQLite 與 DuckDB 各量一次，
重現時再決定要不要拿掉核准日單欄索引，或改成同時含傳票號碼的索引。

階段九照上面的做法，2026-10-25 用 JET 實際的路線在 SQLite 與 DuckDB 各量了一次。量測寫成只在設定 `JET_PRESCREEN_POSTPERIOD_PROBE=1`
時執行的測試 `PostPeriodApprovalTimingProbeTests`（帶 Scale 特徵，`Focused` 與 `Public` 不會跑到），直接執行建置出來的 Debug 測試程式，
用 JET 自己的 SQLite 3.53.4 與 DuckDB v1.5.6 驅動。合成資料 100 萬列、25 萬張傳票，每張四列，核准日落在 2025 全年；
分兩種分布各建一個案件：一種把傳票隨機打散到全年，一種讓核准日跟著列序遞增。查詞照 `LocalPrescreenRunRepository.CountWhereAsync`
的形狀，述詞由 `PrescreenRulePredicates.Build` 取得，和第四步執行時相同；和產品一樣沒有跑 ANALYZE。每個情況熱身一次後量三次，取中位數。

| 資料庫 | 核准日分布 | 索引 | 命中約 8% | 命中約 50% |
|:---|:---|:---|---:|---:|
| SQLite | 隨機散布 | 沒有核准日索引 | 0.167 秒 | 0.204 秒 |
| SQLite | 隨機散布 | 核准日單欄索引（JET 現況） | 0.129 秒 | 0.898 秒 |
| SQLite | 隨機散布 | 核准日加傳票號碼的複合索引 | 0.141 秒 | 0.970 秒 |
| SQLite | 跟著列序 | 沒有核准日索引 | 0.175 秒 | 0.199 秒 |
| SQLite | 跟著列序 | 核准日單欄索引（JET 現況） | 0.023 秒 | 0.131 秒 |
| SQLite | 跟著列序 | 核准日加傳票號碼的複合索引 | 0.020 秒 | 0.136 秒 |
| DuckDB | 隨機散布 | 三種索引情況 | 0.006 到 0.007 秒 | 0.010 到 0.011 秒 |
| DuckDB | 跟著列序 | 三種索引情況 | 0.006 秒 | 0.010 到 0.012 秒 |

結果和 2026-10-22 的形狀量測一致：規則本身不慢。SQLite 選用核准日索引後，命中一半且核准日隨機時要回主表逐列取傳票號碼與有效旗標，
中位 0.9 秒，比整表掃描的 0.2 秒慢；核准日跟著列序時同一個索引反而最快。複合索引沒有幫助，因為查詞還要讀 `is_effective`，仍然要回主表。
DuckDB 不用索引做範圍條件，三種情況都在百分之一秒內。真實總帳的核准日多半跟著列序，所以保留現有的核准日單欄索引、不改規則；
100 萬列的最差情況不到一秒，列成已量測、不處理的效能項。原始輸出與查詢計畫在量測當次的測試輸出裡，重跑時用同一個環境變數即可。

## 附錄四：匯入前資料前置處理的評估

這是階段一交出的三份只讀產出之一，階段六照它的裁定做，2026-10-22 交給使用者裁定，只評估不實作。先寫 JET 匯入現在怎麼運作，
再回答兩份來源依鍵接合可不可行、成本多大、離「復刻舊版 IDEA JE」多遠，最後評估兩個小功能。依據是 2026-10-22 讀到的匯入 handler、
匯入與投影倉儲、暫存表結構、支援日誌欄位，以及 2026-09-17 回饋計畫裡 P3-1 的六項對照表。

### 匯入現在怎麼運作

- 匯入是逐檔串流。`ImportFromFileHandler` 先讀完每個來源的欄名，再把每個來源的資料列串流交給倉儲，所有來源共用一個交易。
  每一列存進 `staging_gl_raw_row`，欄位是批次、批次內排序鍵、來源序號、來源檔列號與整列的 JSON；PBC-GL 的資料預覽就是直接讀這張表。
- 多個來源只能合併欄名相同的列。本機與 SQL Server 倉儲都在寫入前核對後來源的欄名集合和第一個來源相同，不同就拒絕；追加時排序鍵從既有最大值續編。
- 投影在第三步確認配對時進行。`LocalGlRepository` 依排序鍵讀暫存列，`GlRowProjector` 是逐列的純函式，一列失敗整批回復；
  傳票文件項次沒有配對時，投影完成後用一句集合式 SQL 依傳票號碼與排序鍵補上流水號；匯入控制總數 `gl_control_total` 在同一交易落地；
  攸關資料元素第二遍再以排序鍵接回暫存表取值。SQL Server 走 `GlProjectionDataReader` 串流配合 `SqlBulkCopy`，語意對齊本機。
- 來源列號的追溯只有一層：標準化分錄的 `source_row_number` 存的是批次排序鍵，單來源時等於檔內列號，多來源時不是；
  錯誤訊息用來源檔列號加來源標籤寫出位置。
- 支援日誌的匯入失敗欄位固定記選項、標頭、資料列、儲存格轉換、進度與寫入資料庫六個階段，以及來源序號、最後完成的列、失敗的列與欄。
- 直接讀寫 `staging_gl_raw_row` 的產品檔有 17 個，測試檔有 27 個；本機與 SQL Server 的匯入倉儲各約 800 行。

### 兩份來源依鍵接合可不可行

技術上可以做在匯入暫存表之後、投影之前，用集合式 SQL 在同一交易內完成，專案已有兩個同形狀的先例：項次自動編號與攸關資料元素第二遍。
但它不是加一段 SQL 就結束，因為現在的模型是「一個資料集等於一個批次，批次是欄名相同的列的集合」，接合會引進「來源之間的關係」這個新概念，
每個下游都要重新定義「一列來源資料」是什麼：

| 會動到的地方 | 要重新回答的問題 |
|:---|:---|
| 來源契約與匯入畫面 | 第二份來源怎麼指定、鍵欄在哪一欄、對不到與對到多筆怎麼辦 |
| `import_batch`、`import_batch_source`、暫存表 | 接合後的列存哪裡、原始兩份各自保留多少 |
| PBC-GL 的呈現 | 預覽顯示接合前的原樣還是接合後的結果；階段五「呈現資料庫原樣」以哪一張表為原樣 |
| 欄位配對 | 兩份來源欄名聯集與同名欄的命名、配對畫面的來源欄清單 |
| 控制總數與完整性 | `source_row_count` 算主表列數還是接合後列數；一對多時列數膨脹怎麼對 |
| 來源列號追溯 | 一筆分錄有兩個檔的列號，錯誤訊息、驗證報告的來源列號、INF 抽樣基礎都只認一個 |
| 支援日誌 | 新增接合階段與對不到的統計 |
| 三種資料庫實作 | 本機共用一份、SQL Server 另一份，接合 SQL 要寫兩次並各自測 |
| 報告與底稿 | 「來源全欄」依 `batch.Columns` 回取原始列，接合後要決定回取哪一份 |

成本判斷是大：契約、兩套匯入倉儲、兩條投影路徑、資料庫結構升版、預覽、報告與對應測試都要改，影響範圍比 2026-09 加入多來源合併那一次還大。

離「復刻舊版 IDEA JE」的距離：舊流程裡的接合有兩種。一是科目配對檔依傳票或科目接進總帳，JET 已用 `target_account_mapping` 在查詢時完成；
二是預篩選結果接回分錄，JET 改成即時計算。總帳本身的整理，包括移除表頭表尾、合併兩份總帳、補欄位，KCT 都在 Excel 或 IDEA 匯入前做，
而且合併多檔只在欄位相同時進行，見 `kct-gl-workflow.md` 第 3 階段。舊 JE tool 從沒有把兩份結構不同的來源依鍵接起來，所以接合不在復刻範圍內，
是新功能。建議不做，兩份總帳欄位不同時維持在 Excel 對齊；日後要做時第一個要裁定的是「一列來源資料」的定義，不是 SQL 怎麼寫。

### 兩個小功能

**指定欄名在第幾列。** `TabularSourceRequest.LeadingRowsToSkip` 已存在，Open XML 與二進位 Excel 讀取器都支援，以實際列號計算含空白列；
科目配對檔第一列認不出時退兩列、假日檔固定略過一列，都是既有用法。目前沒有開放給一般匯入：`TabularSourcePayload.Parse` 只收工作表、
編碼與分隔符，契約註解寫「不對一般匯入開放新的前置處理選項」；文字檔與 Access 讀取器沒有實作略過列數。開放的話要做的事是：
匯入選項多收一個「欄名在第幾列」、每個來源的畫面多一格、檢視與預覽也帶這個值、文字檔讀取器補支援，Access 的資料表沒有列的概念所以不適用。
成本小。它只解決表頭，表尾的合計列仍會被當成分錄匯入，審計員還是要在 Excel 刪。IDEA 的匯入助手本來就讓人勾選哪一列是欄名，
這項在復刻範圍內。

**對勾選的欄位把空白補成上一列的值。** 可以放在兩個位置，各有取捨：

| 位置 | 做法 | 好處 | 代價 |
|:---|:---|:---|:---|
| 第二步匯入時，對原始欄填 | 在資料列串流進暫存表之前包一層狀態，記住每個勾選欄最後一個非空白值；填了幾格寫進匯入回應與 `import_batch_source` | 和現在審計員在 Excel 填完再匯入的結果一樣，PBC-GL 顯示的就是填後的值；整體複審最初的建議寫「匯入摘要要寫出填補了幾格」，對應這裡 | 第二步只看得到原始欄名，審計員要先知道哪一欄要填；原始空白不再保存，只剩筆數；換選擇要重新匯入 |
| 第三步確認配對時，對已配對的 JET 欄位填 | 在投影讀暫存列的串流上包同一層狀態，本機與 SQL Server 兩條投影路徑都要；填了幾格寫進配對確認的回應與驗證摘要 | PBC-GL 保持原樣，GL 是整理後的值，兩者都查得到；勾選的是審計員已認得的欄位；改選擇只重新投影，走既有的失效規則 | 和最初建議的「匯入摘要」不同位置；投影器是純函式，狀態要放在串流包裝層 |

兩個位置都要處理同一組邊界：多來源追加時不跨來源延續，每個來源第一列的空白就是空白；填補以列序為準，依賴來源檔的列序正確；
只填審計員勾選的欄位，其他欄不動。建議放在第三步，理由是原樣與整理後的值都保得住，比較符合把前置處理記進 CAATs 文件的要求；
若使用者維持最初建議的位置，就放第二步，兩者不同時做。

其餘四項維持在 Excel：刪統制科目與用公式算科目編號都要案件特定的判斷；合併欄位不同的兩份總帳就是上面的接合問題；移除表尾合計列目前沒有辨識依據。
