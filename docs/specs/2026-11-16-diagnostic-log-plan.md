## 目標與起因

使用者 2026-11-16 在測試環境匯出條件篩選報告，跑了三分半還沒完成，於是取消，並把匯出的診斷日誌交給 Agent，
要 Agent 只看日誌找原因。日誌只看得出取消當下程式停在高風險條件彙總的分頁查詢，看不出那三分半花在哪裡：
是一條查詢卡住、很多頁累積起來很慢，還是時間其實花在寫 Excel。原因有三個：

- SQL 紀錄要每個呼叫點自己加，產品程式裡 137 個執行點只有 44 個有記，分頁讀取的查詢都沒有記。
- 已有的 SQL 紀錄在查詢結束後才寫，跑很久的查詢在結束前不留任何紀錄。
- 匯出進度只送到畫面，沒有寫進日誌；取消紀錄也沒有寫停在哪一步。

這份計畫補上這些紀錄，讓使用者下一次在測試環境重現時，交回的日誌足以判斷原因。

## 這一輪的範圍

使用者選的四項：

- **長時間操作定時紀錄**：操作跑超過 30 秒後，每 30 秒記一筆 `action.still_running`，寫目前步驟、經過時間、
  已執行的 SQL 次數與時間，以及這段時間 JET 用掉的處理器時間與記憶體。診斷日誌另外記每次進入步驟的時間 `action.stage_entered`。
- **SQL 太久或被中斷**：在所有 SQLite 查詢共用的命令層監看，不靠各呼叫點自己加。單一查詢在 SQLite 裡連續跑超過 5 秒記 `sql.slow`，
  之後每 30 秒再記一次，結束時記總時間；被中斷記 `sql.cancelled`，出錯記 `sql.failed`，都寫已經跑了多久。SQL 全文與參數只進診斷日誌。
- **匯出進度寫進日誌**：畫面收到的 `export.progress` 同時寫進日誌。換階段、換工作表與每張工作表完成時一定記，其餘最多每 10 秒一筆。
- **診斷日誌檔頭與失敗欄位**：`dev.log.exportFile` 匯出的檔案第一行是 `dev.snapshot`，寫 JET 版本、組建設定、模組代號與匯出範圍；
  診斷日誌的取消與失敗事件補上支援日誌已有的 `failure_stage` 等欄位。

Agent 依使用者「其他你認為追加的日誌紀錄功能」另加三項：

- **每次操作的 SQL 摘要** `action.summary`：操作結束時寫經過的步驟與各步驟花的時間、SQL 次數、在 SQLite 裡的總時間、讀到的列數，
  以及取消時從要求取消到真正停下花了多久；診斷日誌另列最花時間的幾條 SQL。
- **慢查詢的執行計畫** `sql.plan`：查詢第一次被記為跑太久時，另開一條唯讀連線取得它的 `EXPLAIN QUERY PLAN`，只進診斷日誌。
- **處理器與記憶體**：寫在 `action.still_running` 裡，用來分辨那段時間 JET 在計算，還是在等待。

支援日誌同時收 `action.still_running`、`action.summary`、`sql.slow`、`sql.cancelled`、`sql.failed` 與 `export.progress`，
只記程式寫死的代號、時間與筆數，不記 SQL、參數、檔名、工作表名稱或案件資料。

## 設計原則：獨立的監看模組

依使用者的要求，日誌功能放在 `src/JET/JET/Infrastructure/Diagnostics/Monitoring/`，不寫進業務邏輯，也不在 handler、
審計規則或 repository 裡加呼叫。接上的地方只有下面幾處，都在診斷或連線的邊界：

- action 分派器在一次操作開始與結束時通知監看模組，只多一行；組裝 runtime 時把事件發布者外面包一層，用來把匯出進度寫進日誌。
- 所有 SQLite 連線共用的命令類別在執行與逐列讀取前後通知監看模組。
- 原本就是診斷用途的步驟紀錄 `SupportOperationStage` 多一個觀察者，讓監看模組知道何時進入哪一步。

監看模組遵守三件事：不改變任何查詢、結果、例外或流程；自己出錯時吞掉，不影響操作；計時與定時檢查在背景執行，
不讓操作等它。失敗與取消的例外照原樣往外丟，堆疊不變。

## 不做與延後

這一輪不做，記在這裡，使用者交回新的日誌後再決定：

- `operation.cancel` 寫出取消的是哪一個操作與取消來源。
- `action.start` 的 `payload_shape` 對 `validationResultId` 這類系統產生的識別碼記實際值。
- 發布建置的堆疊不寫建置電腦的絕對路徑。
- 前端用 `log.append` 送來的文字出現在匯出檔。
- 開案時記資料庫環境，例如檔案大小、journal 模式、索引清單與各資料表列數。
- 已有的 `sql.executed` 對 SELECT 記讀到的列數。
- 定時紀錄加上 GC 暫停的累計時間與記憶體負載；定期量 UI 執行緒要等多久才輪到；收到取消要求的當下就寫一筆紀錄，
  不等操作結束的摘要。2026-11-17 的日誌已足以查出原因，這幾項等驗收仍有問題時再決定。
