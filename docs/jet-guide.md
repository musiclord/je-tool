# JET 專案指南

更新日期：2026-11-01

JET（Journal Entry Testing）是一套 Windows 桌面工具，用來整理總帳分錄與試算表、執行查核規則，
再輸出 Excel 底稿。這份指南先說清楚產品怎麼運作；程式使用的精確欄位與 action 名稱另見程式碼與
[`action-contract-manifest.md`](action-contract-manifest.md)。

## 1. 產品目的

JET 把原本分散在 IDEA、VBA 與人工 Excel 步驟裡的流程，整理成一個可重複執行的案件工作區。
它不是會計判斷的替代品，也不應替單一客戶或單一檔案寫特殊答案。

主要工作是：

1. 建立案件並選擇資料庫。
2. 匯入總帳與試算表等來源檔。
3. 把來源欄位配對到 JET 的標準欄位。
4. 建立可供查核的有效分錄母體並執行驗證。
5. 依風險訊號與自訂條件篩選分錄。
6. 產生可追溯的 Excel 報告與工作底稿。

## 2. 核心資料

- **GL（General Ledger）**：總帳明細這份資料集。匯入的每一列是待測試的會計分錄。
- **JE（Journal Entry）**：會計分錄，是測試對象，不是另一個要與 GL 二選一的日期欄位。
- **TB（Trial Balance）**：試算表。用來比對科目餘額與期間變動。
- **科目配對**：把公司科目對到 JET 使用的分類，供後續條件與報告使用。
- **日期維度**：國定假日與補班日，供非營業日相關規則使用。
- **授權編製人員**：選用的識別值清單，用來比對未列入名單的人員。編製者彙總與編製筆數統計直接使用 GL，不依賴此名單。
- **案件設定**：期間、資料庫類型（provider）、欄位配對、條件情境與最近結果。

來源資料先進入暫存區（staging），再依已提交的欄位配對轉成標準資料。後續規則只讀標準資料，
不應讓每一個報告產生器各自重新解讀來源欄位。

### 日期名稱與資料含義

期間判斷欄的畫面名稱是「總帳日期」（裁定 2026-10-08-02）。
名稱說明用途，不以受查者來源欄的英文名稱猜測含義；來源配對仍由審計員確認。技術識別字及既有報表正準欄名保留相容，不為文字調整搬移案件資料。
GL 只配對下表兩種日期，沒有傳票日期欄位，也沒有回溯過帳規則（裁定 2026-10-08-03）。

| 畫面名稱 | action 與資料庫欄位 | 用途 |
|:---|:---|:---|
| 總帳日期 | `glDate`、`gl_date`；既有正準欄名 `總帳日期_JE` | 必要配對，用來決定哪些分錄列入 GL，也是日期篩選和非營業日比較的依據。 |
| 傳票核准日 | `approvalDate`、`approval_date` | 供核准日期條件與財報準備日起核准等規則。`approvalDate` 是歷史識別字，不表示 Document Date；只有明確選「與總帳日期相同」時才複製該日期。 |

來源：`JetFieldCatalog`、`GlRowProjector`、`GlExcludedPopulation` 與 `GlRulePredicates`。

## 3. 六步驟流程

畫面與 `wwwroot/js/state.js` 目前使用六個步驟：

| 步驟 | 使用者做什麼 | 系統留下什麼 |
|:---|:---|:---|
| 建立案件 | 填寫案件資訊並選 SQLite、DuckDB 或 SQL Server | 案件中繼資料與資料庫類型 |
| 匯入資料 | 選擇 PBC-GL、PBC-TB 與選用的支援檔 | 原始欄位目錄與暫存資料 |
| 欄位配對 | 完成 GL 與 TB 的欄位配對，並確認金額模式 | 已確認的配對設定與標準資料 |
| 資料驗證與測試 | 確認 GL、檢查完整性與資料品質；預篩選為選用 | 驗證與預篩選結果 |
| 進階條件篩選 | 建立、預覽並儲存條件情境 | 篩選版本與命中結果 |
| 匯出底稿 | 選擇並產生報告 | 五種報告的 Excel 檔；工作底稿每次匯出新增一個版本檔 |

建立案件時，案件名稱與查核期間必填，案件編號和客戶名稱選填；操作人員由目前 Windows 短帳號取得，
不接受表單另填身分。啟動時的 `system.databaseInfo` 明確回報這台電腦沒有設定線上資料庫時，SQL Server 選項停用，
並請使用者改選 SQLite 或 DuckDB；還沒查到結果或已設定但連不上時維持可選，連不上時在建立時回報錯誤。GL 與 TB 支援 `.xlsx`、`.xlsm`、`.xls`、`.csv`、`.txt` 及 Access 的 `.mdb`、`.accdb`。
Excel 檔逐列唯讀解析，不執行巨集；Access 透過既有 Office 資料介面讀取選定的一般資料表。`.xlsb` 不支援。
讀取器的略過列數以 Excel 的實際列號計算，包含空白列，`.xlsx` 和 `.xls` 相同。
一般總帳與試算表的每個來源可以指定欄名在第幾列（裁定 2026-10-22-15）：第二步待匯入清單的每個 Excel 工作表
與文字檔都有「欄名在第 N 列」一格，預設第 1 列，也就是取第一個有內容的列當欄名；填 2 以上時，前面的列全部略過，
從那一列取欄名，文字檔以列計算，空白列也算。那一列起沒有內容時，三種讀取器都回同一句「從第 N 列起沒有內容，找不到欄名」，
錯誤代碼和空白檔相同。Access 資料表的欄名來自資料表本身，沒有這一格。這個選擇跟著來源保存，
匯入後的來源清單與重開案件都看得到。它只解決表頭；表尾的合計列仍會被當成分錄匯入，審計員還是要在 Excel 刪。
國定假日與補班日匯入固定略過第一列；正式範本第一列是說明，第二列是欄名。這種版面固定的略過，以及科目配對舊範本的欄名在第 3 列，
不是審計員指定的欄名列，找不到欄名時說檔案或工作表是空的，不用上面那一句。
國定假日清單有 `IS_Holiday` 欄時，只匯入值為 Y 的列；補班日清單依日期欄匯入。
若檔案第一列空白、第二列是說明、第三列才是欄名，請先整理成正式範本的排列再匯入；JET 會把第二列當成欄名。
一般匯入除了欄名在第幾列，以及第三步確認配對時的往下填補空白，不提供其他資料前置處理；兩份總帳依鍵接合維持在 JET 之外
（裁定 2026-10-02-04）。
多檔功能只合併欄位相同的列，不能把兩份 TB 普通追加後當成期初與期末。
文字檔照一般 CSV 讀法（和 Excel 相同）：只有欄位開頭的引號是引號，欄位中間的引號是一般字元，不會把後面的列併進來。
欄位開頭有引號時，到下一個引號之前都算同一格，可以跨好幾行；這是合法寫法，所以 JET 不擋。但引號放錯位置時，
後面幾列會被併進同一格，資料列因此變少。GL、TB 與科目配對範本匯入完成時，JET 提醒每個檔案有幾列的欄位內含換行，
並列出前五個列號，支援日誌也記一筆。引號沒有成對、檔案結構讀不通時匯入失敗並寫出第幾列。開頭的空白列略過，第一個有內容的列是欄名；只讀到一欄時提醒
可能是報表格式：標題列在欄名前面時，在待匯入清單改填欄名在第幾列即可，其他整理仍先在 Excel 做。標頭之外有資料的欄合成 `COL_n` 佔位欄，少欄視為空，
這和 Excel 檔相同。`.xls` 的錯誤儲存格保留 `#N/A` 這類原文，所以金額欄會以金額無效明確失敗，不會被讀成 0。
`.xls` 與 Access 的是或否值寫成 `true`、`false`，只有時間的值寫成時間，表示方式和 `.xlsx` 一致。
來源檔被其他程式開著時，訊息請審計員關閉檔案後重試，只寫檔名；解碼失敗時可在匯入清單改選編碼重試。
Access 是資料匯入來源，不是新增的案件資料庫。現行讀取器只列出一般本機資料表，排除系統表與儲存查詢；
先檢視表結構，再提供有界預覽，完整匯入逐列串流至原有 SQLite 或 DuckDB 流程。空表、找不到資料表及
不支援的二進位值會說明原因，失敗或取消保留原匯入批次，不覆寫來源檔。
相容性須分開記錄 ACE 實跑與替身測試。win-x64 程式需要既有的 x64 ACE 16 可用，不能由「已安裝 Office」
推定所有位元版本都通過。加密或密碼資料庫、連結資料表、Access 巨集、儲存查詢、多值或附件欄位不在
一般資料表匯入的已驗收範圍；不為這項功能要求一般審計員另裝資料庫或驅動程式。

總帳科目名稱是必要配對欄位，須指定來源欄位（裁定 2026-09-18-03），不列為改成選填的待開發功能；
這不增加逐筆科目名稱都不可空白的檢查。

同一個來源欄可以配給多個欄位，例如總帳日期和傳票核准日都選同一欄，GL 與 TB 都一樣。確認配對後，每個欄位都帶同一個來源值。
報告與底稿列出的欄位定義，依欄位順序由第一個欄位在來源欄原位置改名，其餘欄位照同一個來源欄的定義追加在後面。
JET 依「預設審計員可信」照審計員的選擇配對，不另外擋（裁定 2026-10-19-07）。

欄位資訊記下每個欄位的來歷：來源檔原有的欄、配對後改名的欄、JET 產生的欄，以及數字欄轉成文字時留在原位置的原值。
底稿與報告判斷一個欄位是不是 JET 欄位時只看來歷，不看欄名的後綴或說明文字；沒有配對、只是名字以 `_JE` 結尾的來源欄仍是來源欄
（裁定 2026-11-03-11）。來源欄的名字和配對後的欄名相同時，來源欄在欄位資訊與底稿改稱「原名（來源）」，匯出照常完成
（裁定 2026-11-03-12）。攸關資料元素欄位的輸出欄名是「顯示名稱_JE」；兩個欄位的顯示名稱相同，或和標準欄名相同時，
改成「顯示名稱（來源欄名）_JE」（裁定 2026-11-03-14）。配對過帳狀態後，JET 照舊版產生文字欄 `過帳碼_JE`，
欄位資訊的說明寫來源欄與過帳判斷值（裁定 2026-11-03-15）。

確認 GL 配對時可以勾選已配對的欄位「往下填補空白」（裁定 2026-10-22-16）。
這是給傳票號碼、日期只寫在每張傳票第一列的總帳用的：JET 在投影每一列之前，把勾選欄位來源欄的空白補成同一來源內上一列的值，
只含空白字元的格也算空白；PBC-GL 保持原樣，GL 是整理後的值。多個來源追加時不跨來源延續，每個來源的第一列空白就是空白；
填補以列序為準，依賴來源檔的列序正確；只填勾選欄位的來源欄，其他欄不動；借方與貸方代碼是字面值，不能勾。
填補是對來源欄做的，兩個欄位配同一個來源欄時只填一次，而且一起勾、一起取消，回應、保存與摘要列出全部被填的欄位
（裁定 2026-10-28-04）。勾選與填了幾格都跟著配對保存在案件與報告的配對資訊裡，重開案件帶回來
（裁定 2026-10-28-05）。確認配對的回應與第三步的摘要寫出填了幾格，審計員據此記在 CAATs 文件。
改選擇只要重新確認配對，走既有的失效規則。第三步的「讀取來源值」在來源欄會被往下填補時，依同一規則先填補再計數，
常見值、空白列數與空白提醒都和確認配對後一致；存在性核對照原樣做，因為填補只複製已有的值（裁定 2026-10-28-03）。

往下填補之後，資料可靠性抽樣清單的主表與底稿 Step 2 的分錄來源讀 GL 整理後的值，和同一列的傳票號碼一致；借貸代號照 PBC-GL 原樣，
原始列空白而借貸別有往下填補時，依整理後的借貸方向寫已確認配對的借方或貸方代碼。金額為 0 的列一律算借方，看不出填的是哪一側，
所以和那一側沒有指定代碼的情況一樣留白（裁定 2026-10-28-07）。`可靠性樣本_所有欄位` 仍是 PBC-GL 原樣（裁定 2026-10-28-02）。
報告裡列「來源 GL 全欄」的明細，也就是 `V_Report 1` 到 `V_Report 4` 與 `V_Report 6`、Pre-screening 的 `R1` 到 `R4` 與 `R7`、
`#Criteria Select n` 與 `可靠性樣本_所有欄位`，從 PBC-GL 讀原始列，不含填補後的值。

人工與自動分錄可逐值指定，也可只列一側，將其餘非空白值視為另一側；空白另選人工、自動、
不判定或先補齊來源。選擇會隨案件和報告配對資訊保存。取消或更換來源欄位時清除舊欄政策，避免套錯來源。
只列一側時，清單代碼如果在來源裡一筆都沒有，其餘非空白值會全部歸到另一側。確認配對後 JET 提醒代碼與來源欄，
不擋確認；判定規則不變。
授權人員匯入須選與 GL 相同的識別欄，畫面分別顯示原始列數、空白、重複及有效人員數。
名單的識別值去掉頭尾空白後不分大小寫去重，和 GL 傳票建立人員的比對同一規則，保留第一次出現的寫法。
移除名單會使相依結果失效並清除已存篩選情境，仍保留驗證結果，之後可再次匯入；重新匯入不會恢復情境。
匯入的文字欄位不論來源是 `.csv`、`.xlsx`、`.xls` 或 Access，都去掉頭尾的空白字元，字元集合和 .NET 的 Trim 相同
（半形空白、Tab、換行、全形空白、不換行空格等）；只含空白的值當成空白（裁定 2026-10-04-01）。

步驟位置只代表使用者目前看到哪一頁。是否能往下做，必須由後端根據案件資料與目前版本判定，
不能只靠前端記住一個「完成」布林值。
沒有 TB 也能往下做（裁定 2026-10-29-16）：只匯入 GL 並確認 GL 欄位配對，
就能執行資料驗證、預篩選、條件篩選與匯出。只有 GL 與 TB 逐科目比對不能執行，驗證結果寫出原因，審計員在底稿說明。
沒有匯入 TB 時，原因是「沒有匯入 TB，無法執行 GL 與 TB 逐科目比對。」；已匯入 TB 但還沒確認 TB 欄位配對時，原因是
「TB 欄位配對尚未確認，無法執行 GL 與 TB 逐科目比對。」（裁定 2026-10-30-16）。驗證有差異仍可繼續（裁定 2026-09-17-01）。

### 建案後修改案件資料

「建立案件」頁面可修改客戶名稱、案件編號與期末財報準備日；案件名稱與查核期間維持不變。建案時檢查起始日不晚於截止日。
準備日早於查核起始日，或晚於查核截止日超過一年時，只提醒確認年份，不禁止建立或儲存。
修改準備日會讓預篩選需要重算，並清除篩選命中及全部已儲存情境；驗證結果與欄位配對保留。常用篩選條件的「在該季度前 X 天借記收入」與欄位條件裡傳票核准日底下的「財報準備日起核准」不是同一項：後者比較核准日與財報準備日，前者使用曆年季底及查核期末前的指定天數。
客戶名稱或案件編號變更不影響審計命中。修改案件資料不改寫已匯出的檔案，報告清單把舊檔標為過期，再次匯出時才用新資料。
## 4. 資料驗證

資料驗證先回答「這批資料能不能形成可信的 GL」。它包含匯入品質、欄位配對、GL 與 TB
完整性、借貸平衡、空值與 GL 範圍等檢查。

驗證結果分成摘要與明細。摘要可以回到畫面；大量明細必須用有界分頁查詢，不能把完整 GL 或 TB
放進 WebView2、工作階段狀態或一個過大的 JSON 回應。

資料名稱全系統統一（裁定 2026-10-08-04）：匯入的總帳明細叫 PBC-GL，匯入的試算表叫 PBC-TB；確認配對後納入測試的
分錄叫 GL，未納入測試的分錄叫 GL(未納入測試)，標準化後的試算表叫 TB。資料預覽的 dataset 依序是 `pbcGl`、`pbcTb`、
`gl`、`glExcluded`、`tb`；實體表名、`dataset_kind` 的 `gl` 與 `tb`、底稿與報表的舊欄名不變。
「其他資料」的「資料表摘要」也用這組名稱：`pbc_gl` 寫成 PBC-GL，`pbc_tb` 寫成 PBC-TB，
`gl` 寫成「GL、GL(未納入測試)」，`tb` 寫成 TB。這些名稱只用於顯示，不是 SQL 識別字。
匯入項目顯示 `GL (總帳明細)` 與 `TB (試算表)`，資料預覽顯示 `PBC-GL` 與 `PBC-TB`（裁定 2026-10-08-05）。

GL 在確認 GL 欄位配對時決定。先排除總帳日期空白或不在查核起迄日內的列，日期兩端都包含；
再依過帳狀態政策排除不採用的列。未配對過帳狀態欄位時，期間內的列全部納入；有配對時指定採用代碼清單及是否納入空白值，
至少採用一個非空代碼或選擇納入空白。代碼去掉頭尾空白且不分大小寫。後端保留合計、GL 與 GL(未納入測試) 的筆數，排除原因依上述先後互斥計數；第四步不另外顯示分區摘要。
GL(未納入測試) 的每一列只記一種未納入原因：總帳日期空白、早於查核期間、晚於查核期間，或日期在期間內但過帳狀態不符。
日期不符分成前三種並各自計數（裁定 2026-10-21-04），資料預覽可以只看其中一種；GL 範圍與審計結果都不變，
驗證摘要的日期不符筆數是三種日期原因的合計。
驗證、預篩選、條件篩選與完整性 GL 彙總共用已保存的 GL，不各自重算期間或過帳政策。
總帳日期在查核期末之後的分錄照 legacy 處理（裁定 2026-10-21-05）：一個案件只測一段查核期間，不另設期後母體；
需要期後查核時另開一個案件，建案時把查核期間設成期後月份。

空值與日期異常檢查在 GL 內分成四類：科目空白、傳票號碼空白、空白摘要，以及核准日不在查核期間。
最後一類以核准日判斷，不是總帳日期；核准日空白不命中。一列可以同時命中多類，不能把各類筆數相加當成相異分錄數。
傳票核准日不可用時，最後一類無法執行，筆數不寫 0。後端改寫一句原因，例如「「傳票核准日」尚未選擇來源欄，請回第三步欄位配對補上。」，
畫面只顯示這一句。可不可用照欄位目錄算出的可用欄位判斷，傳票核准日選「與總帳日期相同」也算可用。
驗證報告照同一份驗證結果寫 N/A，不另外判斷（裁定 2026-10-23-01）。
借貸不平的傳票張數、摘要、分頁與底稿 Step 1-1 都不把空白號碼當成一張傳票。

同一非空傳票號碼出現在多個總帳日期時，驗證保存涉及的號碼數及分錄列數，第一步顯示非阻擋提醒。
沒有有效驗證結果時顯示尚未確認，不假定為零，也不因此更改傳票比對鍵。INF 樣本與驗證摘要在同一資料庫交易保存；
失敗或取消不留下半套新結果，只有孤立樣本不能代表已完成驗證。

資料品質問題與查核命中都需要審計員判斷，不能直接當作禁止後續操作的理由。
完整性驗證已完成但有差異，或 GL 與 TB 逐科目比對無法執行時，JET 保留明細與提醒，允許預篩選、條件篩選與匯出；
審計員可說明差異原因後繼續審計程序（裁定 2026-09-17-01）。
「可繼續」不代表「完整性通過」，也不要求另填說明或勾選確認。只有缺少目前資料的驗證結果、
結果損壞或已失效時，才要求重新驗證，避免沿用不存在或過期的結果。

完整性測試有兩項檢查。第一項是存入筆數與合計核對，確認 JET 存下的分錄筆數與借貸合計，和確認欄位配對時算出的一致：
確認配對時，JET 逐列存下分錄，同時計算查核期間內、符合過帳狀態設定的筆數與合計；驗證時再從存下的分錄重新計算一次。
兩組數字都由 JET 計算，所以這一項找得出存下時少掉或重複的分錄，但不和來源檔自己的合計比對，也看不出讀檔時就少掉的列。
第二項是 GL 與 TB 逐科目比對；沒有 TB 時這一項無法執行，提醒直接寫上一節的兩種原因之一。使用者訊息的開頭寫哪一項未通過，不使用 Part A 或 Part B。借貸不平測試逐張傳票比較借方與貸方金額。資料可靠性測試抽出固定且可重現的樣本，
供審計員確認非財務欄位及所選攸關資料元素；程式不替審計員自動判定這些內容可靠。

INF 的目的與人工核對責任已對照兩份 legacy 程式及現行 `WorkingPaperProgram`。較早的 `idea-script.bas`
可選擇是否產生 60 筆樣本；`idea-tool.bas` 已將該詢問註解停用，實際產生 59 筆。現行抽樣使用 GL，
上限 59 筆並記錄可重現的抽樣設定；59 筆及不必重現舊 IDEA 同一批隨機列的差異已由使用者確認（裁定 2026-08-28-03），
不重新改成 60 筆。
現行底稿方法文字要求團隊在高風險篩選前確認所用 RDE 的可靠性，初步預篩選另有例外；樣本供核對附件，
不是軟體自動證明可靠。程式不另增一個核准勾選或操作關卡，也不改寫尚待 DPP 討論的指引（裁定 2026-09-12-01）。

目前 `sourceQuality` 只有總帳日期空白一類。這些來源列無法判斷案件期間，所以保留在 PBC-GL，並列入 GL(未納入測試)；
日期在期間外不是這一類。

母體完整性的逐項判定只在「資料驗證與測試」這一個畫面呈現；流程總覽等其他畫面只摘要既有的後端裁定，
不建立第二套判定面，避免同一件事在兩處給出不同答案（裁定 2026-08-20-02）。

## 5. 預篩選

預篩選提供一組可重複計算的風險訊號，例如財報準備日起核准、特定摘要、非營業日、尾數型態、非授權
編製者，以及編製者與科目的使用彙總。它協助使用者理解母體，但不是進入進階條件篩選的必要前置。

規則名稱、欄位與版本要由 Domain 與 Application 的現行契約決定。前端只顯示後端結果，
不得用 JavaScript 重算另一套命中邏輯。

「財報準備日起核准」沿用 legacy R1 實際比較：核准日大於或等於案件財報準備開始日，不是查核期末日。
2024 篩選表的說明把這一項寫成過帳；JET 維持比較核准日，「過帳」視為舊範本用語（裁定 2026-10-21-06）。
legacy IDEA 用總帳日期把母體縮成財報準備期間的選項已停用，JET 不恢復（裁定 2026-10-21-13）；需要時在第五步用「指定日期區間」限定總帳日期。
「未預期借貸組合」沿用 legacy R3：收入科目的貸方分錄，同一張傳票沒有金額大於 0 的應收、現金或預收借方，
而且這張傳票至少有一筆金額大於 0 的分錄。0 元的應收、現金或預收借方不算對方科目。
舊版先挑出有正金額分錄、但沒有這三類正金額借方的傳票，再和收入貸方配對，所以只有貸方、沒有任何正金額分錄的傳票不命中；
JET 照舊版（裁定 2026-10-29-29）。第四步卡片、第四步明細與預篩選報告的 R3 照舊版列出命中傳票的全部分錄，傳票張數和直接命中相同。
第五步把它當成條件時判斷不變，直接符合的是收入貸方分錄；分錄筆數何時計整張傳票，見第 6 節。
摘要預設清單補回 legacy 的九個簡體詞，共 25 詞；第五步可另選可編輯的摘要關鍵字條件。
第四步照舊版只保留 legacy R5、R6 兩項彙總，不另設「編製分錄較少的人員」與「使用較少的科目」兩條 11 筆以下的規則
（裁定 2026-10-29-27）。要找 11 筆以下的人員或科目，用第五步欄位條件裡傳票建立人員底下的「編製分錄較少的人員」與會計科目編號底下的「較少使用的科目」，預設 11 筆分錄，按 GL 計算，不是 11 張傳票。
「較少使用之科目」卡片的狀態顯示 GL 裡的相異科目數，不拿前 50 列摘要充當答案。
缺少傳票建立人員欄位時，人員彙總及非授權比較顯示原因，其他測試繼續可用。
人員識別值一律去掉頭尾空白、不分大小寫：編製者彙總、非授權編製人員、第五步的編製分錄較少的人員，和既有的編製等於核准、
人員清單用同一規則。非授權編製人員與第五步的編製分錄較少的人員不列入空白人員；編製者彙總把空白人員列成一組。
畫面與報告把空白人員組標為「（空白）」，只改顯示，不改分組鍵或合併同名字面值的人員。
編製者彙總的明細最多列出分錄筆數最多的 50 位；畫面的人數、流程總覽與預篩選報告的摘要列，都寫查核期間的完整人數，空白人員組算一位。
編製者彙總顯示同一人時，固定取同組裡碼位最小的去空白寫法（例如 U1 與 u1 顯示 U1），
SQLite 與 DuckDB 相同。資料庫端去掉的空白字元集合和 .NET 的 Trim 相同，所以全形空白、不換行空格與 Tab 在兩個資料庫
的結果一樣（裁定 2026-10-04-01）。
legacy R5 是總帳實際人員彙總，不等於新版授權編製人員清單比較。連續零尾數預設固定 6 位，是這條規則定義的一部分；
第四步的計數、第五步的「預篩選」條件、欄位條件的「尾數連續」比較方式與報告 R4 呼叫同一條「整數尾數符合」述詞。
第五步的常用查法「尾數連續多個 0」是一條金額條件，比較方式是「尾數連續」，比較基準是絕對值，個數可填 1 至 12（裁定 2026-11-03-07）。
先取金額整數部分，小數不參與，整數部分為零不命中。2026-11-03 以前加入的是「整數尾數符合」與「大於或等於 1」的子條件組，
已儲存的情境照舊能讀，選到的分錄相同，`TrailingZeroRunConditionsTests` 在 SQLite 與 DuckDB 核對兩種寫法與第四步這條規則的結果一致。
這是已裁定的新舊差異（裁定 2026-09-18-04）：保留上述行為，不恢復 legacy R4 依借方平均金額決定位數的算法，
也不列為待補自動算法或待裁定零位數邊界。

規則需要的資料不足時，只有這條規則無法執行，其他規則照常計算。原因句由第 6 節那張 `JetRuleRequirements` 表產生，
缺幾項寫幾句，每句寫出缺什麼、到哪裡補，例如「「傳票核准日」尚未選擇來源欄，請回第三步欄位配對補上。」；
畫面只顯示這幾句，不另接補救文字。週末與假日各合併過帳與核准兩側：只缺傳票核准日的配對時，照常計算總帳日期那一側，
原因另寫「只檢查了總帳日期。」再接核准日那一句；總帳日期那一側也不能計算時，例如沒有上傳國定假日清單，整項無法執行，列出兩側的原因。

預篩選共 12 條規則，每條只有一個定義，登錄在 Domain 的 `PrescreenRuleDefinitions`：鍵、規則名稱、第五步的條件標籤、述詞形狀與需要的資料。
第四步卡片的標題另寫在前端，「金額尾數連續 6 個 0 的分錄」與「非授權編製人員之分錄」兩張卡和登錄的規則名稱不同。
其中 10 條逐筆標記分錄，是第五步「預篩選」分頁的 10 條條件；第四步把週末與假日各合併成一張卡，加上依分錄編製者彙總與較少使用之科目兩張彙總卡，共 10 張。
第五步欄位條件與常用篩選條件裡的摘要關鍵字、空白摘要、尾數、週末、假日條件，和第四步呼叫 `GlRulePredicates` 同一個方法；
第五步欄位條件裡的「編製分錄較少的人員」與「較少使用的科目」用「科目與人員統計」的方法，預設 11 筆是畫面帶入的條件值。
預篩選報告沿既有範本只輸出其中 7 條規則，不能把報告當成全部畫面結果的副本。
報告涵蓋範圍與排序列在第 7 節。常用篩選條件的「在該季度前 X 天借記收入」是第五步條件，不是新增的預篩選規則；
它使用曆年季底 3 月 31 日、6 月 30 日、9 月 30 日及 12 月 31 日，不依案件起日平移會計季度。
另納入查核截止日前 X 天，包含截止日；前 X 天都由末日回推 X 減 1 天。只保留與查核期間有交集的視窗，
重疊或相連時合併，讀回列出實際日期區間；實際命中仍只限 GL 中的分錄。

## 6. 進階條件篩選

進階篩選讓使用者把多個條件組成情境，先預覽，再儲存結果。條件可以針對文字、日期、金額、
借貸性質、科目配對、風險訊號與已配對的攸關資料元素欄位。畫面把審計角色稱為「分類用途」，
把針對整張傳票的條件稱為「整張傳票條件」（裁定 2026-10-14-07）；程式裡的 `semanticRole`、`voucher` 和既有判定不變。
其他跨頁名稱見[前端說明的「同一資料在不同畫面的名稱」](jet-frontend-description.md#同一資料在不同畫面的名稱)。

實務上審計員先看「常用篩選條件」分頁的十張卡片，可以複選；也可以從右側條件組合上方的「從情境範例開始」套用十一個現成情境
（裁定 2026-11-03-05），再搭配預篩選條件與欄位條件，收斂出要測試的分錄。這十張卡最早是 KCT 小組提出的條件清單；JET 給所有審計員使用，
所以畫面、輸出與程式都不寫小組名稱與卡片字母（裁定 2026-10-29-10、2026-10-29-11）。
卡片、預篩選條件與欄位條件都收斂到同一份條件語法樹，卡片加入目前選取的條件組。
十張卡的資料寫在前端 `ui-core.js` 的 `FILTER_COMMON_CONDITIONS`，後端的鏡像是 `FilterCommonConditions`。

下表是十張卡和歷史紀錄裡的字母、現行執行方式的對應。字母只在對照歷史紀錄時使用，不出現在畫面上。

| 歷史紀錄的字母 | 卡片 | 現行執行方式 |
|:---|:---|:---|
| A | 在該季度前 X 天借記收入的會計分錄 | 專用條件型別 `revenueDebitNearQuarterEnd`，天數由審計員輸入 |
| B | 借記固定資產(PPE，不含在建)且貸記費用之分錄 | 借貸科目組合 `specialAccountCategoryPair`，借方與貸方分類由審計員選擇，預設包含下層 |
| C | 貸方為收入但借方非一般對方科目之分錄 | 專用條件型別 `revenueWithoutNormalCounterpart` |
| D | 收入之人工分錄 | 專用條件型別 `manualRevenueEntry` |
| E | 特定人員(財務長/執行長/高階主管等)建立之分錄 | 欄位條件的預設值：傳票建立人員屬於審計員填入的名單 |
| F | 特定摘要(如迴轉、調整等) | 欄位條件的預設值：摘要包含預設的關鍵字，關鍵字可以增刪 |
| G | 空白摘要 | 欄位條件的預設值：摘要是空白 |
| H | 特定尾數(如 999999/000000 結尾) | 欄位條件的預設值：金額絕對值以 000000 結尾，尾數可以改 |

這張卡和其他卡片一樣加入目前條件組，不自成一組（裁定 2026-10-02-03），加入的就是那一條欄位條件，不再包一層子條件組（裁定 2026-11-03-09）。
2026-11-03 以前存下的子條件組照舊能讀，條件說明寫「非營業日」，也照舊認得是這張卡。舊情境若保存週末過帳或假日過帳的組合，
照原條件樹計算、不轉換。`prescreen` 類規則在篩選中直接重用 `GlRulePredicates` 即時計算，不讀取先前預篩選執行的命中檔。

前五張卡的原始定義整理在 [`kct-gl-workflow.md`](kct-gl-workflow.md)，那份文件用字母 A 到 E 稱呼它們；
KCT 的正式全稱與後五張卡的來源還沒跟 KCT 確認（裁定 2026-10-19-32）。舊版 JET 的程式與流程圖沒有 KCT 名稱、
A 到 J 的清單，也沒有固定資產那張卡的分類表；它們只證明部分通用機制早已存在，例如特定人員、特定摘要、空白摘要、
尾數、人工分錄與非工作日。所以上表是現行程式的登錄，不是從舊版還原的。

使用「借記固定資產(PPE，不含在建)且貸記費用之分錄」前，先在第四步新增固定資產及營業費用兩個分類並配對科目；
JET 不自動建立分類。在建工程不要配到固定資產分類。第一個正式版隱藏分類的上下層級（裁定 2026-11-03-27）；
之後打開時，在建工程也不要放在固定資產底下，因為預設包含下層分類。
「貸方為收入但借方非一般對方科目之分錄」不把現金算一般對方科目；要排除現金銷貨，改用預篩選條件「未預期借貸組合」。

自動名稱和自訂條件同一種寫法：取前兩條條件的名稱用「、」接起來，超過兩條時再加「等 N 項條件」，N 是條件總數；超過 64 字只留第一條。卡片帶入的條件用卡片名稱。
自動動機是每張選取的卡片一行，前五張逐字帶入上述流程文件的評估說明，後五張沿用卡片名稱；不是卡片帶入的條件，
每條再加一行「自訂：」與條件說明（裁定 2026-10-07-06）。已儲存或手改的名稱與動機不改寫。
第五步已儲存情境與第六步情境選項列出動機時，自動產生的動機只列前五張卡的評估說明，卡片名稱與「自訂：」那幾行不列；
審計員改寫過的動機整段列出（裁定 2026-10-30-02）。存進情境與寫進底稿的動機不受影響。
名稱與動機不必填：留白儲存時由後端依同一套規則產生名稱與動機，和畫面帶入的文字相同（裁定 2026-10-29-16）；
自動名稱和其他已存情境同名時，照畫面的做法在名稱後加上數字。

篩選的核心原則是：

- 先相容舊版 JET 已涵蓋的審計功能與需求，再在此基礎上重構與改善操作（裁定 2026-09-18-05）。
  條件定義沿來源核對，實作維持共用 AST；已裁定的新制差異保留，不因舊表單不同就自行回復。
- 條件語法樹（AST）由後端驗證，不接受任意 SQL。
- 計算留在資料庫，以參數化、集合式查詢完成。
- 大量命中資料只回摘要與鍵集分頁（keyset pagination）；明細表的排序與搜尋也在資料庫端，換排序或搜尋
  從第一頁重載，空值一律排最後。
- 已儲存的情境要和資料、欄位配對、驗證結果及規則版本連動；上游變更後不能沿用已失效的結果。
- 上游修改時清除下游（裁定 2026-10-07-03）：會讓篩選結果過期的修改，在同一筆交易內清掉全部已存情境與命中，
  審計員依新資料重新設定情境，JET 不保留舊情境讓人逐一修正。會清除的修改是重新匯入或重新確認 GL 或 TB 配對、
  科目配對與分類設定、授權編製人員清單、國定假日與補班日、每週休息日，以及期末財報準備日；
  GL 與 TB 的匯入或配對確認是同一層級的資料修改，資料驗證、預篩選與篩選命中一起失效。
  GL 與 TB 的取代、附加及重新確認配對也清除已存科目配對、原始配對列及配對匯入狀態（裁定 2026-10-08-12），
  前端同步捨棄未儲存分類與勾選。分類定義保留，重新配對時依現行 GL 與 TB 產生科目清單。
  資料庫內的修改失敗時整筆回復，情境照舊保留；
  財報準備日存在案件設定檔，清除結果的交易要等新日期存好才提交；存檔失敗時一起回復，情境與結果都保留。
  已匯出的條件篩選報告與底稿檔不改寫，報告清單標成過期。觸發條件只來自唯一的失效政策
  `AuditDependencyPolicy`，各資料庫共用 `ResultReset` 執行清除。
- 篩選規則更新後，不要求逐案重新儲存情境（裁定 2026-10-02-05）。開啟案件時，JET 先用目前規則逐一檢查
  已儲存的情境，檢查方式與重算命中前相同。全部仍然有效時，整批改用目前規則：名稱、動機與條件內容不變，
  只更新規則版本與 `populationScope` 兩個欄位，並換上新的儲存時間；舊命中在同一交易清除，依舊規則產生的
  條件篩選報告與底稿因此標為過期，第一次查看命中或匯出時才重算。
- 只要有一個情境不符合目前規則，整批都不動，開案回應逐一列出情境位置、名稱與原因。GL 不是依
  查核期間建立、規則版本無法辨識或比目前版本新的情境，也不自動改版，避免默默改變 GL。
  查詢與匯出仍檢查規則版本，資料不一致時擋下。實作見 `FilterScenarioRuleUpgrade` 與 `ProjectLoadHandler`。
  條件內容讀不出來的情境也逐一列出，寫「條件內容無法讀取」，可以移除；只有位置不正確時，
  才不逐一列出（裁定 2026-10-13-21、2026-10-13-24）。每個情境各自儲存，
  各情境的儲存時間本來就不同，不算成不一致（裁定 2026-10-30-33）。
- 待修正清單的原因只寫哪裡不符合，下一步由畫面在清單最後寫一次（裁定 2026-10-13-20）。
  只有下一步和通用說法不同的原因自己帶下一步：攸關資料元素欄位已不在欄位配對中、回溯過帳已停用、
  要先填期末財報準備日、要先匯入授權編製人員清單，以及要先在第四步設定科目分類。
  同一句也標在儲存或預覽時的條件下方。條件用到認不得的欄位時寫「此條件使用的欄位已不存在」。
  條件標題與讀回同樣不印程式代號（裁定 2026-10-14-01）。認不得的欄位，標題寫「欄位已不存在」，讀回寫「已不存在的欄位」。
  不在欄位配對中的攸關資料元素欄位寫「已不在欄位配對中的攸關資料元素欄位」，讀回不接金額比較基準。
  認不得的預篩選條件、比對方式或借貸組合方式寫「已停用的條件」。
  缺科目分類時，原因寫第四步分類設定裡目前的分類名稱，依用途對應收入、應收、現金與預收四個內建分類，審計員改過名稱就寫新名稱。
- 只有存檔內容損毀或程式送錯資料才會出現的條件錯誤，例如結合方式或比較方式的值不在允許範圍，畫面不顯示原本的句子與英文代碼
  （做法見裁定總表 2026-10-13-30）。
  開案的待修正清單同一個情境不論有幾條，只寫一次「條件內容無法讀取」；儲存與預覽時標在那一條條件下方，
  寫「此條件內容有誤，無法儲存。請刪除此條件後重新設定。」，沒有組號條號時寫在儲存鈕上方。
  哪一條、哪一種損毀只記進支援日誌的 `filter.scenario_unreadable` 事件，欄位是動作名稱、情境位置、組號、條號與程式寫死的原因代號，
  不含情境名稱或條件內容。判斷在 `FilterScenarioCorruption`，驗證器與解析情境的程式共用。
- 開案也逐一檢查（裁定 2026-10-13-25）：已是目前規則版本的情境，開案時也用和儲存相同的檢查再看一次。
  因分類、欄位配對這類其他資料改變而不合格的情境，開案時就列在待修正清單，篩選結果照待修正的規則鎖住，
  不會等到查看命中才失敗。全部合格時維持原狀，不換儲存時間，也不重算命中。
- 第五步一次只存或刪一個情境（裁定 2026-10-13-24）。儲存、另存副本與移除只處理正在處理的那一個情境，
  其他情境由 JET 照資料庫裡的原樣保留，不整批重新檢查，所以待修正的情境可以一個一個改或刪，改沒問題的情境也不會被擋。
  每次寫入時 JET 用目前規則逐一檢查全部情境：全部改好或刪掉之後，才和開案自動改版一樣改用目前規則，
  並立即算出命中、解除鎖定；之前高風險條件彙總、條件篩選報告與第六步照樣鎖住。「重新檢查並儲存情境」把能套用目前規則的情境
  改用目前規則，還不能套用的照原樣保留並列出原因，不會整批失敗。開案與寫入用同一段逐筆檢查。實作見 `FilterScenarioBatchWriter`。
- 儲存情境時把篩選結果存進資料庫，之後檢視不必重新計算；移除情境時連同結果一起刪除（裁定 2026-10-30-33）：
  - 儲存或修改一個情境時，只計算並存下這一個情境的結果：命中的分錄存在 `filter_hit`，命中傳票裡每筆分錄符合第幾組第幾條
    存在 `filter_hit_condition`，兩張表都依情境不變的編號 `scenario_id` 區分，所有情境共用同一張結果表。
    其他情境的定義、儲存時間與結果照原樣保留，不重算。
  - 移除情境時，同一個交易只刪掉這個情境的定義與結果。畫面、高風險條件彙總的 C1、C2 代號與底稿依清單順序編號，
    後面的情境順序往前補；結果依 `scenario_id` 存放，所以不必改寫，也不重算。
  - 打開已儲存的情境、換頁、排序、依傳票號碼查看與展開傳票，都讀存好的結果，不對查核期間的分錄判斷條件；
    傳票的分錄數、總額與日期仍讀 GL。「篩選與檢視」的「查看符合的傳票」是還沒儲存的草稿，即時計算。
  - 已儲存情境的傳票頁只綁這個情境自己的版本，存或移除別的情境，正在看的頁面不會過期；這個情境改了、換了位置，
    或上游修改清掉了情境，就要從第一頁重新載入。
  - 還有情境不能套用目前規則時，只寫定義、清掉全部情境的結果並標成過期，
    高風險條件彙總、條件篩選報告與第六步維持鎖住；全部改好時一次重算全部情境。開案時整批改用新規則後結果也標成過期，
    之後第一次儲存、查看結果或匯出時重算全部情境。
  - 上游修改在同一個交易清掉全部情境與兩張結果表（裁定 2026-10-07-03）。

MAC 等外部多層會計科目表及其對照不在目前職責範圍，不作為篩選條件或既有科目配對改善的前置工作。
第一個正式版隱藏分類的上下層級（裁定 2026-11-03-27）：第四步不顯示「進階設定」，分類用途與上層分類都不能設定，
新增的分類沒有上層、用途是其他；第五步不顯示「選取依據」，新建的分類條件照舊包含下層。後端、資料庫與查詢都保留下面的上下層與選取方式，
案件裡已有的上下層照舊計算；前端的開關是 `ui-core.js` 的 `FEATURES.categoryHierarchy`。
本地分類可設定上層分類，分類用途獨立保存。新增下層時畫面先帶入上層用途，審計員仍可修改；改動既有分類的上層不會重設用途。選取分類時可指定僅分類本身、包含所有下層，
或具有相同分類用途的分類。沒有指定選取方式的條件按分類用途判斷。

本地分類樹是為了讓審計員依案件整理科目，並在篩選時決定要選多大的範圍。它不是外部標準科目表，
也不會依分類名稱自動判斷會計含義。例如把「銀行存款」放在「現金類」下面，選分類本身只找直接配對
到該分類的科目；選包含下層才一併找銀行存款。選相同「分類用途」則跨越樹的位置，找用途相同的分類。
新建分類條件，包括欄位條件的「科目分類」與「借方與貸方分類組合」，預設包含下層。條件說明與報告列出比對方式和實際納入的分類；
選的分類都沒有下層時，包含下層與僅分類本身選到的分類相同，條件說明不寫比對方式與實際納入的分類。相同分類用途照舊寫出。

分類由穩定 ID 識別，名稱只供閱讀；改名不會把舊情境誤認成另一分類。上層關係與下層查詢表在同一交易
保存，查詢沿既有篩選編譯器產生集合 SQL，不在前端遍歷分錄。循環、遺失的上層及刪除仍有科目配對使用的分類
會要求先調整，避免留下無法解讀的配對；這是資料一致性保護，不是審計核准程序。保存後更新版本，
使相依結果失效並清除全部已存篩選情境，所以只被情境使用的分類可以直接刪除。
實作見 `AccountCategoryInvariant`、`LocalAccountCategoryStore`、`AccountCategoryHierarchy` 與 `FilterCompilation`。

分類設定可以同一次新建上層和下層。移除上層前列出受影響的下層，確認後把直接下層接到原分類的上一層；儲存前仍可取消，科目配對仍在使用的分類照舊不能刪除。
科目分類條件只判斷分類，要限定方向時另加「借貸別」。整張傳票條件的「不存在符合」若只含分類條件，
表示同一張傳票在 GL 中，借方與貸方都沒有屬於選定分類的科目。
第五步也可依分類樹選入本案的實際科目編號並搜尋，仍儲存為原本的科目編號值清單，不新增條件型別。

科目分類條件有兩種模式：「科目屬於指定分類」「科目不屬於指定分類」。要查整張傳票沒有某側分類，
用「不存在符合」的整張傳票條件，子條件選借貸別與科目屬於指定分類。
選「相同分類用途」時，自訂分類有 Cash 用途也算 Cash。科目配對範本分類留白的科目
依 legacy 視為 Others；沒有出現在配對檔的科目不屬於任何分類。結果只有命中與不命中兩種，沒有待判定
（裁定 2026-09-07-03）；第四步的科目配對卡提醒「分類留白 N 筆，視為 Others」並可展開清單，要改分類就在
範本 C 欄填好再重新匯入。
科目配對範本可沿用前一案件，匯入後提醒「本案沒有的科目」與「配對檔未列的科目」，兩份清單各自分頁。
比較對象是有效 GL 與 TB 的科目聯集，排除無法配對的空白編號；TB 獨有及零變動科目也包含在內。
空白科目配對範本與「配對檔未列的科目」使用同一批可配對科目；科目清單另包含配對檔多出的科目。
範本不列空白科目編號，填好再匯回時不會因空白編號被拒收。
分類留白仍視為 Others，不屬於檔案未列的科目。額外科目照常保存，不阻擋匯入，也不會出現在篩選結果；
它們仍可能影響分類前置條件的資格、分類留白筆數及底稿科目配對表。
差異筆數只在匯入及展開清單時計算；重開案件不額外掃描 GL，未查詢時畫面顯示尚未核對。
匯入完成後摘要查詢失敗不影響已儲存的科目配對，筆數顯示尚未核對，展開清單時可重新查詢。

科目配對欄名先比對確切名稱，去頭尾空白且不分大小寫；支援新範本的 `GL_Number`、`GL_Name`、
`Standardized Account Name*`，以及既有 `GL_NUMBER`、`GL_NAME`、`STANDARDIZED_ACCOUNT_NAME`。
再依分類、科目編號、科目名稱的順序，用中英文關鍵字找未認領的欄，最後依剩餘欄位順序補齊。
依順序判斷的欄位會在匯入完成後提醒來源欄與用途，不阻擋匯入。這個規則只在匯入時使用；預覽只讀已存配對，不重新判讀舊檔欄名。
科目配對範本先以第一個有內容的列辨識欄名；`.xlsx` 無法辨識時，再略過前兩列，依正式範本的第三列欄名讀取。
這時前兩列即使空白也算在略過範圍內。
檔案設有 autoFilter 或隱藏列時，JET 仍讀入全部資料列。

借貸科目組合合併成一張卡，五種白話模式：「借方是 A 且貸方是 B」「借方是 A 且
整張傳票沒有 B 貸方」「貸方是 B 且整張傳票沒有 A 借方」「借方是 A，看它的對方科目」「貸方是 B，看它的
對方科目」。原有配對及常用篩選條件的規則保留原結果。

條件組和子條件組的條件用 AND 或 OR 連接，每一層依原順序由左到右計算；畫面只寫 AND 與 OR（裁定 2026-10-30-32）。欄位條件由同一筆分錄判斷；
只有傳票層條件時，呈現查核期間內的分錄，標示整張傳票條件成立。
整張傳票條件可選「至少一筆符合」「全部符合」或「不存在符合」，不另選借方或貸方範圍。
每筆分錄先判斷子條件的完整組合，再判斷整張傳票。要限定方向時，把「借貸別」放進子條件。
例如借貸別貸方、科目 B 且摘要含 X，必須由同一筆分錄符合，不能分別由兩筆分錄提供佐證。
「全部符合」須至少有一筆，且每筆都符合；「不存在符合」在沒有符合子條件的分錄時成立。
要表達「每筆借方都符合 X」時，「不存在符合：借方且不符合 X」在完全沒有借方的傳票也會成立；要排除這種傳票，還須用 AND 加上另一條「至少一筆符合：借貸別借方」。
空白傳票號碼的分錄不屬於任何傳票，因此三種傳票量詞對它們一律不成立。
列層條件仍依欄位值判斷；空白號碼仍可在空白傳票號碼明細查看。「貸方為收入但借方非一般對方科目」與預篩選「未預期借貸組合」也不選入空白號碼的收入貸方。
只看 GL 中的分錄；零元沿用借方判斷，空白值依子條件原有設定，SQL 的未知值視為不符合。
傳票量詞成立時呈現該傳票在 GL 中的分錄，標示為整張傳票條件成立；要只標記某種主要分錄，
先用一般條件選出要標記的分錄，再用 AND 加上整張傳票條件。已儲存情境裡舊的「同一傳票」比對範圍
讀到時當成無法讀取的條件（裁定 2026-10-30-25）。
科目編號與科目名稱不附帶方向（裁定 2026-10-14-08）。要由同一筆分錄符合借貸別與科目值，就把兩條放在用 AND 連接的子條件組。
例如先選借方且科目 A，再加上「至少一筆符合：貸方且科目 B」，只標記借 A 的分錄；
整張傳票條件的成立原因會顯示在明細中，其他分錄供覆核。這不要求該側每筆都符合，也不改變分類的選取方式。
日期及金額區間包含兩端；指定日期用原生日期框逐筆加入，也可用「每月幾日屬於」「每月幾日不屬於」填 1 到 31
的日子（例如 28、31，重複自動合併）。文字、日期和金額依型別提供清單、否定、空白及其他比較方式；
「包含任一文字」「不包含任何文字」接受多個關鍵字，清單最多 100 個不同值。核心金額只比較絕對值，
額外數值欄位沿用含正負號方式。要排除某些日期、文字或金額，就用該條件的否定模式（不屬於、不在區間、
不包含）放進條件組，沒有獨立的排除區域。所有值條件預設不列入空白，日期空白的分錄不命中；要把空白
也算進來時勾「空白也符合」。開啟舊情境不自動換規則。

摘要關鍵字、金額尾數、每月幾日、人員代號及科目編號清單接受換行、半形或全形逗號、頓號及 Tab。
其他文字值清單維持一行一個，值裡的逗號不拆開；單一開頭或結尾條件只收一個值，多行輸入會提醒。
單日與區間使用原生日期框，不能直接輸入民國年。貼上日期清單仍沿用 GL 匯入的解析方式，
包括西元斜線、點號、八位數 yyyyMMdd 與案件允許的民國年，民國年開關由案件提供。
純數字不當成日期：2025、2025.12、45292 這類值，GL 匯入與日期清單都視為無法辨識（裁定 2026-10-22-11），
確認配對時寫出列號，審計員在 Excel 把欄位設成日期格式後重新匯入。
050315 這類六位數的日期同樣是純數字，一樣視為無法辨識（裁定 2026-10-28-01）。
Excel 裡已經是日期格式的儲存格由讀取器依儲存格格式換算，不受影響。帶逗號的數字（例如 1,234 或 12,31）同樣不當成日期，
也不交給寬鬆解析（裁定 2026-10-19-09）。前後端的日期規則共用一份固定答案 `tools/tests/fixtures/date-normalization.json`
（裁定 2026-10-22-12），一邊改了規則，另一邊的測試就會失敗。交給寬鬆解析的值，原文要寫出四位數年份與日：
12/31、2025-12、Dec 2025、31 Dec 這類缺年份、缺日或只寫兩位數年份的值，同樣視為無法辨識的日期，不補成今年或 1 日；
June 11, 2025 與帶時間的 2025/06/11 00:00:00 照常接受（裁定 2026-10-19-11）。範圍外或無法辨識的值保留原文，由後端寫出格式錯誤。
畫面和後端以實際送出的清單計算 100 個值上限，不把大小寫不同的兩個輸入擅自合併。絕對值金額填負數時只提醒，不另改命中定義。
特定人員、特定摘要、空白摘要與特定尾數四張卡，和欄位的同類常用查法一樣，分別帶入人員清單、摘要關鍵字、空白摘要及金額尾數的欄位條件；
卡片帶入的條件另外記住是哪一張卡。
清單超過 100 個值時，拆成多條放進用 OR 連接的子條件組；否定清單則放進用 AND 連接的子條件組。
常用查法「尾數連續多個 0」的整數部分為 0 時不符合，避免尾數只有一個 0 時多選入零元或不足 1 元的分錄（裁定 2026-11-03-07）。
使用停用寫法的舊情境會列為待修正，不自動轉換定義，也不沿用舊命中；畫面不說明如何重建（裁定 2026-10-30-25）：
五種停用的型別寫「此條件的類型已停用，請刪除此條件」，其餘停用寫法寫「條件內容無法讀取」。
歷史型別 `text`、`textSet`、`dateRange`、`numRange`、`typed` 仍沿用原本的讀回與編輯方式。

日期條件可選週末、假日、補班日、非營業日及各自的否定。非營業日為週末或假日再排除補班日；
週末本身仍包含補班日。清單沒有日期時，不自行推算國定假日。文字另有開頭及結尾不符合。
「非營業日之分錄」這張卡也使用排除補班日的非營業日判斷。舊情境若明確保存週末或假日的組合，仍保留原樹並如實寫出兩者，不默默改成新定義。
第五步的預篩選條件「未預期借貸組合」沿用第四步的前置條件：已配對收入分類，並至少配對應收、現金或預收其中一類。
日期也可選每月月初或月底 1 到 31 天，包含月初或月底當天；天數超過當月長度時涵蓋整月。
月份依所選日期欄位計算，閏年二月也依實際天數處理，與「查核期末最後幾天」分開。
總帳日與核准日的加班例外各自用否定條件設定，放在比對同一筆分錄、用 AND 連接的組內；
例如總帳日在非營業日，且總帳日不在指定加班日期。核准日可另設不同清單，不會修改共用假日或補班日資料。
金額的特定尾數比較忽略正負與小數，保留指定的位數；例如 -1,001.45 符合 001，1 元不符合 001。
日期、金額、人員、會計科目與其他文字分組呈現；建立日或原幣金額需先明確配成攸關資料元素欄位，不能猜來源。
第三步的「傳票建立日」快捷可選未使用的來源，自動勾選並設為日期；已有同名欄時更換來源並保留識別碼。
來源已用於另一個攸關資料元素欄位時，先提示目前用途，讓審計員確認改名及日期型別，或取消。確認後沿用被選欄的識別碼，其他欄不刪除。

「科目與人員統計」可依科目編號、建立人員或核准人員，選擇分錄筆數或傳票張數（同號只算一張），提供等於、小於、
大於、介於及含等號的比較。統計先在 GL 中分組，區間含兩端；空白識別值不命中。同案件相同傳票號碼
算一張，空白號碼不計張，但符合該科目或人員的分錄仍列出。欄位條件裡的「較少使用的科目」與「編製分錄較少的人員」帶入這項條件，預設 11 筆以下。
人員依去空白、不分大小寫的識別值分組；科目編號只去空白，大小寫規則不變。文字比較與空白判斷去掉的空白字元集合
和 .NET 的 Trim 相同，SQLite 與 DuckDB 一致。

第五步的條件只能用 GL 已有來源的欄位，不論哪一種比較方式。核心欄位還沒選擇來源欄時，後端擋下用到它的條件，
原因寫「「欄位名稱」尚未選擇來源欄」，不會把沒有提供的整欄當成內容空白而得到 0 筆。傳票文件項次沒有來源時由系統自動編號，
傳票核准日選「與總帳日期相同」時由總帳日期帶入，兩者都算已有來源。哪些欄位有來源，由欄位目錄依已確認的 GL 配對算出
（`JetFieldCatalog.AvailableGlFields`），第四步、第五步與畫面讀同一份答案（裁定 2026-10-22-05）。已存的情境用到沒有來源的欄位時，
開案時列進待修正清單（裁定 2026-10-22-04）；改好之前，高風險條件彙總、條件篩選報告與第六步照待修正的規則鎖住。
沒有上傳國定假日清單時，第五步的假日條件仍不另外檢查，結果是 0 筆（裁定 2026-10-04-01）。

每條條件與每個預篩選規則需要哪些 GL 欄位、期末財報準備日、授權編製人員清單或科目分類，寫在 Domain 的 `JetRuleRequirements` 一張表。
第四步的無法執行原因、第五步的驗證與畫面的停用原因都讀這張表，所以同一條規則在兩步給同一個原因。RDE 欄位的前置檢查不變。
篩選條件說的「所有欄位」，指每個已配對的文字欄位及攸關資料元素欄位各自比較；不是把整列所有欄位串起來搜尋，也不開放任意 SQL。
畫面及報表的「且」「或」是文字呈現；條件依原順序由左向右合併，第一條連接詞沒有左側條件，不參與運算。
混合連接詞的讀回文字保留括號，不按一般 SQL 的運算子優先序重新解讀。

預覽與儲存都只要求條件有效，名稱與動機可以留白，留白時由後端依條件補上。後端指出某條規則有問題時，

錯誤標明屬於別的情境時，畫面不標在目前的條件上，改在儲存按鈕上方寫出是哪一個情境。命中傳票清單可分頁展開整張傳票的分錄，
每列標示符合第幾組第幾條主要條件、或整張傳票條件成立，其餘為參考分錄，不算命中。
清單上方分開寫符合條件的傳票數量與分錄筆數（裁定 2026-10-16-08）。情境只有一組，而且這組只有一條「未預期借貸組合」時，
分錄筆數和條件篩選報告的摘要一樣計算整張傳票，展開後同一張傳票的其他分錄也列為符合；其他情境只計直接符合的分錄。分頁綁定案件、
資料與情境版本，資料變更後重新預覽。第五步也能更新原情境、另存副本或取消編輯；更新不占新名額，
最多十個情境的上限仍適用副本。右側條件組合上方的「從情境範例開始」有十一個情境範例，一鍵帶入條件、名稱與動機並替換整份條件，可再修改：
「借現金、貸非現金」「貸現金、借非現金」「非營業日且排除指定日期」「期末最後 7 天的人工分錄」「空白摘要或空白核准人員」
「特定人員的大額分錄」「週末人工分錄的特定摘要」「人工分錄的特定部門」「借方與貸方科目編號組合」「指定借貸科目組合的大額分錄」
及「財報準備期間的人工假日分錄」。
範本或草稿還有值沒填時，畫面先擋下預覽，並寫出第幾組第幾條與條件名稱。

欄位條件分頁依日期、數字、文字、類別四組列出欄位，常用查法收在各欄位「加入」打開的選單裡（裁定 2026-10-08-06、2026-11-03-05、2026-11-03-06、2026-11-03-37）；

## 7. 輸出報告

產品目前有五種報告與一份工作檔：

1. 資料驗證報告
2. 資料可靠性抽樣清單
3. 預篩選報告
4. 條件篩選報告
5. 工作底稿
6. 科目配對範本（工作檔，不是報告）

報告的 `Prepared by` 使用建立案件時保存的建案者 `operatorId`，不是目前開啟案件的 Windows 帳號；案件畫面的目前操作人員與它分開顯示。
這條規則適用於範本已有 `Prepared by` 的報告。工作底稿沒有這個欄位，維持既有底稿版面與樣式，不新增欄位。
建案的人可能把案件資料夾交給其他查核團隊匯出，這種交接情境也維持建案者（裁定 2026-10-06-02）。
預篩選報告的既有範本文字照原文保留，包括「之後核准」，不因畫面讀回補日期而改寫範本（裁定 2026-10-04-01 的 Q7）。

底稿與報告裡描述欄位的句子，欄位名稱用【】標示，值照條件說明的寫法用「」，例如「【傳票摘要】 包含「調整」」。
條件說明、欄位資訊的說明句，以及底稿與報告由 JET 寫出的其他句子都照這個寫法；畫面上的條件讀回、滑鼠提示與情境的自動名稱不加
（裁定 2026-11-03-04、2026-11-03-17）。認不得的欄位寫的是替代句，例如「已不存在的欄位」，不是欄位名稱，不加【】；
範本原有的文字照舊版保留，也不加。

資料驗證報告的 `Source_Quality` 工作表維持英文表頭，對照如下。它目前只有 `blankGlDate` 類別，表示「總帳日期空白」，不是期間外分錄。

| 英文欄名 | 內容 |
|:---|:---|
| `CATEGORY` | 品質問題代碼，目前為 `blankGlDate` |
| `SOURCE_ROW_NUMBER` | 匯入來源的資料列號 |
| `SOURCE_LABEL` | 匯入來源標籤，用來辨認來源檔或工作表 |
| `DOCUMENT_NUMBER` | 傳票號碼 |
| `ACCOUNT_CODE` | 科目編號 |
| `GL_DATE` | 總帳日期；本類別通常為空白 |
| `DESCRIPTION` | 傳票摘要 |

工作底稿需要目前可用的資料驗證結果，不需要先產生條件篩選報告。沒有已儲存的篩選情境也能產生底稿（裁定 2026-10-29-16），
有情境但一個都沒勾選時也照樣產生（裁定 2026-10-30-15）；這兩種情況的 Step 3 與 Step 4 只留表頭。已儲存的情境無法套用目前規則時，
要先修改情境才能匯出。沒有情境時產出的底稿沒有篩選版本，之後一儲存情境就標成過期。
底稿匯出直接用儲存情境時存好的結果，只檢查本次所選的情境仍能套用目前規則，不重算；未選情境不影響本次輸出。
存好的結果標成過期時（例如開案時整批改用新規則之後），才只重算本次所選的情境。
重新配對這類上游修改會清除全部已存情境（見篩選的核心原則），不會留下因缺少來源欄位、等待逐一修正的舊情境。
部分重算只替換所選命中，保留未選資料，不能把全案高風險條件彙總標成已更新。新底稿記錄既有的篩選資料版本，
案件重開時仍能區分「這份底稿的來源是目前資料」與「全案情境是否全部重新計算」。條件篩選報告同樣直接用存好的結果，
檢查全部情境；結果標成過期時才重算全部情境。它是獨立輸出，不是底稿的資料來源。
條件篩選報告的 Prepared date 寫按下匯出那一天的本機日期（裁定 2026-11-01-04）；資料驗證報告與預篩選報告也一樣，
不寫執行資料驗證或預篩選的時間（裁定 2026-11-02-03）。
科目配對工作檔只使用已配對的科目、分類及欄位資訊，沒有資料驗證結果時仍可準備；不因工作檔產生而偽造一次驗證。

保留欄名與順序，再依標準資料的分錄識別值取回原始列；不是只輸出畫面預覽的固定欄位。原始明細預設按 `entry_id` 升冪。

### 檔案、發布與版本

程式隨附範本位於 `src/JET/JET/Templates/`，由 `JET.csproj` 複製到輸出目錄。`data/` 內的同名或
近似工作簿是遷移參考，不會因為檔名相似就自動成為程式隨附範本。

報告產生器使用已確認的查詢結果與中繼資料，不重新解讀審計規則。產生大型工作簿時採串流方式：先寫
案件資料夾內以 `.` 開頭的暫存檔，完整寫好後才改名成正式檔名。可處理的失敗或取消會清除半成品；程序
中斷或檔案佔用造成的殘留，會在下次讀寫前嘗試清除。儲存不計算內容雜湊，也不保留交易復原紀錄。
報告清單仍保存檔名、大小與修改時間，用來顯示外部修改提醒，不會因此拒絕載入案件。
兩份驗證報告一起發布時，任何一份或清單索引寫入失敗，都會還原本次已換掉的報告，保留原索引；首次輸出則移除本次新檔。
若外部鎖檔等原因連還原也阻止，JET 明說還原未完成。有原檔時保留備份；原本沒有檔案時，提示本次新檔仍保留，不把半批輸出宣稱為成功。
這個同次操作的暫存備份不是舊版的交易復原紀錄，也不新增內容雜湊。

新增條件的完整說明會寫入條件篩選報告，並列在工作底稿的 Step 3 情境名稱下方。所有規則型別都使用同一個說明產生器，
包含「財報準備日起核准」「金額尾數連續 6 個 0」這類預篩選條件。
底稿展開整張傳票時，參考分錄不重新標成命中。例外是只有一組、這組只有一條「未預期借貸組合」的情境：
Step 4-1 把命中傳票的每一列都標上這個情境，和條件篩選報告摘要的列數相同。
超過 Excel 單格容量的條件會在同一工作表接續列出，保留完整文字。條件篩選報告的摘要會指向
續列位置；工作底稿則以同一情境代號標示續列，不重複計入傳票數。

五種報告與科目配對工作檔的文字都依 Excel 的跳脫格式寫入，來源文字含控制字元時仍能產生報告。
XML 不允許的字元與 CR 寫成 `_xHHHH_`，HHHH 是字元碼的十六進位。原文本來就有 `_x0041_` 這種寫法時，
開頭的底線寫成 `_x005F_`，Excel 才不會把它讀成別的字。Tab、換行與其他文字照原樣寫入。
這套寫法依 [Microsoft 對 Excel 跳脫字串的說明](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/d34ae755-c53f-4a44-a363-c6dd3ee018a4)，
Excel 開啟時會還原成來源文字；用合成報告在 Excel 核對過，控制字元、CR LF 與 `_x0041_` 的顯示都可以接受（裁定 2026-10-21-10）。
來源資料與金額都不改。
文字儲存格一律由 `ExcelText` 建立，架構測試會擋下其他寫法。JET 讀 Excel 檔時用同一規則還原：總帳、試算表、科目配對、
授權編製人員與假日的匯入，以及從報告還原欄位配對，都是審計員在 Excel 看到什麼就讀到什麼；科目配對工作檔在 Excel 填好匯回時，
含控制字元的科目名稱和案件裡的一樣。

五種報告的公司名稱表頭在客戶名稱留空時使用案件名稱，和工作區標題一致。科目配對工作檔維持既有版面，不另加公司名稱表頭。
五種報告檔名加入案件查核起訖日 `yyyyMMdd-yyyyMMdd`，不同期間可直接辨識。
JET 自己寫的工作表，列高是字級的 1.5 倍：10 點的明細頁，例如 V_Report 3 到 5、R1 到 R7、各張 #Criteria Select 與 Source_Quality，
列高 15 點；12 點的可靠性樣本是 18 點。微軟正黑體比舊流程的 Arial 高，沿用 12.5 點會切到字。
10 點明細頁一律 15 點，11 點與 12 點用 16.5 與 18 點（裁定 2026-10-29-08）；1.5 倍是 Claude 從這三個數字歸納的算法，其他字級也照它算。
底稿各頁疊在範本上寫，預設列高沿用範本；資料多到另開接續工作表時，
接續的工作表同樣依字級的 1.5 倍設定列高。Source_Quality 的表頭與內文和其他明細頁相同。驗證報告的「自動化工具-檔案欄位資訊」跟著所在報告用 10 點、版本列不加藍底
（裁定 2026-10-29-07）；
底稿的同名工作表保留 11 點與藍底紅字的版本列，兩頁的欄位、黃色表頭與排列相同，表頭與版本列依字級的 1.5 倍加高。欄位名稱欄寬度上限 40，
底稿 step3 的條件與原因欄上限 60 與 50，超過時換行並依行數加高該列。
所有串流寫出的工作表都有標準工作表視圖，避免高 DPI 的原生 Excel 將列高折半。
報告清單顯示檔名、建立時間及大小，透過「開啟資料夾」定位，不長駐完整路徑。後端定位路徑依案件位置
重新解析，移動案件資料夾後不沿用舊絕對路徑。
只有工作底稿是正式輸出：每次匯出寫新的版本檔 `<案件前綴>_<yyyyMMdd-yyyyMMdd>_WorkingPaper_<yyyyMMdd-HHmmss>.xlsx`，
不覆蓋、不刪舊版；即使檔名選定後才出現同名檔，發布時也保留原檔並提示重新匯出。第六步可分頁查看
全部版本並在檔案總管定位，歷史版本不作為目前流程完成的證據。其餘四種報告每次匯出覆蓋同名檔。
第六步在「有可以套用目前規則的已儲存情境」或「已經有任何工作底稿版本紀錄」時可以進入；只有版本紀錄時
可以查看，但匯出按鈕停用，畫面寫出原因並請使用者到「進階條件篩選」儲存情境。匯出本身仍要求目前的驗證結果
與可用的情境版本。第六步、左側進度與流程總覽用同一個判斷：已有目前版本的工作底稿時第六步算完成。
科目配對範本是給審計員用 Excel 填寫 `Standardized Account Name*` 欄再匯回
的工作檔，固定檔名 `<案件前綴>_AccountMapping.xlsx`，不列入報告清單。
驗證完成後只自動建立尚不存在的範本，已有檔案就保留。手動重新產生空白範本才覆寫，最後發布時也遵守
所選方式，避免自動產生改動審計員已填寫的分類。

範本和報告都在正式檔改名前處理最後一次取消；範本取消時保留原檔。報告開始發布後，取消請求不再中斷
索引寫入；這不保證能排除磁碟或權限等寫入失敗。報告清單即將超過 4,096 筆時，先整理已確認檔案不存在的
底稿紀錄。正式發布前再次確認，期間被放回或無法確認的檔案仍保留；仍超限時不發布新檔，提示使用者
自行整理不需要的舊底稿後重試。整理不刪除實體檔，失敗或取消也不提前保存整理後的清單。

正式檔和索引已成功保存後，附帶清單讀取使用獨立 3 秒期限，不受晚到的使用者取消影響。清單 I/O 失敗或
逾時只在新檔旁提示「檔案已產生，但報告清單沒有更新；重新開啟案件就會更新，不必重新產生。」，不誤報匯出失敗。發布前寫入失敗、程式錯誤
及正式底稿不覆寫規則不放寬；這不表示所有案件索引的讀寫錯誤都可略過。

預設審計員可信（`docs/project-context.md`）：報告檔在 JET 之外被改寫、改名或刪除都不阻擋載入，第六步清單
只在該筆旁標示「已在 JET 之外修改」或「檔案不存在」，重新匯出即可。

## 8. 儲存與資料庫實作

本地分類以 `parent_category_id` 記上層分類，以 `account_category_path` 保存分類及其下層關係。
分類修改與關係表在同一交易保存；循環或不存在的上層會提示重新選擇，不留下部分更新。
修改分類設定會使篩選結果失效，並清除全部已存情境。
訊息紀錄 `message_log` 的等級收 `info`、`warn` 與 `error`（裁定 2026-10-13-15）。
匯入來源表 `import_batch_source` 的 `header_row` 欄保存審計員指定的欄名在第幾列。
SQL Server 把 GL 的項次、科目名稱、摘要與來源模組，TB 與科目配對的科目名稱，以及抽樣結果的項次固定為
`Latin1_General_BIN2`，不沿用資料庫的預設定序，讓三種資料庫的比較結果一致（裁定 2026-10-16-23）。
SQL Server 轉大寫的對照表見本節後段。
新的案件資料庫直接建成現行結構：SQLite 與 DuckDB 標成第 20 版，SQL Server 標成第 21 版，不逐版升級（裁定 2026-10-30-23）。
統一改名改了表名、欄名與 CHECK 值，改名前建立的案件版本較舊，同樣當成舊版案件。
已經建過表的資料庫只接受現行版本；比現行版本舊的是舊版 JET 建立的案件，開啟時回報 `invalid_project_schema`，
請審計員在案件清單刪除這個案件，再用目前版本重新建立並匯入資料。案件設定檔 `project.json` 的 `schemaVersion`
同樣只接受第 2 版（裁定 2026-10-30-23）。版本值讀不出來或比現行版本新時，當成版本資訊無法辨識。

SQLite 與 DuckDB 是本地資料庫實作；每個案件以一個自含資料夾保存中繼資料、資料庫與輸出產物。
SQL Server 是線上資料庫實作，使用共享資料庫中的案件範圍。三種實作在相同輸入與相同契約下應得到
相同結果；不能把資料庫差異當成合理的業務差異。

不分大小寫的比較與分組，都經過方言的 `ISqlDialect.Upper` 轉大寫；條件值在 .NET 端用 `ToUpperInvariant()` 轉換。
SQLite 與 DuckDB 的連線都把 `upper` 換成 .NET 的 `ToUpperInvariant()`，讓篩選資料與條件值採用一致的大寫轉換，
包含 café 等非 ASCII 文字。DuckDB 原生的 `upper` 會把 `ß` 轉成 `ẞ`、`ı` 轉成 `I`，所以和 SQLite 一樣替換。
一般連線、唯讀連線與底稿專用連線都保留這項設定；不另外安裝資料庫擴充，也不把分錄載入前端比較。
文字仍區分重音符號，沒有新增模糊比對或變更空白規則。

SQL Server 不能替換 `UPPER`，所以轉大寫用 `Latin1_General_100_BIN2` 的大小寫對照表（裁定 2026-10-19-30）。
文字欄本身仍是 `Latin1_General_BIN2`；兩種定序都依字元碼比較，只有轉大寫的對照表不同，舊表和 .NET 有 546 個字元不同。
在 SQL Server 2022 逐字元比對基本多語言平面的結果：ASCII、全形英數、中文與基本西里爾字母都和 .NET 相同，
Latin-1 與 Latin Extended-A 的字母也相同，只有 `µ`、`ı`、`ſ` 例外。仍不同的共 308 個字元，集中在喬治亞文、切羅基文、
西里爾字母的補充與擴充區，以及擴充拉丁字母；例如 `ı` 在 SQL Server 會轉成 `I`，`µ` 不轉成希臘字母 `Μ`，喬治亞文小寫字母不轉大寫。
補充平面的字元 SQL Server 一律不轉大寫。這些記為已知差異，不另做對照表。

沒有指定空值位置的排序，三種資料庫都把空值排在遞增的最前面、遞減的最後面。DuckDB 預設遞增時把空值排最後，
所以連線字串固定加上 `default_null_order=nulls_first_on_asc_last_on_desc`。

匯入的文字欄在三種資料庫共用同一組長度上限，定義在 `TextStorageLimits`（裁定 2026-10-19-28）。
傳票號碼、科目編號、授權人員名稱與攸關資料元素的文字值是 450 字；項次、科目名稱、來源模組、編製者、核准者與過帳狀態是 400 字；
假日名稱 256 字；摘要不限。上限照 SQL Server 的欄寬訂定。GL 與 TB 超過上限時，投影回報列錯誤；
科目配對範本、授權編製人員清單與國定假日清單整批不儲存，並列出超長的列號。錯誤訊息裡過長的值只顯示前 50 字。
篩選情境名稱也在三種資料庫共用 400 字上限（裁定 2026-10-19-26）。超過時儲存回
`invalid_scenario`，訊息寫出上限，任何資料庫都不截斷；畫面的名稱輸入欄同樣最多 400 字。

匯入紀錄的 `source_file_path` 是舊欄名。三種資料庫都只存來源檔名，不存本機完整路徑；呼叫端給的檔名帶目錄時，
存放層只取最後一段。驗證結果與預篩選結果分別存在 `validation_result` 與 `prescreen_result`，每次執行新增一列；
同一種結果有兩筆時間相同時，三種資料庫都以 `result_id` 較大的一筆當最新。

使用者按取消後，三種資料庫執行中的語句都會停下，原 request 以 `operation_cancelled` 結束，交易內被中斷的寫入一併回復。
SQLite 的驅動本身不中斷執行中的語句，JET 的 SQLite 連線在執行期間把取消接到 `sqlite3_interrupt`
（`CancellableSqliteConnection`）。SQL Server 停下時驅動丟出自己的例外，由 dispatcher 在 action 出口改回報成取消。

科目配對表的 `classification_explicit` 記科目分類是否實際填寫，`schema_info` 另記篩選資料版本。這個紀錄只用在第四步
「分類留白 N 筆，視為 Others」的提醒；篩選一律把留白視為 Others（裁定 2026-09-07-03），開案不另做分類
證據修復，也不重複掃描科目配對資料。上游資料變更會在同一交易更新篩選資料版本，使舊分頁失效。

選擇 SQLite 與 DuckDB 作為本地實作的理由來自正式環境限制（見
[`project-context.md`](project-context.md)）：兩者都免伺服器、免系統管理權限、單一案件資料夾自含，
一般 GA 不需要管理資料庫服務就能作業。歷史量測已用 DuckDB 驗證 500 萬到 2,000 萬列母體的匯入、
驗證、預篩選與底稿輸出。兩個引擎能力不完全相同——例如 DuckDB 1.5.3 沒有 trigger，`operation_log`
的 append-only 在 SQLite 與 SQL Server 由資料庫層強制，在 DuckDB 維持程式紀律——這類差異由
Infrastructure 吸收，不得外溢成業務行為差異。

DuckDB 每次開啟資料庫要幾十毫秒，所以 DuckDB 案件在一次操作期間保持資料庫開啟，同一個操作裡的多次讀寫
沿用同一個已開啟的資料庫。兩次操作之間資料庫照舊關閉，檔案解除鎖定。刪除案件時若還有操作在使用這個
DuckDB 資料庫，JET 回 `operation_in_progress` 而且不刪任何檔案，等那個操作完成後再刪除即可。
SQLite 與 SQL Server 案件不受影響。

本地案件的可攜性以前提為「JET 已正常離開案件，再冷複製完整案件資料夾」。正在使用的資料庫、
WAL 熱複製與 SQL Server 案件不在這個保證內。

案件資料夾的 `project.json` 由寫入型操作整份換檔更新；資料預覽、案件清單等唯讀查詢可能在同一時間讀它。
同一個 JET 程式裡，同一份 `project.json` 的讀和寫互相等待，讀檔時也允許其他程式同時換檔；
其他程式（例如另一個 JET 視窗、備份或防毒軟體）短暫鎖住檔案時，讀寫各自稍候重試。
重試後仍讀寫不了，或內容確實損壞，才回 `file_read_error`。
換檔進行中，正式檔名會有一小段時間不存在，所以讀取也要等寫入完成後，才判斷案件在不在。
正在儲存的案件不會被當成找不到，也不會從案件清單上暫時消失。

本地案件不做刪案留痕（裁定 2026-08-20-01）：本地案件屬個人工作性質，持久刪案證據是中心化管理議題，
只屬於 SQL Server 線；企業範圍封存在 [SQL Server 封存事項](history/2026-10-20-sqlserver-archive.md)。

本地案件不使用暫緩中的 SQL Server 機制（裁定 2026-10-02-06）。SQLite 與 DuckDB 案件開啟後不定時送出心跳，
工作鎖由本機檔案鎖負責，支援日誌也不會被心跳紀錄佔滿。本機找不到案件資料夾時，JET 直接回報找不到案件，
不去查線上登錄；只有案件清單標示為 SQL Server 的案件才會查。重新匯入、重新配對與匯出報告完成後，
JET 會在 `operation_log` 寫一筆操作紀錄。本地案件寫這筆紀錄失敗時，例如紀錄表損壞，作業照常完成並回報成功，
失敗記在支援日誌的 `project_audit.write_failed` 事件。重新匯入與重新配對寫不進操作紀錄時，回應另附提醒
「變更已儲存，但這次變更沒有寫入操作紀錄。」；匯出報告時的提醒是「檔案已產生，但這次產生的檔案沒有寫入操作紀錄。」。
SQL Server 案件也回報成功並附同樣的提醒，失敗記在支援日誌的 `operation_log.append_failed` 事件。
本地案件重新配對前讀不到紀錄表、無法判斷這次要不要記時，不寫紀錄，同樣附重新配對的那句提醒。
重新匯入與重新配對見裁定 2026-10-19-19，匯出報告見裁定 2026-10-19-20。SQL Server 案件的心跳與線上登錄行為不變。

## 9. 系統分層

| 層 | 責任 | 主要位置 |
|:---|:---|:---|
| WinForms 主程式 | 視窗、WebView2、原生檔案對話框與程序生命週期 | `src/JET/JET/Form1*`, `Program.cs` |
| Web 前端 | 操作、呈現、分頁與使用者回饋 | `src/JET/JET/wwwroot/` |
| Bridge | 傳送請求、回應與非權威進度事件 | `src/JET/JET/Bridge/` |
| Application | action 處理器、流程協調、取消與工作階段 | `src/JET/JET/Application/` |
| Domain／AuditCore | 欄位、規則、金額與查核語意 | `src/JET/JET/Domain/`, `AuditCore/` |
| Infrastructure | SQLite、DuckDB、SQL Server、檔案讀寫與報告輸出 | `src/JET/JET/Infrastructure/` |

前端不做審計裁定，Bridge 不做業務判斷，報告產生器不重算規則。這三條比任何類別命名都重要。

程式依賴由 Bridge 與 WinForms 主程式進入 Application，再由 Application 使用 AuditCore 與 Domain。
AuditCore 只依賴 Domain，不能回頭依賴 Application、Infrastructure、Bridge 或 WebView2；Domain 不依賴任何外層。
Infrastructure 實作資料存取與檔案能力，不能讓 Application 或 Bridge 直接依賴它。
組裝各層的 `AppCompositionRoot` 與主程式位於 `JET` 命名空間，不受這組分層限制。

`LayerDependencyTests` 逐一核對兩份白名單。Infrastructure 目前只有 `DemoWorkbookWriter`、`SqlServerBackendProbe`
及 `SqlServerHealthCheck` 可以依賴 Application。AuditCore 的公開型別只有 `AuditProjectSnapshot`、`AuditExecutionPlan`、
`AuditOutcome`、`AuditRunManifest`、`AuditUserParameters`、`ISqlDialect`、`JetAuditProgram`、`ProcedureDefinition`、
`ProcedureVerdict` 與 `ValidationProcedures`；新增公開入口不能默默擴大這份清單。

原生選檔與主機控制留在 UI 執行緒，其餘 action 的 handler 與資料庫保留範圍都在背景執行；取消仍走同一 action 通道。
Release 關閉 WebView2 的瀏覽器快捷鍵，避免 F5 等重載讓畫面與案件狀態分離；Debug 與 AgentGuiTest 保留開發用途。
WebView2 初始化失敗時顯示中文復原步驟。瀏覽器或主要呈現程序中止時，先取消在途作業、等作業結束後關閉視窗，
請使用者重開並確認最後一次操作；不自動重新載入而遺失未儲存的畫面輸入。僅暫時沒有回應時先提醒，不逕自關閉案件。

Bridge 遇到不是 `JetActionException` 的非預期例外時，回應錯誤碼 `bridge_error`，訊息固定為「發生非預期的錯誤，
此操作未完成。請再試一次。」，不帶例外原文、本機路徑或例外型別；correlation 保留。畫面不請審計員輸出日誌或
交給支援人員（裁定 2026-10-13-28）。例外在丟出前已由 action 分派器寫進日誌：支援日誌留下整條例外鏈的型別、
系統錯誤碼與 JET 方法位置，不留例外訊息；完整訊息只在本機的診斷日誌。`JetActionException` 的訊息不受影響。
只有前端送錯資料才會出現的格式檢查也顯示同一句，錯誤碼不變，沒過的檢查代號記進支援日誌的 `action.payload_rejected` 事件。
篩選條件編譯時的檢查沒過，只會是驗證器和執行時檢查不一致的程式錯誤。畫面同樣顯示這一句，錯誤碼仍是 `invalid_scenario`；
檢查代號與第幾組第幾條記進支援日誌的 `filter.compile_check_failed` 事件，不含欄位名稱或輸入值（裁定 2026-10-14-01）。

支援日誌是給維護 JET 的人使用的工具，畫面上的訊息不會叫審計員去輸出。`support.log.export` 指定案件時，
匯出該案件從建立以來的整份支援紀錄，關閉案件或重新啟動程式後再開也不缺開頭，寫到該案件資料夾；
不指定案件時匯出這個程式記憶體裡目前保留的全部去識別紀錄，寫到 `%LOCALAPPDATA%\JET\logs\`，不需要先開案件。
案件的支援紀錄存在案件資料夾內，整個案件一個檔，保留到刪除案件（裁定 2026-10-21-08）；搬移或交給別人後再開啟，
只記這次啟動的隨機代號與 JET 版本。紀錄寫不進去時不影響審計操作，匯出時寫出缺口與原因。
案件資料夾裡沒有支援紀錄時，例如紀錄檔被刪除，紀錄從這次開啟開始，並標明之前沒有保存的紀錄。欄位與規則見 action 契約。

畫面上的金額以兩位小數加千分位顯示，由前端共用的格式化函式處理；報表與底稿不變（裁定 2026-10-02-01）。
輸入框、篩選條件值與送給後端的值不經過這個格式化。
右側資料預覽是唯一的例外：那裡的金額固定顯示四位小數，例如 1,234.5000（裁定 2026-10-22-06）。
GL、GL(未納入測試) 與 TB 的金額欄，以及 GL 下方統計列的金額都是四位；PBC-GL 與 PBC-TB 顯示來源文字（做法見裁定總表 2026-10-22-10）。
後端把資料庫存的整數換算成十進位字串交給前端，前端只補零與加千分位，不把金額轉成數字再格式化。
畫面上的筆數、列數這類數量也加千分位，前端由 `countText`、後端訊息由 `CountText.Format` 處理（裁定 2026-10-30-19）；
Excel 列號、第幾組第幾條、頁碼這類位置，以及年份、日期、傳票號碼與科目代號這類代碼不加。報告與底稿照舊版範本的格式。

金額在資料庫裡存成乘以 10,000 的整數，所以保留到小數第四位。來源金額超過四位小數時，確認配對、寫成標準化資料時
四捨五入到第四位，剛好在中間的值往遠離零的方向進位，例如 0.12345 存成 0.1235，-0.12345 存成 -0.1235；
攸關資料元素的金額也一樣。這不算錯誤，也不另外提醒（裁定 2026-10-22-08）。案件沒有可以調整這個位數的設定。

三種資料庫各有一組資料存取物件（repository），程式啟動時建好。建立或載入案件時，Application 依
`project.json` 記錄的資料庫種類選定其中一組，和案件編號一起存進工作階段。其他動作開始時取一次這份紀錄，
整個動作只用這一組；即使途中另一個請求載入了別的案件，進行中的動作也不會改用新的一組。刪除不在使用中的案件時，
依該案件自己的 `project.json` 選組，不改變工作階段。

## 10. 大資料量原則

SQLite 與 DuckDB 處理本機資料庫能支援的案件，短期目標是順暢處理約一百萬筆分錄。約一千萬筆起，SQLite 與 DuckDB
就有壓力；這類大型案件是中期目標，交給 SQL Server 處理，資料量粗估在一千萬到十億筆，實際可能不超過一億筆。
一千萬筆是粗估的界線，不是絕對指標，日後效能改善可以調整（裁定 2026-10-29-14）。

| 維度 | 目前的規模基準 |
|:---|:---|
| GL 分錄筆數 | 短期以 SQLite 與 DuckDB 處理約一百萬筆為基準；約一千萬筆以上的大型案件是中期 SQL Server 的目標，粗估到十億筆 |
| TB 科目數 | 典型約 1,000，上界 1 萬 |
| 科目配對列數 | 數百至數千，上界 1 萬 |
| 工作底稿 Excel 大小 | 數 MB 至數百 MB，以 OpenXML SAX writer 控制記憶體 |

這些是設計基準，不是已完成極限量測的證據；歷史量測範圍見第 8 節。SQL Server 目前暫緩，不能由這張表推導出
「超過某個筆數就必須啟動 SQL Server」的限制。公司硬體上的耗時與資源用量仍需實測。

- 金額以固定精度的整數表示，避免浮點誤差。
- 匯入與輸出採串流；篩選、彙總與資料表連接留在資料庫。
- Bridge 只傳中繼資料、摘要與有界頁面。
- 查詢必須可取消，失敗時不發布不完整結果。
- 效能數字只有在相同資料形狀、環境與命令下才可比較；舊證據不能當成新儲存庫的效能承諾。

## 17. Legacy 比對邊界

保留第 17 節編號，是因為既有的結果比對訊息會引用 `docs/jet-guide.md §17`。

從 IDEA 或 VBA 遷移時，不逐段翻譯。先找出規則目的與輸入輸出，再放到合適的 Domain、Application、
Infrastructure 或 UI 邊界。

比對差異只分五類：

| 類別 | 怎麼處理 |
|:---|:---|
| JET 缺陷 | 修正產品，重新執行同一比較 |
| 已裁定的刻意差異 | 引用明確裁定，不改回 legacy |
| 舊系統缺陷或輸入條件不同 | 保存可重現理由，不把差異算成 JET 通過 |
| Legacy 無對應項 | 說明可比較範圍，不假裝完全等價 |
| 待使用者裁定 | 停下並提出兩邊證據，不自行選邊 |

不同資料庫結果不一致時，不會在這五類中另開例外；相同契約在 SQLite、DuckDB 與 SQL Server 得到不同結果時，
一律視為 JET 問題。

省略的精確規則與來源決策，但不會凌駕 `je-tool` 後續經核准的新行為；追溯與衝突處理見
