# JET 專案指南

更新日期：2026-09-09

JET（Journal Entry Testing）是一套 Windows 桌面工具，用來整理總帳分錄與試算表、執行查核規則，
再輸出 Excel 底稿。這份指南先說清楚產品怎麼運作；程式使用的精確欄位與 action 名稱另見程式碼與
[`action-contract-manifest.md`](action-contract-manifest.md)。

## 1. 產品目的

JET 把原本分散在 IDEA、VBA 與人工 Excel 步驟裡的流程，整理成一個可重複執行的案件工作區。
它不是會計判斷的替代品，也不應替單一客戶或單一檔案寫特殊答案。

主要工作是：

1. 建立案件並選擇資料庫。
2. 匯入總帳與試算表等來源檔。
3. 把來源欄位配對到 JET 的標準欄位。
4. 建立可供查核的有效分錄母體並執行驗證。
5. 依風險訊號與自訂條件篩選分錄。
6. 產生可追溯的 Excel 報告與 Working Paper。

## 2. 核心資料

- **GL（General Ledger）**：總帳分錄。至少需要能辨識傳票、過帳日期、科目與金額。選填的傳票日期只供
  回溯過帳判斷，不和過帳日期視為同一欄。
- **TB（Trial Balance）**：試算表。用來比對科目餘額與期間變動。
- **科目配對**：把公司科目對到 JET 使用的分類，供後續條件與報告使用。
- **日期維度**：假日與補班日，供非營業日相關規則使用。
- **授權編製人員**：選用名單，用來辨識非授權或低頻編製者。
- **案件設定**：期間、資料庫類型（provider）、欄位配對、條件情境與最近結果。

來源資料先進入暫存區（staging），再依已提交的欄位配對轉成標準資料。後續規則只讀標準資料，
不應讓每一個報告產生器各自重新解讀來源欄位。

## 3. 六步驟流程

畫面與 `wwwroot/js/state.js` 目前使用六個步驟：

| 步驟 | 使用者做什麼 | 系統留下什麼 |
|:---|:---|:---|
| 建立案件 | 填寫案件資訊並選 SQLite、DuckDB 或 SQL Server | 案件中繼資料與資料庫類型 |
| 匯入資料 | 選擇 GL、TB 與選用的支援檔 | 原始欄位目錄與暫存資料 |
| 欄位配對 | 對應 GL／TB 欄位並確認金額模式 | 已確認的配對設定與標準資料 |
| 資料驗證與測試 | 建立有效母體、檢查完整性與資料品質；預篩選為選用 | 驗證與預篩選結果 |
| 進階條件篩選 | 建立、預覽並保存條件情境 | 篩選版本與命中結果 |
| 匯出底稿 | 選擇並產生報告 | 五種報告的 Excel 檔；Working Paper 每次匯出新增一個版本檔 |

建立案件時，案件名稱與查核期間必填，案件編號和客戶名稱選填；操作人員由目前 Windows 短帳號取得，
不接受表單另填身分。GL 與 TB 的主資料支援 `.xlsx`、`.xlsm`、`.csv` 與 `.txt`。`.xlsm` 以唯讀 Open XML
串流解析，不啟動 Excel 或執行巨集。多檔功能只合併欄位相同的列，不能把兩份 TB 普通追加後當成期初與期末。

步驟位置只代表使用者目前看到哪一頁。是否能往下做，必須由後端根據案件資料與目前版本判定，
不能只靠前端記住一個「完成」布林值。

## 4. 資料驗證

資料驗證先回答「這批資料能不能形成可信的測試母體」。它包含匯入品質、欄位配對、GL／TB
完整性、借貸平衡、空值與有效母體等檢查。

驗證結果分成摘要與明細。摘要可以回到畫面；大量明細必須用有界分頁查詢，不能把完整 GL 或 TB
放進 WebView2、工作階段狀態或一個過大的 JSON 回應。

資料品質問題與查核命中是兩件事。無法形成有效母體時應停止後續規則；某筆分錄命中風險訊號，
則是提供查核方向，不等於資料本身無效。

完整性測試包含匯入前後控制總數核對，以及 GL 與 TB 的逐科目金額比對。使用者訊息直接說明哪一項未通過，
不使用 Part A 或 Part B。借貸不平測試逐張傳票比較借方與貸方金額。資料可靠性測試抽出固定且可重現的樣本，
供審計員確認非財務欄位及所選攸關資料元素；程式不替審計員自動判定這些內容可靠。

目前 `sourceQuality` 只有過帳日空白一類。這些來源列無法判斷案件期間，所以保留在匯入原貌但不進入測試母體；
日期在期間外不是這一類。

母體完整性的逐項判定只在「資料驗證與測試」這一個畫面呈現；流程總覽等其他畫面只摘要既有的後端裁定，
不建立第二套判定面。這是 2026-08-20 的裁定，避免同一件事在兩處給出不同答案。

## 5. 預篩選

預篩選提供一組可重複計算的風險訊號，例如期後核准、特定摘要、非營業日、尾數型態、非授權
編製者或低頻科目。它協助使用者理解母體，但不是進入進階條件篩選的必要前置。

規則名稱、欄位與版本要由 Domain 與 Application 的現行契約決定。前端只顯示後端結果，
不得用 JavaScript 重算另一套命中邏輯。

## 6. 進階條件篩選

進階篩選讓使用者把多個條件組成情境，先預覽，再保存結果。條件可以針對文字、日期、金額、
借貸性質、科目配對、風險訊號與已配對的額外欄位。

實務主線是 KCT A–J 條件清單：GA 可以勾選 KCT 條件、預篩選述詞與自訂條件，收斂出要測試的分錄。
KCT 卡、預篩選述詞與自訂條件都收斂到同一份條件語法樹；`prescreen` 類規則在篩選中直接重用
`GlRulePredicates` 即時計算，不讀取先前預篩選執行的命中檔。A–J 與現行執行的完整對應、KCT 的
legacy 來源邊界，見遷移基準指南
[`history/superseded/jet-guide-2026-08.md`](history/superseded/jet-guide-2026-08.md) §3–§4；
KCT 正式全稱與新條件仍待使用者提供，現況見
[`development-status.md`](development-status.md) 的延後事項。

篩選的核心原則是：

- 條件語法樹（AST）由後端驗證，不接受任意 SQL。
- 計算留在資料庫，以參數化、集合式查詢完成。
- 大量命中資料只回摘要與鍵集分頁（keyset pagination）；明細表的排序與搜尋也在資料庫端，換排序或搜尋
  從第一頁重載，空值一律排最後。
- 保存的情境要和資料、欄位配對、驗證結果及規則版本連動；上游變更後不能沿用已失效的結果。

借貸科目分類條件有三種模式：「科目屬於指定分類」「科目不屬於指定分類」「整張傳票的這一側都不屬於
指定分類」。分類依既有業務意義判斷，自訂分類有 Cash 意義時也算 Cash。科目配對範本分類留白的科目
依 legacy 視為 Others；沒有出現在配對檔的科目不屬於任何分類。結果只有命中與不命中兩種，沒有待判定
（2026-09-07 裁定）；第四步的科目配對卡提醒「分類留白 N 筆，視為 Others」並可展開清單，要改分類就在
範本 C 欄填好再重新匯入。借貸科目組合合併成一張卡，五種白話模式：「借方是 A 且貸方是 B」「借方是 A 且
整張傳票沒有 B 貸方」「貸方是 B 且整張傳票沒有 A 借方」「借方是 A，看它的對方科目」「貸方是 B，看它的
對方科目」。原有配對及 KCT 規則保留原結果。

同一分錄組合可選全部符合或符合任一；同一傳票組合固定全部符合，第一個主要條件決定命中分錄，
其餘條件可由該傳票不同分錄符合。只有傳票層條件時，呈現查核期間內的分錄，標示傳票條件成立。
日期及金額區間包含兩端；日期可用多選日曆挑指定日，也可用「每月幾日屬於」「每月幾日不屬於」填 1 到 31
的日子（例如 28、31，重複自動合併）。文字、日期和金額依型別提供清單、否定、空白及其他比較方式；
「包含任一文字」「不包含任何文字」接受多個關鍵字，清單最多 100 個不同值。核心金額預設比較絕對值，
額外數值欄位沿用含正負號方式。要排除某些日期、文字或金額，就用該條件的否定模式（不屬於、不在區間、
不包含）放進條件組，沒有獨立的排除區域。所有值條件預設不列入空白，日期空白的分錄不命中；要把空白
也算進來時勾「空白也符合」。開啟舊情境不自動換規則。

「空白」與「非空白」只能判斷已有來源的欄位。核心欄位未配對時，後端提示回「欄位配對」指派或改選其他欄位，
不能把未提供的整欄當作內容空白。核准日採「同過帳日」時已有衍生來源，仍可使用空白判斷。
畫面及報表的「且」「或」是文字呈現；條件依原順序由左向右合併，第一條連接詞沒有左側條件，不參與運算。
混合連接詞的讀回文字保留括號，不按一般 SQL 的運算子優先序重新解讀。

預覽只要求條件有效，自訂情境保存時才要求名稱與動機；KCT 沿用既有例外。後端指出某條規則有問題時，
畫面把那一條標紅並就地寫原因。預覽、保存及匯出共用後端判斷。命中傳票清單可分頁展開整張傳票的分錄，
每列標示符合第幾組第幾條主要或佐證條件、或傳票條件成立，其餘為參考分錄，不算命中。分頁綁定案件、
資料與情境版本，資料變更後重新預覽。第五步也能更新原情境、另存副本或取消編輯；更新不占新名額，
最多十個情境的上限仍適用副本。常用情境範本（借現金貸非現金、貸現金借非現金、非營業日且排除指定日期、
期末最後 N 天的人工分錄、空白摘要或核准人員、特定人員的大額分錄）一鍵帶入條件、名稱與動機，可再修改。

## 7. 輸出報告

產品目前有五種報告與一份工作檔：

1. Validation Report
2. INF Report
3. Pre-screening Report
4. Criteria Selection Report
5. Working Paper
6. Account Mapping 範本（工作檔，不是報告）

程式隨附範本位於 `src/JET/JET/Templates/`，由 `JET.csproj` 複製到輸出目錄。`data/` 內的同名或
近似工作簿是遷移參考，不會因為檔名相似就自動成為程式隨附範本。

報告產生器使用已確認的查詢結果與中繼資料，不重新解讀審計規則。產生大型工作簿時採串流方式：先寫
案件資料夾內以 `.` 開頭的暫存檔，完整寫好後才改名成正式檔名。可處理的失敗或取消會清除半成品；程序
中斷或檔案佔用造成的殘留，會在下次讀寫前嘗試清除。儲存不計算內容雜湊，也不保留交易復原紀錄。
報告清單仍保存檔名、大小與修改時間，用來顯示外部修改提醒，不會因此拒絕載入案件。

新增條件的完整說明會寫入 Criteria Selection Report，並列在 Working Paper 的 Step 3 情境名稱下方。
底稿展開整張傳票時，參考分錄不重新標成命中。
超過 Excel 單格容量的條件會在同一工作表接續列出，保留完整文字。Criteria Selection 的摘要會指向
續列位置；Working Paper 則以同一情境代號標示續列，不重複計入傳票數。

只有 Working Paper 是正式輸出：每次匯出寫新的版本檔 `<案件前綴>_WorkingPaper_<yyyyMMdd-HHmmss>.xlsx`，
不覆蓋、不刪舊版；即使檔名選定後才出現同名檔，發布時也保留原檔並提示重新匯出。第六步可分頁查看
全部版本並在檔案總管定位，歷史版本不作為目前流程完成的證據。其餘四種報告每次匯出覆蓋同名檔。
Account Mapping 範本是給審計員用 Excel 填 C 欄再匯回
的工作檔，固定檔名 `<案件前綴>_AccountMapping.xlsx`，不列入報告清單。
驗證完成後只自動建立尚不存在的範本，已有檔案就保留。手動重新產生空白範本才覆寫，最後發布時也遵守
所選方式，避免自動產生改動審計員已填寫的分類。

範本和報告都在正式檔改名前處理最後一次取消；範本取消時保留原檔。報告開始發布後，取消請求不再中斷
索引寫入；這不保證能排除磁碟或權限等寫入失敗。報告清單即將超過 4,096 筆時，先整理已確認檔案不存在的
底稿紀錄。正式發布前再次確認，期間被放回或無法確認的檔案仍保留；仍超限時不發布新檔，提示使用者
自行整理不需要的舊底稿後重試。整理不刪除實體檔，失敗或取消也不提前保存整理後的清單。

預設審計員可信（`docs/project-context.md`）：報告檔在 JET 之外被改寫、改名或刪除都不阻擋載入，第六步清單
只在該筆旁標示「已在 JET 之外修改」或「檔案不存在」，重新匯出即可。2026-09-02 以前版本留下的輸出紀錄檔
會在載入時直接刪除並記一筆支援日誌事件。

## 8. 儲存與資料庫實作

SQLite 與 DuckDB 是本地資料庫實作；每個案件以一個自含資料夾保存中繼資料、資料庫與輸出產物。
SQL Server 是線上資料庫實作，使用共享資料庫中的案件範圍。三種實作在相同輸入與相同契約下應得到
相同結果；不能把資料庫差異當成合理的業務差異。

SQLite 連線的 `UPPER` 由 .NET `ToUpperInvariant()` 處理，讓篩選資料與條件值採用一致的大寫轉換，
包含 café 等非 ASCII 文字。一般連線、唯讀連線與底稿專用連線都保留這項設定；不另外安裝 SQLite 擴充，
也不把分錄載入前端比較。文字仍區分重音符號，沒有新增模糊比對或變更空白規則。

schema v10 增加科目分類是否實際填寫的紀錄（`classification_explicit`），以及篩選資料版本。舊案件升級時
以原始分類資料分批回填，缺少來源證據則保留未知，原本的分類欄值不改寫。這個紀錄只用在第四步
「分類留白 N 筆，視為 Others」的提醒；篩選一律把留白視為 Others（2026-09-07 裁定），開案不另做分類
證據修復，也不重複掃描科目配對資料。上游資料變更會在同一交易更新篩選資料版本，使舊分頁失效。

選擇 SQLite 與 DuckDB 作為本地實作的理由來自正式環境限制（見
[`project-context.md`](project-context.md)）：兩者都免伺服器、免系統管理權限、單一案件資料夾自含，
一般 GA 不需要管理資料庫服務就能作業。歷史量測已用 DuckDB 驗證 500 萬到 2,000 萬列母體的匯入、
驗證、預篩選與底稿輸出。兩個引擎能力不完全相同——例如 DuckDB 1.5.3 沒有 trigger，`audit_event_log`
的 append-only 在 SQLite 與 SQL Server 由資料庫層強制，在 DuckDB 維持程式紀律——這類差異由
Infrastructure 吸收，不得外溢成業務行為差異。

本地案件的可攜性以前提為「JET 已正常離開案件，再冷複製完整案件資料夾」。正在使用的資料庫、
WAL 熱複製與 SQL Server 案件不在這個保證內。

本地案件不做刪案留痕：2026-08-20 裁定本地案件屬個人工作性質，持久刪案證據是中心化管理議題，
只屬於 SQL Server 線；企業範圍見 [`sqlserver-enterprise-deferred.md`](sqlserver-enterprise-deferred.md)。

## 9. 系統分層

| 層 | 責任 | 主要位置 |
|:---|:---|:---|
| WinForms 主程式 | 視窗、WebView2、原生檔案對話框與程序生命週期 | `src/JET/JET/Form1*`, `Program.cs` |
| Web 前端 | 操作、呈現、分頁與使用者回饋 | `src/JET/JET/wwwroot/` |
| Bridge | 傳送請求、回應與非權威進度事件 | `src/JET/JET/Bridge/` |
| Application | action 處理器、流程協調、取消與工作階段 | `src/JET/JET/Application/` |
| Domain／AuditCore | 欄位、規則、金額與查核語意 | `src/JET/JET/Domain/`, `AuditCore/` |
| Infrastructure | SQLite、DuckDB、SQL Server、檔案讀寫與報告輸出 | `src/JET/JET/Infrastructure/` |

前端不做審計裁定，Bridge 不做業務判斷，報告產生器不重算規則。這三條比任何類別命名都重要。

## 10. 大資料量原則

資料規模早已定義，並未在遷移時取消。遷移基準
[`history/superseded/jet-guide-2026-08.md`](history/superseded/jet-guide-2026-08.md) §1.5.1 的原表列出：

| 維度 | 原有規模基準 |
|:---|:---|
| GL rows | 本機持久案件典型約 1,000 萬以下；大型資料或雲端案件的設計上限為 10 億 rows |
| TB accounts | 典型約 1,000，上界 1 萬 |
| AccountMapping rows | 數百至數千，上界 1 萬 |
| SQLite path | 原表定位於小於 1,000 萬 GL rows 的本機持久案件，不是 10 億 row 執行引擎 |
| SQL Server path | 原表定位於大於 1,000 萬 GL rows 或雲端及共享案件，10 億 row 等級仍是設計目標 |
| Workpaper Excel 大小 | 數 MB 至數百 MB，以 OpenXML SAX writer 控制記憶體 |

這些是既有設計基準，不能當作已完成極限量測的證據。後續本機方向已加入 DuckDB，歷史量測範圍見第 8 節；
SQL Server 目前暫緩，不能由舊表推導「超過 1,000 萬列就必須啟動 SQL Server」的新限制。
公司硬體上的耗時與資源用量仍需實測，但目標資料量不應再次列為等待使用者提供。

- 金額以固定精度的整數表示，避免浮點誤差。
- 匯入與輸出採串流；篩選、彙總與資料表連接留在資料庫。
- Bridge 只傳中繼資料、摘要與有界頁面。
- 查詢必須可取消，失敗時不發布不完整結果。
- 效能數字只有在相同資料形狀、環境與命令下才可比較；舊證據不能當成新儲存庫的效能承諾。

## 17. Legacy 比對邊界

保留第 17 節編號，是因為既有的結果比對訊息會引用 `docs/jet-guide.md §17`。

從 IDEA 或 VBA 遷移時，不逐段翻譯。先找出規則目的與輸入輸出，再放到合適的 Domain、Application、
Infrastructure 或 UI 邊界。

比對差異只分五類：

| 類別 | 怎麼處理 |
|:---|:---|
| JET 缺陷 | 修正產品，重新執行同一比較 |
| 已裁定的刻意差異 | 引用明確裁定，不改回 legacy |
| 舊系統缺陷或輸入條件不同 | 保存可重現理由，不把差異算成 JET 通過 |
| Legacy 無對應項 | 說明可比較範圍，不假裝完全等價 |
| 待使用者裁定 | 停下並提出兩邊證據，不自行選邊 |

不同資料庫結果不一致時，不會在這五類中另開例外；相同契約在 SQLite、DuckDB 與 SQL Server 得到不同結果時，
一律視為 JET 問題。

遷移基準的完整 2,000 行指南保存在
[`history/superseded/jet-guide-2026-08.md`](history/superseded/jet-guide-2026-08.md)。它用來查找本指南
省略的精確規則與來源決策，但不會凌駕 `je-tool` 後續經核准的新行為；追溯與衝突處理見
[`business-logic-provenance.md`](business-logic-provenance.md)。
