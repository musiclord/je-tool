# JET 專案指南

更新日期：2026-09-23

JET（Journal Entry Testing）是一套 Windows 桌面工具，用來整理總帳分錄與試算表、執行查核規則，
再輸出 Excel 底稿。這份指南先說清楚產品怎麼運作；程式使用的精確欄位與 action 名稱另見程式碼與
[`action-contract-manifest.md`](action-contract-manifest.md)。

## 1. 產品目的

JET 把原本分散在 IDEA、VBA 與人工 Excel 步驟裡的流程，整理成一個可重複執行的案件工作區。
它不是會計判斷的替代品，也不應替單一客戶或單一檔案寫特殊答案。

主要工作是：

1. 建立案件並選擇資料庫。
2. 匯入總帳與試算表等來源檔。
3. 把來源欄位配對到 JET 的標準欄位。
4. 建立可供查核的有效分錄母體並執行驗證。
5. 依風險訊號與自訂條件篩選分錄。
6. 產生可追溯的 Excel 報告與 Working Paper。

## 2. 核心資料

- **GL（General Ledger）**：總帳明細這份資料集。匯入的每一列是待測試的會計分錄。
- **JE（Journal Entry）**：會計分錄，是測試對象，不是另一個要與 GL 二選一的日期欄位。
- **TB（Trial Balance）**：試算表。用來比對科目餘額與期間變動。
- **科目配對**：把公司科目對到 JET 使用的分類，供後續條件與報告使用。
- **日期維度**：假日與補班日，供非營業日相關規則使用。
- **授權編製人員**：選用的識別值清單，用來比對未列入名單的人員。編製者彙總與編製筆數統計直接使用 GL，不依賴此名單。
- **案件設定**：期間、資料庫類型（provider）、欄位配對、條件情境與最近結果。

來源資料先進入暫存區（staging），再依已提交的欄位配對轉成標準資料。後續規則只讀標準資料，
不應讓每一個報告產生器各自重新解讀來源欄位。

### 日期名稱與資料含義

2026-09-23 使用者採用「總帳入帳日」，並保留三種日期。名稱說明用途，不以受查者來源欄的英文名稱
猜測含義；來源配對仍由審計員確認。技術識別字及既有報表正準欄名保留相容，不為文字調整搬移案件資料。

| 畫面名稱 | action 與資料庫欄位 | 用途 |
|:---|:---|:---|
| 總帳入帳日 | `postDate`、`post_date`；既有正準欄名 `總帳日期_JE` | 必要配對，用來決定查核期間與測試母體，也是日期篩選和非營業日比較的依據。 |
| 傳票日期 | `voucherDate`、`voucher_date` | 選填，可用於日期條件；回溯過帳比較總帳入帳日是否早於此日期。不自行改稱建立日或登錄日。 |
| 傳票核准日 | `docDate`、`approval_date` | 供核准日期條件與財報準備日起核准等規則。`docDate` 是歷史識別字，不表示 Document Date；只有明確選「與總帳入帳日相同」時才複製該日期。 |

來源：`JetFieldCatalog`、`GlRowProjector`、`GlEffectivePopulation` 與 `GlRulePredicates`。

## 3. 六步驟流程

畫面與 `wwwroot/js/state.js` 目前使用六個步驟：

| 步驟 | 使用者做什麼 | 系統留下什麼 |
|:---|:---|:---|
| 建立案件 | 填寫案件資訊並選 SQLite、DuckDB 或 SQL Server | 案件中繼資料與資料庫類型 |
| 匯入資料 | 選擇 GL、TB 與選用的支援檔 | 原始欄位目錄與暫存資料 |
| 欄位配對 | 對應 GL／TB 欄位並確認金額模式 | 已確認的配對設定與標準資料 |
| 資料驗證與測試 | 建立有效母體、檢查完整性與資料品質；預篩選為選用 | 驗證與預篩選結果 |
| 進階條件篩選 | 建立、預覽並儲存條件情境 | 篩選版本與命中結果 |
| 匯出底稿 | 選擇並產生報告 | 五種報告的 Excel 檔；Working Paper 每次匯出新增一個版本檔 |

建立案件時，案件名稱與查核期間必填，案件編號和客戶名稱選填；操作人員由目前 Windows 短帳號取得，
不接受表單另填身分。啟動時的 `system.databaseInfo` 明確回報這台電腦沒有設定線上資料庫時，SQL Server 選項停用，
並請使用者改選 SQLite 或 DuckDB；還沒查到結果或已設定但連不上時維持可選，連不上時照舊在建立時回報錯誤。GL 與 TB 支援 `.xlsx`、`.xlsm`、`.xls`、`.csv`、`.txt` 及 Access 的 `.mdb`、`.accdb`。
Excel 檔逐列唯讀解析，不執行巨集；Access 透過既有 Office 資料介面讀取選定的一般資料表。`.xlsb` 不支援。
多檔功能只合併欄位相同的列，不能把兩份 TB 普通追加後當成期初與期末。
文字檔照一般 CSV 讀法（和 Excel 相同）：只有欄位開頭的引號是引號，欄位中間的引號是一般字元，不會把後面的列併進來。
欄位開頭有引號時，到下一個引號之前都算同一格，可以跨好幾行；這是合法寫法，所以 JET 不擋。但引號放錯位置時，
後面幾列會被併進同一格，資料列因此變少。匯入完成時，JET 提醒每個檔案有幾筆資料的欄位內含換行，並列出前五個列號，
支援日誌也記一筆。引號沒有成對、檔案結構讀不通時匯入失敗並寫出第幾列。開頭的空白列略過，第一個有內容的列是欄名；只讀到一欄時提醒
可能是報表格式，請先在 Excel 整理後再匯入，JET 不另做略過前幾列。標頭之外有資料的欄合成 `COL_n` 佔位欄，少欄視為空，
這和 Excel 檔相同。`.xls` 的錯誤儲存格保留 `#N/A` 這類原文，所以金額欄會以金額無效明確失敗，不會被讀成 0。
`.xls` 與 Access 的是或否值寫成 `true`、`false`，只有時間的值寫成時間，表示方式和 `.xlsx` 一致。
來源檔被其他程式開著時，訊息請審計員關閉檔案後重試，只寫檔名；解碼失敗時可在匯入清單改選編碼重試。
Access 是資料匯入來源，不是新增的案件資料庫。現行讀取器只列出一般本機資料表，排除系統表與儲存查詢；
先檢視表結構，再提供有界預覽，完整匯入逐列串流至原有 SQLite 或 DuckDB 流程。空表、找不到資料表及
不支援的二進位值會說明原因，失敗或取消保留原匯入批次，不覆寫來源檔。
相容性須分開記錄 ACE 實跑與替身測試。win-x64 程式需要既有的 x64 ACE 16 可用，不能由「已安裝 Office」
推定所有位元版本都通過。加密或密碼資料庫、連結資料表、Access 巨集、儲存查詢、多值或附件欄位不在
一般資料表匯入的已驗收範圍；不為這項功能要求一般審計員另裝資料庫或驅動程式。

總帳科目名稱是必要配對欄位，須指定來源欄位。2026-09-18 使用者確認維持此規則，
不將「改成選填」列為待開發功能；這不增加逐筆科目名稱都不可空白的檢查。

人工與自動分錄可逐值指定，也可只列一側，將其餘非空白值視為另一側；空白另選人工、自動、
不判定或先補齊來源。選擇會隨案件和報告配對資訊保存。取消或更換來源欄位時清除舊欄政策，避免套錯來源。
只列一側時，清單代碼如果在來源裡一筆都沒有，其餘非空白值會全部歸到另一側。確認配對後 JET 提醒代碼與來源欄，
不擋確認；判定規則不變。
授權人員匯入須選與 GL 相同的識別欄，畫面分別顯示原始列數、空白、重複及有效人員數。
名單的識別值去掉頭尾空白後不分大小寫去重，和 GL 傳票建立人員的比對同一規則，保留第一次出現的寫法。
移除名單會使相依結果失效，仍保留驗證和情境定義，之後可再次匯入。
匯入的文字欄位不論來源是 `.csv`、`.xlsx`、`.xls` 或 Access，都去掉頭尾的空白字元，字元集合和 .NET 的 Trim 相同
（半形空白、Tab、換行、全形空白、不換行空格等）；只含空白的值當成空白。這是 2026-10-04 使用者裁定 C3 的做法。

步驟位置只代表使用者目前看到哪一頁。是否能往下做，必須由後端根據案件資料與目前版本判定，
不能只靠前端記住一個「完成」布林值。
2026-09-23 使用者確認正常操作流程仍須匯入 GL 和 TB，並完成兩者的欄位配對後才進入驗證。
後端對無法比對 TB 的結果保留原因，不代表前端可略過 TB 前置；驗證有差異仍可繼續的規則不變。

### 建案後修改案件資料

「建立案件」頁面可修改客戶名稱、案件編號與期末財報準備日；案件名稱與查核期間維持不變。建案時檢查起始日不晚於截止日。
準備日早於查核起始日，或晚於查核截止日超過一年時，只提醒確認年份，不禁止建立或儲存。
修改準備日會讓預篩選與篩選命中需要重算，驗證結果、欄位配對及已儲存情境保留。KCT A 與舊表 A 不是同一項：舊表 A 使用財報準備日起核准條件，KCT A 仍用既有季度規則。
客戶名稱或案件編號變更不影響審計命中。修改案件資料不改寫已匯出的檔案，報告清單把舊檔標為過期，再次匯出時才用新資料。
## 4. 資料驗證

資料驗證先回答「這批資料能不能形成可信的測試母體」。它包含匯入品質、欄位配對、GL／TB
完整性、借貸平衡、空值與有效母體等檢查。

驗證結果分成摘要與明細。摘要可以回到畫面；大量明細必須用有界分頁查詢，不能把完整 GL 或 TB
放進 WebView2、工作階段狀態或一個過大的 JSON 回應。

測試母體由確認 GL 配對時決定。先排除總帳入帳日空白或不在查核起迄日內的列，日期兩端都包含；
再依過帳狀態政策排除不採用的列。未配對過帳狀態欄位時，期間內的列全部納入；有配對時指定採用代碼清單及是否納入空白值，
至少採用一個非空代碼或選擇納入空白。代碼去掉頭尾空白且不分大小寫。摘要分開列出原始、有效與排除筆數，排除原因依上述先後互斥計數。
驗證、預篩選、條件篩選與完整性 GL 彙總共用已保存的有效母體，不各自重算期間或過帳政策。

空值與日期異常檢查在有效母體內分成四類：科目空白、傳票號碼空白、摘要空白，以及核准日不在查核期間。
最後一類以核准日判斷，不是總帳入帳日；核准日空白不命中。一列可以同時命中多類，不能把各類筆數相加當成相異分錄數。
借貸不平的傳票張數、摘要、分頁與底稿 Step 1-1 都不把空白號碼當成一張傳票。

同一非空傳票號碼出現在多個總帳入帳日時，驗證保存涉及的號碼數及分錄列數，第一步顯示非阻擋提醒。
沒有有效驗證結果時顯示尚未確認，不假定為零，也不因此更改傳票比對鍵。INF 樣本與驗證摘要在同一資料庫交易保存；
失敗或取消不留下半套新結果，只有孤立樣本不能代表已完成驗證。

資料品質問題與查核命中都需要審計員判斷，不能直接當作禁止後續操作的理由。
依 2026-09-17 使用者裁定，完整性驗證已完成但有差異，或 GL 與 TB 科目比對無法執行時，
JET 保留明細與提醒，允許預篩選、條件篩選與匯出；審計員可說明差異原因後繼續審計程序。
舊案件沒有確認欄位配對時算出的數字，保留「無法核對」的狀態並允許繼續；不能因缺少這組數字而要求反覆驗證。
「可繼續」不代表「完整性通過」，也不要求另填說明或勾選確認。只有缺少目前資料的驗證結果、
結果損壞或已失效時，才要求重新驗證，避免沿用不存在或過期的結果。

完整性測試有兩項檢查。第一項確認 JET 存下的分錄筆數與借貸合計，和確認欄位配對時算出的一致：
確認配對時，JET 逐列存下分錄，同時計算查核期間內、符合過帳狀態設定的筆數與合計；驗證時再從存下的分錄重新計算一次。
兩組數字都由 JET 計算，所以這一項找得出存下時少掉或重複的分錄，但不和來源檔自己的合計比對，也看不出讀檔時就少掉的列。
第二項是 GL 與 TB 的逐科目金額比對。使用者訊息直接說明哪一項未通過，不使用 Part A 或 Part B。借貸不平測試逐張傳票比較借方與貸方金額。資料可靠性測試抽出固定且可重現的樣本，
供審計員確認非財務欄位及所選攸關資料元素；程式不替審計員自動判定這些內容可靠。

INF 的目的與人工核對責任已對照兩份 legacy 程式及現行 `WorkpaperProgram`。較早的 `idea-script.bas`
可選擇是否產生 60 筆樣本；`idea-tool.bas` 已將該詢問註解停用，實際產生 59 筆。現行抽樣使用有效母體，
上限 59 筆並記錄可重現的抽樣設定；59 筆及不必重現舊 IDEA 同一批隨機列的差異，已在
[`2026-08-28 計畫`](history/specs/2026-08-28-harness-rebuild-plan.md)由使用者確認，不重新改成 60 筆。
現行底稿方法文字要求團隊在高風險篩選前確認所用 RDE 的可靠性，初步預篩選另有例外；樣本供核對附件，
不是軟體自動證明可靠。程式不另增一個核准勾選或操作關卡，也不改寫尚待 DPP 討論的指引。

目前 `sourceQuality` 只有總帳入帳日空白一類。這些來源列無法判斷案件期間，所以保留在匯入原貌但不進入測試母體；
日期在期間外不是這一類。

母體完整性的逐項判定只在「資料驗證與測試」這一個畫面呈現；流程總覽等其他畫面只摘要既有的後端裁定，
不建立第二套判定面。這是 2026-08-20 的裁定，避免同一件事在兩處給出不同答案。

## 5. 預篩選

預篩選提供一組可重複計算的風險訊號，例如財報準備日起核准、特定摘要、非營業日、尾數型態、非授權
編製者或使用較少的科目。它協助使用者理解母體，但不是進入進階條件篩選的必要前置。

規則名稱、欄位與版本要由 Domain 與 Application 的現行契約決定。前端只顯示後端結果，
不得用 JavaScript 重算另一套命中邏輯。

「財報準備日起核准」沿用 legacy R1 實際比較：核准日大於或等於案件財報準備開始日，不是查核期末日。
摘要預設清單補回 legacy 的九個簡體詞，共 25 詞；第五步可另選可編輯的摘要關鍵字條件。
回溯過帳比較總帳入帳日早於傳票日期；未配對傳票日期時明示無法執行。
編製分錄較少的人員與使用較少的科目的既有上限為 11 筆分錄，按分錄測試範圍計算，不是 11 張傳票。
「較少使用之科目」卡片的狀態顯示符合這個條件的科目數，不拿全案科目數或前 50 列摘要充當答案；命中的分錄筆數另外保留。
缺少傳票建立人員欄位時，人員彙總、編製筆數及非授權比較顯示原因，其他測試繼續可用。
人員識別值一律去掉頭尾空白、不分大小寫：編製者彙總、編製分錄較少的人員、非授權編製人員，和既有的編製等於核准、
人員清單用同一規則。編製分錄較少的人員與非授權編製人員不列入空白人員；編製者彙總和原本一樣把空白人員列成一組。
畫面與報告把空白人員組標為「（空白）」，只改顯示，不改分組鍵或合併同名字面值的人員。
編製者彙總的明細最多列出分錄筆數最多的 50 位；畫面的人數、流程總覽與預篩選報告的摘要列，都寫查核期間的完整人數，空白人員組算一位。
編製者彙總顯示同一人時，固定取同組裡碼位最小的去空白寫法（例如 U1 與 u1 顯示 U1），
SQLite 與 DuckDB 相同。資料庫端去掉的空白字元集合和 .NET 的 Trim 相同，所以全形空白、不換行空格與 Tab 在兩個資料庫
的結果一樣，這之前匯入的案件也一樣（2026-10-04 使用者裁定 C3）。
legacy R5 是總帳實際人員彙總，不等於新版授權清單比較。連續零尾數預設固定 6 位，進階條件
`customTrailingZeros` 可指定 1 至 12 位；先取金額整數部分（不含小數），小數不參與，整數部分為零不命中。
2026-09-18 使用者裁定以目前新版方針為主，保留上述行為，不恢復 legacy R4 依借方平均金額決定位數的算法。
這是已裁定的新舊差異，不再列為待補自動算法或待裁定零位數邊界；原話見現行回饋計畫。

畫面提供 13 項預篩選檢查，預篩選報告沿既有範本只輸出其中 7 條規則，不能把報告當成全部畫面結果的副本。
報告涵蓋範圍與排序列在第 7 節。KCT A「季末前借記收入」是第五步條件，不是新增的預篩選規則；
它使用曆年季底 3 月 31 日、6 月 30 日、9 月 30 日及 12 月 31 日，不依案件起日平移會計季度。
前 X 天包含季底當日，從季底回推 X 減 1 天；只採用與查核期間有交集的視窗，實際命中仍受有效母體限制。

## 6. 進階條件篩選

2026-09-22 的操作畫面將原「審計角色」稱為「分類用途」，將「傳票量詞」稱為「傳票分錄條件」。
這是介面與條件說明的用語調整，`semanticRole`、`voucher` 和既有判定不變。
其他跨頁名稱見[前端說明的「同一資料在不同畫面的名稱」](jet-frontend-description.md#同一資料在不同畫面的名稱)。

進階篩選讓使用者把多個條件組成情境，先預覽，再儲存結果。條件可以針對文字、日期、金額、
借貸性質、科目配對、風險訊號與已配對的攸關資料元素欄位。

實務主線是 KCT A–J 條件清單：GA 可以勾選 KCT 條件、預篩選述詞與自訂條件，收斂出要測試的分錄。
KCT 卡、預篩選述詞與自訂條件都收斂到同一份條件語法樹，KCT 卡加入目前選取的條件組。
非營業日 I 是一條條件括號，括號內只有一條「總帳入帳日是非營業日」，條件說明寫成「非營業日（排除補班日）」；
非營業日的定義見下方日期條件，是週末或假日、再排除補班日。2026-10-02 使用者裁定它不再自成一組；
舊情境若保存週末過帳或假日過帳的組合，照原條件樹計算、不轉換。
`prescreen` 類規則在篩選中直接重用 `GlRulePredicates` 即時計算，不讀取先前預篩選執行的命中檔。A–J 與現行執行的完整對應、KCT 的
legacy 來源邊界，見遷移基準指南
[`history/superseded/jet-guide-2026-08.md`](history/superseded/jet-guide-2026-08.md) §3–§4；
KCT 正式全稱與新條件仍待使用者提供，現況見
[`development-status.md`](development-status.md) 的延後事項。

篩選的核心原則是：

- 2026-09-18 使用者確認先相容舊版 JET 已涵蓋的審計功能與需求，再在此基礎上重構與改善操作。
  條件定義沿來源核對，實作維持共用 AST；已裁定的新制差異保留，不因舊表單不同就自行回復。
- 條件語法樹（AST）由後端驗證，不接受任意 SQL。
- 計算留在資料庫，以參數化、集合式查詢完成。
- 大量命中資料只回摘要與鍵集分頁（keyset pagination）；明細表的排序與搜尋也在資料庫端，換排序或搜尋
  從第一頁重載，空值一律排最後。
- 已儲存的情境要和資料、欄位配對、驗證結果及規則版本連動；上游變更後不能沿用已失效的結果。
- 2026-10-02 使用者同意篩選規則更新後不再要求逐案重新儲存情境。開啟案件時，JET 先用目前規則逐一檢查
  已儲存的情境，檢查方式與重算命中前相同。全部仍然有效時，整批改用目前規則：名稱、動機與條件內容不變，
  只更新規則版本與分錄測試範圍兩個欄位，並換上新的儲存時間；舊命中在同一交易清除，依舊規則產生的
  條件篩選報告與底稿因此標為過期，第一次查看命中或匯出時才重算。
- 只要有一個情境不符合目前規則，整批都不動，開案回應逐一列出情境位置、名稱與原因。分錄測試範圍不是
  查核期間、規則版本無法辨識或比目前版本新的情境，也不自動改版，避免默默改變測試母體。
  查詢與匯出仍檢查規則版本，資料不一致時照舊擋下。實作見 `FilterScenarioRuleUpgrade` 與 `ProjectLoadHandler`。

MAC 等外部多層會計科目表及其對照不在目前職責範圍，不作為篩選條件或既有科目配對改善的前置工作。
本地分類可設定上層分類，分類用途獨立保存。新增下層時畫面先帶入上層用途，審計員仍可修改；改動既有分類的上層不會重設用途。選取分類時可指定僅分類本身、包含所有下層，
或具有相同分類用途的分類。未指定新選取方式的舊條件仍按原本的分類用途判斷。

本地分類樹是為了讓審計員依案件整理科目，並在篩選時決定要選多大的範圍。它不是外部標準科目表，
也不會依分類名稱自動判斷會計含義。例如把「銀行存款」放在「現金類」下面，選分類本身只找直接配對
到該分類的科目；選包含下層才一併找銀行存款。選相同「分類用途」則跨越樹的位置，找用途相同的分類。
新建分類條件與舊表 P 的新卡預設包含下層，舊情境沒有指定選取方式時仍按原本分類用途判斷。條件說明與報告列出比對方式和實際納入的分類。

分類由穩定 ID 識別，名稱只供閱讀；改名不會把舊情境誤認成另一分類。上層關係與下層查詢表在同一交易
保存，查詢沿既有篩選編譯器產生集合 SQL，不在前端遍歷分錄。循環、遺失的上層及刪除仍被使用的分類
會要求先調整關係，避免留下無法解讀的條件；這是資料一致性保護，不是審計核准程序。保存後更新版本並
使相依結果失效，重算時套用目前分類。實作見 `AccountTaxonomyInvariant`、`LocalAccountTaxonomyStore`、
`AccountTaxonomyHierarchy` 與 `FilterCompilation`。

分類設定可以同一次新建上層和下層。移除上層前列出受影響的下層，確認後把直接下層接到原分類的上一層；儲存前仍可取消，使用中的分類保護不變。
科目分類條件可選不限借貸。此時「不存在符合」表示同一張傳票在分錄測試範圍內，借方與貸方都沒有屬於選定分類的科目，沿用傳票條件的既有定義。
第五步也可依分類樹選入本案的實際科目編號並搜尋，仍儲存為原本的科目編號值清單，不新增條件型別。

借貸科目分類條件有三種模式：「科目屬於指定分類」「科目不屬於指定分類」「整張傳票的這一側都不屬於
指定分類」。選「相同分類用途」時，自訂分類有 Cash 用途也算 Cash。科目配對範本分類留白的科目
依 legacy 視為 Others；沒有出現在配對檔的科目不屬於任何分類。結果只有命中與不命中兩種，沒有待判定
（2026-09-07 裁定）；第四步的科目配對卡提醒「分類留白 N 筆，視為 Others」並可展開清單，要改分類就在
範本 C 欄填好再重新匯入。借貸科目組合合併成一張卡，五種白話模式：「借方是 A 且貸方是 B」「借方是 A 且
整張傳票沒有 B 貸方」「貸方是 B 且整張傳票沒有 A 借方」「借方是 A，看它的對方科目」「貸方是 B，看它的
對方科目」。原有配對及 KCT 規則保留原結果。

同一分錄組合可選全部符合或符合任一；同一傳票組合固定全部符合，第一個主要條件決定命中分錄，
其餘條件可由該傳票不同分錄符合。只有傳票層條件時，呈現查核期間內的分錄，標示傳票條件成立。
條件括號可巢狀組合「且」「或」，每一層依原順序由左到右計算。放在同傳票佐證位置的括號，
其中的欄位條件必須由同一筆分錄滿足，例如貸方科目 B 且摘要含 X 不能分別由兩筆分錄提供佐證。

傳票量詞可選整張傳票、借方或貸方，並選至少一筆符合、全部符合或不存在符合。
每筆分錄先判斷括號內的完整條件，再判斷所選範圍。全部符合須至少有一筆，且每筆均符合；
沒有該側分錄時，至少一筆及全部符合都不成立，不存在符合成立。這是 2026-09-18 使用者裁定。
空白傳票號碼的分錄不屬於任何傳票，因此三種傳票量詞與科目分類「整張傳票的這一側都不屬於」對它們一律不成立。
列層條件仍依欄位值判斷；空白號碼仍可在空白傳票號碼明細查看。KCT C 與預篩選「未預期借貸組合」也不選入空白號碼的收入貸方。
只看查核期間的有效母體；零元沿用借方判斷，空白值依子條件原有設定，SQL 的未知值視為不符合。
傳票量詞成立時呈現該傳票的有效母體分錄，標示為傳票條件成立；要只標記某種主要分錄，
可將它放在既有同一傳票組的第一條，再把傳票量詞放在後面的佐證位置。
科目編號與科目名稱條件可在同一條內選「不限借貸」「借方」或「貸方」，方向與欄位值必須由同一筆分錄滿足。
例如同一傳票的第一條為「借方、科目編號屬於 A」，第二條為「貸方、科目編號屬於 B」，只標記借 A 的
分錄；貸 B 是佐證，其他明細供覆核。這不要求該側每筆分錄都符合，也不改變既有分類依審計角色比對的方式。
日期及金額區間包含兩端；日期可用多選日曆挑指定日，也可用「每月幾日屬於」「每月幾日不屬於」填 1 到 31
的日子（例如 28、31，重複自動合併）。文字、日期和金額依型別提供清單、否定、空白及其他比較方式；
「包含任一文字」「不包含任何文字」接受多個關鍵字，清單最多 100 個不同值。核心金額預設比較絕對值，
額外數值欄位沿用含正負號方式。要排除某些日期、文字或金額，就用該條件的否定模式（不屬於、不在區間、
不包含）放進條件組，沒有獨立的排除區域。所有值條件預設不列入空白，日期空白的分錄不命中；要把空白
也算進來時勾「空白也符合」。開啟舊情境不自動換規則。

摘要關鍵字、金額尾數、每月幾日、人員代號及科目編號清單接受換行、半形或全形逗號、頓號及 Tab。
其他文字值清單維持一行一個，值裡的逗號不拆開；單一開頭或結尾條件只收一個值，多行輸入會提醒。
指定日期沿用 GL 匯入的解析方式，包括西元斜線、點號、八位數 yyyyMMdd 與案件允許的民國年，民國年開關由案件提供。
畫面和後端以實際送出的清單計算 100 個值上限，不把大小寫不同的兩個輸入擅自合併。絕對值金額填負數時只提醒，不另改命中定義。

日期條件可選週末、假日、補班日、非營業日及各自的否定。非營業日為週末或假日再排除補班日；
週末本身仍包含補班日。清單沒有日期時，不自行推算國定假日。文字另有開頭及結尾不符合。
新 KCT I 也使用排除補班日的非營業日判斷。舊情境若明確保存週末或假日的組合，仍保留原樹並如實寫出兩者，不默默改成新定義。
第五步的「未預期借貸組合」與舊表 C 沿用第四步的前置條件：已配對收入分類，並至少配對應收、現金或預收其中一類。
日期也可選每月月初或月底 1 到 31 天，包含月初或月底當天；天數超過當月長度時涵蓋整月。
月份依所選日期欄位計算，閏年二月也依實際天數處理，與「查核期末最後幾天」分開。
總帳日與核准日的加班例外各自用否定條件設定，放在「同一分錄、全部符合」的組內；
例如總帳日在非營業日，且總帳日不在指定加班日期。核准日可另設不同清單，不會修改共用假日或補班日資料。
金額的特定尾數比較忽略正負與小數，保留指定的位數；例如 -1,001.45 符合 001，1 元不符合 001。
日期、金額、人員、會計科目與其他文字分組呈現；建立日或原幣金額需先明確配成攸關資料元素欄位，不能猜來源。

「科目與人員統計」可依科目編號、建立人員或核准人員，選擇分錄筆數或傳票張數（同號只算一張），提供等於、小於、
大於、介於及含等號的比較。統計先依分錄測試範圍分組，區間含兩端；空白識別值不命中。同案件相同傳票號碼
算一張，空白號碼不計張，但符合該科目或人員的分錄仍列出。這項條件不改寫既有的 11 筆以下篩選規則。
人員依去空白、不分大小寫的識別值分組；科目編號只去空白，大小寫規則不變。文字比較與空白判斷去掉的空白字元集合
和 .NET 的 Trim 相同，SQLite 與 DuckDB 一致。

「空白」與「非空白」只能判斷已有來源的欄位。核心欄位未配對時，後端提示回「欄位配對」指派或改選其他欄位，
不能把未提供的整欄當作內容空白。核准日採「與總帳入帳日相同」時已有衍生來源，仍可使用空白判斷。
第五步的一般欄位比較，除了空白與非空白，不另外檢查核心欄位是否已配對；未配對時可出現 0 筆，未匯入假日清單時也不另加提醒。
這是使用者 2026-10-04 裁定保留的行為，不表示來源完整；第四步仍照各規則顯示無法執行原因。原有 KCT、預篩選特定條件與 RDE 欄位的前置檢查不因此移除。
F08、F17 所說的「所有欄位」，指每個已配對的文字欄位及攸關資料元素欄位各自比較；不是把整列所有欄位串起來搜尋，也不開放任意 SQL。
畫面及報表的「且」「或」是文字呈現；條件依原順序由左向右合併，第一條連接詞沒有左側條件，不參與運算。
混合連接詞的讀回文字保留括號，不按一般 SQL 的運算子優先序重新解讀。

預覽只要求條件有效，自訂情境儲存時才要求名稱與動機；KCT 沿用既有例外。後端指出某條規則有問題時，
畫面把那一條標紅並就地寫原因。預覽、儲存及匯出共用後端判斷。命中傳票清單可分頁展開整張傳票的分錄，
每列標示符合第幾組第幾條主要或佐證條件、或傳票條件成立，其餘為參考分錄，不算命中。分頁綁定案件、
資料與情境版本，資料變更後重新預覽。第五步也能更新原情境、另存副本或取消編輯；更新不占新名額，
最多十個情境的上限仍適用副本。常用情境範本（借現金貸非現金、貸現金借非現金、非營業日且排除指定日期、
期末最後 N 天的人工分錄、空白摘要或核准人員、特定人員的大額分錄）一鍵帶入條件、名稱與動機，可再修改。
範本或草稿還有值沒填時，畫面先擋下預覽，並寫出第幾組第幾條與條件名稱。

自訂條件另有「舊表條件 A 到 U 與範例」，依 2024 篩選表的代號選取，與 KCT A–J 分開；畫面在舊表字母前標明「舊表」。
各項直接帶入同一編輯器和 AST。O、R 先選已配對欄位，U 可選指定人員或編製傳票張數；
P 可選科目代號或科目分類。科目代號分成借方、貸方兩個集合，在同張傳票內各找至少一筆，
不能由另一張傳票補足；選分類時沿用既有借貸組合編輯器，明確選分類本身、下層或相同審計角色。
P 的文字說明使用「同張傳票」，單筆欄位的複合判斷才使用「同一分錄」。
工作簿的五個組合範例也能直接帶入；日期例外、金額、科目及理由均可再改。
I、L 帶入的每月 1–5 號及其他已填值明示為範例，不是所有案件都應套用的預設審計要求。
A 仍按核准日與財報準備開始日比較，D 仍按已裁定的新版固定尾零方式；不恢復舊表的互斥選項限制。
來源位置與逐項固定答案見現行計畫「A–U 操作相容與警告修正」。

## 7. 輸出報告

產品目前有五種報告與一份工作檔：

1. Validation Report
2. INF Report
3. Pre-screening Report
4. Criteria Selection Report
5. Working Paper
6. Account Mapping 範本（工作檔，不是報告）

報告的 `Prepared by` 使用建立案件時保存的建案者 `operatorId`，不是目前開啟案件的 Windows 帳號；案件畫面的目前操作人員與它分開顯示。
預篩選報告的既有範本文字依使用者裁定保留，包括「之後核准」，不因畫面讀回補日期而改寫範本。

Validation Report 的 `Source_Quality` 工作表維持英文表頭，對照如下。它目前只有 `nullPostDate` 類別，表示「總帳入帳日空白」，不是期間外分錄。

| 英文欄名 | 內容 |
|:---|:---|
| `CATEGORY` | 品質問題代碼，目前為 `nullPostDate` |
| `SOURCE_ROW_NUMBER` | 匯入來源的資料列號 |
| `SOURCE_LABEL` | 匯入來源標籤，用來辨認來源檔或工作表 |
| `DOCUMENT_NUMBER` | 傳票號碼 |
| `ACCOUNT_CODE` | 科目編號 |
| `POST_DATE` | 總帳入帳日；本類別通常為空白 |
| `DESCRIPTION` | 傳票摘要 |

工作底稿需要目前可用的資料驗證結果及已儲存的篩選情境，不需要先產生條件篩選報告。
底稿匯出會使用目前資料，只驗證並重算本次所選的情境；未選情境缺少來源欄位，不阻擋有效情境輸出。
部分重算只替換所選命中，保留未選資料，不能把全案矩陣標成已更新。新底稿記錄既有的篩選資料版本，
案件重開時仍能區分「這份底稿的來源是目前資料」與「全案情境是否全部重新計算」。條件篩選報告需要完整
矩陣，仍重算全部情境；它是獨立輸出，不是底稿的資料來源。
科目配對工作檔只使用已配對的科目、分類及欄位資訊，沒有資料驗證結果時仍可準備；不因工作檔產生而偽造一次驗證。

### 五份報告的欄位與排序

以下列的是程式實際寫出的資料用途與順序，不改寫既有範本的欄名。所稱「來源全欄」依匯入的 `batch.Columns`
保留欄名與順序，再依標準資料的分錄識別值取回原始列；不是只輸出畫面預覽的固定欄位。原始明細預設按 `entry_id` 升冪。
畫面上暫時選的排序不會改變報告順序。依據是 `LegacyReportWriter` 各報告實作、`WorkpaperWriter`、`WorkpaperProgram`
及它們使用的查詢；`ResultPageSorting` 定義有界分頁的預設鍵。

| 報告與工作表 | 實際資料欄位 | 排序與範圍 |
|:---|:---|:---|

| `V_Report 1` 到 `V_Report 4` | 來源 GL 全欄，依序對應科目空白、傳票號碼空白、摘要空白、核准日不在查核期間 | 各類按 `entry_id` 升冪；沒有核准日配對時不建立第 4 表。 |

預篩選畫面另有週末、假日、回溯過帳、非授權編製人員、編製分錄較少的人員與使用較少的科目六組，沒有新增到七條報告規則中。
週末與假日各含過帳、核准兩側，所以後端程序數與畫面卡片數不同。

### 檔案、發布與版本

程式隨附範本位於 `src/JET/JET/Templates/`，由 `JET.csproj` 複製到輸出目錄。`data/` 內的同名或
近似工作簿是遷移參考，不會因為檔名相似就自動成為程式隨附範本。

報告產生器使用已確認的查詢結果與中繼資料，不重新解讀審計規則。產生大型工作簿時採串流方式：先寫
案件資料夾內以 `.` 開頭的暫存檔，完整寫好後才改名成正式檔名。可處理的失敗或取消會清除半成品；程序
中斷或檔案佔用造成的殘留，會在下次讀寫前嘗試清除。儲存不計算內容雜湊，也不保留交易復原紀錄。
報告清單仍保存檔名、大小與修改時間，用來顯示外部修改提醒，不會因此拒絕載入案件。
兩份驗證報告一起發布時，任何一份或清單索引寫入失敗，都會還原本次已換掉的報告，保留原索引；首次輸出則移除本次新檔。
若外部鎖檔等原因連還原也阻止，JET 明說還原未完成。有原檔時保留備份；原本沒有檔案時，提示本次新檔仍保留，不把半批輸出宣稱為成功。
這個同次操作的暫存備份不是舊版的交易復原紀錄，也不新增內容雜湊。

新增條件的完整說明會寫入 Criteria Selection Report，並列在 Working Paper 的 Step 3 情境名稱下方。
所有規則型別都使用同一個說明產生器，包含 A、D 等預篩選條件，不再只替欄位或巢狀條件列出完整說明。
底稿展開整張傳票時，參考分錄不重新標成命中。
超過 Excel 單格容量的條件會在同一工作表接續列出，保留完整文字。Criteria Selection 的摘要會指向
續列位置；Working Paper 則以同一情境代號標示續列，不重複計入傳票數。

五種報告的公司名稱表頭在客戶名稱留空時使用案件名稱，和工作區標題一致。科目配對工作檔維持既有版面，不另加公司名稱表頭。
五種報告檔名加入案件查核起訖日 `yyyyMMdd-yyyyMMdd`，不同期間可直接辨識。
V_Report 5 的表頭與資料列均明確指定 18 點列高，並提供標準工作表視圖，避免高 DPI 的原生 Excel 將高度折半。
報告清單顯示檔名、建立時間及大小，透過「開啟資料夾」定位，不長駐完整路徑。後端定位路徑依案件位置
重新解析，移動案件資料夾後不沿用舊絕對路徑。
只有 Working Paper 是正式輸出：每次匯出寫新的版本檔 `<案件前綴>_<yyyyMMdd-yyyyMMdd>_WorkingPaper_<yyyyMMdd-HHmmss>.xlsx`，
不覆蓋、不刪舊版；即使檔名選定後才出現同名檔，發布時也保留原檔並提示重新匯出。第六步可分頁查看
全部版本並在檔案總管定位，歷史版本不作為目前流程完成的證據。其餘四種報告每次匯出覆蓋同名檔。
第六步在「有可以套用目前規則的已儲存情境」或「已經有任何工作底稿版本紀錄」時可以進入；只有版本紀錄時
可以查看，但匯出按鈕停用，畫面寫出原因並請使用者到「進階條件篩選」儲存情境。匯出本身仍要求目前的驗證結果
與可用的情境版本。第六步、左側進度與流程總覽用同一個判斷：已有目前版本的工作底稿時第六步算完成。
Account Mapping 範本是給審計員用 Excel 填寫 `Standardized Account Name*` 欄再匯回
的工作檔，固定檔名 `<案件前綴>_AccountMapping.xlsx`，不列入報告清單。
驗證完成後只自動建立尚不存在的範本，已有檔案就保留。手動重新產生空白範本才覆寫，最後發布時也遵守
所選方式，避免自動產生改動審計員已填寫的分類。

範本和報告都在正式檔改名前處理最後一次取消；範本取消時保留原檔。報告開始發布後，取消請求不再中斷
索引寫入；這不保證能排除磁碟或權限等寫入失敗。報告清單即將超過 4,096 筆時，先整理已確認檔案不存在的
底稿紀錄。正式發布前再次確認，期間被放回或無法確認的檔案仍保留；仍超限時不發布新檔，提示使用者
自行整理不需要的舊底稿後重試。整理不刪除實體檔，失敗或取消也不提前保存整理後的清單。

正式檔和索引已成功保存後，附帶清單讀取使用獨立 3 秒期限，不受晚到的使用者取消影響。清單 I/O 失敗或
逾時只在新檔旁提示「可開啟案件資料夾查看，無須重新產生」，不誤報匯出失敗。發布前寫入失敗、程式錯誤
及正式底稿不覆寫規則不放寬；這不表示所有案件索引的讀寫錯誤都可略過。

預設審計員可信（`docs/project-context.md`）：報告檔在 JET 之外被改寫、改名或刪除都不阻擋載入，第六步清單
只在該筆旁標示「已在 JET 之外修改」或「檔案不存在」，重新匯出即可。2026-09-02 以前版本留下的輸出紀錄檔
會在載入時直接刪除並記一筆支援日誌事件。

## 8. 儲存與資料庫實作

資料庫第 11 版為本地分類增加 `parent_category_id`，以 `config_account_taxonomy_path` 保存分類及其下層關係。
分類修改與關係表在同一交易保存；循環或不存在的上層會提示重新選擇，不留下部分更新。
第 10 版升級後既有分類均維持最上層，分類 ID、角色與已保存情境定義保留。分類改動依既有規則使篩選結果失效。
新的本地資料庫先建成第 6 版，再逐版升到現行版。第 1 到第 5 版是舊版 JET 建立的格式，目前版本不再升級；
開啟時回報 `invalid_project_schema`，請使用者用目前版本重新建立案件，再重新匯入資料。

SQLite 與 DuckDB 是本地資料庫實作；每個案件以一個自含資料夾保存中繼資料、資料庫與輸出產物。
SQL Server 是線上資料庫實作，使用共享資料庫中的案件範圍。三種實作在相同輸入與相同契約下應得到
相同結果；不能把資料庫差異當成合理的業務差異。

SQLite 連線的 `UPPER` 由 .NET `ToUpperInvariant()` 處理，讓篩選資料與條件值採用一致的大寫轉換，
包含 café 等非 ASCII 文字。一般連線、唯讀連線與底稿專用連線都保留這項設定；不另外安裝 SQLite 擴充，
也不把分錄載入前端比較。文字仍區分重音符號，沒有新增模糊比對或變更空白規則。

schema v10 增加科目分類是否實際填寫的紀錄（`classification_explicit`），以及篩選資料版本。舊案件升級時
以原始分類資料分批回填，缺少來源證據則保留未知，原本的分類欄值不改寫。這個紀錄只用在第四步
「分類留白 N 筆，視為 Others」的提醒；篩選一律把留白視為 Others（2026-09-07 裁定），開案不另做分類
證據修復，也不重複掃描科目配對資料。上游資料變更會在同一交易更新篩選資料版本，使舊分頁失效。

選擇 SQLite 與 DuckDB 作為本地實作的理由來自正式環境限制（見
[`project-context.md`](project-context.md)）：兩者都免伺服器、免系統管理權限、單一案件資料夾自含，
一般 GA 不需要管理資料庫服務就能作業。歷史量測已用 DuckDB 驗證 500 萬到 2,000 萬列母體的匯入、
驗證、預篩選與底稿輸出。兩個引擎能力不完全相同——例如 DuckDB 1.5.3 沒有 trigger，`audit_event_log`
的 append-only 在 SQLite 與 SQL Server 由資料庫層強制，在 DuckDB 維持程式紀律——這類差異由
Infrastructure 吸收，不得外溢成業務行為差異。

DuckDB 每次開啟資料庫要幾十毫秒，所以 DuckDB 案件在一次操作期間保持資料庫開啟，同一個操作裡的多次讀寫
沿用同一個已開啟的資料庫。兩次操作之間資料庫照舊關閉，檔案解除鎖定。刪除案件時若還有操作在使用這個
DuckDB 資料庫，JET 回 `operation_in_progress` 而且不刪任何檔案，等那個操作完成後再刪除即可。
SQLite 與 SQL Server 案件不受影響。

本地案件的可攜性以前提為「JET 已正常離開案件，再冷複製完整案件資料夾」。正在使用的資料庫、
WAL 熱複製與 SQL Server 案件不在這個保證內。

本地案件不做刪案留痕：2026-08-20 裁定本地案件屬個人工作性質，持久刪案證據是中心化管理議題，
只屬於 SQL Server 線；企業範圍見 [`sqlserver-enterprise-deferred.md`](sqlserver-enterprise-deferred.md)。

本地案件不使用暫緩中的 SQL Server 機制，這是 2026-10-02 的裁定。SQLite 與 DuckDB 案件開啟後不定時送出心跳，
工作鎖由本機檔案鎖負責，支援日誌也不會被心跳紀錄佔滿。本機找不到案件資料夾時，JET 直接回報找不到案件，
不去查線上登錄；只有案件清單標示為 SQL Server 的案件才會查。重新匯入、重新配對與匯出報告完成後，
JET 會在 `audit_event_log` 寫一筆操作紀錄。本地案件寫這筆紀錄失敗時，例如紀錄表損壞，作業照常完成並回報成功，
失敗只記在支援日誌的 `project_audit.write_failed` 事件。SQL Server 案件的心跳、線上登錄與操作紀錄行為不變。

## 9. 系統分層

| 層 | 責任 | 主要位置 |
|:---|:---|:---|
| WinForms 主程式 | 視窗、WebView2、原生檔案對話框與程序生命週期 | `src/JET/JET/Form1*`, `Program.cs` |
| Web 前端 | 操作、呈現、分頁與使用者回饋 | `src/JET/JET/wwwroot/` |
| Bridge | 傳送請求、回應與非權威進度事件 | `src/JET/JET/Bridge/` |
| Application | action 處理器、流程協調、取消與工作階段 | `src/JET/JET/Application/` |
| Domain／AuditCore | 欄位、規則、金額與查核語意 | `src/JET/JET/Domain/`, `AuditCore/` |
| Infrastructure | SQLite、DuckDB、SQL Server、檔案讀寫與報告輸出 | `src/JET/JET/Infrastructure/` |

前端不做審計裁定，Bridge 不做業務判斷，報告產生器不重算規則。這三條比任何類別命名都重要。

程式依賴由 Bridge 與 WinForms 主程式進入 Application，再由 Application 使用 AuditCore 與 Domain。
AuditCore 只依賴 Domain，不能回頭依賴 Application、Infrastructure、Bridge 或 WebView2；Domain 不依賴任何外層。
Infrastructure 實作資料存取與檔案能力，不能讓 Application 或 Bridge 直接依賴它。
組裝各層的 `AppCompositionRoot` 與主程式位於 `JET` 命名空間，不受這組分層限制。

`LayerDependencyTests` 逐一核對兩份白名單。Infrastructure 目前只有 `DemoWorkbookWriter`、`SqlServerBackendProbe`
及 `SqlServerHealthCheck` 可以依賴 Application。AuditCore 的公開型別只有 `AuditCaseSnapshot`、`AuditExecutionPlan`、
`AuditOutcome`、`AuditRunManifest`、`AuditUserParameters`、`ISqlDialect`、`JetAuditProgram`、`ProcedureDefinition`、
`ProcedureVerdict` 與 `ValidationProcedures`；新增公開入口不能默默擴大這份清單。

原生選檔與主機控制留在 UI 執行緒，其餘 action 的 handler 與資料庫保留範圍都在背景執行；取消仍走同一 action 通道。
Release 關閉 WebView2 的瀏覽器快捷鍵，避免 F5 等重載讓畫面與案件狀態分離；Debug 與 AgentGuiTest 保留開發用途。
WebView2 初始化失敗時顯示中文復原步驟。瀏覽器或主要呈現程序中止時，先取消在途作業、等作業結束後關閉視窗，
請使用者重開並確認最後一次操作；不自動重新載入而遺失未儲存的畫面輸入。僅暫時沒有回應時先提醒，不逕自關閉案件。

Bridge 遇到不是 `JetActionException` 的非預期例外時，回應錯誤碼 `bridge_error`，訊息固定為「發生非預期的錯誤，
這個動作沒有完成。請按畫面上方的「輸出支援日誌」，把檔案交給支援人員。」，不帶例外原文、本機路徑或例外型別；
correlation 照舊。例外在丟出前已由 action 分派器寫進日誌：支援日誌依設計只留例外型別、系統錯誤碼與前幾層的
方法名稱，完整訊息只在本機的診斷日誌。`JetActionException` 的訊息不受影響。

畫面上的金額一律以兩位小數加千分位顯示，由前端共用的格式化函式處理；這是使用者 2026-10-02 的裁定：
畫面統一兩位小數加千分位，報表與底稿不變。輸入框、篩選條件值與送給後端的值不經過這個格式化。

三種資料庫各有一組資料存取物件（repository），程式啟動時建好。建立或載入案件時，Application 依
`project.json` 記錄的資料庫種類選定其中一組，和案件編號一起存進工作階段。其他動作開始時取一次這份紀錄，
整個動作只用這一組；即使途中另一個請求載入了別的案件，進行中的動作也不會改用新的一組。刪除不在使用中的案件時，
依該案件自己的 `project.json` 選組，不改變工作階段。

## 10. 大資料量原則

短期目標是 SQLite 與 DuckDB 能順暢處理約一百萬筆分錄的案件；千萬筆等級的案件是中後期目標，由 SQL Server
承擔。早期文件寫過的「10 億列設計上限」已不再是目標。

| 維度 | 目前的規模基準 |
|:---|:---|
| GL 分錄筆數 | 短期以 SQLite 與 DuckDB 處理約一百萬筆為基準；千萬筆是中後期 SQL Server 的目標 |
| TB 科目數 | 典型約 1,000，上界 1 萬 |
| 科目配對列數 | 數百至數千，上界 1 萬 |
| 工作底稿 Excel 大小 | 數 MB 至數百 MB，以 OpenXML SAX writer 控制記憶體 |

這些是設計基準，不是已完成極限量測的證據；歷史量測範圍見第 8 節。SQL Server 目前暫緩，不能由這張表推導出
「超過某個筆數就必須啟動 SQL Server」的限制。公司硬體上的耗時與資源用量仍需實測。

- 金額以固定精度的整數表示，避免浮點誤差。
- 匯入與輸出採串流；篩選、彙總與資料表連接留在資料庫。
- Bridge 只傳中繼資料、摘要與有界頁面。
- 查詢必須可取消，失敗時不發布不完整結果。
- 效能數字只有在相同資料形狀、環境與命令下才可比較；舊證據不能當成新儲存庫的效能承諾。

## 17. Legacy 比對邊界

保留第 17 節編號，是因為既有的結果比對訊息會引用 `docs/jet-guide.md §17`。

從 IDEA 或 VBA 遷移時，不逐段翻譯。先找出規則目的與輸入輸出，再放到合適的 Domain、Application、
Infrastructure 或 UI 邊界。

比對差異只分五類：

| 類別 | 怎麼處理 |
|:---|:---|
| JET 缺陷 | 修正產品，重新執行同一比較 |
| 已裁定的刻意差異 | 引用明確裁定，不改回 legacy |
| 舊系統缺陷或輸入條件不同 | 保存可重現理由，不把差異算成 JET 通過 |
| Legacy 無對應項 | 說明可比較範圍，不假裝完全等價 |
| 待使用者裁定 | 停下並提出兩邊證據，不自行選邊 |

不同資料庫結果不一致時，不會在這五類中另開例外；相同契約在 SQLite、DuckDB 與 SQL Server 得到不同結果時，
一律視為 JET 問題。

省略的精確規則與來源決策，但不會凌駕 `je-tool` 後續經核准的新行為；追溯與衝突處理見
