# JET 大型開發與跨 session 續接

更新日期：2026-09-01

這份文件只處理需要跨多個步驟或多個 session 的開發。小型、可在一次工作內完成並驗證的修改，不必建立
額外流程文件。

## 何時建立現行計畫

工作符合下列任一情況時，應在 `docs/specs/` 建立一份現行計畫：

- 會同時改動多個產品層、資料庫實作、GUI、Excel 或正式報告。
- 有多個驗收階段、外部能力或使用者裁定。
- 預期會跨 session、換用 Agent，或可能因環境中斷而續接。
- 一旦誤解範圍，會造成大量無效實作或改變對外行為。

使用者提出的執行計畫、範圍與裁定優先。若使用者只給了清楚的成果目標，Agent 可以先整理成最小計畫；
遇到會改變範圍、對外行為或需要新權限的選擇時，仍要請使用者決定。

## 一次只有一份現行大型計畫

`docs/development-status.md` 的「目前大型計畫」只放「無」或一個連結。計畫本身至少保存：

- 目標、範圍與不做事項。
- 審計員在哪一步做什麼、看到什麼；每個可能擋住使用者的錯誤，使用者接下來能做什麼。分段開發最容易
  在模組交接處失去這條線，所以它要寫在計畫最前面，不是實作完再補。
- 使用者已確定的裁定，以及仍需確認的問題。需求與裁定逐字保留使用者原話並附日期，不改成 Agent 自己的
  轉述；要改寫需求段落或計畫標題，先取得使用者授權。提交前的複審對照原話，不對照改寫後的版本。
  2026-09-05 到 06 的篩選工作就是對照改寫後的需求複審，才會做出使用者沒有要的功能。
- 目前步驟、已完成工作與尚未完成工作。
- 第一次失敗、失敗原因及後來如何驗證；診斷重跑不能覆蓋第一次失敗。
- 最後有效驗證的命令、結果和適用範圍。
- 中斷後的下一個具體動作。

計畫不複製完整程式差異、逐行終端輸出或每一次 receipt 路徑。詳細證據留在本次 ignored 執行目錄；計畫只
保存換機或重新 clone 後仍看得懂的摘要。

## 專案記憶與跨 session 收斂

JET 的專案記憶是受版控的現行文件、程式、測試與目前計畫，不是某一個 Agent 的對話或本機 memory。
Task／thread、memory、compaction 摘要與 ignored receipt 可以協助找回來源，但不能單獨建立規則或證明
目前狀態。完整層級、分類與回寫位置見
[`../.agents/harness/convergence-and-memory.md`](../.agents/harness/convergence-and-memory.md)。

使用者明確呼叫 `$jet-converge` 時，由 `.agents/skills/jet-converge/SKILL.md` 收集多個 session 的觀點、
需求、功能與待完成事項，先區分已確認、候選、衝突、延後、已取代與無依據，再用目前核心業務與重啟條件
收斂。收斂結果只有在使用者確認並授權保存後才寫回現行文件；不建立第二份 backlog、`CONTEXT.md`、ADR
或 session dump。

待完成事項若要長期保留，至少要寫清楚背景、目前邊界、現在不做的原因、重啟條件與重啟後第一個可驗證
動作。只有標題或曾在對話提過的想法，不直接進入 `development-status.md`。

## 新 session 如何開始

1. 讀取 `AGENTS.md`、`docs/project-context.md` 與 `docs/development-status.md`，包含「已知但延後的事項」。
2. 若有現行大型計畫，讀取其目標、目前步驟、未決問題、最後驗證及中斷續接段落。
3. 核對實際 branch、HEAD、工作樹、忽略規則與共享資源狀態。文件和實際狀態不一致時，以實際狀態為準，
   並先修正續接點。
4. 只讀和本次工作相關的現行規格與程式；大型文件先搜尋標題和關鍵字。
5. 執行計畫中唯一的下一個步驟。沒有新的範圍或權限時，不自行擴張工作。

## 工作中如何更新

- 完成一個可獨立驗證的步驟後，更新目前步驟、結果、第一次失敗及下一動作。
- 使用者作出會影響後續工作的裁定時，同輪寫回計畫；長期有效的產品或環境決策也要寫入相應現行文件。
- 若 session 即將中斷，先保存實際修改、未完成狀態、已執行與未執行的驗證，以及可直接開始的下一動作。
- 不用「全部完成」取代具體範圍。沒有執行 GUI、Excel、provider 或私人案件時，要逐項說明。
- 大型階段結束或使用者詢問未完成事項時，逐項核對 `development-status.md` 的「已知但延後的事項」。只在
  有新證據或使用者裁定時更新狀態；問題解決後才移除，不能因目前不阻擋工作就省略。

## 驗收與關閉

1. 依計畫的驗收條件執行正式 `tools/verify.ps1` 命令，保留第一次失敗與最後有效結果。
2. 提交前由沒有參與實作的另一個 session 或子 Agent 複審。只給它 diff 與計畫，請它核對每項需求都有實作
   與測試、範圍外沒有改動、移除的行為有重建、既有測試沒有被放寬；只回報影響正確性或需求的缺口，不報
   風格。另外問每個新增的關卡或核對防的是誰：防 JET 自己的失敗可以留，防審計員自己的操作要改成提醒
   或拿掉（`AGENTS.md`「預設審計員可信」）。缺口修完後重跑對應命令。2026-09-01 的提交前複審就是這樣
   抓到 `dev.log.exportFile` 的 fallback 缺陷。
3. 將長期有效的背景、操作方法、契約和限制寫回各自現行文件，不讓完成計畫成為唯一事實來源。
4. 計畫標為「待使用者驗收」；只有使用者確認成果或計畫明定的客觀驗收已完成後，才標為「已完成」。
5. 將 `development-status.md` 的目前計畫改回「無」，並保留一段短的完成摘要。詳細過程不搬進現況入口，
   「已知但延後的事項」仍繼續保留。
6. 是否 stage、commit 或 push 仍由使用者另外授權，計畫完成本身不是 Git 授權。

## 不同 Agent 的共同做法

GitHub Copilot、Claude Code、Codex 與 VS Code 的 AI Agent 都使用相同文件、命令與驗收條件。工具有沒有
原生計畫模式、子 Agent 或本機記憶，不會改變這份流程；缺少某項原生能力時，就用現行計畫和較小的可驗證
步驟續接。各工具如何讀取共用規則，見 [`agent-compatibility.md`](agent-compatibility.md)。
